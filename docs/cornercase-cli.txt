================================================================ cornercase status
List the projects, workspaces, tabs and panes, with their ids

Usage: cornercase status [OPTIONS]

Options:
      --panes                     One line per pane, its columns separated by tabs, for scripts
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --follow                    Keep running and print the whole state as one JSON line each time it changes (`cornercase view` does it for a view)
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --app                       Print the TODO list, the queue, away, the update found and keep awake as JSON; with --follow, again each time they change
      --view <ID>                 Act in this view (see `cornercase view`): its tab is the default, and --focus moves the view instead of the window
      --json                      Print JSON instead of text
  -h, --help                      Print help

Each pane shows its program and folder, and for a coding agent what it is doing (working,
waiting for an answer, done out of sight, failed, idle), its model and how full its context is. `(you)`
marks the pane running the command, `(shown)` what the window shows. `working (background shell)`
is a Claude Code agent whose turn is over while a shell it started in the background still runs:
it wakes up when that shell ends (`background_shell` in the JSON, where the status stays working).
`working (2 subagents)` is an agent whose own turn is over while subagents it started still run
(`subagents` in the JSON, the number): it goes on when they report back, so it stays working.
`(dialog open)` is a Claude Code agent showing a dialog, a panel or its shell mode instead of its
input box, which `cornercase send` refuses (`dialog` in the JSON).
`(survey open)` is Claude Code's feedback survey above its input box, which `cornercase send`
refuses too (`survey` in the JSON): `cornercase keys --pane N 0` dismisses it.
`(resuming)` is a pane whose agent is coming back in its conversation after a restart: until it
is back, it takes no input and `cornercase send` refuses it (`resuming` in the JSON).
`(role coder)` marks a flow member and the role it plays (`role` in the JSON).
`(collapsed)` is an agent whose children are hidden in the agents section (`collapsed` in the JSON).
`Opus 5.5 · compacted` is an agent whose conversation was just compacted: its context is empty
until its next reply and comes back then (`compacted` in the JSON, there only while true).

With --panes it prints one line per pane instead, for scripts, in the sidebar's order: a header
line naming the columns, then one row per pane, its columns separated by tabs. The columns are
pane, tab, workspace, project (their ids), program, agent, status, background_shell, dialog,
at_prompt, model, context, caller (the pane running the command), shown (the pane the window
shows), active (its tab's active pane), tab_name, workspace_name, branch, worktree, project_name,
path, survey (Claude Code's feedback survey shows), resuming (the agent is coming back in its
conversation), parent (the pane that started it), subagents (how many it still runs) and role (the
role it plays in a flow, from its run) and compacted (true while the context is empty because the
conversation was just compacted, the last column); new ones only ever go at the end. Values are as in the
JSON (true or false, context as a number, full paths), with - where there is none and a space for a tab or line break in a name.
With --json, it prints {"panes": [...]}, one object per pane with the columns as keys and null
where there is no value.

With --follow it keeps running and prints the whole state as one JSON line: first as it is now,
then again shortly after each time something in it changes, always JSON, with
--json or without. Each line is what --json prints plus `revision`, which grows with every line,
with `caller` always null;
`boot` names the server's run, and revisions only compare within one boot. Each line replaces the
one before. It ends when the server stops or restarts, or once what reads it is gone; to go on, run
it again, and its first line
is the state then, so nothing is missed. A reader that falls behind reads at most four older
lines, then the latest state.

With --app it prints, as JSON, what is outside the session: `todos` (as `todo list --json`), `queue`
(the entries of `queue list --json`), `away` (one row per chat app: `platform`, `ready`, `away`),
`update` (the release found and its notes, why there is none, whether a check or an install runs,
and how installing works here) and `keep_awake` (null while the setting is off), with the server's
`version` and `boot`. With --follow it keeps running and prints one such line first and again each
time one of them changes, each with a `revision` that grows by one per line, built at most twice a
second while someone follows; rules for ending and for slow readers are --follow's.

Examples:
  cornercase status
  cornercase status --json
  cornercase status --panes | awk -F'\t' '$7 == "waiting" { print $1 }'
  cornercase status --panes --json | jq '.panes[] | select(.agent) | .pane'
  cornercase status --follow | jq -c '[.revision, (.projects | length)]'
  cornercase status --app --follow | jq -c '[.revision, (.todos | length)]'

================================================================ cornercase start
Start a coding agent in a new tab, give it a prompt, and print its pane's id

Usage: cornercase start [OPTIONS] [AGENT]

Arguments:
  [AGENT]
          The agent, such as claude or codex [default: the one chosen in settings → agents, else the one running here]

Options:
      --model <MODEL>
          The model, such as opus or gpt-5.5 [default: the agent's own]

      --remote <DESTINATION>
          Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)

      --mode <NAME>
          One of the agent's modes, as settings → agents lists them, such as plan [default: the one chosen there]

      --remote-command <COMMAND>
          How to run cornercase there, as sh reads it [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]

      --effort <LEVEL>
          The agent's effort, such as high: Claude Code, Codex, Grok Build and GitHub Copilot CLI take one [default: the agent's own]

      --worktree <BRANCH>
          Start it in the worktree of this branch, made when missing

      --workspace <ID>
          The workspace [default: the one this runs in, else the shown one]

      --project <ID>
          The project: a new tab in its folder, or where --worktree or --issue makes the worktree [default: the one this runs in, else the shown one]

      --name <NAME>
          The tab's name [default: the agent's]

      --prompt <TEXT>
          What to ask it

      --prompt-file <FILE>
          Read the prompt from a file, or from standard input with -

      --wait
          Then wait until the agent stops working, and print how it ended

      --until <UNTIL>
          Wait until the pane is in this state instead

          Possible values:
          - idle:      The agent is idle or done
          - working:   The agent is working
          - waiting:   The agent waits for an answer to a question or a permission prompt
          - shell:     The program in the foreground ended and the shell is back
          - turn-over: The agent's turn is over: it stopped working, or only a background shell it started still runs

      --timeout <SECONDS>
          Give up after this long, with status 1

      --issue <KEY>
          Work on this issue instead: a key such as #482, sc-48 or ENG-42, or its URL, with the prompt the Issues dialog's start uses and its branch (settings → Worktrees → issue branches; --worktree names another)

      --source <SOURCE>
          The tracker, for a key that more than one could have
          
          [possible values: github, gitlab, shortcut, linear, jira, plane, asana]

      --workspace-name <NAME>
          The workspace's name when the issue makes a worktree [default: the issue's key and title]

      --profile <NAME>
          Start it with the accounts of this profile; an empty name is each agent's own login [default: the default accounts]

      --account <AGENT=ACCOUNT>
          Start that agent with this account, over the default ones; AGENT= is its own login. Give it once per agent

      --focus
          Also show it in the window, or in the view with --view, which otherwise stay as they are

      --view <ID>
          Act in this view (see `cornercase view`): its tab is the default, and --focus moves the view instead of the window

      --json
          Print JSON instead of text

  -h, --help
          Print help (see a summary with '-h')

The agent starts with its command and arguments from settings → agents. --mode replaces the mode
chosen there by another of the agent's modes, --model adds the agent's own model flag and --effort its
effort (Claude Code, Codex, Grok Build and GitHub Copilot CLI take one; an older server refuses all three rather than
start the agent without them). If it asks whether
you trust the folder, the question waits for your answer unless settings → agents accept it for
you. Once it is ready, the prompt is pasted and
submitted, and the command prints the pane's id; it fails if the agent never shows up. With
--wait, a second line says how the wait ended: idle, done (it finished out of sight) or waiting
(it needs an answer); with --until it waits for that state instead, as `cornercase wait --until` does.

--issue KEY (a key such as #482, sc-48 or ENG-42, or the issue's URL) starts the agent on that issue as
the Issues dialog's start does: GitHub and GitLab issues in a worktree on the branch named after the issue, of
the project's own repository; the prompt comes from settings' prompt template and is always submitted.
Shortcut, Linear, Jira, Plane and Asana issues aren't tied to a repository: when several places are open the
command lists them and asks for --project (a new worktree) or --workspace (a new tab). A workspace already
on the branch gets a new tab. It needs a server that knows the `issues` feature.

Examples:
  cornercase start claude --issue '#482'
  cornercase start codex --issue ENG-42 --project 3
  cornercase start claude --worktree fix-login --prompt 'Fix the login form, then commit'
  cornercase start codex --prompt-file task.md --wait --timeout 1800
  cornercase start claude --mode plan --model opus --prompt 'Plan the login rework'

================================================================ cornercase send
Paste text into a pane, and press Enter with --enter

Usage: cornercase send [OPTIONS] [TEXT]

Arguments:
  [TEXT]
          The text, or - to read it from standard input

Options:
      --pane <ID>
          The pane [default: the one this runs in, else the shown one]

      --remote <DESTINATION>
          Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)

      --remote-command <COMMAND>
          How to run cornercase there, as sh reads it [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]

      --tab <ID>
          A tab: its agent's pane, else its active one

      --view <ID>
          Act in this view (see `cornercase view`): its tab is the default, and --focus moves the view instead of the window

      --enter
          Press Enter once the screen settles

      --wait
          Then wait until the agent stops working, and print how it ended

      --until <UNTIL>
          Wait until the pane is in this state instead

          Possible values:
          - idle:      The agent is idle or done
          - working:   The agent is working
          - waiting:   The agent waits for an answer to a question or a permission prompt
          - shell:     The program in the foreground ended and the shell is back
          - turn-over: The agent's turn is over: it stopped working, or only a background shell it started still runs

      --timeout <SECONDS>
          Give up waiting after this long, with status 1

      --force
          Send even when the agent shows a dialog, a panel or its shell mode instead of its input box, or its feedback survey

      --json
          Print JSON instead of text

  -h, --help
          Print help (see a summary with '-h')

The text goes in as one paste, bracketed when the program asked for it. A pane whose agent
waits for an answer to a question or a permission prompt is refused, since the text would answer
it; use `cornercase keys` for that. So is a Claude Code agent that shows a dialog, a panel or
its shell mode instead of its input box (`dialog` in `cornercase status --json`), unless you pass
--force. So is its feedback survey above the input box (`1: Bad  2: Fine  3: Good  0: Dismiss`,
`survey` in the JSON), where a digit sent alone would answer it: dismiss it with
`cornercase keys --pane N 0`, or pass --force. So is a pane whose agent is resuming its conversation
after a restart (`resuming` in the JSON), where the text would reach its shell or its start-up:
send again once it is back, or pass --force.

With --enter, the command returns once Claude Code, Codex, Gemini CLI, opencode, Grok Build, Cursor CLI or
GitHub Copilot CLI has recorded the prompt in its own history, and fails with `not confirmed: the prompt may not
have been submitted` when it records none: read the pane before sending it again. A working Codex,
Gemini, Grok Build, Cursor CLI or GitHub Copilot CLI holds a prompt until it takes it, so the command returns then.
Grok Build queues that prompt; pressing Enter again sends it now and cancels the turn. Gemini local
slash commands, ? help and ! shell input, and the / and ! commands of Grok Build and Cursor CLI, and the / and !
commands and a lone ? of GitHub Copilot CLI, return after Enter without confirming a prompt record. A compact command
(`/compact` of Claude Code and Codex) returns once the agent records the compaction, however long that takes
while the agent works on it; --timeout bounds it. In other programs it returns once Enter is pressed.

With --wait, the command fails if the agent does not start working within 10 seconds of the Enter,
and otherwise prints how the wait ended; with --until it waits for that state instead, as
`cornercase wait --until` does.

Examples:
  cornercase send --pane 12 --enter 'Now add tests for it'
  cornercase send --pane 12 --enter --wait --timeout 900 - < next-step.md
  cornercase send --pane 12 --enter --wait --until turn-over 'Run the tests'

================================================================ cornercase read
Print the screen of a pane as text, or its last lines

Usage: cornercase read [OPTIONS]

Options:
      --pane <ID>                 The pane; with --last-message, repeat it to read several [default: the one this runs in, else the shown one]
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --tab <ID>                  A tab: its agent's pane, else its active one; with --last-message, repeat it
      --lines <N>                 The last N lines, scrollback included (a pane keeps its last 10 MB of output)
      --last-message              The last message of the agent in the pane, from its own record
      --view <ID>                 Act in this view (see `cornercase view`): its tab is the default, and --focus moves the view instead of the window
      --json                      Print JSON instead of text
  -h, --help                      Print help

Lines the terminal wrapped come back joined, and empty lines at the end are left out.

With --last-message it prints the last message the agent in the pane wrote, as plain text, from
its own record (Claude Code's transcript, Codex's rollout, Gemini's session file, opencode's
database, Grok Build's session, Cursor CLI's chat store, GitHub Copilot CLI's session events) instead of the
screen, so it comes whole even once it scrolled off, without the input box or status lines. While the agent works
it is the newest one so far. --json adds when it was written and whether the agent's turn is over. It fails on a
pane without Claude Code, Codex, Gemini CLI, opencode, Grok Build, Cursor CLI or GitHub Copilot CLI, and before
the agent wrote anything.

With --last-message, repeat --pane or --tab to read several agents at once. Each message has a
header with its pane, agent, turn_over and written time; --json gives {"panes": [...]}. Panes come
first, then tabs, in the order given, and a repeated id is read once. Errors stay with their target,
and it exits 3 after reading them all if any failed; with no server it prints nothing and exits 1.
One target keeps the output above. Reading the screen takes only one target.

Claude Code's feedback survey (`How is Claude doing this session? (optional)`, then
`1: Bad  2: Fine  3: Good  0: Dismiss`) may show above its input box: it is Claude Code asking you,
not the agent's output. `cornercase keys --pane N 0` dismisses it.

Examples:
  cornercase read --pane 12
  cornercase read --pane 7 --lines 200 > build.log
  cornercase read --pane 12 --last-message
  cornercase read --tab 4 --last-message --json
  cornercase read --last-message --pane 12 --pane 15 --json

================================================================ cornercase wait
Wait until an agent stops working, a program ends, text shows up or the output stops

Usage: cornercase wait [OPTIONS]

Options:
      --pane <ID>
          The pane; repeat it, or add --tab, to wait on several [default: the one this runs in, else the shown one]

      --remote <DESTINATION>
          Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)

      --remote-command <COMMAND>
          How to run cornercase there, as sh reads it [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]

      --tab <ID>
          A tab: its agent's pane, else its active one; repeat it to wait on several

      --any
          Return once any of the panes meets the condition

      --all
          Return once every one of the panes has met the condition

      --until <UNTIL>
          Until the pane is in this state

          Possible values:
          - idle:      The agent is idle or done
          - working:   The agent is working
          - waiting:   The agent waits for an answer to a question or a permission prompt
          - shell:     The program in the foreground ended and the shell is back
          - turn-over: The agent's turn is over: it stopped working, or only a background shell it started still runs

      --text <REGEX>
          Until a line on its screen matches, one already there included

      --quiet <SECONDS>
          Until it writes nothing for this long

      --timeout <SECONDS>
          Give up after this long, with status 1

      --view <ID>
          Act in this view (see `cornercase view`): its tab is the default, and --focus moves the view instead of the window

      --json
          Print JSON instead of text

  -h, --help
          Print help (see a summary with '-h')

By default it waits until the agent stops working: idle, done, failed, pending (marked for review) or
waiting. A Claude Code agent whose turn is over while a background shell it started still runs
counts as working, since it wakes up when the shell ends; --until turn-over also ends there, and
prints shell. Subagents an agent started keep every wait waiting, --until turn-over included: the
agent goes on when they end. It then prints how it ended (idle, done, failed, pending, waiting, working, shell or quiet),
or the line that matched.
Waiting for an agent needs OSC 7501 reports, or a reader for Claude Code, Codex, Gemini CLI,
opencode, Grok Build, Cursor CLI or GitHub Copilot CLI in the pane. Without reports, Gemini status needs its dynamic window title,
and Cursor CLI's waiting needs /status-indicators. A timeout exits with 1 and does not prove that the
agent missed what you sent: read the pane before sending it again.

Several panes and tabs take --any or --all, and the condition applies to each. --any returns once
one of them meets it and prints one line, its id and how it ended; --all returns once every one has
met it, and prints one such line each, in the order given. The id is the one given, so a tab's line
starts with the tab's id. A pane that closes meanwhile ends as `closed` instead of failing the wait.

Examples:
  cornercase wait --pane 12 --timeout 600
  cornercase wait --pane 7 --until shell
  cornercase wait --pane 12 --until turn-over --timeout 600
  cornercase wait --pane 7 --text 'test result: (ok|FAILED)'
  cornercase wait --any --pane 12 --pane 15 --tab 9 --timeout 1800

================================================================ cornercase close
Close a pane, tab, workspace or project

Usage: cornercase close [OPTIONS] <--pane <ID>|--tab <ID>|--workspace <ID>|--worktree <BRANCH>|--project <ID>>

Options:
      --pane <ID>                 A pane
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --tab <ID>                  A tab and its panes
      --workspace <ID>            A workspace and its tabs
      --worktree <BRANCH>         The workspace on this branch, looked up in the project this runs in, else the shown one
      --project <ID>              A project and its workspaces
      --remove-worktree           Also remove the workspace's git worktree from disk
      --agent                     Close the agent in --pane with what it started there, as its close agent in the window does; nothing is removed from disk
      --force                     Remove it even when git would lose changes
      --unlock                    Unlock a locked worktree first, as the window's unlock and remove does; changes still need --force
      --check                     Only say what removing it would lose, or with --agent what would close, as the window's dialog does; nothing stops
      --json                      Print the check, or with --agent what was closed, as JSON
  -h, --help                      Print help

Its shells stop, as with its ×, but nothing asks first, not even for a project. A worktree's
workspace stays listed while its worktree exists, and its branch is kept.
--remove-worktree runs the project's teardown first; a teardown that fails is a warning on
stderr, and the worktree is removed anyway. --check only says what removing it would lose, as the
window's dialog does (changes that are not committed, a lock and whether its process still runs, the
worktrees of a flow's roles that go with it, the teardown), and stops nothing. --unlock does what
the dialog's unlock and remove does; changes still need --force.
--agent closes the agent in --pane as its close agent in the window does, without asking: its tab
and the tabs of the agents it started in the same workspace, at any depth. For a member of a flow
run, its whole team closes and the run ends. Agents it started elsewhere keep running. Nothing is
removed from disk, a worktree and its branch stay (close --workspace ID --remove-worktree removes
a worktree). With --check it only says what would stop and keep running.

Examples:
  cornercase close --tab 9
  cornercase close --workspace 5 --remove-worktree
  cornercase close --worktree fix/login --remove-worktree
  cornercase close --worktree fix/login --remove-worktree --check
  cornercase close --worktree fix/login --remove-worktree --unlock
  cornercase close --agent --pane 12 --check
  cornercase close --agent --pane 12

in a view), and with --json its token, agent, status, place, message and panes:
  workspace 2  notice  claude needs you in shop › main  cc-3f2a9c-4
`cornercase go TOKEN` then does what a click on that notification does.
With --host, a program's own requests to the terminal are told too, for programs that draw the panes:
  pane 7  clipboard  11 bytes         it wrote to the clipboard (OSC 52); the text itself only with --json
  pane 7  bell  3 times               it rang the bell: one line a second per pane, with how many rang
With --json, each line is a JSON object with the event, the ids, the old and new state and the time.

It ends when the server stops, once every pane given with --pane has closed, or soon after what reads
its output is gone (a closed pipe or socket, such as an ssh that ended), with status 0. Programs are looked
at every half second while something follows events, so one that ends sooner may not show. Start it
before what you want to follow, or read `cornercase status` once it runs, so nothing falls between.
A reader that falls far behind loses events, and a line says how many.

Examples:
  cornercase events
  cornercase events --pane 12 --pane 14 --json
  cornercase events --host --json
  cornercase events --notices --json

================================================================ cornercase flow run
Start a flow in a worktree, and print its workspace's id and each role's pane id

Usage: cornercase flow run [OPTIONS] <NAME>

Arguments:
  <NAME>  The flow, as `cornercase flow list` names it

Options:
      --prompt <TEXT>             The task: what the team should do
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --prompt-file <FILE>        Read the task from a file, or from standard input with -
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]

      --project <ID>              The project [default: the one this runs in, else the shown one]
      --issue <KEY>               Work on this issue instead: a key such as #482, sc-48 or ENG-42, or its URL, with the prompt the Issues dialog's start uses and its branch (settings → Worktrees → issue branches; --worktree names another)
      --source <SOURCE>           The tracker, for a key that more than one could have [possible values: github, gitlab, shortcut, linear, jira, plane, asana]
      --workspace-name <NAME>     The workspace's name when the issue makes a worktree [default: the issue's key and title]
      --profile <NAME>            Start it with the accounts of this profile; an empty name is each agent's own login [default: the default accounts]
      --account <AGENT=ACCOUNT>   Start that agent with this account, over the default ones; AGENT= is its own login. Give it once per agent
      --focus                     Also show it in the window, or in the view with --view, which otherwise stay as they are

      --json                      Print JSON instead of text
  -h, --help                      Print help

It makes the worktree (or uses a worktree already on that branch, if it runs no flow), opens a
tab per role named after it, the orchestrator first, and starts every agent with its role prompt,
answering their trust prompts. The orchestrator starts last, with a brief: the task, the team and
its pane ids, the stages, and how to drive the agents. Nothing is shown in the window unless you
pass --focus.

With --issue KEY instead of --prompt, the task is the issue's, from the same prompt template and branch the
Issues dialog's start a flow uses; an issue that isn't tied to a repository needs --project when several
projects are repositories. Otherwise, without --worktree, the branch comes from the task's first words, with a short suffix when that
says nothing, is a default branch or is already taken. A chosen branch that is main, master, the
project's default or the one its own folder is on is refused: a flow works on a branch of its own.

A role set to work in a worktree of its own (worktree = own) gets one on the branch <branch>--<role>, made from the
run's branch, with the project's setup; the other roles work in the run's worktree.

It prints the workspace's id, then one line per role: its pane's id and the role's name, separated
by a tab. The run's folder for files, where every role writes its answers, is printed on stderr
(run_dir with --json) and is in $CORNERCASE_RUN_DIR in the team's panes. A name is looked up in yours, then the built-in flows, then the project's: yours replaces
a built-in flow of its name, and a project's flow never stands in for another of the same name; the
command says so on stderr when it happens. A built-in flow deleted in Settings › Flows is refused,
and keeps its name: a project's flow named like it does not run either.

Examples:
  cornercase flow run Quick --prompt 'Fix the login form'
  cornercase flow run 'Bug, test first' --prompt-file bug.md --worktree fix-crash --json

another size. With --tab the surface resizes no terminal: terminals keep the size of whoever sizes the tab (the
window, or a view), so size can differ from rect. With --view ID it streams the tab that view
shows, at the view's size, and follows the view to other tabs (each line carries view and
projection); it pauses while the view is inactive or has no size, and ends when the view closes.
The window keeps showing what it showed, also when the tab is not the one on screen. It ends when the tab closes, the
server stops or what reads it is gone (status 0); stopping it leaves the shells running. A reader that falls behind gets
fewer lines, each complete.

With --popup it streams the plugin popup open in the window (see `cornercase plugin run`) instead of a tab:
one pane, its program's terminal, at the popup's own size, with `popup` naming the plugin and the action,
`tab` 0 and no layout. It ends when the popup closes. `cornercase input --popup` types into it.

With --patches, each line after the first carries only what changed since the line before: `base` is the
revision it applies to, and each changed pane has its cursor and what changed of the rest (`lines` by
row number, `copy` for rows that moved). A complete line, without `base`, comes again whenever the layout,
a size, the panes or the view change, after the reader fell behind, and when `cornercase redraw --surface
ID` asks for one.

Examples:
  cornercase surface --tab 3 --cols 120 --rows 40
  cornercase surface --tab 3 --cols 120 --rows 40 | jq -c '[.revision, [.panes[].pane]]'
  cornercase surface --tab 3 --cols 120 --rows 40 --patches
  cornercase surface --view 41
  cornercase surface --popup

================================================================ cornercase view
Open a view of your own: its own tab and size, for programs that draw cornercase themselves

Usage: cornercase view [OPTIONS]

Options:
      --cols <N>                  Columns of the view's surface (1 to 1000); without a size it only follows the session
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --rows <N>                  Rows of the view's surface (1 to 500)
      --inactive                  Start inactive: it sizes nothing and streams no terminals until `view-set --active`
      --tab <ID>                  Start on this tab [default: what the window shows]
      --workspace <ID>            Start on this workspace's active tab
      --project <ID>              Start on this project's active workspace
      --hidden                    Start hidden: the tab it shows does not count as seen until `view-set --visible`
  -h, --help                      Print help

For programs that draw cornercase themselves, such as an editor extension or a GUI, so that each
picks its own tab and size without touching the window or the others. It keeps running and prints
the session as one JSON line each time it changes, like `status --follow`, with a `view` object:
id, projection, active, cols, rows, shown (the project, workspace, tab and pane it shows) and
controls (whether it sizes its tab's terminals now). The view lives while this command runs:
stopping it closes the view and gives its tabs back. The first line is the state now; the view's id
is in it. Keep it running in the background (`cornercase view --cols 120 --rows 40 > view.jsonl &`),
read the id from the first line, and pass it as --view ID to `focus`, `new-tab`, `split`, `start`,
`send`, `keys`, `read`, `wait`, `status`, `rename`, `mark`, `go` or `surface`: the view's tab is their
default and --focus moves it.

While the view is active, has a size and is not hidden, the tab it shows counts as seen like the
window's: an agent there gets no done mark, toast or desktop notification. --hidden starts it hidden
(`view-set --hidden` and `--visible` change it), for a window that is minimised or behind others:
agents in its tab then notify again. While a view is open, the window's tab counts as seen only while
a window is attached.

A tab's terminals take the size of the window or the view that claimed it last, without the
window's sidebar and panels: a view claims the tab it shows when it opens, moves there or turns
active, and using the window takes back the tab it shows. Only that one resizes them. Without
--cols and --rows the view only follows the session and sizes nothing. Shared with the window and
other views: the processes, the split layout, the focused pane of a tab, scrolling and selection.

Examples:
  cornercase view --cols 120 --rows 40
  cornercase view --cols 120 --rows 40 --tab 7

================================================================ cornercase view-set
Change a view: its size, whether it is active, or take back the tab it shows

Usage: cornercase view-set [OPTIONS] --view <ID>

================================================================ cornercase input
Type keys, text, pastes and mouse events into a pane, for programs that draw its terminal

Usage: cornercase input [OPTIONS] <EVENT>...

Arguments:
  <EVENT>...  One JSON event, or - to read one per line from standard input

Options:
      --pane <ID>                 The pane to type into; `cornercase status --panes` lists them. With --follow, for the lines that name none. With --popup, the popup's id from its surface lines (`popup.pane`), so nothing reaches a popup opened since
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --popup                     Type into the plugin popup open in the window instead of a pane
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --follow                    Keep running and send each line of standard input as soon as it arrives, until it ends (give - as the only EVENT)
      --json                      Print JSON instead of text
  -h, --help                      Print help

For programs that draw cornercase's terminals themselves (see `cornercase surface`). Each
EVENT is one JSON object, sent in order:
  {"key": {"code": "c", "mods": ["ctrl"]}}   code as for `keys`; mods ctrl, alt, shift, super; kind press, repeat, release
  {"text": "héllo"}                           typed text, without control characters
  {"paste": "two\nlines"}                     bracketed when the program asked for it
  {"mouse": {"kind": "down", "button": "left", "x": 3, "y": 1}}
                                             kind down, up, drag, moved, scroll-up, scroll-down,
                                             scroll-left, scroll-right; x and y are cells of the
                                             pane's terminal, from 0
- reads one event per line from standard input.

Events are encoded the way the program in the pane asked for (its keyboard protocol, application
cursor keys, bracketed paste, mouse mode), whatever the window shows: a dialog or a field there
takes nothing. Keys, text and pastes bring the pane's view back to the bottom. Mouse events and key
releases that the program does not take are not sent, and said on stderr. When one event is wrong,
or the program is not reading its input, nothing is sent. Scripts and agents should use `send` and
`keys`, which check before typing into an agent. With --popup the events go to the plugin popup open
in the window, its x and y being cells of the popup's terminal; add --pane with the popup's id from its
surface lines (popup.pane) so that nothing is sent if that popup closed and another one opened.

With --follow it keeps running and reads one event per line from standard input (give - as the
only EVENT) until it ends: each line goes as soon as it arrives, and the lines that arrive while
the answer before is on its way go together, so a program types through one process (and with
--remote one ssh connection). A line may name its pane, {"pane": 14, "key": {"code": "enter"}},
else it goes to --pane. Each request is all or nothing on its own: with --json it prints one line
each, the answer with events (how many lines it answers) or its error, and a line that is wrong or
refused does not stop the next ones; the command then exits with 3.

Examples:
  cornercase input --pane 12 --follow --json -
  cornercase input --pane 12 '{"text": "ls"}' '{"key": {"code": "enter"}}'
  cornercase input --pane 12 '{"mouse": {"kind": "scroll-up", "x": 10, "y": 5}}'
  cornercase input --popup --pane 40 '{"key": {"code": "down"}}' '{"key": {"code": "enter"}}'

================================================================ cornercase paste-file
Paste a file of this machine into a pane: kept on the server's machine, its path pasted, so an agent there can open it

Usage: cornercase paste-file [OPTIONS] --pane <ID> [FILE]

Arguments:
  [FILE]  The file to paste, on this machine; - or none reads standard input

Options:
      --pane <ID>                 The pane to act on; `cornercase status --panes` lists them
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --name <NAME>               The file's name there [default: FILE's name, else pasted, with an image's extension]

  -h, --help                      Print help

meanwhile only rewrites the keys it touches, and it does not write over a file it cannot read.

================================================================ cornercase changes
List, read, mark, stage and discard the changes of a workspace, as the changes panel shows them

Usage: cornercase changes [OPTIONS] <COMMAND>

Commands:
  list         Print the changed files of a workspace, or of every project
  file         Print one file's diff
  gap          Print the unchanged lines between a hunk of a file and the one before
  base         List the branches to compare with, or choose one
  merge-check  Merge a workspace's work, committed or not, into its base and with the workspaces it shares files with, in a scratch copy, and print the conflicts
  shared       Print the files a workspace changes that other workspaces of its project change too
  viewed       Mark a file as viewed, or clear the mark
  discard      Throw away a file's uncommitted changes, after asking
  stage        Put a file's changes in git's index, as `git add` does
  unstage      Take a file's changes out of git's index; the file keeps them
  help         Print this message or the help of the given subcommand(s)

Options:
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
  -h, --help                      Print help

`list` prints the changed files of a workspace (the one you are in, or the one --workspace or --worktree names), or of every project with --every, and with --follow keeps printing them as JSON lines each time they change. `file` prints one file's diff, `gap` the unchanged lines between one of its hunks and the one before (hunks count from 0, so the first has no gap), `base` the branches the Commits and All modes can compare with (naming one sets it, --default goes back to following the default branch), and `viewed` marks a file as viewed or clears the mark. `discard` throws a file's uncommitted changes away (a file git does not track is deleted), asks first on a terminal and needs --yes in a script; it cannot be undone. `stage` puts a file's changes in git's index, as `git add` does, and `unstage` takes them out of it. `viewed`, `stage`, `unstage` and `discard` act on the version `changes file` shows; with --digest, on the version whose digest `changes list --json` or `changes file --json` printed, the one you saw, so a file that changed since is left alone (`viewed` does not mark it, the others fail and say so). The modes are uncommitted (the default), commits and all. The base and the viewed marks are shared with the window's changes panel; the mode of a stream is its own.

Examples:
  cornercase changes list
  cornercase changes list --every --follow
  cornercase changes list --worktree fix/login --mode commits --json
  cornercase changes file src/main.rs --json
  cornercase changes gap src/main.rs --hunk 1
  cornercase changes base origin/main
  cornercase changes viewed src/main.rs
  cornercase changes stage src/main.rs
  cornercase changes unstage src/main.rs
  cornercase changes discard src/main.rs --yes
  cornercase changes discard src/main.rs --digest 550a7a517a389403 --yes

  search  Search the names or the text of the files of a workspace
  help    Print this message or the help of the given subcommand(s)

Options:
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
  -h, --help                      Print help

`list` prints the entries of one or more folders, `read` a file, and `search` finds files by name or by text, all as the files panel does, so a program on another machine (--remote) sees what the panel shows without reading the disk itself.

A path is relative to the workspace (the one you are in, or the one --workspace or --worktree names), never to the folder the command runs in; an absolute path, or one starting with ~/ (the server's home folder), reaches any folder on the server's machine, with no workspace needed, but then git marks only appear inside the workspace.

`list` prints one line per entry after a header: folder, name, kind (file, folder or other: a device, a pipe, a socket or a link to nothing), status (git's mark: modified, added, deleted, renamed or untracked, and for a folder added when everything in it is new and modified when it holds changes), bytes and modified (UTC). A - stands for nothing and . for the workspace's root. What git ignores and .git are left out, hidden files are listed (`hidden` in the JSON), at most 10000 entries per folder (said on stderr, `more` in the JSON), and a folder that cannot be listed prints on stderr and, with --json, in its `error`; the command still prints the rest and exits with 3.

`read` prints a text file as it is, up to 8 MB. An image (told by its first bytes) up to 32 MB prints its format, size and bytes; with --json its `image` holds those and `data`, the file in base64, and its `language` the grammar a viewer highlights it with. What is binary, too large, a folder or gone says so (`kind` in the JSON: text, image, binary, too-large, folder or missing); a folder or a missing file exits with 1. Only regular files are read, so a link to a device answers binary.

`search` prints the best 200 file names that match QUERY, ranked, smart-cased, or with --text (the default) the lines of at most 1000 matches as path:line:text, as `grep -n` does. It looks in the workspace only.

--follow on `list` and `read` keeps running and prints one JSON line each time the folders or the file change, checked on the server every 2 s for folders and every second for a file: first as it is now, with `stream`, `revision` and `boot`; each line replaces the one before. It ends when the workspace goes or once what reads it is gone. A connection follows one at a time.

Examples:
  cornercase files list --workspace 3 --json
  cornercase files list src --workspace 3 --follow
  cornercase files list '~/code' --json
  cornercase files read src/main.rs --workspace 3 --json
  cornercase files search parse --text --workspace 3 --json
  cornercase files search main.rs --names

================================================================ cornercase ports stop
Stop the program of a workspace that listens on a port: SIGTERM, then SIGKILL after 3 s

Usage: cornercase ports stop [OPTIONS] <PORT>

Arguments:
  <PORT>  The port, as `cornercase ports` lists it

Options:
      --pid <PID>                 Which program, when several listen on the port
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --json                      Print JSON instead of text

================================================================ cornercase processes
List what every pane runs with its CPU and memory, as the Processes dialog does, or stop a program

daemonizes leaves its pane's tree. `cornercase processes stop PID` stops one (see its --help).

A plugin is a folder with a cornercase-plugin.toml that declares commands: actions in the row menus, hooks on events, services the server keeps running and processes each local window keeps running. Its commands talk back through these same commands.

Install one from GitHub, any https:// git address or a git folder, pinned to a commit; a repository can hold several plugins, each in its own folder (owner/repo/folder on GitHub, address//folder elsewhere): you see where it comes from, what it asks for and every command it runs before anything runs, and it is installed turned off. Link a folder of yours instead while you write one.

`--preview` fetches a plugin, or an update of one, and prints that same preview, then exits without asking or installing, also with no terminal; with `--json` (and an ID for `update`) it is one JSON object, for a program that shows it and asks itself. `--commit` then installs, or updates to, exactly the commit the preview printed: it fails and installs nothing once the source gives another commit, and unlike SOURCE@COMMIT, which pins the plugin there, later updates still follow its branch or tag.

A plugin runs as you and can do anything you can, including typing into every terminal. What it asks for is shown before you turn it on, not enforced. A running server picks up changes within a second.

`actions` lists what plugins add to the menus, for a kind of row (--context) or all of them, and `run` runs one on a project, workspace, tab or pane as its menu entry does: in the workspace's folder, with the ids of what you name, stopped after 5 minutes, its output in the plugin's log. Both ask the running server; `run` waits for the action and exits with 1 when it fails. An action on a plugin's button runs with no target, on what the window shows. A popup action waits until its popup closes, and needs a window attached; `popup-close` closes it. An action listed before the plugins changed is refused (pass the --revision `actions --json` printed, or none for the current one).

`status` prints the plugins as Settings › Plugins shows them: on, off or cannot run, the label and the note, and what each service is doing (running, restarting or still starting), and why `plugins.json` cannot be read. It asks the running server. `list` still reads the files and works with no server.

Examples:
  cornercase plugin install acme/notes
  cornercase plugin install acme/notes@v1.2.0
  cornercase plugin install acme/notes --preview --json
  cornercase plugin update acme.notes --preview
  cornercase plugin install acme/tools/plugins/notes
  cornercase plugin install https://git.example.com/acme/tools.git//plugins/notes
  cornercase plugin link ~/code/my-plugin
  cornercase plugin enable my-plugin
  cornercase plugin list
  cornercase plugin status
  cornercase plugin status --json
  cornercase plugin actions --context pane
  cornercase plugin run acme.notes open --pane 5
  cornercase plugin run acme.notes browse
  cornercase plugin popup-close
  cornercase plugin logs my-plugin --follow
  cornercase plugin disable my-plugin
  cornercase plugin update
  cornercase plugin remove notes
