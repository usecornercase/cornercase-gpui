cornercase 0.13.51: the help of every command and subcommand, in the order of `cornercase --help`.
Made by tools/cornercase-cli.sh, which runs CORNERCASE_BIN, else cornercase on the PATH.

================================================================ cornercase status
List the projects, workspaces, tabs and panes, with their ids

Usage: cornercase status [OPTIONS]

Options:
      --panes                     One line per pane, its columns separated by tabs, for scripts
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --follow                    Keep running and print the whole state as one JSON line each time it changes (`cornercase view` does it for a view)
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --app                       Print the TODO list, the queue, away, the update found and keep awake as JSON; with --follow, again each time they change
      --view <ID>                 Act in this view (see `cornercase view`): its tab is the default, and --focus moves the view instead of the window
      --json                      Print JSON instead of text
  -h, --help                      Print help

Each pane shows its program and folder, and for a coding agent what it is doing (working,
waiting for an answer, done out of sight, failed, idle), its model and how full its context is. `(you)`
marks the pane running the command, `(shown)` what the window shows. `working (background shell)`
is a Claude Code agent whose turn is over while a shell it started in the background still runs:
it wakes up when that shell ends (`background_shell` in the JSON, where the status stays working).
`working (2 subagents)` is an agent whose own turn is over while subagents it started still run
(`subagents` in the JSON, the number): it goes on when they report back, so it stays working.
`(dialog open)` is a Claude Code agent showing a dialog, a panel or its shell mode instead of its
input box, which `cornercase send` refuses (`dialog` in the JSON).
`(survey open)` is Claude Code's feedback survey above its input box, which `cornercase send`
refuses too (`survey` in the JSON): `cornercase keys --pane N 0` dismisses it.
`(resuming)` is a pane whose agent is coming back in its conversation after a restart: until it
is back, it takes no input and `cornercase send` refuses it (`resuming` in the JSON).
`(role coder)` marks a flow member and the role it plays (`role` in the JSON).
`(collapsed)` is an agent whose children are hidden in the agents section (`collapsed` in the JSON).
`Opus 5.5 · compacted` is an agent whose conversation was just compacted: its context is empty
until its next reply and comes back then (`compacted` in the JSON, there only while true).
The JSON also names the conversation a pane's agent is in (`conversation`, the id `places` gives in
`cornercase recap --json`), null until the agent has one and always for opencode.

With --panes it prints one line per pane instead, for scripts, in the sidebar's order: a header
line naming the columns, then one row per pane, its columns separated by tabs. The columns are
pane, tab, workspace, project (their ids), program, agent, status, background_shell, dialog,
at_prompt, model, context, caller (the pane running the command), shown (the pane the window
shows), active (its tab's active pane), tab_name, workspace_name, branch, worktree, project_name,
path, survey (Claude Code's feedback survey shows), resuming (the agent is coming back in its
conversation), parent (the pane that started it, while what started it still runs there),
subagents (how many it still runs), role (the role it plays in a flow, from its run),
held_sends (how many messages `cornercase send` holds until the person in the pane is done
typing), draft (true while it has text a person typed and has not sent), account_restart
(waiting while it waits for its turn to end to restart on another account), pid (its
shell's process id), memory (the bytes its shell and the programs under it use, while that setting is
on) and compacted (true while the context is empty because the conversation was just compacted);
new ones only ever go at the end. Values are as in the
JSON (true or false, context as a number, full paths), with - where there is none and a space for a tab or line break in a name.
With --json, it prints {"panes": [...]}, one object per pane with the columns as keys and null
where there is no value.

With --follow it keeps running and prints the whole state as one JSON line: first as it is now,
then again shortly after each time something in it changes, always JSON, with
--json or without. Each line is what --json prints plus `revision`, which grows with every line,
with `caller` always null;
`boot` names the server's run, and revisions only compare within one boot. Each line replaces the
one before. It ends when the server stops or restarts, or once what reads it is gone; to go on, run
it again, and its first line
is the state then, so nothing is missed. A reader that falls behind reads at most four older
lines, then the latest state.

With --app it prints, as JSON, what is outside the session: `todos` (as `todo list --json`), `queue`
(the entries of `queue list --json`), `away` (one row per chat app: `platform`, `ready`, `away`, and
on Discord `forum`, its setup, with `servers` while it waits for `config forum-server ID`),
`update` (the release found and its notes, why there is none, whether a check or an install runs,
and how installing works here) and `keep_awake` (null while the setting is off), with the server's
`version` and `boot`. `accounts_revision` moves each time `account list` would name other accounts,
and is left out until it first does, so a client lists them again only when it moves. With --follow
it keeps running and prints one such line first and again each time one of them changes, each with
a `revision` that grows by one per line, sent at most twice a second while someone follows; rules
for ending and for slow readers are --follow's.

Examples:
  cornercase status
  cornercase status --json
  cornercase status --panes | awk -F'\t' '$7 == "waiting" { print $1 }'
  cornercase status --panes --json | jq '.panes[] | select(.agent) | .pane'
  cornercase status --follow | jq -c '[.revision, (.projects | length)]'
  cornercase status --app --follow | jq -c '[.revision, (.todos | length)]'

================================================================ cornercase open
Open a folder as a project, or find the open one, and print its id; import a .code-workspace file as a group

Usage: cornercase open [OPTIONS] <PATH>

Arguments:
  <PATH>  The folder, or a VS Code .code-workspace file to import as a group

Options:
      --into <GROUP>              Put it in this group, as the group's add project does
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --focus                     Also show it in the window, or in the view with --view, which otherwise stay as they are
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --view <ID>                 Act in this view (see `cornercase view`): its tab is the default, and --focus moves the view instead of the window
      --json                      Print JSON instead of text
  -h, --help                      Print help

PATH is a folder, or a VS Code .code-workspace file, which is read on the server's machine and
imported as the folder picker does: into a group named after the file (a group of that name is
reused), each of its folders a project there, in order. A folder already open moves into the group
instead of opening twice, a folder's `name` names a project that has no name of its own, and a
folder that is gone is skipped. So is one on another machine (a vscode-remote:// address, a network
path on Windows), as in the picker: it counts nowhere and changes no exit status.

A file prints the group's id, and with --json {"group", "name", "projects", "missing", "failed"}:
the group (null when nothing could go in a new one), its name, the projects' ids, how many folders
are gone and how many could not start a shell. It exits with 3 when either count is not 0 or
nothing was imported, after printing that; without --json, a warning on stderr says what happened.
--focus shows its first project.

--into GROUP puts what it opens in that group, as the group's add project does, a folder or a file.
A folder already open moves there.

With --remote, PATH is the other machine's, and so is the file: absolute, or starting with ~/,
quoted so that this machine's shell leaves it alone.

Examples:
  cornercase open ~/src/shop
  cornercase open . --focus
  cornercase open ~/src/team.code-workspace --focus
  cornercase open ~/src/docs --into 3
  cornercase --remote devbox open '~/src/team.code-workspace' --json

================================================================ cornercase clone
Clone a git repository into a folder, open it as a project, and print its path

Usage: cornercase clone [OPTIONS] <URL> [FOLDER]
       cornercase clone --list-ignored [--from <FOLDER>] [--json]

Arguments:
  [URL]     The repository, as `git clone` takes it
  [FOLDER]  The folder the clone goes in, as a new folder named after the repository [default: the current one; with --remote, the home folder there]

Options:
      --file <PATH>               A file of the repository here to copy into the clone, such as the git-ignored .env, by its path from the repository's root; repeat it for more
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --from <FOLDER>             The repository here that --file and --list-ignored read, on this machine also with --remote [default: the current folder]
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --list-ignored              Print the git-ignored files in that folder that --file can copy, and clone nothing; it needs no server, and --remote changes nothing for it
      --focus                     Also show it in the window, or in the view with --view, which otherwise stay as they are
      --view <ID>                 Act in this view (see `cornercase view`): its tab is the default, and --focus moves the view instead of the window
      --json                      Print JSON instead of text
  -h, --help                      Print help

Runs `git clone` on the server's machine into a new folder inside FOLDER, named after the
repository as git names it, then opens that folder as a project, as `cornercase open` does, and
prints its path once git is done. A folder of that name that exists and is not empty is refused;
an empty one is used. A FOLDER with `..` in it is refused, and so is a repository named `.git`.
A repository on this machine can be given by its path, relative to the current folder. A clone
that fails leaves no folder behind, the folders it made for FOLDER included, and says what failed:
not a repository, access denied, or git's own reason. git never asks for a password: the server's
ssh keys and git credentials must already reach the repository. With --remote, FOLDER and a
repository's path are the other machine's (absolute, or starting with ~/), and without FOLDER the
clone goes in that machine's home folder.

--file copies a file of the repository here into the new clone once git is done, such as the
git-ignored .env a project needs to run, as the Clone on machine dialog does with the ones you
tick. This command reads it, on the machine it runs on also with --remote, and sends it with its
permissions. PATH goes from the root of the repository that --from is in (the current folder by
default). Refused by name before anything is cloned: a path that is absolute, goes up with `..` or
into `.git` (status 2); a file that is missing, a folder, a link or a file over 1 MiB (status 1),
and more than 200 files or 8 MiB in all. A file the clone could not take, such as one the
repository has, leaves the clone done and is not written: it is named on standard error, or under
"unwritten" with --json, and the command exits 3.

--list-ignored prints the git-ignored files in that folder, which the dialog offers, and clones
nothing: each from the repository's root with its size, and `too big to copy` over 1 MiB, then how
many more past the 200th. With --json: {"root", "files": [{"path", "size", "mode", "too_big"}],
"left_out"}. It reads this machine's folder, since the files are here even when the clone goes
elsewhere, so it needs no server, and --remote changes nothing for it. On Windows --file and
--list-ignored say they are not supported yet.

Examples:
  cornercase clone git@github.com:acme/shop.git ~/src
  cornercase clone https://github.com/acme/shop --focus
  cornercase --remote devbox clone git@github.com:acme/shop.git ~/src --json
  cornercase clone --list-ignored --from ~/code/shop --json
  cornercase --remote devbox clone git@github.com:acme/shop.git '~/src' --file .env --from ~/code/shop

================================================================ cornercase new-workspace
Add a workspace to a project, or a git worktree, and print its id

Usage: cornercase new-workspace [OPTIONS] <NAME>

Arguments:
  <NAME>  Its name, or its branch with --worktree

Options:
      --project <ID>              The project [default: the one this runs in, else the shown one]
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --worktree                  Check the branch out in a git worktree of its own, at a repository's root only
      --fresh                     Make a missing branch from the up-to-date default branch, as a routine's run does: fetch the remote first (origin, else the first one) and fail with git's reason if that fails [default: settings → worktrees → new branches]
      --no-fresh                  Make a missing branch from the project's HEAD, whatever settings → worktrees → new branches says
      --machine <NAME>            Do it on this machine, as `cornercase machines` names it: ids are then that machine's, as `status --json` lists them under machines, and so are its accounts and trackers
      --focus                     Also show it in the window, or in the view with --view, which otherwise stay as they are
      --view <ID>                 Act in this view (see `cornercase view`): its tab is the default, and --focus moves the view instead of the window
      --json                      Print JSON instead of text
  -h, --help                      Print help

The workspace gets one tab. A worktree goes in the worktrees folder from settings, on a new
branch when the branch does not exist yet; the command returns once git made it. A new branch
starts from the project's HEAD, or, with --fresh or settings → worktrees → new branches, from its
default branch fetched from the remote first, as a routine's run does: a fetch that fails fails the
command with git's reason and nothing is made. A branch that exists is checked out as it is. --fresh
needs a server that knows the `fresh-branches` feature. The project's setup (settings →
project settings) then runs in the new tab, which `start --worktree` waits for before it types the
agent.

With --machine NAME the workspace is made on that machine of `cornercase machines`, by its server:
--project is that machine's id, as `status --json` lists it under machines, and so is the id printed.
--focus shows it in this window once the machine lists it. It needs a server that knows the
`machine-start` feature.

Examples:
  cornercase new-workspace experiments
  cornercase new-workspace fix/login --worktree --project 3
  cornercase new-workspace fix/login --worktree --fresh
  cornercase new-workspace fix/login --worktree --project 2 --machine vps --focus

================================================================ cornercase new-tab

as ssh does, so quote what the shell should read as one argument. The command returns once it
is typed.

Usage: cornercase new-tab [OPTIONS] [-- <COMMAND>...]

Arguments:
  [COMMAND]...
          What to type into its shell

Options:
      --remote <DESTINATION>
          Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)

      --workspace <ID>
          The workspace [default: the one this runs in, else the shown one]

      --remote-command <COMMAND>
          How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]

      --worktree <BRANCH>
          The workspace on this branch, looked up in the project this runs in, else the shown one

      --name <NAME>
          The tab's name [default: the name of the program it runs]

      --profile <NAME>
          Start it with the accounts of this profile; an empty name is each agent's own login [default: the default accounts]

      --account <AGENT=ACCOUNT>
          Start that agent with this account, over the default ones; AGENT= is its own login. Give it once per agent

      --focus
          Also show it in the window, or in the view with --view, which otherwise stay as they are

          Print JSON instead of text

  -h, --help
          Print help (see a summary with '-h')

  cornercase new-tab --workspace 5 -- 'cargo test 2>&1 | tee test.log'

================================================================ cornercase setup
Run a worktree's setup again in a new tab, as its menu's run setup does, and print its pane's id when done

Usage: cornercase setup [OPTIONS]

Options:
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --workspace <ID>            The workspace [default: the one this runs in, else the shown one]
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --worktree <BRANCH>         The workspace on this branch, looked up in the project this runs in, else the shown one
      --focus                     Also show it in the window, or in the view with --view, which otherwise stay as they are
      --view <ID>                 Act in this view (see `cornercase view`): its tab is the default, and --focus moves the view instead of the window
      --json                      Print JSON instead of text
  -h, --help                      Print help

Runs the project's setup again in a new tab of a worktree's workspace, as run setup in the
workspace's menu does, to retry after a fix. It runs as it does when the worktree is made, with
CORNERCASE_ROOT, CORNERCASE_WORKTREE and CORNERCASE_BRANCH set, and the tab then becomes a shell.
Meanwhile `status --json` shows the workspace's setup as running, its failed mark is gone, and
agents started in the workspace wait for it.

The command returns once the setup is done, however long it takes, and prints the pane's id; --json
prints {"project", "workspace", "tab", "pane"}. A setup that fails exits with 1, naming its exit
status and the pane to read, and so does one whose tab closes before it ended. It also exits with 1,
saying why, for what the menu does not offer: a workspace that is not a worktree, a project with no
setup (`cornercase config project`), or a setup already running. Stopping the command does not stop
the setup: press Ctrl+C in its tab (`cornercase keys --pane N ctrl+c`) or close the tab.

Examples:
  cornercase setup
  cornercase setup --worktree fix/login --focus
  cornercase setup --workspace 16 --json

================================================================ cornercase start
Start a coding agent in a new tab, give it a prompt, and print its pane's id

Usage: cornercase start [OPTIONS] [AGENT]

Arguments:
  [AGENT]
          The agent, such as claude or codex [default: the one chosen in settings → agents, else the one running here]

Options:
      --model <MODEL>
          The model, such as opus or gpt-5.5 [default: the agent's own]

      --remote <DESTINATION>
          Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)

      --mode <NAME>
          One of the agent's modes, as settings → agents lists them, such as plan, or default for no mode arguments [default: the one chosen there]

      --remote-command <COMMAND>
          How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]

      --effort <LEVEL>
          The agent's effort, such as high: Claude Code, Codex, Grok Build and GitHub Copilot CLI take one [default: the agent's own]

      --worktree <BRANCH>
          Start it in the worktree of this branch, made when missing

      --workspace <ID>
          The workspace [default: the one this runs in, else the shown one]

      --project <ID>
          The project: a new tab in its folder, or where --worktree or --issue makes the worktree [default: the one this runs in, else the shown one]

      --name <NAME>
          The tab's name [default: the agent's]

      --prompt <TEXT>
          What to ask it

      --prompt-file <FILE>
          Read the prompt from a file, or from standard input with -

      --wait
          Then wait until the agent stops working, and print how it ended

      --until <UNTIL>
          Wait until the pane is in this state instead

          Possible values:
          - idle:      The agent is idle or done
          - working:   The agent is working
          - waiting:   The agent waits for an answer to a question or a permission prompt
          - shell:     The program in the foreground ended and the shell is back
          - turn-over: The agent's turn is over: it stopped working, or only a background shell it started still runs

      --timeout <SECONDS>
          Give up after this long, with status 1

      --placed
          Answer as soon as the tab is open, with the same ids, while the launch goes on: for a program that shows the new tab itself

      --fresh
          Make a missing branch from the up-to-date default branch, as a routine's run does: fetch the remote first (origin, else the first one) and fail with git's reason if that fails [default: settings → worktrees → new branches]

      --no-fresh
          Make a missing branch from the project's HEAD, whatever settings → worktrees → new branches says

      --issue <KEY>
          Work on this issue instead: a key such as #482, sc-48 or ENG-42, or its URL, with the prompt the Issues dialog's start uses and its branch (settings → Worktrees → issue branches; --worktree names another)

      --source <SOURCE>
          The tracker, for a key that more than one could have
          
          [possible values: github, gitlab, shortcut, linear, jira, plane, asana]

      --workspace-name <NAME>
          The workspace's name when the issue makes a worktree [default: the issue's key and title]

      --profile <NAME>
          Start it with the accounts of this profile; an empty name is each agent's own login [default: the default accounts]

      --account <AGENT=ACCOUNT>
          Start that agent with this account, over the default ones; AGENT= is its own login. Give it once per agent

      --machine <NAME>
          Do it on this machine, as `cornercase machines` names it: ids are then that machine's, as `status --json` lists them under machines, and so are its accounts and trackers

      --focus
          Also show it in the window, or in the view with --view, which otherwise stay as they are

      --view <ID>
          Act in this view (see `cornercase view`): its tab is the default, and --focus moves the view instead of the window

      --json
          Print JSON instead of text

  -h, --help
          Print help (see a summary with '-h')

The agent starts with its command and arguments from settings → agents. --mode replaces the mode
chosen there by another of the agent's modes, or drops it with --mode default,
--model adds the agent's own model flag and --effort its effort (Claude Code, Codex, Grok Build and GitHub
Copilot CLI take one; an older server refuses all three rather than start the agent without them). If it asks
whether you trust the folder, the question waits for your answer unless settings → agents accept it for
you. Once it is ready, the prompt is pasted and
submitted, and the command prints the pane's id; it fails if the agent never shows up. With
--wait, a second line says how the wait ended: idle, done (it finished out of sight) or waiting
(it needs an answer); with --until it waits for that state instead, as `cornercase wait --until` does.

--issue KEY (a key such as #482, sc-48 or ENG-42, or the issue's URL) starts the agent on that issue as
the Issues dialog's start does: GitHub and GitLab issues in a worktree on the branch named after the issue, of
the project's own repository; the prompt comes from settings' prompt template and is always submitted.
Shortcut, Linear, Jira, Plane and Asana issues aren't tied to a repository: when several places are open the
command lists them and asks for --project (a new worktree) or --workspace (a new tab). A workspace already
on the branch gets a new tab. It needs a server that knows the `issues` feature.

A branch that --worktree or --issue makes, when it does not exist yet, starts from the project's HEAD, or,
with --fresh or settings → worktrees → new branches, from its default branch fetched from the remote first
(origin, else the first one), as a routine's run does; a fetch that fails fails the command with git's
reason and nothing is made, and --no-fresh asks for HEAD whatever the setting says. A branch that exists
is checked out as it is, with no fetch. --fresh needs a server that knows the `fresh-branches` feature.

With --machine NAME the agent starts on that machine of `cornercase machines`, by its server, as if
the command ran there: --project, --workspace and the pane's id printed are that machine's ids, as
`status --json` lists them under machines, and the agent, its accounts, profiles and issue trackers
are the machine's own. --wait, --until and --timeout are refused: follow the agent there, with
`cornercase --remote`. --focus shows its tab in this window once the machine lists it. It needs a
server that knows the `machine-start` feature.

With --placed the command answers as soon as the tab is open, after its worktree is made or its
issue read, with the same ids, and the launch goes on, here or on a machine, as the window's dialogs
do: a trust question then waits in the tab, not in this command, and the prompt follows its answer.
It is for a program that shows the new tab itself, and it can no longer say that the agent never
showed up. --wait, --until and --timeout are refused, since nothing is waited for. It needs a server
that knows the `machine-start` feature, which came with it.

`cornercase wait` and `send` only work once that launch is over, and the answer does not mean it
is. Until the agent runs, wait says the pane runs no agent; until its prompt is typed, wait can end
on idle; and send goes to whatever reads the pane then, the shell, or the trust question, which it
would answer. `status --json` has no field for the launch, so read the pane there (under machines
for one on a machine): `agent` is null until the agent runs and reports, and `at_prompt` true while
its shell still waits for it; `agent` with the status idle only says it runs, since it may still be
asking its question and its prompt may not be typed; and the status working says it took its prompt,
so the launch is over. Without a prompt, or with an agent that reports no status, only its

answer then comes when the launch is over.

================================================================ cornercase send
Paste text into a pane, and press Enter with --enter

Usage: cornercase send [OPTIONS] [TEXT]

Arguments:
  [TEXT]
          The text, or - to read it from standard input

Options:
      --pane <ID>
          The pane [default: the one this runs in, else the shown one]

      --remote <DESTINATION>
          Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)

      --remote-command <COMMAND>
          How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]

      --tab <ID>
          A tab: its agent's pane, else its active one

      --view <ID>
          Act in this view (see `cornercase view`): its tab is the default, and --focus moves the view instead of the window

      --enter
          Press Enter once the screen settles

      --wait
          Then wait until the agent stops working, and print how it ended

      --until <UNTIL>
          Wait until the pane is in this state instead

          Possible values:
          - idle:      The agent is idle or done
          - working:   The agent is working
          - waiting:   The agent waits for an answer to a question or a permission prompt
          - shell:     The program in the foreground ended and the shell is back
          - turn-over: The agent's turn is over: it stopped working, or only a background shell it started still runs

      --timeout <SECONDS>
          Give up waiting after this long, with status 1

      --force
          Send even when the agent shows a dialog, a panel or its shell mode instead of its input box, or its feedback survey

      --json
          Print JSON instead of text

  -h, --help
          Print help (see a summary with '-h')

The text goes in as one paste, bracketed when the program asked for it. A pane whose agent
waits for an answer to a question or a permission prompt is refused, since the text would answer
it; use `cornercase keys` for that. So is a Claude Code agent that shows a dialog, a panel or
its shell mode instead of its input box (`dialog` in `cornercase status --json`), unless you pass
--force. So is its feedback survey above the input box (`1: Bad  2: Fine  3: Good  0: Dismiss`,
`survey` in the JSON), where a digit sent alone would answer it: dismiss it with
`cornercase keys --pane N 0`, or pass --force. So is a pane whose agent is resuming its conversation
after a restart (`resuming` in the JSON), where the text would reach its shell or its start-up:
send again once it is back, or pass --force. While a person is typing in the pane the text waits for them
and goes right after their prompt (`held_sends` in the JSON); `cornercase held` acts on it from elsewhere.
If they choose send now while they have a draft, the text is pasted after it without its Enter, and the
command fails saying it is in their input.

With --enter, the command returns once Claude Code, Codex, Gemini CLI, opencode, Grok Build, Cursor CLI,
Vibe CLI or GitHub Copilot CLI has recorded the prompt in its own history, and fails with `not confirmed: the prompt may not
have been submitted` when it records none: read the pane before sending it again. A working Codex,
Gemini, Grok Build, Cursor CLI, Vibe CLI or GitHub Copilot CLI holds a prompt until it takes it, so the command returns
then.
Grok Build queues that prompt; pressing Enter again sends it now and cancels the turn. Gemini local
slash commands, ? help and ! shell input, and the / and ! commands of Grok Build and Cursor CLI, and the / and !
commands and a lone ? of GitHub Copilot CLI, and the / (but not /skill), ! and & commands of Vibe CLI, return after Enter without
confirming a prompt record. A compact command
(`/compact` of Claude Code and Codex) returns once the agent records the compaction, however long that takes
while the agent works on it; --timeout bounds it. In other programs it returns once Enter is pressed.

With --wait, the command fails if the agent does not start working within 10 seconds of the Enter,
and otherwise prints how the wait ended; with --until it waits for that state instead, as
`cornercase wait --until` does.

Examples:
  cornercase send --pane 12 --enter 'Now add tests for it'
  cornercase send --pane 12 --enter --wait --timeout 900 - < next-step.md
  cornercase send --pane 12 --enter --wait --until turn-over 'Run the tests'

================================================================ cornercase held
Send now a message that `send` holds for a person typing in a pane, or say it can wait its turn

Usage: cornercase held [OPTIONS] <--send-now|--wait-turn>

Options:
      --pane <ID>                 The pane [default: the one this runs in, else the shown one]
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --tab <ID>                  A tab: its agent's pane, else its active one
      --view <ID>                 Act in this view (see `cornercase view`): its tab is the default, and --focus moves the view instead of the window
      --send-now                  Send the first held message at once, still after an earlier Enter; over the person's draft it is pasted without its Enter, which is left to them
      --wait-turn                 Only say the person saw it: the messages held so far still go after their prompt
      --json                      Print JSON instead of text
  -h, --help                      Print help

`cornercase send` holds a message while a person is typing in the pane, and the window's bar on that
pane offers two buttons. This is what they do, for a program that draws that bar itself: --send-now
is its send now, --wait-turn its wait turn. Give exactly one.

--send-now puts the first held message through at once, as `send --force` does, but never sends the
person's half-written line with it: if they have a draft in the pane then, the message is pasted after
it and its Enter is left to them, to send both with Enter or edit them first, and its sender gets an
error saying the message is in their input. Without a draft it is pasted and entered, and its sender
gets the usual answer, or the refusal when the pane cannot take it (an agent asking a question). If an
earlier message is between its paste and its Enter, it goes right after that Enter, so held_sends may
only drop a moment later. The other held messages keep waiting.

--wait-turn only says the person saw it: nothing goes earlier or later. It covers the messages held so
far, so one held later turns held_queued off again.

Both exit with status 1 and say why when nothing is held in the pane: the message may just have gone
out. --send-now also refuses a pane that is restarting or resuming its agent, where the window has no bar.

It prints what is held now, after a line saying so when --send-now left the Enter to the person. With
--json it prints {"pane", "held_sends", "held_from", "held_queued", "after_draft"}. The first four
are what `status --json`, `status --follow` and `view` have on each pane: held_from is the pane that sent
the first held message (null for a sender outside a pane; a pane since closed keeps its id, and ids
last one run of the server), and held_queued is true once --wait-turn covers the newest held message.
after_draft is true when --send-now pasted the message after the person's draft and left its Enter to
them. A server without the feature held-after-draft (`cornercase contract`) sends both as one line.

Examples:
  cornercase held --pane 9 --send-now
  cornercase held --pane 9 --wait-turn --json

================================================================ cornercase wait
Wait until an agent stops working, a program ends, text shows up or the output stops

Usage: cornercase wait [OPTIONS]

Options:
      --pane <ID>
          The pane; repeat it, or add --tab, to wait on several [default: the one this runs in, else the shown one]

      --remote <DESTINATION>
          Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)

      --remote-command <COMMAND>
          How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]

      --tab <ID>
          A tab: its agent's pane, else its active one; repeat it to wait on several

      --any
          Return once any of the panes meets the condition

      --all
          Return once every one of the panes has met the condition

      --until <UNTIL>
          Until the pane is in this state

          Possible values:
          - idle:      The agent is idle or done
          - working:   The agent is working
          - waiting:   The agent waits for an answer to a question or a permission prompt
          - shell:     The program in the foreground ended and the shell is back
          - turn-over: The agent's turn is over: it stopped working, or only a background shell it started still runs

      --text <REGEX>
          Until a line on its screen matches, one already there included

      --quiet <SECONDS>
          Until it writes nothing for this long

      --timeout <SECONDS>
          Give up after this long, with status 1

      --view <ID>
          Act in this view (see `cornercase view`): its tab is the default, and --focus moves the view instead of the window

      --json
          Print JSON instead of text

  -h, --help
          Print help (see a summary with '-h')

By default it waits until the agent stops working: idle, done, failed, pending (marked for review) or
waiting. A Claude Code agent whose turn is over while a background shell it started still runs
counts as working, since it wakes up when the shell ends; --until turn-over also ends there, and
prints shell. Subagents an agent started keep every wait waiting, --until turn-over included: the
agent goes on when they end. It then prints how it ended (idle, done, failed, pending, waiting, working, shell or quiet),
or the line that matched.
Waiting for an agent needs OSC 7501 reports, or a reader for Claude Code, Codex, Gemini CLI,
opencode, Grok Build, Cursor CLI or GitHub Copilot CLI in the pane. Without reports, Gemini status needs its dynamic window title,
and Cursor CLI's waiting needs /status-indicators. Vibe CLI's status comes only from its reports. A timeout exits with 1 and does not prove that the
agent missed what you sent: read the pane before sending it again.

Several panes and tabs take --any or --all, and the condition applies to each. --any returns once
one of them meets it and prints one line, its id and how it ended; --all returns once every one has
met it, and prints one such line each, in the order given. The id is the one given, so a tab's line
starts with the tab's id. A pane that closes meanwhile ends as `closed` instead of failing the wait.

Examples:
  cornercase wait --pane 12 --timeout 600
  cornercase wait --pane 7 --until shell
  cornercase wait --pane 12 --until turn-over --timeout 600
  cornercase wait --pane 7 --text 'test result: (ok|FAILED)'
  cornercase wait --any --pane 12 --pane 15 --tab 9 --timeout 1800

Options:
      --pane <ID>                 A pane
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]

      --workspace <ID>            A workspace and its tabs

      --project <ID>              A project and its workspaces
      --remove-worktree           Also remove the workspace's git worktree from disk

      --force                     Remove it even when git would lose changes

the dialog's unlock and remove does; changes still need --force.

and the tabs of the agents it started in the same workspace, at any depth. For a member of a flow
run, its whole team closes and the run ends. Agents it started elsewhere keep running. Nothing is

command prints why and exits with 4.

  cornercase close --agent --pane 12

group rows, until it is marked as reviewed or its agent starts working again on a new prompt or an
answer to its question. Looking at the tab does not take it off, unlike the ✓ of an agent that finished while you looked elsewhere.
Both marks are saved with the session, so they come back after a restart with the conversation.

--boot BOOT says which run of the server the pane or tab id is from: `boot` in `status --json`, or in
a machine's entry there. Ids last one run, so a server that restarted since refuses, nothing is
marked, and the command prints why and exits with 4.

Examples:

  cornercase mark --pane 12
  cornercase mark --pane 12 --reviewed
  cornercase --remote vps mark --pane 9 --boot 4242-1700000000

================================================================ cornercase events
Follow agents, programs, panes and tabs as they change, one line per event

Usage: cornercase events [OPTIONS]

Options:
      --pane <ID>...              Only what happens to these panes, and stop once they all closed
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --host                      Also print what programs ask of the terminal: their clipboard writes (with the text in --json) and bells
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --notices                   Also print each notice about an agent that needs you, failed or finished, with its token for `cornercase go`, and the server's other notices (notify, the queue, a failed setup, a flow)
      --json                      Print one JSON object per line instead of text
  -h, --help                      Print help

It keeps running and prints one line per event, as it happens:
  pane 5  claude  working → waiting   an agent changed state: working, shell (its turn is over but a
                                      background shell it started still runs), waiting, done, idle,
                                      or none once it left the pane
  pane 7  cargo  exited               the program in the foreground ended and the shell is back
  tab 3  opened in workspace 2        a project, workspace, tab or pane opened, or closed
With --notices, each notice about an agent is told too, as the window's toast and desktop notification
say it, with the same rules (a second's wait, once per change, never for a tab seen in the window or
in a view), and with --json its token, agent, status, place, message and panes:
  workspace 2  notice  claude needs you in shop › main  cc-3f2a9c-4
An agent on a linked machine tells its notices too, with the machine's name and without ids here:
  machine vps  notice  claude on vps needs you in shop › main  cc-3f2a9c-5
`cornercase go TOKEN` then does what a click on that notification does.
The server's other notices come with --notices too, as the window's toast says them, with a kind and
no token: notify (`cornercase notify`, naming the pane it ran in), queue-started, queue-failed,
queue-missed and queue-kept (a queued agent or routine run; a one-off entry that missed its time sends
none), setup-failed (only while nobody looks at its tab), flow-consent (a flow's member waits for your
consent) and flow-merged (a run's agents closed once its pull request merged). With --json they have
kind, message, panes and the workspace's ids, which queue-failed and queue-missed leave out:
  notify  the release build is ready
  workspace 2  flow-merged  pull request merged in fix-login: 3 agents closed · ▶ on the workspace reopens them
With --host, a program's own requests to the terminal are told too, for programs that draw the panes:
  pane 7  clipboard  11 bytes         it wrote to the clipboard (OSC 52); the text itself only with --json
  pane 7  bell  3 times               it rang the bell: one line a second per pane, with how many rang
With --json, each line is a JSON object with the event, the ids, the old and new state and the time.

It ends when the server stops, once every pane given with --pane has closed, or soon after what reads
its output is gone (a closed pipe or socket, such as an ssh that ended), with status 0. Programs are looked
at every half second while something follows events, so one that ends sooner may not show. Start it
before what you want to follow, or read `cornercase status` once it runs, so nothing falls between.
A reader that falls far behind loses events, and a line says how many.

Examples:
  cornercase events
  cornercase events --pane 12 --pane 14 --json
  cornercase events --host --json
  cornercase events --notices --json

================================================================ cornercase flow run
Start a flow in a worktree, and print its workspace's id and each role's pane id

Usage: cornercase flow run [OPTIONS] <NAME>

Arguments:
  <NAME>  The flow, as `cornercase flow list` names it

Options:
      --prompt <TEXT>             The task: what the team should do; with --issue, it replaces the prompt made from the issue
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --prompt-file <FILE>        Read the task from a file, or from standard input with -; with --issue, it replaces the prompt made from the issue
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --worktree <BRANCH>         The worktree's branch, made when missing [default: the issue's with --issue, else from the task's first words, made unique]
      --project <ID>              The project [default: the one this runs in, else the shown one]
      --issue <KEY>               Work on this issue instead: a key such as #482, sc-48 or ENG-42, or its URL, with the prompt the Issues dialog's start uses and its branch (settings → Worktrees → issue branches; --worktree names another)
      --source <SOURCE>           The tracker, for a key that more than one could have [possible values: github, gitlab, shortcut, linear, jira, plane, asana]
      --workspace-name <NAME>     The workspace's name when the issue makes a worktree [default: the issue's key and title]
      --profile <NAME>            Start it with the accounts of this profile; an empty name is each agent's own login [default: the default accounts]
      --account <AGENT=ACCOUNT>   Start that agent with this account, over the default ones; AGENT= is its own login. Give it once per agent
      --machine <NAME>            Do it on this machine, as `cornercase machines` names it: ids are then that machine's, as `status --json` lists them under machines, and so are its accounts and trackers
      --close-when-merged         Close the team's agents, as agents close does, once the run's pull request has merged and none of them has worked for 3 minutes; the workspace's ▶ or agents reopen brings them back
      --fresh                     Make a missing branch from the up-to-date default branch, as a routine's run does: fetch the remote first (origin, else the first one) and fail with git's reason if that fails [default: settings → worktrees → new branches]
      --no-fresh                  Make a missing branch from the project's HEAD, whatever settings → worktrees → new branches says
      --focus                     Also show it in the window, or in the view with --view, which otherwise stay as they are
      --view <ID>                 Act in this view (see `cornercase view`): its tab is the default, and --focus moves the view instead of the window
      --json                      Print JSON instead of text
  -h, --help                      Print help

It makes the worktree (or uses a worktree already on that branch, if it runs no flow), opens a
tab per role named after it, the orchestrator first, and starts every agent with its role prompt,
answering their trust prompts. The orchestrator starts last, with a brief: the task, the team and
its pane ids, the stages, and how to drive the agents. Nothing is shown in the window unless you
pass --focus, which shows the orchestrator's tab and opens the Flow panel; with --view ID it shows
that tab in the view instead, and the window and its Flow panel stay as they are.

With --issue KEY, the task, the branch and the workspace's name are the issue's: the same prompt template
and branch the Issues dialog's start a flow uses. --prompt or --prompt-file give a task of your own instead,
as editing that dialog's prompt does, and --worktree and --workspace-name name the branch and the
workspace. An issue that isn't tied to a repository needs --project when several
projects are repositories. Without --issue or --worktree, the branch comes from the task's first words, with a short suffix when that
says nothing, is a default branch or is already taken. A chosen branch that is main, master, the
project's default or the one its own folder is on is refused: a flow works on a branch of its own.

A role set to work in a worktree of its own (worktree = own) gets one on the branch <branch>--<role>, made from the
run's branch, with the project's setup; the other roles work in the run's worktree.

The run's branch, when it does not exist yet, starts from the project's HEAD, or, with --fresh or
settings → worktrees → new branches, from the project's default branch fetched from the remote first
(origin, else the first one), as a routine's run does; a fetch that fails stops the run before any tab
opens, and --no-fresh asks for HEAD whatever the setting says. Role branches start from the run's branch
either way. --fresh needs a server that knows the `fresh-branches` feature.

It prints the workspace's id, then one line per role: its pane's id and the role's name, separated
by a tab. The run's folder for files, where every role writes its answers, is printed on stderr
(run_dir with --json) and is in $CORNERCASE_RUN_DIR in the team's panes. A name is looked up in yours, then the built-in flows, then the project's: yours replaces
a built-in flow of its name, and a project's flow never stands in for another of the same name; the
command says so on stderr when it happens. A built-in flow deleted in Settings › Flows is refused,
and keeps its name: a project's flow named like it does not run either.

With --close-when-merged the run's agents close, as `agents close` does, once the run's pull request has merged
and nothing in the workspace has worked, waited, started or been typed into for 3 minutes. Nothing is removed: the workspace's ▶ or
`agents reopen` brings each agent back in its own conversation (opencode and custom agents start over), and a reopen
keeps them open. A flow that leaves the commits has no pull request, so it is refused. It needs a server that knows the
`flow-close-when-merged` feature; `flow close-when-merged` turns it on or off for a run that is already going.

With --machine NAME the flow runs on that machine of `cornercase machines`, by its server: the flow,
its agents and accounts are the machine's, --project and the ids printed are that machine's, as
`status --json` lists them under machines, and so is the run's folder. --focus shows the run in this
window once the machine lists it, and takes no --view there. It needs a server that knows the
`machine-start` feature.

Examples:
  cornercase flow run Quick --prompt 'Fix the login form'
  cornercase flow run 'Bug, test first' --prompt-file bug.md --worktree fix-crash --json
  cornercase flow run 'Full issue' --issue '#482' --prompt-file task.md
  cornercase flow run Quick --issue '#482' --project 2 --machine vps
  cornercase flow run 'Full issue' --issue '#482' --close-when-merged

already are in changes nothing.

================================================================ cornercase surface
Stream a tab's terminals as cells, with their panes and dividers, for programs that draw them

Usage: cornercase surface [OPTIONS]

Options:
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --tab <ID>                  The tab to stream; `cornercase status` lists them
      --cols <N>                  Columns of the surface the tab is laid out in (1 to 1000)
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --rows <N>                  Rows of the surface the tab is laid out in (1 to 500)
      --view <ID>                 Stream the tab this view shows, at the view's size, and follow it (see `cornercase view`)
      --popup                     Stream the plugin popup open in the window, at its own size, until it closes
      --patches                   After the first line, send only what changed (see below)
  -h, --help                      Print help

For programs that draw cornercase's terminals themselves, such as an editor extension or a
GUI. It keeps running and prints the tab as one JSON object per line: first as it is now, then again
each time something it shows changes, at most about 60 times a second. Each line is complete and
replaces the one before. It holds the panes laid out at the given size, each with its place (rect),
its terminal's own size (size), its cells (with their hyperlinks), the colours its program changed,
which rows go on in the next one (wrapped), cursor, modes and scroll position, plus the split tree,
the dividers, and boot, session and revision.

Each line names its stream with `surface`, which `cornercase resize` takes to lay a --tab surface out at
another size. With --tab the surface resizes no terminal: terminals keep the size of whoever sizes the tab (the
window, or a view), so size can differ from rect. With --view ID it streams the tab that view
shows, at the view's size, and follows the view to other tabs (each line carries view and
projection); it pauses while the view is inactive or has no size, and ends when the view closes.
The window keeps showing what it showed, also when the tab is not the one on screen. It ends when the tab closes, the
server stops or what reads it is gone (status 0); stopping it leaves the shells running. A reader that falls behind gets
fewer lines, each complete.

With --popup it streams the plugin popup open in the window (see `cornercase plugin run`) instead of a tab:
one pane, its program's terminal, at the popup's own size, with `popup` naming the plugin and the action,
`tab` 0 and no layout. It ends when the popup closes. `cornercase input --popup` types into it.

With --patches, each line after the first carries only what changed since the line before: `base` is the
revision it applies to, and each changed pane has its cursor and what changed of the rest (`lines` by
row number, `copy` for rows that moved, `wrapped` whole). A complete line, without `base`, comes again
whenever the layout, a size, the panes or the view change, after the reader fell behind, and when
`cornercase redraw --surface ID` asks for one.

Examples:
  cornercase surface --tab 3 --cols 120 --rows 40
  cornercase surface --tab 3 --cols 120 --rows 40 | jq -c '[.revision, [.panes[].pane]]'
  cornercase surface --tab 3 --cols 120 --rows 40 --patches
  cornercase surface --view 41
  cornercase surface --popup

================================================================ cornercase view
Open a view of your own: its own tab and size, for programs that draw cornercase themselves

Usage: cornercase view [OPTIONS]

Options:
      --cols <N>                  Columns of the view's surface (1 to 1000); without a size it only follows the session
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --rows <N>                  Rows of the view's surface (1 to 500)
      --inactive                  Start inactive: it sizes nothing and streams no terminals until `view-set --active`
      --tab <ID>                  Start on this tab [default: what the window shows]

      --project <ID>              Start on this project's active workspace
      --hidden                    Start hidden: the tab it shows does not count as seen until `view-set --visible`
  -h, --help                      Print help

For programs that draw cornercase themselves, such as an editor extension or a GUI, so that each
picks its own tab and size without touching the window or the others. It keeps running and prints
the session as one JSON line each time it changes, like `status --follow`, with a `view` object:
id, projection, active, cols, rows, shown (the project, workspace, tab and pane it shows) and
controls (whether it sizes its tab's terminals now). The view lives while this command runs:
stopping it closes the view and gives its tabs back. The first line is the state now; the view's id
is in it. Keep it running in the background (`cornercase view --cols 120 --rows 40 > view.jsonl &`),
read the id from the first line, and pass it as --view ID to `focus`, `open`, `clone`, `new-workspace`,

`mark`, `go`, `plugin run`, `surface`, `account add --login` or `account login`: the view's tab is
their default and --focus moves it.

While the view is active, has a size and is not hidden, the tab it shows counts as seen like the
window's: an agent there gets no done mark, toast or desktop notification. --hidden starts it hidden
(`view-set --hidden` and `--visible` change it), for a window that is minimised or behind others:
agents in its tab then notify again. While a view is open, the window's tab counts as seen only while
a window is attached.

A tab's terminals take the size of the window or the view that claimed it last, without the
window's sidebar and panels: a view claims the tab it shows when it opens, moves there or turns
active, and using the window takes back the tab it shows. Only that one resizes them. Without
--cols and --rows the view only follows the session and sizes nothing. Shared with the window and
other views: the processes, the split layout, the focused pane of a tab, scrolling and selection.

Examples:
  cornercase view --cols 120 --rows 40
  cornercase view --cols 120 --rows 40 --tab 7

================================================================ cornercase input
Type keys, text, pastes and mouse events into a pane, for programs that draw its terminal

Usage: cornercase input [OPTIONS] <EVENT>...

Arguments:
  <EVENT>...  One JSON event, or - to read one per line from standard input

Options:
      --pane <ID>                 The pane to type into; `cornercase status --panes` lists them. With --follow, for the lines that name none. With --popup, the popup's id from its surface lines (`popup.pane`), so nothing reaches a popup opened since
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --popup                     Type into the plugin popup open in the window instead of a pane
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --follow                    Keep running and send each line of standard input as soon as it arrives, until it ends (give - as the only EVENT)
      --json                      Print JSON instead of text
  -h, --help                      Print help

For programs that draw cornercase's terminals themselves (see `cornercase surface`). Each
EVENT is one JSON object, sent in order:
  {"key": {"code": "c", "mods": ["ctrl"]}}   code as for `keys`; mods ctrl, alt, shift, super; kind press, repeat, release
  {"text": "héllo"}                           typed text, without control characters
  {"paste": "two\nlines"}                     bracketed when the program asked for it
  {"mouse": {"kind": "down", "button": "left", "x": 3, "y": 1}}
                                             kind down, up, drag, moved, scroll-up, scroll-down,
                                             scroll-left, scroll-right; x and y are cells of the
                                             pane's terminal, from 0
- reads one event per line from standard input.

Events are encoded the way the program in the pane asked for (its keyboard protocol, application
cursor keys, bracketed paste, mouse mode), whatever the window shows: a dialog or a field there
takes nothing. Keys, text and pastes bring the pane's view back to the bottom. Mouse events and key
releases that the program does not take are not sent, and said on stderr. When one event is wrong,
or the program is not reading its input, nothing is sent. Scripts and agents should use `send` and
`keys`, which check before typing into an agent. With --popup the events go to the plugin popup open
in the window, its x and y being cells of the popup's terminal; add --pane with the popup's id from its
surface lines (popup.pane) so that nothing is sent if that popup closed and another one opened.

With --follow it keeps running and reads one event per line from standard input (give - as the
only EVENT) until it ends: each line goes as soon as it arrives, and the lines that arrive while
the answer before is on its way go together, so a program types through one process (and with
--remote one ssh connection). A line may name its pane, {"pane": 14, "key": {"code": "enter"}},
else it goes to --pane. Each request is all or nothing on its own: with --json it prints one line
each, the answer with events (how many lines it answers) or its error, and a line that is wrong or
refused does not stop the next ones; the command then exits with 3.

Examples:
  cornercase input --pane 12 --follow --json -
  cornercase input --pane 12 '{"text": "ls"}' '{"key": {"code": "enter"}}'
  cornercase input --pane 12 '{"mouse": {"kind": "scroll-up", "x": 10, "y": 5}}'
  cornercase input --popup --pane 40 '{"key": {"code": "down"}}' '{"key": {"code": "enter"}}'

================================================================ cornercase requests
Keep one connection and run each command of standard input as it arrives, for programs that send many

Usage: cornercase requests [OPTIONS] --follow <LINES>

Arguments:
  <LINES>  - to read one command per line from standard input

Options:
      --follow                    Keep running and run each line of standard input as soon as it arrives, until it ends (give - as the only LINES)
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
  -h, --help                      Print help

For programs that send many commands, such as a window that draws cornercase itself (see `cornercase view`): it keeps one connection, and with --remote one ssh connection, and runs each line of standard input as it arrives, in order, until standard input ends. A line is a command as the command line takes it, in JSON, with what it reads from - in stdin:
  {"args": ["focus", "--tab", "6", "--view", "21"]}
  {"args": ["send", "--pane", "5", "-"], "stdin": "cargo test"}
Other keys are refused, so a typo never runs a command without its text. Each line gets one answer line, in order: status (the exit status the command would have had), json (what it printed with --json) or text, stderr (its warnings) and error. A wrong or refused line does not stop the next ones. Streams (events, surface, view, changes list, config pair, every --follow), start-server, update, restart, kill-server, logs and the plugin commands that work on the files (plugin link, install, list…) need a process of their own and are refused with 2, as is --remote on a line. A line that waits (wait, send --wait, start --wait) holds the lines after it until it is answered. It exits with 0 when every line had 0, 3 when some did not, 1 when the server stops or the connection drops (it never reconnects: ids change with a restart), and 0 once what reads its answers is gone.

Examples:
  cornercase requests --follow -
  cornercase --remote devbox requests --follow -
  printf '%s\n' '{"args": ["status", "--json"]}' | cornercase requests --follow -

      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --json                      Print JSON instead of text
  -h, --help                      Print help

Every setting of the Settings dialog, with its value, default, choices and the note the dialog
shows, whether each account and bot is connected (and as whom), refused or not set, and each
project's setup and teardown. `--json` prints the whole answer, which a program can draw a form from.

With --json it also lists `agents`: each agent the `agent` setting can name, with its title, whether
cornercase reads its status (`reads_status`: a routine can remove the workspace of those only),
whether a flow can run it (`flows`), and the `models` and `efforts` the flow editor offers for it.

`set` changes settings with the dialog's own checks and applies them at once, as the dialog does;
nothing is saved unless every value is accepted. Values are converted by the setting's type: true or
false for a switch, a whole number, a comma-separated list for issue_tabs, otherwise text.

A token is never an argument: `secret` reads it from standard input (hidden on a terminal), checks it
with its service as the dialog does, and says which account accepted it, never the token. `remove`
forgets a token, a bot, a paired chat or the paired browsers. `pair` connects a phone to a chat or a
browser: `cornercase config pair --help`.

`forum-server` picks the server of the Discord forum, when forum mode waits for one and the app is in
several: `status --app` lists them as `servers`, in Discord's `forum`, and this is a click on one in the
forum's dialog. It answers once the pick is taken: the channel is made next, and `status --app --follow`
goes on to `ready`. An id that is not listed, or a moment when no pick waits, is refused and says why.

`export` writes the settings a colleague can use, as TOML, and says on standard error what it left
out: tokens, accounts, personal keys. `import` shows what a shared file would change and asks first;
reading standard input or without a terminal it needs --yes. --preview prints that preview and exits
without asking or importing: the same text on standard output, or, with --json, the preview a program
draws. --only limits either one to some sections. --preview and --yes cannot be combined.

The server notices edits to config.json within a second and applies them. What cornercase changes
meanwhile only rewrites the keys it touches, and it does not write over a file it cannot read.

================================================================ cornercase config pair
Pair a phone: print the address its QR code holds, then wait for it

Usage: cornercase config pair [OPTIONS] <KEY>

Arguments:
  <KEY>  What to pair: browsers, telegram.chat or discord.chat

Options:
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --json                      Print JSON instead of text
  -h, --help                      Print help

Does what the window's dialog does, for a program that draws cornercase itself: for browsers what
opening More > remote... > open in your phone's browser does, for a chat what Enter on the phone row
in Settings > Remote does. It prints the address the dialog's QR code holds and the lines under it,
and again whenever they change, such as Discord's advice and failures. With --json each is one line:
{"url", "lines"}, url null while there is none yet (Tailscale still starting). Draw the QR code from url.

It stays open while it waits. A browser that takes the code ends it with {"paired": true}, a chat
with {"paired": true, "chat": NAME}, and status 0. Once nothing can pair it ends with
{"paired": false, "error"} and status 1: remote access turned off, Tailscale not ready, the bot's
token removed or refused, or ten minutes gone by without a phone. Why it cannot start at all goes to
standard error, also with status 1: remote access off, Tailscale not installed, the port taken, no bot yet.

The code is dropped when the command ends, also when whoever reads its output goes. While the window's
dialog or another `config pair` holds the same key they share one code: it lives ten minutes from the
last one that came, and it is dropped when the last one goes. Nothing opens in the window; once paired
it says so as it does for its dialog. The address holds a code, so treat it as a secret: it is never
written to server.log. Discord has no code: its owner is asked for while this runs.

================================================================ cornercase changes
List, read, mark, stage and discard the changes of a workspace, as the changes panel shows them

Usage: cornercase changes [OPTIONS] <COMMAND>

Commands:
  list         Print the changed files of a workspace, or of every project
  file         Print one file's diff
  gap          Print the unchanged lines between a hunk of a file and the one before
  base         List the branches to compare with, or choose one
  merge-check  Merge a workspace's work, committed or not, into its base and with the workspaces it shares files with, in a scratch copy, and print the conflicts
  shared       Print the files a workspace changes that other workspaces of its project change too
  viewed       Mark a file as viewed, or clear the mark
  discard      Throw away a file's uncommitted changes, after asking
  stage        Put a file's changes in git's index, as `git add` does
  unstage      Take a file's changes out of git's index; the file keeps them
  help         Print this message or the help of the given subcommand(s)

Options:
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
  -h, --help                      Print help

`list` prints the changed files of a workspace (the one you are in, or the one --workspace or --worktree names), or of every project with --every, and with --follow keeps printing them as JSON lines each time they change. `file` prints one file's diff, `gap` the unchanged lines between one of its hunks and the one before (hunks count from 0, so the first has no gap), `base` the branches the Commits and All modes can compare with (naming one sets it, --default goes back to following the default branch), and `viewed` marks a file as viewed or clears the mark. `discard` throws a file's uncommitted changes away (a file git does not track is deleted), asks first on a terminal and needs --yes in a script; it cannot be undone. `stage` puts a file's changes in git's index, as `git add` does, and `unstage` takes them out of it. `viewed`, `stage`, `unstage` and `discard` act on the version `changes file` shows; with --digest, on the version whose digest `changes list --json` or `changes file --json` printed, the one you saw, so a file that changed since is left alone (`viewed` does not mark it, the others fail and say so). The modes are uncommitted (the default), commits and all. The base and the viewed marks are shared with the window's changes panel; the mode of a stream is its own.

Examples:
  cornercase changes list
  cornercase changes list --every --follow
  cornercase changes list --worktree fix/login --mode commits --json
  cornercase changes file src/main.rs --json
  cornercase changes gap src/main.rs --hunk 1
  cornercase changes base origin/main
  cornercase changes viewed src/main.rs
  cornercase changes stage src/main.rs
  cornercase changes unstage src/main.rs
  cornercase changes discard src/main.rs --yes
  cornercase changes discard src/main.rs --digest 550a7a517a389403 --yes

================================================================ cornercase changes file
Print one file's diff

Usage: cornercase changes file [OPTIONS] <PATH>

Arguments:
  <PATH>  The file, relative to the workspace

Options:
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --workspace <ID>            The workspace [default: the one this runs in, else the shown one]
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --worktree <BRANCH>         The workspace on this branch, looked up in the project this runs in, else the shown one
      --mode <MODE>               What to compare: uncommitted, commits or all [default: uncommitted] [possible values: uncommitted, commits, all]
      --json                      Print JSON instead of text
  -h, --help                      Print help

Prints one file's diff as a unified diff, with tabs as four spaces.

With --json it prints {"workspace", "mode", "path", "old_path", "status", "added", "removed", "fold",
"viewed", "staged", "digest", "styles", "hunks"}. A hunk is {"old_start", "new_start", "context",
"lines"} and a line is {"kind", "old", "new", "text", "raw", "emphasis", "syntax"}: kind is context,
removed or added; old and new are its numbers, null where it is not on that side; text is what a
window draws, with tabs as four spaces; raw is the line as it is in the file, tabs included, left out
when it would be the same as text; emphasis is the words that changed, as [start, end) pairs in
characters of text, left out when there are none; syntax is runs of {"style", "text"} over text,
style being an index into styles, left out where the line is not highlighted.

To copy a line as the file has it, take its raw, or its text when it has none. A tab of raw is always
four characters of text, so a selection made in text maps back to raw.

Examples:
  cornercase changes file src/main.rs
  cornercase changes file src/main.rs --mode commits --json
  cornercase changes file Makefile --json | jq -r '.hunks[].lines[] | .raw // .text'

================================================================ cornercase files
List folders, read files and search the names or text of a workspace, as the files panel does

Usage: cornercase files [OPTIONS] <COMMAND>

Commands:
  list    List the entries of folders, with their kind, size, modification time and git mark
  read    Print a file's text, or what kind of file it is
  search  Search the names or the text of the files of a workspace
  help    Print this message or the help of the given subcommand(s)

Options:
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
  -h, --help                      Print help

`list` prints the entries of one or more folders, `read` a file, and `search` finds files by name or by text, all as the files panel does, so a program on another machine (--remote) sees what the panel shows without reading the disk itself.

A path is relative to the workspace (the one you are in, or the one --workspace or --worktree names), never to the folder the command runs in; an absolute path, or one starting with ~/ (the server's home folder), reaches any folder on the server's machine, with no workspace needed, but then git marks only appear inside the workspace.

`list` prints one line per entry after a header: folder, name, kind (file, folder or other: a device, a pipe, a socket or a link to nothing), status (git's mark: modified, added, deleted, renamed or untracked, and for a folder added when everything in it is new and modified when it holds changes), bytes and modified (UTC). A - stands for nothing and . for the workspace's root. What git ignores and .git are left out, hidden files are listed (`hidden` in the JSON), at most 10000 entries per folder (said on stderr, `more` in the JSON), and a folder that cannot be listed prints on stderr and, with --json, in its `error`; the command still prints the rest and exits with 3.

`read` prints a text file as it is, up to 8 MB. An image (told by its first bytes) up to 32 MB prints its format, size and bytes; with --json its `image` holds those and `data`, the file in base64, and its `language` the grammar a viewer highlights it with. What is binary, too large, a folder or gone says so (`kind` in the JSON: text, image, binary, too-large, folder or missing); a folder or a missing file exits with 1. Only regular files are read, so a link to a device answers binary.

`search` prints the best 200 file names that match QUERY, ranked, smart-cased, or with --text (the default) the lines of at most 1000 matches as path:line:text, as `grep -n` does. It looks in the workspace only.

--follow on `list` and `read` keeps running and prints one JSON line each time the folders or the file change, checked on the server every 2 s for folders and every second for a file: first as it is now, with `stream`, `revision` and `boot`; each line replaces the one before. It ends when the workspace goes or once what reads it is gone. A connection follows one at a time.

Examples:
  cornercase files list --workspace 3 --json
  cornercase files list src --workspace 3 --follow
  cornercase files list '~/code' --json
  cornercase files read src/main.rs --workspace 3 --json
  cornercase files search parse --text --workspace 3 --json
  cornercase files search main.rs --names

================================================================ cornercase usage
Print your Claude Code and Codex plan limits, as the Usage dialog's Limits tab shows them

Usage: cornercase usage [OPTIONS]

Options:
      --cached                    Print the last answers with their age, without asking the agents again
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --machine <NAME>            Ask a machine for its limits, or with `all` this computer and every machine
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --json                      Print JSON instead of text
  -h, --help                      Print help

Asks Claude Code and Codex for your plan limits as the Limits tab of the Usage dialog does, and
prints each limit with how much of it is used and when it resets, then extra usage or credits. It
runs `claude` and `codex` on the server's machine (the ones agent_commands names): the installed
ones, or both when neither is, each saying why it could not run. That sends no prompt and costs no
tokens, and each waits at most ten seconds. A probe already running, from the dialog or another
`cornercase usage`, is waited for rather than started again. With --cached it asks nothing and
prints the last answers with their age. With --json it prints {"agents": [...]}: each agent's
plan, its limits (label, kind, scope, percent, severity, resets_at in UTC), extra, notice, error,
and when it was read (read_at, and age in seconds). It exits with 3 when an agent could not be
asked, after printing them all, that one with its error. --machine NAME asks that machine over ssh
and adds "machine" (name, state, seen, read_at, error); --machine all prints this computer and
then each machine under "machines", and exits with 3 when a machine could not be read either.

Examples:
  cornercase usage
  cornercase usage --cached --json
  cornercase usage --machine vps
  cornercase usage --machine all --json

================================================================ cornercase ports
List the TCP ports a workspace's programs listen on, with the URL to open each

Usage: cornercase ports [OPTIONS]
       cornercase ports <COMMAND>

Commands:
  stop  Stop the program of a workspace that listens on a port: SIGTERM, then SIGKILL after 3 s
  help  Print this message or the help of the given subcommand(s)

Options:
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --workspace <ID>            The workspace [default: the one this runs in, else the shown one]
      --worktree <BRANCH>         The workspace on this branch, looked up in the project this runs in, else the shown one
      --all                       Every TCP port your processes listen on, each with its workspace or none
      --json                      Print JSON instead of text
  -h, --help                      Print help

Lists the TCP ports in LISTEN state held by the programs of a workspace: the processes its panes
started (and their children), and, in a workspace with a worktree of its own, any of your processes
working in that worktree. Each line gives the URL to open (http://localhost:PORT when it listens on
every address or on 127.0.0.1), the addresses, the program and its pid, and how it belongs to the
workspace: pane N, agent claude in pane N (the agent itself or a program it started), or cwd. A
plain workspace (no worktree of its own) shares its folder with the others, so only its panes count.
--all lists every port your processes listen on, those of no workspace too. Ports published by
Docker are held by Docker, not by the workspace that started the containers, so they show only
with --all. With --json it prints {"ports": [...]}: port, addresses, url, pid, program, args,
project, workspace, pane, via (pane, agent or cwd) and agent, null when they do not apply.

The text shows the program and its arguments cut to 40 characters; --json gives them whole.
`cornercase ports stop PORT` stops one (see its --help).

Examples:
  cornercase ports
  cornercase ports --worktree feat/login --json
  cornercase ports --all
  cornercase ports stop 5173

================================================================ cornercase ports stop
Stop the program of a workspace that listens on a port: SIGTERM, then SIGKILL after 3 s

Usage: cornercase ports stop [OPTIONS] <PORT>

Arguments:
  <PORT>  The port, as `cornercase ports` lists it

Options:
      --pid <PID>                 Which program, when several listen on the port
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --json                      Print JSON instead of text
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
  -h, --help                      Print help

Stops the program that listens on PORT, if it belongs to a workspace (`cornercase ports --all`
lists the others, which it refuses). It checks first that the program still holds the port, sends
it SIGTERM, waits up to 3 s for the port to be released, then sends SIGKILL. Only that process is
signalled, never its process group, so the shell or the agent that started it stays. When several
programs listen on the port, --pid says which. It prints stopped, killed (it ignored SIGTERM) or
still running, and exits with 1 when it is still running. With --json it prints {"port",
"pid", "program", "outcome"}, the outcome being stopped, killed or still-running.

Examples:
  cornercase ports stop 5173
  cornercase ports stop 3000 --pid 48211 --json

================================================================ cornercase tunnel
Forward a port of this server's machine to the computer of the window attached to it, or close the tunnel

Usage: cornercase tunnel [OPTIONS] <COMMAND>

Commands:
  open    Forward a port of this server's machine to the computer of the window attached to it
  close   Close the tunnel of a port
  forget  Forget a tunnel: close it and stop windows from opening it again
  hold    Hold a tunnel to the machine of --remote with no window, until this command ends
  help    Print this message or the help of the given subcommand(s)

Options:
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
  -h, --help                      Print help

A tunnel forwards a port of this server's machine to the computer of a window attached to it:
the window runs your own ssh, `ssh -N -L 127.0.0.1:LOCAL:localhost:PORT DESTINATION`, with the
destination it used, so every ssh setting of yours applies, and the far end is always the
machine's own loopback. The window listens on the same port when it is free there and on another
when it is not, and says which. `tunnel open PORT` asks every attached window and waits up to
45 s until it is up; it prints one line per window and exits with 1 when none came up, or when
no window is attached (tunnels are held by windows opened with `cornercase remote`).
`tunnel close PORT` closes it but keeps it remembered, as closed. `tunnel forget PORT` removes it.
A window remembers its tunnels per machine on its own computer, in tunnels.json beside
machines.json: the next window to that machine brings back the ones that are not closed, on the
same port when it is free. Windows of one computer share a tunnel: one runs the ssh and the others
take it over when it ends. With --json they print {"tunnels": [...], "windows": N}, as
`cornercase tunnels --json` does.

`cornercase --remote vps tunnel hold PORT` is for a program with no window: it starts its own ssh
from this computer, waits until it is up and prints one line, {"port", "local", "url"}, then
holds the tunnel until it is killed (exit 0), its output reader leaves (0), `tunnel close PORT` or
`tunnel forget PORT` is run on the server (0), or ssh or the server connection fails (1). It
needs --remote (exit 2 without it), and it remembers nothing in tunnels.json.

      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --check                     Print what the Worktrees dialog's confirmation names for each folder, and stop and delete nothing
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --force                     Go on when a folder has uncommitted files, programs in it or commits that would be lost
      --unlock                    Unlock a locked worktree and remove it
      --delete-branch             Also delete the branch checked out there, never the default branch or the main checkout's
      --json                      Print JSON instead of text
  -h, --help                      Print help

Removes worktrees as the Worktrees dialog does, one or more, each named by its folder as
`worktrees list` prints it, open in cornercase or not: an open workspace stops its programs, runs
its project's teardown and goes, a closed project's worktree runs that teardown too, a prunable
entry leaves git's list, and a folder whose repository is gone or that git no longer knows is
deleted. Only a folder `worktrees list` knows is touched: anything else, a repository's main
checkout and a project's own folder included, is refused and left alone, as is a worktree git
records at a symbolic link, which git would delete through, and a folder holding another listed
worktree or an open project, which would go with it unseen (remove or close that one first). So is
what the dialog cannot tick:
a worktree of a role of a live flow run (it goes with the run's workspace), one being removed or
closed, one whose build folders are being freed, and an open workspace git no longer knows (close
it, then remove the folder).

--check prints what the dialog's confirmation names for each folder (files changed, commits not
pushed, a lock, the programs that stop, processes outside cornercase and in other tabs, the
teardown, with --delete-branch a branch that would lose commits), and what removing it takes. It
stops and deletes nothing. Without it the folders are checked again the same way, and one that is
at risk is refused: --force goes on when it has uncommitted files or could not be checked, when
programs work in it, when its files are all that is left (repository gone, unknown to git), when
it holds commits on no branch, or when --delete-branch would lose commits; --unlock is needed for a
locked one and does not imply --force. --delete-branch deletes the branch checked out there after
the worktree is gone, and a run's workspace its roles' branches too, never the default branch or
the main checkout's, and only the branch still checked out when the removal starts, at the commit
the check saw.

It waits until every removal has ended and prints one line per folder: removed, could not remove
or did not remove, and why. It exits 3 when some folder was not removed, its branch was kept or
could not be deleted, its teardown failed, or only git's entry went and its folder stays (with
--check, when some folder or role cannot be removed or checked), after printing the rest. A
command that goes away before the removals start leaves everything as it was; one that goes away
later leaves them running. With --json it prints {"check", "folders": [...]}, one per --path in
order, each with "path", "outcome" (removed, failed, refused; removable with --check), "why",
"needs" (force, unlock), "removed_with", "branches" (deleted), "kept" (branches kept and why),
"warnings", "lines", "lost", "unchecked", "teardown", "roles" and "worktree" (the row `worktrees
list` prints).

older. With --json it prints {"here": {"icon", "version"}, "machines": [{"name", "icon",

"updating", "problem"}]}: version is the cornercase installed there and server_version the one
its server runs, seen when the link was last up (UTC), retry_at when a link that fell tries next
(UTC; a time that has passed means that try is under way; left out while the link is up or
connecting, and while a person has to act there), error why it is down, and problem what is wrong
with an entry of config.json, which then gets no link. Every subcommand prints the list the same way.

================================================================ cornercase account

  login    Open a tab that logs an account in again, or the agent's own login
  remove   Remove an account and its folder; an agent that used it goes back to its own login
  rename   Give an account a name the window shows; its folder keeps its name
  use      Make an account the default for an agent's new workspaces; open panes keep theirs

  help     Print this message or the help of the given subcommand(s)

Options:
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)

An account is a folder of its own under cornercase's state folder in which an agent keeps its
login: CLAUDE_CONFIG_DIR for Claude Code, CODEX_HOME for Codex, GEMINI_CLI_HOME for Gemini CLI.
Each agent has a default account, which new workspaces, scripts run outside a pane and the queue
start with: `account use`, or Settings › Accounts in the window, changes it. A new tab or a split
takes the accounts of the pane it comes from, and panes already open keep theirs until
`account restart`, or the account button under the pane, restarts them on another, each once its
turn is over, in the same conversation. `account rename` gives an account (or the agent's
own login, with --system) the name the window shows; commands always name an account by its
folder. `start`, `new-tab`, `flow run` and `queue` take --account AGENT=ACCOUNT to start once
with another. A new account links the settings it shares from the agent's own folder (settings,
instructions, skills); `account list` names the ones that stopped being links. `account add
--login` opens a tab that logs the new account in; when a login expires (`account list --check`
says signed out), `account login AGENT ACCOUNT`, or --system for the agent's own login, opens that
tab again. Gemini CLI has no login command: start it in a tab of that account and sign in from its
first screen. Removing an account deletes its folder, never the system's keychain, and an agent
that used it goes back to its own login.

account restart takes --boot BOOT, the `boot` of the `status --json` its pane ids come from: a
server that restarted since refuses, nothing restarts, and it exits with 4.

  cornercase account remove claude work

================================================================ cornercase profile
Make, change and switch profiles: which account each agent uses

Usage: cornercase profile [OPTIONS] <COMMAND>

Commands:
  list    List the profiles, the active one marked with *
  new     Make a profile: which account each agent uses
  set     Change which account an agent uses in a profile, or rename it
  use     Make a profile the active one: new workspaces and agents use its accounts
  delete  Delete a profile; its accounts stay
  help    Print this message or the help of the given subcommand(s)

Options:
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)

default: new workspaces and agents use its accounts; panes already open keep the ones they started

`profile use --system` goes back to each agent's own login. `start`, `new-tab` and `flow run` take
--profile to use another one once, without changing the default.

Examples:

  cornercase profile set Work --provider codex --account personal
  cornercase profile use Work
  cornercase start claude --profile Home --prompt "fix the tests"

================================================================ cornercase remote
Open the window on the cornercase server of another machine, over ssh

Usage: cornercase remote [OPTIONS] <DESTINATION>
       cornercase remote --known [--json]
       cornercase remote --remember <DESTINATION> [--command <COMMAND>]
       cornercase remote --forget <DESTINATION>

Arguments:
  [DESTINATION]  Where ssh connects: a host from ~/.ssh/config, or user@host

Options:
      --command <COMMAND>         How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --known                     Print the machines a window on this machine offers in its machine button, those it reached and those added with --remember, and open no window; it reads this machine's list, so it needs no server or ssh
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --remember <DESTINATION>    Add a machine to the list --known prints, or give one already there this --command (none clears it), and open no window; a window asks before it first reaches a machine added this way. It writes this machine's list, so it needs no server or ssh
      --forget <DESTINATION>      Take a machine off the list --known prints, as the machine button's forget… does, and open no window; it exits with 1 when the machine is not listed
      --json                      With --known, print JSON instead of text
  -h, --help                      Print help

cornercase runs `ssh DESTINATION cornercase proxy`, so your ssh config, keys, agent and
ProxyJump apply, and starts the server there if none is running. The shells, agents and files stay
on that machine; this one only shows them, and copies and notifications go through this terminal.
If the connection drops, the window stays and reconnects by itself; Esc or quit gives up. Both
machines need the same version of cornercase. Reconnecting never asks for a password, so use a
key or an agent. To send the commands for scripts and agents there, give them --remote DESTINATION.
The other machine may run Windows: the first time, cornercase finds out whether its sshd runs
commands with cmd.exe or PowerShell, and remembers it.

--known prints the machines a window on this machine offers in its machine button, in the order
its menu lists them: those a window reached, with `cornercase remote` or the button, and those a
program added with --remember, each with its --command, and opens no window. With --json:
{"machines": [{"destination", "command", "unreached"}]}, command being null without one, and
unreached true for a machine added with --remember that no window has reached yet (left out
otherwise). It reads this machine's list, so it needs no server and no ssh, and CORNERCASE_REMOTE
changes nothing for it: a program that offers to move to another server reads it this way rather
than the file, whose shape can change.

--remember DESTINATION adds a machine to that list, with --command if given, and --forget
DESTINATION takes one off, as the button's forget… does. Like --known they open no window, need
no server and no ssh, and CORNERCASE_REMOTE changes nothing for them. A window asks before it
first reaches a machine added this way, then stops asking. Remembering a listed machine again
replaces its --command (none clears it). A window already open sees the change at its next
connection or forget, or when it opens again; one on that machine writes it back, with the
--command it reached it with, when it reconnects. DESTINATION is one word of at most 255 bytes that does not start with -;
another exits with 2. A machine's host key must be known to ssh, since a window never asks for it: accept it with a plain
ssh DESTINATION, or run cornercase remote DESTINATION with the same --command (without it, the saved
command is cleared). A machines.json that exists but cannot be read is refused with 1 and left alone. --forget of a machine that is not listed writes nothing and exits with 1.

Examples:
  cornercase remote devbox
  cornercase remote me@10.0.0.5 --command '~/bin/cornercase'
  cornercase remote me@winbox --command 'C:\tools\cornercase.exe'
  cornercase remote --known --json
  cornercase remote --remember me@10.0.0.5 --command '~/bin/cornercase'
  cornercase remote --forget devbox

================================================================ cornercase restart
Restart the server: every program in its terminals stops, and the session comes back with new shells

Usage: cornercase restart [OPTIONS]

Options:
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
  -y, --yes                       Restart the server without asking
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --when-idle                 Wait until no agent is working, then restart
      --timeout <SECONDS>         With --when-idle, give up after this many seconds and keep the server running
  -h, --help                      Print help

It lists what runs in the terminals and asks first, since every program in them stops; agents
resume their conversations afterwards. Every attached window reopens on the new server.

With --when-idle, it waits until no agent is working before restarting: idle, done, pending review
and waiting for you count as stopped, and so does a Claude Code agent whose turn is over while a
shell it started in the background still runs, but not one whose subagents still run. The server restarts in the same step it sees that,
so no agent starts a turn in between, and every window shows that a restart is pending meanwhile,
with a button that cancels it. Programs that are not agents, such as a dev server, stop as with any restart. The pane
this runs in never holds the restart. --timeout gives up with status 1 and the server keeps running,
as it does when the command is interrupted. With --remote DESTINATION it runs on that machine, through ssh.

Examples:
  cornercase restart
  cornercase restart --when-idle --yes --timeout 3600

================================================================ cornercase logs
Print the server's log: what it did, step by step

Usage: cornercase logs [OPTIONS]

Options:
  -n, --lines <N>                 How many of the last lines to print [default: 200]
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
  -f, --follow                    Keep printing what the server writes, until interrupted
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
      --path                      Print only where the log is
  -h, --help                      Print help

The server writes one line per event: the time in UTC, the level, where it happened and what,
then key=value details. It says which windows attached, which commands ran and how they were
answered, what started and stopped, how long background jobs took, what each agent was doing and
each step of starting one. It never holds what is typed, pasted or shown in a pane, nor tokens.

The log is server.log in the state folder ($XDG_STATE_HOME/cornercase, else ~/.local/state/cornercase),
or next to the socket when CORNERCASE_SOCKET is set. Past 8 MiB it moves to server.log.1 and starts
over. Start the server with CORNERCASE_LOG=debug for more: every event it handled, every git run,
slow frames.

With --remote DESTINATION it prints that machine's log, through ssh.

Examples:
  cornercase logs -n 50
  cornercase logs --follow
  cornercase kill-server && CORNERCASE_LOG=debug cornercase

================================================================ cornercase plugin
Install, add, list, turn on and off the plugins that extend cornercase

Usage: cornercase plugin [OPTIONS] <COMMAND>

Commands:
  link         Add the plugin in a folder of yours, turned off; for writing one
  install      Install a plugin from GitHub, a git address or a folder, turned off, after showing what it runs
  update       Fetch an installed plugin again and, if it changed, show what it runs and ask before updating
  remove       Stop a plugin and delete its installed copy; a linked plugin's folder stays
  unlink       Forget a linked plugin; its folder stays as it is
  list         List the plugins, whether they are on, and what they run
  status       Show the plugins as Settings › Plugins does, including what each service is doing; asks the server
  actions      List the actions plugins add to the menus, for one kind of row or every one; asks the server
  run          Run a plugin's action on a project, workspace, tab or pane as its menu entry does, or a button's on what the window or a view shows; asks the server
  popup-close  Close the plugin popup that is open; asks the server
  windows      Keep the plugins' window processes running until it ends, for a program that draws its own window
  enable       Turn a plugin on: it runs as you, with access to every terminal
  disable      Turn a plugin off, stopping what it runs
  logs         Print what a plugin's commands wrote, and when cornercase started and stopped them
  help         Print this message or the help of the given subcommand(s)

Options:
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
  -h, --help                      Print help

A plugin is a folder with a cornercase-plugin.toml that declares commands: actions in the row menus, hooks on events, services the server keeps running and processes each local window keeps running. Its commands talk back through these same commands.

Install one from GitHub, any https:// git address or a git folder, pinned to a commit; a repository can hold several plugins, each in its own folder (owner/repo/folder on GitHub, address//folder elsewhere): you see where it comes from, what it asks for and every command it runs before anything runs, and it is installed turned off. Link a folder of yours instead while you write one.

`--preview` fetches a plugin, or an update of one, and prints that same preview, then exits without asking or installing, also with no terminal; with `--json` (and an ID for `update`) it is one JSON object, for a program that shows it and asks itself. `--commit` then installs, or updates to, exactly the commit the preview printed: it fails and installs nothing once the source gives another commit, and unlike SOURCE@COMMIT, which pins the plugin there, later updates still follow its branch or tag.

A plugin runs as you and can do anything you can, including typing into every terminal. What it asks for is shown before you turn it on, not enforced. A running server picks up changes within a second.

`actions` lists what plugins add to the menus, for a kind of row (--context) or all of them, and `run` runs one on a project, workspace, tab or pane as its menu entry does: in the workspace's folder, with the ids of what you name, stopped after 5 minutes, its output in the plugin's log. Both ask the running server; `run` waits for the action and exits with 1 when it fails. An action on a plugin's button runs with no target, on what the window shows. A popup action waits until its popup closes, and needs a window attached; `popup-close` closes it. An action listed before the plugins changed is refused (pass the --revision `actions --json` printed, or none for the current one).

A program that draws cornercase itself passes `run` the --view ID of its `cornercase view`: a button's action then runs on what that view shows, in its workspace's folder. A popup action opens with no window attached too, sized from that view while none is, and following it; it stays open if the view goes, as when the last window leaves, so the program that comes back shows it (`status --app`, `surface --popup`) or closes it with `popup-close`.

`status` prints the plugins as Settings › Plugins shows them: on, off or cannot run, the label and the note, and what each service is doing (running, restarting or still starting), and why `plugins.json` cannot be read. It asks the running server. `list` still reads the files and works with no server.

`windows` keeps the plugins' window processes running until it ends, as a window of cornercase does, for a program that draws its own window. See `cornercase plugin windows --help`.

With --remote DESTINATION (or CORNERCASE_REMOTE) every command but `windows` acts on that machine's plugins: `status`, `actions`, `run` and `popup-close` ask its server, the others run there as its own `cornercase plugin` through ssh, with the same output and exit status. A folder given to `link` or `install` is that machine's: absolute, or ~/… for its home folder (quote it so this shell leaves it alone); a relative one is refused. At a terminal, `install` and `update` show their preview and ask there; a program uses --preview --json, then --commit.

Examples:
  cornercase plugin install acme/notes
  cornercase plugin install acme/notes@v1.2.0
  cornercase plugin install acme/notes --preview --json

================================================================ cornercase plugin windows
Keep the plugins' window processes running until it ends, for a program that draws its own window

Usage: cornercase plugin windows [OPTIONS]

Options:
      --json                      Print JSON instead of text
      --remote <DESTINATION>      Run the command against the cornercase of another machine, through ssh: a host from ~/.ssh/config, or user@host (or set CORNERCASE_REMOTE)
      --remote-command <COMMAND>  How to run cornercase there, as sh reads it, or on a Windows machine its path (~\ for the profile folder) [default: cornercase, also looked for in ~/.local/bin, ~/.cargo/bin and Homebrew's folders]
  -h, --help                      Print help

For a program that draws cornercase itself. Keep this command running for as long as your window is
open, and what each plugin that is on declares as [[window]] runs beside it, as beside a window of
cornercase: it starts what is wanted, reloads within a second when plugins change, starts again what
stops (after 1, 2, 4… up to 60 s) and keeps the files `plugin remove` reads. Two programs run two
copies, as two windows do. It reads the plugins of this machine, not a server: with no server, or no
plugin that has a window process, it keeps running and waits for one. An update does not restart it:
it stays the old version until you start it again.

It stops them all and exits with 0 on SIGTERM, SIGINT, SIGHUP or SIGQUIT (on Windows Ctrl+C, taskkill
without /f or its console closing), and when the reader of its standard output leaves: read it
through a pipe, and closing that pipe, or your program dying, ends it. Rust's Child::kill sends
SIGKILL, which nothing can catch: what it runs then keeps running on Linux and macOS, so close the
pipe instead. On Windows a process killed that way takes them along, but a reader that left is seen
only at the next line.

It prints a line for each change, such as `acme.notes panel: running, pid 4242`, `acme.notes panel:
stopped, restarts in 2s`, or `acme.notes panel: stopped` once it will not start again (the plugin
was turned off or lost that entry). With --json each line is a JSON object: plugin, id, state
(running or stopped), pid and restart_in (the seconds until it starts again, null once it will
not). Its output ends once everything has stopped. `plugin logs ID` says why one stopped.

It takes no --remote, and cannot run on a line of `requests`: window processes run on the machine
that shows the window.

Examples:
  cornercase plugin windows
  cornercase plugin windows --json
  cornercase plugin windows --json | your-window
