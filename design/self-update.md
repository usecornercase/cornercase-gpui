# Updating the window

Code: `src/self_update.rs`, `src/self_update/` (`release`, `fetch`, `install`, `bundle`, `relaunch`, `dialog`, `arrival`), `main.rs`'s `--version` and quit path, `release.yml`'s `CORNERCASE_GPUI_RELEASE`, `platform/probe.rs`. The model is cornercase's own updater (`design/updates.md` in `usecornercase/cornercase-terminal`); `design/notifications.md` has the server's update, which is a separate chip and dialog.

- **What it does**: at start (after 10 s, so it never competes with finding the binary) and every hour, a release build asks GitHub's `releases/latest`. A newer release shows `↑ cornercase-gpui X` in the status bar, whose dialog lists every `## X.Y.Z` section of the release's `CHANGELOG.md` asset after the running version (the release body stands in when the asset is missing or lacks the release), drawn as Markdown as cornercase's notes are (`design/widgets.md`). **The chip and the dialog name the program**, `cornercase-gpui`, as cornercase's own chip says `↑ cornercase X` beside it: the two chips once read `↑ X` and `↑ window X`, and "window" did not say which program it was (changed on 2026-11-09). The rest of the app still calls itself "cornercase" (`design/releases.md`).
- **Which builds check**: release builds ask GitHub; a debug build asks nothing unless `CORNERCASE_GPUI_RELEASES_URL` is set, which is then the URL asked (and may be plain `http://`, for a local fake release). Release builds ignore the variable, so the environment cannot turn off https-only downloads. So `cargo run` and the tests never call GitHub. **The `check_updates` setting is cornercase's own, reused on purpose**: one switch for "do not call GitHub for updates" is what a user who turned it off expects of the window too, and the window has no settings of its own for this. It is read (`config --json`, a boolean, on by default) before each check; a config that cannot be read checks anyway, since a newer window may be what fixes the connection.
- **Notes are retried**: a release whose `CHANGELOG.md` could not be downloaded shows the release body, and the next hourly check asks for the changelog again; the notes are kept only once it came down. Its download has a 20 s overall limit, so a trickling response cannot hold the check open.
- **A failed install keeps Install and adds Download** of the same asset beside it: a retry can work (a network failure), and when the folder lets files be made but not renamed it would fail the same way. The failure stays until the next install or restart.
- **A failed check is silent**: a muted line in the dialog, never a toast (an offline laptop would get one an hour). An **install** the user started is told: an error toast with Details that opens this dialog (`design/notifications.md` has the toast, shared with cornercase's). 404 means nothing is published (true until 0.1.0 is tagged), not an error; 429, and a 403 with `x-ratelimit-remaining: 0` or `retry-after`, say GitHub's limit of 60 checks an hour was reached. The last release found stays after a failure.
- **Not a status-bar job**: nobody started the hourly check, and the bar would flash "Checking…" every hour. The install, which the user starts, is a job (`store::run_local_busy`), with a spinner on the chip and `ui::busy_button` in the dialog.
- **The updater is created once in `main.rs`**, not per `Root`: `Root::switch` builds a new `Store`, and an install must survive a switch. It calls `Store::get(cx)` whenever it needs the session or the jobs.

## How a copy updates

Decided off the main thread when a newer release is found (`install::way`, pure; the folder probe is passed in):

| The copy | The dialog offers |
|---|---|
| Built by the release workflow, Windows or Linux x86_64, folder writable | Install, then Restart |
| macOS, inside `cornercase.app`, its folder writable | Install, then Restart |
| macOS, `cornercase.app` in a folder it cannot write, or a program outside an app | Download the DMG |
| A folder it cannot write | Download, naming the folder |
| No asset for this machine (Linux or Windows arm64) | The release page |
| A build from source | Copy command: `cargo install --locked --git … --tag vX.Y.Z` |

- **Only builds made by the release workflow replace themselves** (`CORNERCASE_GPUI_RELEASE=1`, read with `option_env!`): a build from source could hold more than the release. Rejected: guessing from the path (`.cargo/bin`, `target/`), which a copied build fools.
- **Another window already installed it**: the program at the path read at start is asked its `--version`; if it already is the release, the chip and the dialog offer the restart, not a second download (as `notifications.md` says of cornercase).
- **The program's path is read at start**: on Linux `/proc/self/exe` reads `… (deleted)` once the file is replaced, and the relaunch must start the new file at the old path.

## Install (macOS)

The download is the DMG and its `.sha256`, checked as below. Then, on the background executor: the staging folder made beside `cornercase.app` (in `/Applications` usually, so the renames stay on one volume); the DMG attached there with `hdiutil attach -nobrowse -readonly -noautoopen -noverify -mountpoint` (hidden from the Finder; `-noverify` since the checksum already passed) and detached whatever happens (`-force` if a plain detach fails; if both fail once the app is copied, the install stops with the image's place, `hdiutil detach` being the way out, rather than leave a hidden image attached after a success); the `.app` at its root copied out with `ditto`, which keeps the signature, the extended attributes and the stapled tickets; the copy checked with `codesign --verify --deep --strict` against a requirement naming Apple's anchor, the app's id and the release's Developer ID team (`design/releases.md`), so only an app the team signed replaces this one; its program run with `--version`, as on the other platforms; then the swap: `cornercase.app` renamed to `.cornercase-gpui-old-<pid>-<time>` beside it, the new one renamed into its place, and the old one moved back if that fails. The new app keeps the old one's name, so a renamed copy stays renamed. Each tool is run by its full path in `/usr/bin`.

- **The running app is set aside, not deleted**: it keeps running from the old bundle until the restart, and macOS reads the bundle (its `Info.plist`, its icon) while it runs. Its name holds the pid of the window that set it aside, and a start deletes every `.cornercase-gpui-old-*` beside the app whose window no longer runs, on top of the staging folders over an hour old. So a second window starting meanwhile leaves alone both the bundle the first one still runs from and the one a failed swap is about to move back. It is gone only when `ps -p` answers that no such process exists: `kill -0` fails on another user's process too, and `ps` that cannot run keeps the bundle. A pid reused by another program only keeps the old bundle until a later start. Not covered: another copy of the window started from the old bundle before the swap, whose bundle goes once the updating window has quit; macOS opens one copy of an app unless asked otherwise. Rejected: a lock between windows, for a moment two renames long.
- **The team is written in the code**, not read from the running app's signature, and the check is on the downloaded app only: whether this copy installs at all is `CORNERCASE_GPUI_RELEASE`'s call (above), so a copy built by the release workflow installs a release even from a bundle re-signed or left unsigned, while a release signed by another team (a move to an organization account, `design/releases.md`) is refused, so that move needs one manual download. Rejected: reading the running app's designated requirement, which needs parsing `codesign -d -r-` and lets an ad-hoc copy accept anything ad-hoc. `spctl --assess` is not asked: what the window downloads carries no quarantine flag, so Gatekeeper does not assess it at launch either, and the signature is what decides; a release is notarized and stapled anyway.
- **Rejected**: Sparkle (an appcast, its own keys and a framework to embed), and copying the new app over the old one file by file, which leaves a half-updated bundle if it fails and breaks the running app's seal while it runs.
- **The folder must be writable**: `/Applications` is, for an administrator. An app run straight from the DMG, one App Translocation moved (an app opened from Downloads with the quarantine flag runs from a read-only copy) and a standard user's `/Applications` fall back to Download, naming the folder.
- **macOS's App Management protection** lets an app replace its own bundle and those of its own team without asking, which is the case here; it was not seen asking in the check below, where the running program was a development build.

## Install (Windows and Linux)

On the background executor, in this order: the archive and its `.sha256` downloaded (256 MiB at most, and a stall of 30 s ends it, with no limit on the total time so a slow connection can finish; `https_only` unless the URL asked was `http://`); the checksum compared, in memory; the staging folder made beside the exe (same volume, so the renames are atomic; removed whatever happens; a crash leaves it, and each start sweeps those over an hour old, with the old copies, on every platform), only now so a long download cannot let another window sweep it; the archive unpacked with the system's `tar` (Windows: `System32\tar.exe` by its full path, since a bare `tar` may find a GNU tar beside the exe that cannot read zips; Linux: `tar -xzf`); the binary found at the root or one folder down; the new binary run with `--version`, which must print `cornercase-gpui <the release>` (so a binary that cannot run here, one needing a newer glibc say, never replaces a working one); then the swap.

- **Linux** renames the new file over the running one, which Unix allows.
- **Windows** cannot overwrite or delete a running exe but can rename it, as cornercase's updater does: the exe becomes `cornercase-gpui.old.exe` (`.old.1.exe`… when an older copy still runs, say in another window), the new file takes its name, and if that fails the old one is moved back. Each start removes the old copies nothing runs any more; a delete that fails means one still runs.
- **HTTP is `ureq` 3**, blocking, on the background executor like every other job. Rejected: gpui's `http_client` (a trait without a client in 0.2.2; Zed's needs tokio), `curl` as a child (not on every Linux desktop, and tests could not run without it), the `self_update` crate (no DMG, its own HTTP stack, and we need our own states), Sparkle and WinSparkle (a tool per platform, appcasts and keys we do not have).
- **TLS**: rustls with the **ring** provider and the system's roots (`RootCerts::PlatformVerifier`: the Keychain, Windows' store, `/etc/ssl`), so corporate roots work. Not ureq's default `rustls` feature, which brings `webpki-roots` under CDLA-Permissive-2.0, a licence the notices check does not accept; not `aws-lc-rs`, which needs cmake and NASM on Windows. `Cargo.lock` lists `webpki-root-certs` through `rustls-platform-verifier`, but only for wasm32, which no target builds. `HTTPS_PROXY` and `ALL_PROXY` are honoured by ureq.
- **The checksum comes from the same release**, so it catches a broken or cut download, not a bad release. A download matches when the first word of its `.sha256` file, in upper or lower case, equals its SHA-256 as 64 lower-case hex digits, which are made from the digest's bytes and not through `sha2`'s own formatting, which 0.11 no longer has (#180); an empty file matches nothing. A file the window downloads itself carries no Mark of the Web or quarantine flag, so SmartScreen and Gatekeeper do not ask again: what installs in place (Windows and Linux) is not signed, so the checksum is the only gate there until Windows is signed (#24). It is not a signature: whoever can publish the release can publish a matching checksum. This is the trust model of cornercase's updater.

## Relaunch

The layout is written in the keeper's own quit callback, synchronously, before `main.rs`'s future starts the new program (`design/window.md`).

**Restart** stores the program and the arguments (`--tab <shown tab>` and the current server's `--remote`, `--remote-command`, from `cli::target()`, since a switch may have changed it), then quits. In `on_app_quit` a relaunch runs `cli::kill_all()` **without** `theme --clear`: the new window gives the same palette at once, so clearing first would only flash every terminal, and over ssh `cli::quit` does not wait for the clear, which could land after the new window's `start-server --theme -`. Then it starts the new program with stdin null and stdout and stderr inherited. There is no confirmation: the server keeps every program, and the dialog says so.

- **On macOS the new app is opened by `open`**, once this one has ended: a `/bin/sh` waits until this process's pid is gone (`kill -0`, every 100 ms), then runs `/usr/bin/open -n <the app> --args <the arguments>`. Started by `open`, the new window is launched by LaunchServices as if from the Finder: it is its own responsible process for macOS's privacy grants, rather than a child of a process that is gone, and the Dock and activation treat it as a fresh launch. This is what gpui's own `restart` does on macOS, which cannot be used because it passes no arguments. `-n` opens a new copy even if another one runs, so the arguments are not lost to an activation. The environment is launchd's, not this process's, as when the app is opened from the Finder.

## After the restart

- **The window says whether its update took.** Install, once done, and Restart write `relaunch.json` beside the settings (`prefs::beside`, `design/window.md`): the version awaited and the app or program it was installed in. The next start of any copy that checks for updates reads it, removes it, and says `cornercase-gpui is now X` (also when newer), or `This window runs cornercase-gpui A, not X, which the update installed in <place>`, naming where it started from when that is another place (`arrival`, pure). A failed write at install is an error toast; at Restart it goes to standard error and the restart still happens, since the confirmation is not worth stopping an update for. The second write covers a copy that another window installed.
- **Not read in a debug build without `CORNERCASE_GPUI_RELEASES_URL`**, so a `cargo run` never eats the real app's note: the read sits after the gate that ends `start` there.
- **Why a file**: an argument or an environment variable does not reach the case that matters, a relaunch that failed and the user opening another copy from the Dock; on macOS `open` also starts the app with launchd's environment. `settings.json` has one writer (`Store::set_pref`, `design/window.md`), and waiting for the next hourly check is the `↑` 10 s later that users missed.
- **The window's own version is in the status bar's connection tooltip**, a line under the server's (`This window is cornercase-gpui X`): where a person looks to see what runs after a restart, a hover away and taking no room. Rejected: a Settings row, since Settings is cornercase's form from `config --json`, and the label, since the bar is already full on a laptop.

## Limits

- The window comes back at its size, place, display and state, with its widths, as at every launch (`design/window.md`). What only the window holds (open panels and dialogs, the Browser panel's Chrome) starts again.
- A relaunch that fails to start ends the window with a message box and standard error (the server and its programs keep running). On macOS only a failure to start `/bin/sh` is seen at once; an `open` that fails afterwards is told by the next copy that starts (After the restart), and the app is opened from the Finder as usual.
- The asset names are a contract (`design/releases.md`): renaming one breaks the update of every installed copy.
- What installs in place on Windows and Linux is not signed: the checksum is the only check. On macOS the app's signature by the team is checked too.

## Waits on

- **Signing Windows** (#24).
- **Package managers and installers** (#24, #25, #26): a package's folder that cannot be written (`/usr/bin`, a mounted AppImage) falls back to Download already. Scoop and winget put the zip's exe in a folder the user can write, so #26 must add their paths and commands before they ship, or the window would replace a file their manager owns. An AppImage (#25) would replace `$APPIMAGE`.
