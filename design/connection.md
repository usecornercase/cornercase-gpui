# Connection

Code: `src/main.rs`, `src/cli.rs`, `src/store.rs`

- **One more client of the command line**: the app never speaks cornercase's socket protocol. Every command, stream and input event goes through the `cornercase` binary (found as the next bullet says), the contract cornercase documents for programs that draw it (#345 upstream). A protocol change upstream then cannot break the window silently. `cli::Target` says where it runs: this Mac, or another machine, which adds `--remote DESTINATION` (`design/remote.md`).
- **Finding cornercase** (`cli/locate.rs`, `cli/locate/system.rs`): a window started from the Finder, an app menu or the Start menu does not have the shell's `PATH`, so `cornercase` may not be on it. The first program found decides, in this order: `CORNERCASE_BIN` (the only candidate when set: the user said which one, so falling back would hide the mistake; a bare name is searched on the `PATH`); a binary chosen by hand on the missing page and kept in `settings.json` (before the `PATH`, or a choice made because an old binary shadowed a newer one would be lost at the next start; one that is gone, or no longer passes the version check, is passed over for the places below, and is named only when none of them works (a file that is gone too), so updating cornercase on the `PATH` fixes a stale choice); `cornercase` on the process `PATH`; on macOS and Linux the login shell's `PATH`, asked only when the steps before found nothing; then the folders the installers use (`~/.local/bin`, cargo's `bin`, Homebrew's; on Windows `~\.local\bin` and cargo's), in the order cornercase's own list for a remote host uses. The login shell comes before the installers' folders so the window runs the binary the user's terminal runs: cornercase refuses a window client from another build, and the TUI asks to restart a server started by another one.
  - **The login shell** runs as `-l -i -c` (`-i -c` for csh and tcsh), because many users set their `PATH` in `.zshrc` or `.bashrc`, and prints its `PATH` between two marks, since rc files print other things before and after. It is read until the second mark or for 5 s, then killed: a background job of an rc file can keep the pipe open after the shell ends. Windows never asks one; the registry's user `PATH` is not read either, since a Start-menu launch already gets it and a window open during an install finds `~\.local\bin` on Try again. nushell has no `$PATH`, so its script fails and the lookup goes on to the installers' folders.
  - **The shell's `PATH` is handed on** when the binary came through it: every command runs with it first, then the window's own entries, so a server the window starts gives its panes what a terminal would (Homebrew's tools, which usually sit in `.zprofile`, are otherwise missing). The window's other children (Chrome, `open`) are untouched. A binary chosen by hand or found in the installers' folders from a Finder launch still gives the server the launcher's `PATH`; that is a limit.
  - **The version is checked with `<bin> --version`** (5 s limit, not through `Target::command`, which would add `--remote`; run with the login shell's `PATH` when the binary came through it, as the commands will be; a program that prints nothing is reported with its exit status or the timeout, and the probes keep at most 256 KiB of output and stop reading at the deadline even if more is queued): the minimum is 0.12.234, or 0.12.287 on Windows, its first release there. This is not scraping text output: `--version` is the binary's own statement of its version, in clap's fixed `name version` form, in every release. The one structured alternative, `contract --json`, answers for the *server*, needs one running, and does not exist in the old binaries this check is there to catch. A wrapper behind `CORNERCASE_BIN` must pass `--version` on. An old binary is not skipped to look for a newer one: it is what the terminal runs, and the page names it.
  - **When it runs**: once per window, found binary kept in `cli` (`ensure_binary`), so the reconnects every 1.5 s, a restarted server and `Root::switch` do not look again (a command that cannot start the binary forgets it (only if it is still the cached one, by the program that failed; `cli::output` and `cli::spawn` are the ways to start one), so the next reconnect looks again and ends on the missing page). It looks when the window opens, on Try again and on Choose. A chosen file is saved only after it checks out (`Store::set_pref`, never `prefs::save` alone, or the next Settings change would write the old copy back), so a mistake cannot shadow a good install. What is missing is a page (`design/terminal.md`), and nothing waits upstream.
  - Rejected: installers' folders before the login shell (could pick another binary than the terminal's); always asking the login shell (pointless when the `PATH` has it); canonicalising the found path (Homebrew's link is repointed on upgrade and its old Cellar deleted); a retry on its own (the lookup can run rc files, and an install needs the user).
- **Commands run without the caller's variables**: `Target::command` removes `CORNERCASE_PANE`, `CORNERCASE_SERVER` and `CORNERCASE_REMOTE` (`CALLER`). Launched from inside a cornercase pane, the first two would make every command default to that pane instead of what the window's view shows; the third would send this Mac's commands to another machine. The window's own `--remote` is always passed as the flag.
- **Streams stop when dropped**: `view`, `surface`, `events`, `status --app --follow` and the panels' `--follow` commands are children kept in a global list; dropping their `Stream` kills and reaps the process, and `kill_all` stops the rest when the app quits (then `theme --clear` withdraws the palette the window gave cornercase). A stream's stdout is read with a 1 MiB buffer, since a full `surface` frame can be one long line; stderr is collected on its own thread and handed to `on_end`, which is how a refused or stopped stream reports why.
- **Input and the actions that must follow it go through one ordered queue** (`cli::Queue`): requests on different connections are not ordered by the server, so a key followed by a focus or a split could arrive in the wrong order. One worker thread runs them one after the other.
  - **Typing goes through one process per connection** (`cli/typist.rs`): `cornercase input --follow --json -`, started at the first key and kept while the queue lives (#478 upstream), each line naming its pane (`{"pane": 14, "key": …}`), so a key costs a line on a pipe rather than a process, and over ssh one connection rather than one per batch. Consecutive events (at most 256, any panes) are written together.
  - **A command waits for the keys before it** (`Typist::settle`): `--json` answers each request with how many lines it took (`events`), and before any other command the worker reads answers until every line written is answered (at most 10 s), since `--follow` is a connection of its own. A refused line's `error` becomes a toast; the others go on.
  - **When the typist ends** (the server restarted, the link dropped), the next batch starts a new one; if it cannot be started or written to, that batch goes as before, in one `input --pane P -` call per run of the same pane, so typing never depends on `--follow`. Its end is toasted with the last line it wrote on stderr, unless the window stopped it. It is one of the kept children, so `kill_all` and dropping the queue's worker stop it.
  - Rejected: one `input --follow` per pane (a split would start a process per pane typed in), and not waiting for answers (a key followed by ⌘T could land in the new tab).
  - **The queue's commands go through one process too** (`cli/requests.rs`): `cornercase requests --follow -` (#558 upstream, cornercase 0.12.234), started at the first command and kept while the queue lives, one line per command (`{"args": [...], "stdin": "..."}`). Over ssh a one-shot command was a whole session; through it a focus or a scroll costs a round trip on a link that stays open (#558 has the numbers). The worker waits for each answer before the next command, as it waited for each one-shot process, so coalesced runs and summed scrolls still gather behind the one on its way. An answer becomes what the command printed (`json` written back as text, else `text`) or, for a status other than 0, an error from its `error` or `stderr`, as a one-shot's exit status did.
  - **When it cannot run a line**: a command that carries bytes that are not text (a pasted image) runs one-shot, since a line's `stdin` is text; so does a command when the process cannot be started or written to, so a command never depends on `requests`. A process that ended while idle is replaced before the line is sent. A line written but left without an answer (the server stopped, the link dropped) is an error toasted with the last line cornercase wrote, never sent again: it may have run. Without `requests` (a cornercase older than 0.12.234) the process ends at once, so every command fails: the window needs that version, as it needs `input --follow`, and checks it before it starts the server, saying so on its missing page.
  - **A new view drops both processes** (`Queue::reconnect`, from `Root::open_view`): neither notices a dead link until its next line, so after the server restarted or the link dropped the first key or command would be lost with a toast. The next ones start fresh, on the server the view now follows.
  - Rejected: sending lines without waiting for their answers (a drag's every move and a trackpad's every wheel event would each cost a round trip in turn, nothing would gather), and the panels' reads through the same process (`store::run` and the jobs run beside the queue so a slow read never holds a focus; they stay one-shot).
  - A queue belongs to the target it was made for: its worker stops once `cli::connect` changes the target, and the jobs left in it are dropped.
  - A command with a `coalesce` key (a drag's selection, a divider being moved, the view's size) only sends the last of a run of jobs with the same key; the replaced ones' replies are dropped.
  - **The wheel over a pane's history adds up** (`Queue::scroll`): consecutive rows for the same pane go as one `scroll --pane P --up/--down N`, the sum of those waiting, so a trackpad's stream of wheel events costs one command per answer, not one each. Each answer is a round trip through `requests`; one per event would still queue a trackpad's sixty a second in front of every later focus, split or key. `input` cannot move the view, so it cannot ride the typist's connection.
  - A job that ends a batch or a coalesced run is kept and runs next, so nothing is reordered.
  - Errors become toasts through the queue's `on_error`, unless the job asked for its reply (`cmd_then`).
- **Commands that carry bytes** (`Queue::cmd_with_stdin`, `paste-file` of a pasted image) go through the same queue, after the keys before them, with the bytes on standard input.
- **`Store` is a global entity** every part of the window shares, so panels and widgets act without importing the window (`design/code-layout.md`). It holds the session, the view's id, `app` (what `status --app --follow` prints: todos, queue, away, update, keep awake, tour), the docked panel, the sheet, the dialog and the toasts.
  - `act` adds `--view ID` so a command acts in this window's view, not in the TUI's window; `cmd` is for commands that take no view.
  - `follow_app` is called again after a reconnect; the store keeps the stream only for its `Drop`.
  - At most five toasts are kept; each expires by kind (info 4 s, error 8 s, notices 15 s), checked by a timer 16 s after it appears. A toast's action is a button label and the command it runs (`go TOKEN` for an agent's notice).
- **`store::run`, `run_json`, `follow`, `follow_until`**: commands whose answer the UI needs run off the main thread and hand the output back to the entity; fire-and-forget actions go through `Store::act`/`Store::cmd`, which keep their order. `store::queued` is the queue's `cmd_then` for the UI: the action keeps its place in the order and its answer comes back on the main thread, for an action whose refusal the caller handles itself. A followed command's lines reach the entity until it ends; `on_end` gets what it wrote on stderr (or the spawn error) once, and the caller follows again to resume. Updates stop when the entity is gone.
- **A command that can take a while is a job** (`store/jobs.rs`): `store::run_busy`, `Store::act_busy` and `Store::run_aside` record a `Busy` (a key and what it says) while the command runs, end it in the store whatever became of the entity that asked (a dialog closes on confirm), and toast an error. Panels draw their busy state from `Store::busy(key)`, so it lasts while a sheet is closed and opened again, and the status bar shows the newest job and how many more once it has run 300 ms (`SHOW_AFTER`), so a quick one never flashes.
  - `act_busy` goes through the ordered queue, for an action whose order matters (`start --focus`, `new-workspace --focus`, `open --focus`: keys typed after it must reach the new tab).
  - `run_aside` and `run_busy` run beside the queue, for a command that only waits (removing a worktree, closing an agent or a workspace's agents, stopping a process or a port, reopening agents, closing a project): in the queue it held every key and focus behind it for seconds.
  - `store::queued_busy` is `queued` with a job, for an ordered action whose refusal the caller handles (staging, discarding).
  - **What stays without a job was measured** on 2026-10-30 with cornercase 0.12.230, on a throwaway project: renaming, moving, a new tab, focusing, marking, `todo` and `queue` edits, `flow export`, `flow list` and `tour` answer in 3 to 10 ms, closing a shell's tab in about 60 ms. They change the server's state and nothing else, so a spinner would only flash. Staging one file took about 290 ms in a 50-file repository, which is why it has one.
  - `Jobs::removed` keeps a workspace whose worktree was removed marked as removing until the session drops it, since the command answers before the `view` line that drops the row.
