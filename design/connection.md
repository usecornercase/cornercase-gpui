# Connection

Code: `src/main.rs`, `src/cli.rs`, `src/cli/kept.rs`, `src/cli/features.rs`, `src/store.rs`

- **One more client of the command line, with one or two connections**: the app never speaks cornercase's socket protocol. Every command, stream and input event goes through the `cornercase` binary (found as the next bullet says), the contract cornercase documents for programs that draw it (#345 upstream). A protocol change upstream then cannot break the window silently. `cli::Target` says where it runs: this Mac, or another machine, which adds `--remote DESTINATION` (`design/remote.md`).
- **Finding cornercase** (`cli/locate.rs`, `cli/locate/system.rs`): a window started from the Finder, an app menu or the Start menu does not have the shell's `PATH`, so `cornercase` may not be on it. The first program found decides, in this order: `CORNERCASE_BIN` (the only candidate when set: the user said which one, so falling back would hide the mistake; a bare name is searched on the `PATH`); a binary chosen by hand on the missing page and kept in `settings.json` (before the `PATH`, or a choice made because an old binary shadowed a newer one would be lost at the next start; one that is gone, or no longer passes the version check, is passed over for the places below, and is named only when none of them works (a file that is gone too), so updating cornercase on the `PATH` fixes a stale choice); `cornercase` on the process `PATH`; on macOS and Linux the login shell's `PATH`, asked only when the steps before found nothing; then the folders the installers use (`~/.local/bin`, cargo's `bin`, Homebrew's; on Windows `~\.local\bin` and cargo's), in the order cornercase's own list for a remote host uses. The login shell comes before the installers' folders so the window runs the binary the user's terminal runs: cornercase refuses a window client from another build, and the TUI asks to restart a server started by another one.
  - **The login shell** runs as `-l -i -c` (`-i -c` for csh and tcsh), because many users set their `PATH` in `.zshrc` or `.bashrc`, and prints its `PATH` between two marks, since rc files print other things before and after. It is read until the second mark or for 5 s, then killed: a background job of an rc file can keep the pipe open after the shell ends. Windows never asks one; the registry's user `PATH` is not read either, since a Start-menu launch already gets it and a window open during an install finds `~\.local\bin` on Try again. nushell has no `$PATH`, so its script fails and the lookup goes on to the installers' folders.
  - **The shell's `PATH` is handed on** when the binary came through it: every command runs with it first, then the window's own entries, so a server the window starts gives its panes what a terminal would (Homebrew's tools, which usually sit in `.zprofile`, are otherwise missing). The window's other children (Chrome, `open`) are untouched. A binary chosen by hand or found in the installers' folders from a Finder launch still gives the server the launcher's `PATH`; that is a limit.
  - **The version is checked with `<bin> --version`** (5 s limit, not through `Target::command`, which would add `--remote`; run with the login shell's `PATH` when the binary came through it, as the commands will be; a program that prints nothing is reported with its exit status or the timeout, and the probes keep at most 256 KiB of output and stop reading at the deadline even if more is queued): the minimum is 0.13.19 on every platform, the release that has every command the window uses (raised on 2026-11-07 from 0.13.1, the release with machines and routines; one number since 2026-11-06, until then 0.12.234, or 0.12.287 on Windows, its first release there): a window that offers them has nothing to say to a server without them. This is not scraping text output: `--version` is the binary's own statement of its version, in clap's fixed `name version` form, in every release. The one structured alternative, `contract --json`, answers for the *server*, needs one running, and does not exist in the old binaries this check is there to catch. A wrapper behind `CORNERCASE_BIN` must pass `--version` on. An old binary is not skipped to look for a newer one: it is what the terminal runs, and the page names it and offers `cornercase update` for it (`design/terminal.md`). Status 5, like 3 and 4, is read from the exit status, together with `--json`'s facts (`cli/older.rs`, `design/remote.md`).
  - **When it runs**: once per window, found binary kept in `cli` (`ensure_binary`), so the reconnects every 1.5 s, a restarted server and `Root::switch` do not look again (a command that cannot start the binary forgets it (only if it is still the cached one, by the program that failed; `cli::output` and `cli::spawn` are the ways to start one), so the next reconnect looks again and ends on the missing page). It looks when the window opens, on Try again and on Choose. A chosen file is saved only after it checks out (`Store::set_pref`, never `prefs::save` alone, or the next Settings change would write the old copy back), so a mistake cannot shadow a good install. What is missing is a page (`design/terminal.md`), and nothing waits upstream.
  - Rejected: installers' folders before the login shell (could pick another binary than the terminal's); always asking the login shell (pointless when the `PATH` has it); canonicalising the found path (Homebrew's link is repointed on upgrade and its old Cellar deleted); a retry on its own (the lookup can run rc files, and an install needs the user).
- **A feature of a server is asked in one place** (`cli/features.rs`): each field a server sends, or request it carries out, that the window gates by release is a `cli::Feature` variant named after cornercase's contract feature (`machine-tunnels` is `MachineTunnels`), with the release that brought it in `Feature::since`, read from upstream's tags; `Feature::on(release)` answers `Has::Yes` or `No(release)`. The release `Feature::on` is given is that of the server that sends or does it, never the command line's (`Store::cli_release`): a server left running across an update is older than its binary, and the server sends the fields, which the command line prints as they came. A request carried out through a flag or subcommand this computer's command line parses is the one case where `Feature::since` is also asked of the command line's release, through `cli::Releases` (below).
  - **Where the next gate goes.** A field of the running server the window reads: a variant, asked of `Session::release()`, which every view line gives, through `Store::server_has(feature)` where the moment before a connection's first view line draws something of its own (it answers `Unread` then; the tunnels' list of other holders draws nothing), or `Feature::on` in a function that takes the release its caller read, as the Flows, Queue and Issues gates do, which draw an unread release as an unknown one (none of them shows before the first view line without a press). A field of a machine's server: a variant, asked with `Feature::on` of its `server_version` (`run_on::server_release`, its one reader); a machine has no `Unread`, since only one from the list read can be chosen, and one that sent no release counts as older. A field this server and a machine's server must both have stays one variant, asked of each release with `Feature::on`. **A gate that also asks this computer's command line**, because a flag or subcommand it parses carries the request (`flow run --close-when-merged` and `--free-builds`, `flow close-when-merged`, `queue show`, #250's `--boot` with `--machine` (`machine-boot`)): when its server half is a `Feature` and the flag came in that feature's release, it is that variant and `cli::Releases { server, here, machine }.lacks(feature)`, with `Store::releases()` giving `server` and `here` (`Store::heard_release()` for the command line's half). A gate that asks only the command line keeps a constant: its server half is told by a field's absence, as Free merged's (`design/worktrees.md`), or not asked, as the acts' `--boot`; so does a flag that came in another release than its feature's. A flag both command lines parse through `--remote` keeps both releases in one type of its own, as `update --json`'s `cli::UpdateGate` (`design/notifications.md`, "Which command goes by which release"). **Every "needs cornercase X or newer on this Mac" sentence takes its words from `cli::newer_here`** (`cli::it_has` gives the tunnels' split one its tail), so a sentence is never written a sixth time.
  - **What stays outside `Feature`, and why**: a gate that pairs a command line's release with another that is not one feature's `since` keeps them together in its own type: the tunnels' `Gate` (this computer's command line and the server a tunnel goes to, `design/browser.md`), `cli::UpdateGate` and a machine's reads with `--boot` (`ReadReleases::carry_boot`, `design/machines.md`), each with its own constants.
  - **The flag half of the three server gates is asked, by `cli::Releases`** (#279). This computer's command line parses every one of these flags before anything goes, through `--remote` and to this computer's server alike (`cornercase proxy` there parses no argument), so one older than the flag refused it after the press. Seen on the bench with 0.13.27, 0.13.50 and 0.13.63 here against a 0.13.76 server over `--remote`: status 2, clap's words on standard error, nothing on standard output, for every command carrying a flag or subcommand newer than the copy. Each flag came in the release that brought its server feature (0.13.33, 0.13.51, 0.13.64), so `Feature::since` is the one constant for both halves, and the type lives in `cli/features.rs` beside it, shared by the Flows and Queue gates.
    - **The order is the server, then this computer's command line, then the machine** (`Releases::lacks`: `Lacks::Server`, `ThisComputer` or `Machine`); the first too old gives the sentence. The server stays first, so no sentence shown today moves, and where the command line and the server are one install of one release the command line is never the first older side. The command line comes before a machine because both of the first two are on this computer and clap refuses before anything is relayed.
    - **`Release::Unread`** asks nothing, so the gate is what the server's half makes it: no surface draws before a press, except through `CORNERCASE_GPUI_OPEN`, and a press in that moment can still meet clap. **`Read(None)`**, a release that could not be read, counts as older, as `Version::reached_by` does and the tunnels do: the box rests with `… on this Mac.` (no parenthesis, since there is no release to name) and the Queue offers nothing and says so.
    - **The words**: `Needs cornercase 0.13.33 or newer on this Mac (it has 0.13.27).` (`computer` on Linux, `PC` on Windows). The server's and the machine's sentences are unchanged. What each surface draws and sends is in `design/flows.md` and `design/queue.md`.
    - Not done: raising `cli::MINIMUM` to 0.13.64 (it would remove every case by refusing the window to anyone with an older cornercase, #111).
    - Rejected: three constants for the flag half (they would equal `Feature`'s numbers, the duplication #281 removed), counting an unread release as older (`Needs…` would flash at every start), a fourth state of a box resting without words (drawn only in a moment no surface reaches without a press), naming both sides when both are too old (it changes today's sentence on one install), naming the host in the server's sentence (the status bar already names it), and `contract --json` (it answers for the server, not for the command line); mapping clap's refusal back to a sentence is rejected in `design/flows.md`.
  - Rejected: a gate's release in a constant beside its code (four did until #262: a reader told of one place found four, and a model read two releases from a panel's file); `Has` in the sheets' gates (one more input for a moment none of them draws); one table for servers' and command lines' releases; `contract --json` (a read and a state per boot for what the release already says); inferring from a field (absent means none as well as cannot say).
- **Commands run without the caller's variables**: `Target::command` removes `CORNERCASE_PANE`, `CORNERCASE_SERVER` and `CORNERCASE_REMOTE` (`CALLER`). Launched from inside a cornercase pane, the first two would make every command default to that pane instead of what the window's view shows; the third would send this Mac's commands to another machine. The window's own `--remote` is always passed as the flag.
- **Streams stop when dropped** (and say how they ended: a stream's `on_end` gets a `StreamEnd`, its stderr and the exit status reaped as its output ends, so status 4, a refused `--boot`, is told from a lost link by the status and never by the words): `view`, `surface`, `events`, `status --app --follow` and the panels' `--follow` commands are children kept in a global list; dropping their `Stream` kills and reaps the process, and `kill_all` stops the rest when the app quits (then `theme --clear` withdraws the palette the window gave cornercase). `tunnel orders` (the window's taker of a destination, `design/browser.md`) is a stream in that list, killed on drop. `plugin windows` and the tunnel holds are the children not in that list: they must be asked to end, and are kept by `cli/kept.rs`, which ends them with `SIGTERM` on Unix and with `Child::kill` and, on Windows, their Job object. `plugin windows` lets go of the job as it ends (`End::LetGo`, `design/plugins.md`), a hold drops it without letting go so that the `ssh` it started goes too (`End::TakeAlong`, `design/browser.md`). A stream's stdout is read with a 1 MiB buffer, since a full `surface` frame can be one long line; stderr is collected on its own thread and handed to `on_end`, which is how a refused or stopped stream reports why.
- **Input and the actions that must follow it go through one ordered queue** (`cli::Queue`): requests on different connections are not ordered by the server, so a key followed by a focus or a split could arrive in the wrong order. One worker thread runs them one after the other.
  - **Typing goes through one process per connection, a machine's tab's too** (`cli/typist.rs`, measured live on the bench for that tab: same pids before and after 200 characters, `design/machines.md`): `cornercase input --follow --json -`, started at the first key and kept while the queue lives (#478 upstream), each line naming its pane (`{"pane": 14, "key": …}`), so a key costs a line on a pipe rather than a process, and over ssh one connection rather than one per batch. Consecutive events (at most 256, any panes) are written together.
  - **A command waits for the keys before it** (`Typist::settle`): `--json` answers each request with how many lines it took (`events`), and before any other command the worker reads answers until every line written is answered (at most 10 s), since `--follow` is a connection of its own. A refused line's `error` becomes a toast; the others go on.
  - **When the typist ends** (the server restarted, the link dropped), the next batch starts a new one; if it cannot be started or written to, that batch goes as before, in one `input --pane P -` call per run of the same pane, so typing never depends on `--follow`. Its end is toasted with the last line it wrote on stderr, unless the window stopped it or it ended on a refused `--boot` (`design/machines.md`, "What the tab sends carries its run"). It is one of the kept children, so `kill_all` and dropping the queue's worker stop it.
  - Rejected: one `input --follow` per pane (a split would start a process per pane typed in), and not waiting for answers (a key followed by ⌘T could land in the new tab).
  - **The queue's commands go through one process too** (`cli/requests.rs`): `cornercase requests --follow -` (#558 upstream, cornercase 0.12.234), started at the first command and kept while the queue lives, one line per command (`{"args": [...], "stdin": "..."}`). Over ssh a one-shot command was a whole session; through it a focus or a scroll costs a round trip on a link that stays open (#558 has the numbers). The worker waits for each answer before the next command, as it waited for each one-shot process, so coalesced runs and summed scrolls still gather behind the one on its way. An answer becomes what the command printed (`json` written back as text, else `text`) or, for a status other than 0, an error from its `error` or `stderr`, as a one-shot's exit status did; an answer with status 4 is a refused `--boot` (`cli::stale_boot`), as a one-shot's exit 4.
  - **When it cannot run a line**: a command that carries bytes that are not text (a pasted image) runs one-shot, since a line's `stdin` is text; so does a command when the process cannot be started or written to, so a command never depends on `requests`. A process that ended while idle is replaced before the line is sent. A line written but left without an answer (the server stopped, the link dropped) is an error toasted with the last line cornercase wrote, never sent again: it may have run. Without `requests` (a cornercase older than 0.12.234) the process ends at once, so every command fails: the window needs that version, as it needs `input --follow`, and checks it before it starts the server, saying so on its missing page.
  - **A new view drops both processes** (`Queue::reconnect`, from `Root::open_view`): neither notices a dead link until its next line, so after the server restarted or the link dropped the first key or command would be lost with a toast. The next ones start fresh, on the server the view now follows.
  - Rejected: sending lines without waiting for their answers (a drag's every move and a trackpad's every wheel event would each cost a round trip in turn, nothing would gather), and the panels' reads through the same process (`store::run` and the jobs run beside the queue so a slow read never holds a focus; they stay one-shot).
  - A queue belongs to the target it was made for: `Queue::new` takes the window's, `Queue::on` a machine's (`design/machines.md`, a machine's tab), a machine's queue also holds the run it sends its ids for (`Queue::on`'s machine and boot: the worker writes the boot into what it sends, and a refusal's words name the machine; `None` for the window's own queue, which sends commands as given; `design/machines.md` says which commands), and every worker stops once `cli::connect` changes the window's target, with the jobs left in it dropped: a window that moves server leaves its machine's tab behind too. Dropping the last handle ends the worker once it has run what it holds, and its typist and `requests` with it, so a machine's tab that falls or leaves costs nothing more. `Queue::nowhere` has no worker at all and takes everything: it is what a machine's tab holds while it is down, so that nothing typed there can be sent, whatever asks.
  - A command with a `coalesce` key (a drag's selection, a divider being moved, the view's size) only sends the last of a run of jobs with the same key; the replaced ones' replies are dropped.
  - **The wheel over a pane's history adds up** (`Queue::scroll`): consecutive rows for the same pane go as one `scroll --pane P --up/--down N`, the sum of those waiting, so a trackpad's stream of wheel events costs one command per answer, not one each. Each answer is a round trip through `requests`; one per event would still queue a trackpad's sixty a second in front of every later focus, split or key. `input` cannot move the view, so it cannot ride the typist's connection.
  - A job that ends a batch or a coalesced run is kept and runs next, so nothing is reordered.
  - Errors become toasts through the queue's `on_error`, unless the job asked for its reply (`cmd_then`) or the command was refused for its `--boot` (nothing waits for it). A command that moves the view (`cli::moves_view`) also calls `on_view_move`, which drops a machine's picked place (`design/machines.md`).
- **Commands that carry bytes** (`Queue::cmd_with_stdin`, `paste-file` of a pasted image; `Queue::cmd_fed_then` is the same with its answer, a bot's message: `design/bots.md`) go through the same queue, after the keys before them, with the bytes on standard input.
- **`Store` is a global entity** every part of the window shares, so panels and widgets act without importing the window (`design/code-layout.md`). It holds the session, the view's id, `app` (what `status --app --follow` prints: todos, queue, away, update, keep awake, tour), the docked panel, the sheet, the dialog and the toasts.
  - `act` adds `--view ID` so a command acts in this window's view, not in the TUI's window; `cmd` is for commands that take no view.
  - `follow_app` is called again after a reconnect; the store keeps the stream only for its `Drop`.
  - At most five toasts are kept; each expires by kind (info 4 s, error 8 s, notices 15 s), checked by a timer 16 s after it appears. A toast's action is a button label and the command it runs (`go TOKEN` for an agent's notice).
- **`store::run`, `run_json`, `follow`, `follow_until`**: commands whose answer the UI needs run off the main thread and hand the output back to the entity; fire-and-forget actions go through `Store::act`/`Store::cmd`, which keep their order. `store::queued` is the queue's `cmd_then` for the UI: the action keeps its place in the order and its answer comes back on the main thread, for an action whose refusal the caller handles itself. A followed command's lines reach the entity until it ends; `on_end` gets what it wrote on stderr (or the spawn error) once, and the caller follows again to resume. Updates stop when the entity is gone.
- **A command that can take a while is a job** (`store/jobs.rs`): `store::run_busy`, `Store::act_busy` and `Store::run_aside` record a `Busy` (a key and what it says) while the command runs, end it in the store whatever became of the entity that asked (a dialog closes on confirm), and toast an error. `Store::run_then(Busy, work, then)` is the same for work whose answer the store settles itself once the dialog that asked is gone (a worktree's removal from the sidebar). Panels draw their busy state from `Store::busy(key)`, so it lasts while a sheet is closed and opened again, and the status bar shows the newest job and how many more once it has run 300 ms (`SHOW_AFTER`), so a quick one never flashes.
  - `act_busy` goes through the ordered queue, for an action whose order matters (`start --focus --placed`, `new-workspace --focus`, `open --focus`: keys typed after it must reach the new tab). A `start` here has to be `--placed`: without it the queue waits on a folder's trust question, whose answer is typed through that same queue, so the keys never reach it and the job never ends (seen on 2026-11-07 with cornercase 0.13.19, `design/terminal.md`).
  - `run_aside` and `run_busy` run beside the queue, for a command that only waits (closing an agent or a workspace's agents, stopping a process or a port, reopening agents, closing a project): in the queue it held every key and focus behind it for seconds.
  - `store::queued_busy` is `queued` with a job, for an ordered action whose refusal the caller handles (staging, discarding); `store::busy_reply` is the job and the answer for any queue's `cmd_then` (a machine tab's close uses it).
  - **What stays without a job was measured** on 2026-10-30 with cornercase 0.12.230, on a throwaway project: renaming, moving, a new tab, focusing, marking, `todo` and `queue` edits, `flow export`, `flow list` and `tour` answer in 3 to 10 ms, closing a shell's tab in about 60 ms. They change the server's state and nothing else, so a spinner would only flash. Staging one file took about 290 ms in a 50-file repository, which is why it has one.
  - `Jobs::removed` keeps a workspace whose worktree was removed marked as removing until the session drops it, since the command answers before the `view` line that drops the row.
- **`Feature::Bots`** (0.13.77) asks this computer's half only, the list being the server's: `design/bots.md`. The notifier's stream has a second reader, `Store::bot_heard`, for the `bot` events.
