# Issues

Code: `src/panels/issues.rs`, `src/panels/issues/`

- **What the sheet covers**: the trackers `issue sources` reports, their lists with the filters of the TUI's Issues dialog, an issue's detail, and starting work on it now (`start --issue`), later (`queue add --issue`) or with a team of agents (`flow run --issue`). Connecting a tracker is Settings' job: when a tracker (or every tracker) is not connected, the sheet says what it lacks, how to connect it from a shell, and links to Settings. Tokens are checked and kept by cornercase, never by this window.
- **Reading again**: opening the sheet, or the window showing another project, reads the sources, the list and the agents again. It reads the selected issue again too, keeping its text and scroll until the answer differs: the reads were dropped with nothing asking again, so a reopened sheet said "Reading the issue…" for good (found on 2026-10-30). Another project drops the selection, whose key could name an issue of the new one. A read is asked for and kept by project (`page::take`): an answer that comes after the window moved to another project is dropped, since GitHub and GitLab keys belong to one repository; it used to be kept under the key the new project's issue of the same number shares, so that issue showed the other repository's page, and the read it then asked for was skipped as already running (found by Greptile on #7, 2026-11-01, once the page's task began to prefill a flow's start). The first answer of `issue sources` for a project brings the filters the server remembers (closed, and the people filters of each tracker); the tab stays if it is still shown, else the only connected tracker's, else All.
- **Cached first, then live**: each list is asked with `--cached` (what the server holds, at once) and then live. An empty cached answer is not drawn over "loading" once something was shown. A cached answer's failure is ignored; a live one's is shown.
- **One list per filter set**: lists are kept by project, tab, closed and people, so going back to a filter shows its answer at once and asks again only when it never loaded.
- **People filters**: the two filters are the tracker's own fields (assignee/author, owner/requester…). A person belongs to one tracker, so the All tab passes only `me` or `anyone` and drops a person filter. A person is passed by id where the tracker has one, else by handle. The picker lists at most 80 people, narrowed by the search words.
- **At most 100 issues**: trackers answer at most `LIST_CAP` issues per list and offer no further pages, so the list says so and asks to narrow the filters rather than pretending to be complete. The All tab's merged list is sorted newest first; a time that does not parse goes last.
- **Times**: `data::parse_time` reads the RFC 3339 forms trackers send (`Z`, fractions, `+02:00`, and Jira's `+0200`); a bare date is midnight UTC. Days use Howard Hinnant's civil-date algorithm; no date crate is needed for "3d ago".
- **Keys**: up and down move through the list and scroll it so the selected row stays in view (`scroll_to_reveal_item` on the list's row index); Enter in the filter opens the start form for the selected issue. Escape closes the people popover first, as it closes a menu, then the sheet (`design/terminal.md`); Enter in the popover's search picks the first person it matches. A new filter or search scrolls the list back to the top. The list measures every row whenever its issues or its width change (`measure_all`): `scroll_to_reveal_item` knows only the heights it has measured, so after a filter ↓ from a row out of view scrolled too little.
- **The layout** (asked for on 2026-10-30, to make the sheet clearer and match the rest of the window): one toolbar (the trackers as segments, each with a drawn status dot whose tooltip says how it connects or what it lacks, and a refresh icon that turns into a spinner while anything loads; the filter field with its search icon and a clear button, "Include closed", the two people buttons), then the list beside the issue. The list starts with a line of what it holds ("20 open issues", "3 of 20 open issues" while filtering) and, for a tracker's tab, how it connects ("through gh"), which used to sit alone under the filters. A row is the issue's state icon (Lucide's `circle-dot` green while open, `circle-check` grey once closed, as GitHub marks them), the title (two lines, then an ellipsis; gpui truncates a clamped text by its width times its lines, so a title whose words wrap early can lose its last words without one) and one line with the key, a tracker's own state when it is neither open nor closed ("In Progress"), who and when, and at most two labels and a "+N". A selected row takes the window's cobalt tint (`ui::row`), not the grey fill it had, so it reads like every other list.
- **Only what shows is laid out** (asked for on 2026-10-30: reading an issue scrolled slowly). gpui 0.2.2 draws the whole window again on every frame of a scroll and lays out every element it is given, so a scrolled div holding the 100 rows and the whole text paid for all of them on every frame, whichever side scrolled. The list and the text are gpui `list`s, as the Changes diff, which lay out only the items in view and keep the heights of the others: a row (and the cap note) per item; the text's heading, each Markdown block of the description (or its source), the comments' heading and each comment. Markdown is parsed once, when the read arrives (`page.rs`), not on every frame. Measured on 2026-10-30 (release build, 1280×800, `ZED_MEASUREMENTS=1`, issues of zed-industries/zed): a frame took 25 ms on a 60 KB issue and 17 ms on a 19 KB one, about 10 ms of it from the list alone (12.6 ms on a short issue, 2.2 ms with the list filtered to one row); now 2.1 and 4.3 ms, and scrolling the list 4.2 ms instead of 17. A comment is one item, so its card stays whole; a 904-line log in one code block costs about 2.4 ms a frame while it shows. Rejected: cutting a long code block into items (their boxes would meet at fractional heights and show seams), and cached views (they spare one side only while the other scrolls).
- **The people filter is a popover, not a card in the toolbar**: the card pushed the list down while open. It floats under its button (`deferred(anchored())`, anchored to the button's bottom right) and looks like the window's menus: a title, the search, then Anyone, Me and the tracker's people, the current one with a check. It opens on the press, as macOS pop-up buttons do, and the button stops the press so the panel does not close it again; a press anywhere else in the panel closes it, as does choosing. `on_mouse_down_out` was rejected: it runs in the capture phase, before the button's own handler, so pressing the button to close the popover closed it and opened it again. Its search field takes the focus only on a tracker's tab, the only place it is drawn.
- **The issue's header stays while its text scrolls**: the state (a pill: icon and "Open", "Closed" or the tracker's state), the key, the tracker, the title (three lines at most), who opened it and when it changed, the labels, and the actions: Start…, Schedule… and Start a flow… with their icons (the TUI's start, schedule and start a flow), and open in the browser and copy the link as icon buttons with tooltips. The text below scrolls on its own, under "Description" and its Rendered/Markdown switch, which moved out of the actions since it changes the text and not the issue. Each read keeps a list per view, and choosing an issue scrolls them to the top, so another issue opens at its top. Comments are cards of the panel's lighter fill (`colours::panel`, as the design asks of boxes inside a panel) with the author's initial.
- **A tracker that is not connected** is a centred page: the Issues mark, what to do, and a card per tracker with its status dot, what it lacks and the command that connects it, in a field with a copy button.
- **Checked live** on 2026-10-30 (gpui 0.2.2, cornercase 0.12.230) on a throwaway project whose remote is a public GitHub repository: the popover opening, closing from its button, from a press elsewhere (which also selects the row pressed), from Escape (on a tracker's tab and on All) and by choosing, Enter in its search; ↑ and ↓ past the visible rows; the header while the text scrolls; closed issues; a 900×640 window. The copy buttons were not pressed, so as not to replace the clipboard.
- **Starting shows the new tab as soon as it is open** (`start --placed`, 0.13.14; `Store::start_here`): `start` then answers once the tab is open, after the issue is read and the worktree made, even while the agent asks to trust the folder, and the launch goes on. The form stays with `Starting…` on its button until then, as a machine's does (`design/machines.md`), and it and the sheet close on the answer, with the tab on screen and the keys on it, so the question can be answered there. A refusal leaves the form open with what was typed, and the toast says `Could not start #7: …`. Until 2026-11-07 the form closed at once, the panel guessed the tab (it remembered the project's tabs, focused the new one as soon as the session had it and gave up after five minutes), and the job ran until the agent took its prompt, however long the question waited.
- **A launch that fails after the answer shows in the tab**, as in upstream's window (`design/machines.md`): zsh's `no such file or directory` for a command that does not exist, and nothing from the window. So the toast says `claude is starting on #7`, where it said `is working on`.
- **`start` runs in our view** (`--view ID --focus`, added by `Store::with_view`), so cornercase itself shows the new pane there as the tab opens, before it answers: no id is read back and no `focus` is sent. The answer closes the form and the sheet, and drops a machine's picked place (`leave_machine_place`), which `moves_view` does for what goes through the queue and this runs beside it. The place is still named (`--project` for a new worktree, `--workspace` for a new tab), since it is the one the form chose. `--issue` with `--view` passes cornercase's feature check since #461 was fixed (checked with cornercase 0.12.225).
- **A partial answer is an answer**: `issue list` exits 3 when it printed every tracker but some failed (#472 upstream), each failure in its source's entry. Every command of the sheet but `start` runs through `store::run_partial` (`cli::run_partial`): exit 0 and 3 give standard output, any other status an error from standard error, whatever standard output holds.
- **Checked live on 2026-11-07** (cornercase 0.13.19, Linux x86_64 under Xvfb with lavapipe, a private server, a fake `gh` and a fake agent that asks to trust the folder before it reads its prompt, with `accept_trust_prompts` off; no macOS, no Windows): an issue's start in a new worktree and in the same branch again, with `issue view` held for 5 s: `Starting…` and the job while it read, then the sheet and form closed, the tab with the question and the toast; a typed answer reached the question and the issue's address followed as the prompt. From a machine's picked place it came back to this computer's new tab. A failing `gh`: the form stayed, `Could not start #7: …`. A command that does not exist: `claude is starting`, zsh's error in the tab, nothing more 35 s later. `--account` with `--issue --mode --placed` by hand: the pane on that account.
- **The start form**: for a tracker whose issues belong to the project's repository (GitHub, GitLab) there is no place to choose: the project's own place, a new worktree when its folder is a repository root, else a new tab. Other trackers choose among the places `issue sources` lists (a project's new worktree, or a new tab in a workspace); the only place, or the one marked `here`, is preselected. The agent starts on settings' default agent when it is one of the choices (`auto`, "the agent in your tab", is left out), else on the first. Branch and name take a row each and wrap (`TextField::wraps`), since an issue's branch or title ran past a half-row field into its neighbour; for a tracker without a choice the place shows as a "Where" field.
- **The account**: a dropdown under Agent when that agent has accounts, for now and for Schedule alike, on the one in use unless picked (`design/accounts.md`, An account where agents start); it follows the agent chip. Upstream opens its pick when **start** is pressed, because a button on the issue's page was never found; a row in this form is seen on the way to Start, so no second step. Its **start a flow** seeds the flow's combos with the issue's choice; here the choice is made in the form that starts, so Start a flow… has its own.
- **What the plan sends**: the mode only when it differs from the agent's chosen mode, the branch only when it differs from the issue's own branch, effort only for the agents whose `start --help` takes it (`EFFORT_AGENTS`). `queue add` takes no model or effort, and names a worktree's branch only when told, so a worktree place always gets the issue's branch (or the one typed). The schedule's kinds are the TUI's schedule form's.
- **Markdown** (the Recap panel reads and draws its text with these two files too, giving its own `OnLink`, `design/recap.md`): `markdown.rs` is a small reader, enough to read issue bodies and comments as formatted text (headings, setext headings, paragraphs, lists, task boxes, quotes, fenced and indented code, tables, rules, emphasis, inline code, links, images as `[image: alt]`, autolinks, bare URLs), not a full CommonMark parser: unknown syntax stays as its text. HTML comments are dropped, `<br>` becomes a space and other tags vanish. `_` does not open emphasis inside a word, for snake_case; an opening marker is kept as text until it is closed, so a lone `*` stays. A bare URL leaves trailing punctuation out.
- **Runs, not nested marks**: gpui's text highlights cannot overlap, so `Inline::runs` cuts the marks into sorted ranges, each with every mark that covers it (nested emphasis, a bold link). Code is drawn in the terminal's font; a code block is one text (a div per line cost a layout node each), keeps blank lines' height and turns tabs into four spaces. The "Markdown" switch shows the source as it is.
- **Starting an agent on an issue is a job** the status bar names until `start` answers, rather than a 4 s toast that went before the agent did.
- **The Run on row** sits under the start form's heading once a machine is listed (`design/machines.md`, Starting work on a machine). With a machine picked the form shows that machine's accounts, says when the agent is missing or logged out there, hides Schedule and the Mode (the queue starts work here, and the modes listed are this computer's), replaces the place by where it lands there, and keeps the model, the effort, the branch and the workspace's name. A tracker with no choice of place stands for the project; one with places keeps its chips, since a place chooses the project, and a place that is a workspace here stands for its project there, as `start --issue --project` places the work. The form stays open with a busy button until the machine answers or lists the tab.
- **Start a flow…** opens the Flows sheet's start dialog over this sheet (`design/flows.md`), preset by `data::flow_start` with the issue (its key and tracker, its branch, its key and title for the workspace's name, and the task of the page read for it, which the dialog prefills) and the projects a flow can run in, which are repository roots: the issue's own project for a GitHub or GitLab issue; for the other trackers, the places `issue sources` lists as a project's new worktree, with the sheet's own project chosen when it is one of them, else the only one. The place marked `here`, which the agent's start form still preselects, is not used: it follows the process that asks (a window started from a pane is that pane's project, whatever the sheet shows), which was seen live when `issue sources --project 175`, asked from a pane of project 1, marked project 1. Cancel or Escape comes back to the sheet; a start that shows the run in the window closes the sheet and lands on the run's orchestrator, as starting an agent lands on its pane; until 2026-11-02 it left the window where it was (#583 upstream, `design/flows.md`). Checked live on 2026-11-01 with GitHub issues (`design/flows.md`); no other tracker was connected.
