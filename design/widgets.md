# Widgets

Code: `src/ui/`, `src/theme.rs`, `src/dialogs.rs`

- **One set of building blocks** (`ui/mod.rs`) every panel uses, so the window reads as one thing: buttons (plain, primary for a form's main action, danger for what cannot be undone, icon buttons for one glyph, and an icon beside a label in any of the three tones), rows, sections, notes, fields, input boxes, search fields, checkboxes, segments, titles, bars, one-line texts, the undo bar (a removal's text and its Undo button, which the TODO and Queue panels show for a few seconds instead of asking first) and the emblem (a panel's icon in a cobalt disc, at the top of a page that says what the panel is for when it has nothing to show: Issues without a tracker, the empty Queue). They return gpui `Div`s the caller finishes with `.on_click(…)`.
- **Signs** (`ui/signs.rs`): chips (`accent_chip` for what is chosen, `quiet_chip` for a fact, `tinted_chip` in a status colour), the status `dot` (filled in a colour, or a faint ring for unknown), `error_line`, `warning_line` and `done_line` (an icon and a sentence), `callout` (a tinted card with an alert, a title and a body) and `row_action` (a faint icon with a tooltip, in a row's fixed slot, red on hover when it removes) with `resting_action` (its place while it cannot be pressed), and `field_action` (a small icon button inside a field, with a tooltip: Settings' search clear, a setting's Save and Revert). The Accounts sheet drew them first; they moved here on 2026-10-31 when Settings took the same look, so both sheets share one set. `resting_button` is a button shown before it can be pressed, dimmed and inert, so it does not appear from nowhere (Settings' Connect until a token is typed).
- **`TextField` is adapted from gpui 0.2.2's own `input` example (Apache-2.0, `LICENSE-GPUI`)**: gpui has no text field. Text goes through macOS's input method (`EntityInputHandler`), so dead keys, ⌥ characters and composition (marked text, underlined) work. Pasted newlines become spaces, since the field holds one line. `masked()` shows dots for secrets. Enter and escape are actions in the `TextField` key context, emitted as `Submit` and `Cancel`; every edit emits `Changed`. `clears_on_escape()` makes escape clear the text instead, and pass on when it is already empty; `in_tab_order()` makes the field a tab stop (`design/terminal.md`). `reverts_on_escape()` makes a field remember the value it was saved with (`keep_saved`, which also fills an unedited field with a newer value): escape puts that value back when the text differs (and emits `Cancel`), and passes on to `Root` when it does not, so a settings field never keeps the sheet from closing; `edited()` tells whether the text differs (2026-10-31, `design/settings.md`).
- **`wraps()` makes a field a textarea in looks, not in content**: the text stays one line (Enter still submits, pasted newlines still become spaces), but it breaks into rows at the field's width and the field grows a row at a time, instead of running out of its box. The height is measured from the width at layout (`request_measured_layout`), the way gpui's own text element does it; clicks, the caret, the selection (one band per row) and the input method's rectangles follow the rows. Every field is drawn as a `WrappedLine`, with no wrap width when it does not wrap, so both kinds share one path. It is opt-in because a one-line field (filters, settings, names) should stay one row high. A wrapping field must not sit in a flex column that scrolls itself (`overflow_y_scroll` on the column): in the queue's form it was laid out at no width and drew one letter per row (2026-10-31). The scroll goes on a plain container around the column, as in the Issues start form and the queue's form. There is no ↑/↓ between rows and no inner scroll: a very long text makes the field tall. Checked live on 2026-10-30 (gpui 0.2.2) in the TODO panel: typing, a selection across a wrap, a click on a middle row.
- **A text that can hold line breaks is clamped by its height** (`ui::clamped`: as many lines as asked, the rest hidden), not with gpui's `line_clamp`, which in gpui 0.2.2 counts only the lines it wraps. A text's own line breaks did not count, so a collapsed message holding a list showed every item and a run's task every line; and once the count was spent, the lines left were no longer wrapped but ran on in one row, which the clamp's own hidden overflow cut at the edge, mid-word. Cut by height, the text wraps as when shown whole and stops between two lines. Titles, which hold no line breaks, keep `line_clamp`: with `text_ellipsis` a cut title ends in an ellipsis, which a cut by height cannot draw. Checked live on 2026-10-31 with a fake flow run's task and messages (lists, blank lines, a long paragraph), expanded and collapsed.
- **A text kept to one line is drawn by `ui::one_line`**, an element of its own, and ends in "…" where its box ends. It measures the whole line, takes the width its box gives it, and cuts the text only when painting, keeping its highlights (a search's match, a file's colours) up to the cut; its narrowest width is nothing, so a full row shrinks it rather than the figures beside it. Line breaks and tabs read as spaces. gpui 0.2.2's own ways both failed. `truncate()` (`whitespace_nowrap` with `text_ellipsis`) keeps a text's first measure, taken at its full width before its box has one, so the sidebar's names, the status bar, Changes and Files clipped long texts mid-letter with no ellipsis; `clippy.toml` disallows it. `line_clamp(1)` with `text_ellipsis` measures again at each new width but cuts the text's styled runs in place, so the next measure in the same frame shaped the text with runs that no longer fit it: the window crashed (`not a char boundary`) on Search's "In sessions" results on 2026-10-31. The two- and three-line titles of Issues still take that cut, so they share the risk. Checked live on 2026-10-31 at 700, 980 and 1280 px wide: the sidebar, the status bar, Changes, Files (tree, viewer, search), Search (names and sessions, with matches), Processes, Ports and the server dialog. **A box that takes its width from the text must be a flex container** (`.flex()`, as the Files panel's `ellipsis`); a box with a share of its row (`flex_1`, a list row's full width) can stay a block. In a block box sized by the text, the text was left 0 px wide although the box had its width, so the Files viewer's title and tree header showed no names (found later on 2026-10-31 by logging the element's layout), nor did the Changes panel's open file (its file list's names, in the same kind of box, happened to show), nor, on 2026-11-01, the names in the Flows sheet's lists (`design/flows.md`): taffy 0.9 also lays a block box's children out while measuring the box at its narrowest, where this text measures nothing, and when the box then ends at a width its cache already holds a final layout for (the text fits, so the box is as wide as before), taffy reuses that layout without laying the text out again. So only a text that fits disappears: one cut to a narrower width gets a new layout and draws, which is why a long flow name cut beside its tags showed while the short names beside it did not. A flex container measured for its size lays nothing out. Whether a block box is hit depends on the order taffy measures the tree in (a run member's branch and the import check's agents, in such boxes, draw), so follow the rule rather than what shows today.
- **`input_box` is a flex column** (2026-10-31): a block box laid out as a flex item lays its children out at their narrowest in gpui 0.2.2 (taffy 0.9, the same trap as the block box under "A text kept to one line"), so a field's inner row (the search icon, the text, a clear button) was as narrow as the icon: the clear button was drawn over the text, and Settings' Save and Revert inside a field would have been too. As a flex column the row stretches to the box. The same holds for any wrapper of a full-width row inside a flex column: Settings' navigation stacks its rows in flex columns, not in plain boxes, or the selected row's tint and the search field hugged their text.
- **Hover cannot recolour text** in gpui 0.2.2: text is shaped with its colour while the element is laid out, and hover styles are only known when it is painted (a group's hover is even pushed only during paint), so `hover(|s| s.text_color(…))` and `group_hover` change backgrounds and icons (SVGs are tinted at paint) but leave text as it was. For the same reason they cannot change the layout: the layout is computed without hitboxes, so a size or margin set under hover is ignored; what must make room on hover keeps the hovered element in its state (`on_hover`), as the sidebar's rows do (`design/sidebar.md`). Light text on the cobalt pill hid it, since `text` and `on_brand` are nearly the same white; a faint note stayed faint on cobalt. A menu that recolours text on hover keeps the hovered row in its state (`on_hover`) and draws every colour from it, as Settings' choice popover does, where the mouse and the arrows share one highlight. Checked in gpui's source (`Interactivity::paint` pushes `GroupHitboxes`; `compute_style` applies hover only with a hitbox) and live on 2026-10-31.
- **Dialogs** (`dialogs.rs`) share `frame`, `cancel_and` and `show` (open and focus), and their fields sit in `ui::boxed`. `frame` has no height of its own, so a dialog whose body can outgrow the window scrolls it within `body_height` (the window's height less 240, from 200 to 560 px), leaving the title and the buttons in view: the pull request dialog and a flow's start dialog, whose body from an issue passed an 800 px window once it gained the task (2026-11-01). Anything that cannot be undone asks first through `confirm(Question::new(title, message, button, command), …)`, which runs the command with `Store::cmd` on enter or the danger button. No caller needed `--view` (they pass ids, and `--yes` where the command asks), so the dialog runs the command as given and takes no flag for it. A caller that must know the answer (the Changes panel, to read a file again when cornercase refuses a stale discard) adds `on_reply`: the command then goes through the same queue with `store::queued`, and its error reaches the caller instead of a toast.
- **The terminal's palette is Tokyo Night**, the dark theme cornercase's own fixtures use: the same 16 ANSI colours (the bright ones equal the normal ones, except bright black, and bright white is the foreground) are given to cornercase with `theme -`, with the xterm 256-colour cube and grey ramp built from them, so programs pick a look that matches what the window draws. A pane's program can override the palette, foreground, background and cursor; `Painter` applies its overrides first.
- **The chrome takes usecornercase.dev's colours** (its dark theme, read from the site's stylesheet on 2026-10-23), so the site, the TUI and this window draw one brand (cornercase's `design/website.md`, "The brand"): neutral greys for the ground and surfaces (`glass` `#0b0c0e`, cards `#15171b`, `raised` `#1d2025`), four greys for text (`text`, `soft`, `muted`, `faint`: `#eceef1`, `#b6bcc4`, `#8b929b`, `#6b727c`), cobalt `#005fff` (xterm colour 27, the brand's one accent) for fills, bars and focus, its ink `#74a3ff` (`accent`) for accent text and icons, and the site's status colours: yellow working, orange waiting, red failed, green done. The terminal keeps Tokyo Night, as the site's own terminal pictures do. Placeholders take the third grey and text fields a darker edge, as the site's fields do for contrast.
- **Icons are [Lucide](https://lucide.dev) 0.460.0 SVGs (ISC, `assets/icons/LICENSE`)** with the stroke thinned from 2 to 1.75, closer to SF Symbols at 14–18 px. SF Symbols' licence allows them only through Apple's system APIs, which gpui 0.2.2 does not reach. They are embedded in the binary, so the app needs no files beside it; a new icon is a file in `assets/icons/` and a line in `Icon` (its variant, `ALL` and its group's match), and a test fails when two icons share a file. `play-filled` and `star-filled` are Lucide's `play` and `star` filled with `currentColor`: a start button and a default read better solid. The `status-*` icons are drawn here, not taken from Lucide.
- **A file's icon tells its type, as the TUI's does** (`ui/file_icons.rs`, asked for on 2026-10-30): the glyphs are the TUI's own, Seti UI's file-type icons and Nerd Fonts' folders, taken as SVGs from Nerd Fonts 3.5.1's `src/svgs` (MIT, `assets/file-icons/LICENSE`, which also lists the renames), and the table is the TUI's `ui/icons/kinds.rs` copied: a known name first (`Cargo.toml`, `Dockerfile`, `README.md`), then the extension, ignoring case, else a generic file. Each is tinted with the palette's ANSI colour the TUI gives it, so a type looks alike in both. They are filled glyphs drawn at 16 px, beside Lucide's outlines at 12–14, since Seti's glyphs sit inside their square with room around them. Rejected: Lucide's generic `file-code` and the like (they do not tell Rust from TypeScript) and full-colour sets such as Material Icon Theme (gpui 0.2.2 draws an `svg` as one tinted mask, and an `img` of an SVG would be a second path for icons; it would not match the TUI either). Keep the table in step with the TUI's when it changes.
- **The whole window is glass in layers** (asked for on 2026-10-26, after a translucent macOS app with a see-through sidebar and darker content): it is `Blurred`, and `Root` paints `glass` (the site's ground at 55 %) once, under everything, so the blurred desktop shows through the whole window; each surface is a further translucent layer on it, never an opaque block. Each layer adds opacity, so the panes' colour is worked out to look, over the ground, as Tokyo Night at `terminal_opacity()` (0.65, or `CORNERCASE_GPUI_OPACITY`, kept between 0.3 and 1) would over the desktop (`theme::over_ground`, exact since gpui 0.2.2 blends in the colours' own space, `BGRA8Unorm`). The terminal keeps the translucency that was asked for, but it cannot be more see-through than the ground: below 0.55 it shows the ground alone. The ground's 55 % keeps the chrome's faint text readable over a bright desktop (50 % lost the status bar's, checked by eye over a bright checkerboard). Painting the ground everywhere but under the panes was rejected: the corners outside a rounded pane would need paths, and where a path's edge meets a pane's, each covers only part of the edge pixels, which would leave a lighter seam (reasoned, not tried). The cards (`surface`, a lighter grey at 30 %: the rail's, the sidebar's, the dock) read lighter than the ground and stay see-through, as the reference's sidebar; the boxes inside a panel (`panel`) are white at 4 %, one more lighter layer. Lines and hovers are white at low alpha (`border`, `edge`, `hover`, `selected`), so they read the same over any backdrop.
- **Floating cards stay nearly opaque** (`ui/glass.rs` `card(radius)`: sheets, dialogs, menus, toasts, at 88 to 91 %; `popover` for tooltips): gpui 0.2.2 blurs only the desktop behind the window, not the window's own content, so a more see-through card would show the text under it, unblurred. At about 90 % it shows only a hint of what is under it, enough to read as one more layer. Depth comes from the card instead: a sheen (lighter at the top), a light top edge fading from the left (inset by the radius, so it stays on the straight part), a 1 px line and a deep shadow, over the site's dimming veil (`#0a0b10` at 62 %). Translucent surfaces (panes, the dock, the rail's and the sidebar's cards) take no shadow: gpui draws a shadow under the whole element, so it would darken them from inside.
- **Rounded corners and more air, as macOS and iOS draw them** (asked for on 2026-10-23; the site's square corners were used until then). One scale, `theme::radius`: `CHIP` (5) for tags, counters, key caps, checkboxes and a row's buttons; `CONTROL` (8) for buttons, fields, rows, tabs, menu entries and the rail's icons; `CARD` (12) for the floating surfaces (the rail's and the sidebar's cards, the panes, the dock, menus, toasts and the boxes inside panels); `SHEET` (16) for sheets and dialogs. Switches, bars, dots and swatches are capsules or circles. A shape inside another takes the outer radius less the space between them (a segment in its track, an entry in its menu), so the curves stay parallel. The spacing grew with it: rows are 4 to 6 px taller, panels sit 12 to 16 px in from their edges, and 8 px (`GAP`) separate the floating surfaces from each other and from the window's edges. Code and diff lines keep square, full-width bands. gpui 0.2.2 clips a child to a rectangle, not to its parent's rounded shape, so a child that paints a background into a corner rounds that corner itself (the Files viewer, the Settings page list, the queue's form, a table's header row).
- **Cobalt marks what is chosen, without bars** (`ui/glass.rs`): a selected row is a rounded cobalt tint (`lit`), as macOS fills a selected sidebar row; the shown tab and segment are a lighter rounded fill, as the system's segmented controls; the highlighted menu entry is a cobalt pill. The 2 px glowing bars and underlines they had went with the square shapes. Primary buttons, checked boxes and switches stay a cobalt gradient with a soft glow (`cobalt`, `glow`); a focused field takes a 3 px cobalt ring (`ring`), as macOS draws focus; the shown panel's rail icon is tinted, without a glow; a cobalt wash lights the top of the rail's and the sidebar's cards. The site draws no glows or glass; this window does because it is a native window over the desktop, where translucency is the platform's look and depth tells what floats from what is docked. The colours and the mark stay the site's.
- **The mark** (`ui/brand.rs`) is the site's corner and cursor on its 12-unit grid, drawn with `div`s: small beside the wordmark in the title row, right of the traffic lights, and large in the terminal's place while there is no terminal to show.
- **Every border between two parts can be dragged** (`ui/split.rs`): the sidebar's and the dock's (`design/window.md`), the list columns of Issues and Flows, the Settings page list, the queue's form, the Changes file list (`design/changes-panel.md`) and the terminal's dividers (`design/terminal.md`). A `Split` holds the size chosen by a drag, none until then so the default applies, within its limits and always leaving room for the other side; a double click on the border goes back to the default, as a double click evens a terminal split. Sizes last for the session, as the zoom does: the window saves nothing of its own to disk.
- **A split's handle is an invisible 8 px strip centred on the border** (a card's edge, or the line between a list and its page), with the resize cursor and nothing drawn on hover: gpui has no hover delay, so a highlight would flash whenever the pointer crosses a border. It is drawn after both sides, in their container at the line's offset, and `occlude`s them, so a press on its half over the terminal cannot start a selection there. Inside one side it would lie under the other, which is drawn later; `deferred` would draw it over sheets and dialogs too. The drag is gpui's `on_drag` with a blank preview, and the container's `on_drag_move`, called for every move of that drag wherever the pointer is, measures from the container's fixed edge, so the side follows the pointer. Each split has its own drag type: a docked panel and a sheet are drawn together, and both would follow one drag of a shared type.
- **A hover style is set once per element**: gpui 0.2.2 asserts in debug builds when `hover` is called twice, so the builders take what decides it (`row_base(target, lit)`, the menu row's danger flag) and a lit row does not hover.
- **`FONT_FAMILY`** lives in `theme.rs`, not `app.rs`, so panels need not import the window (`design/code-layout.md`).
- **Motion uses gpui 0.2.2's own `with_animation`** (`ui/motion.rs`), not [gpui-motion](https://github.com/1bye/gpui-motion) (`gpui-ce-motion`): that crate is built on `gpui-ce`, a fork whose element types do not mix with Zed's `gpui`, so adopting it would mean moving the whole app to the fork (checked 2026-10-23, gpui-ce-motion 0.4.0). gpui's tweens are enough for what the window needs. Springs that can be interrupted would need that crate or a port of its math.
- **What moves**: sheets and dialogs rise 14 and 10 px and fade in over a fading backdrop; the dock slides 24 px in from the right; toasts slide in from the right; context menus drop 4 px quickly (`Way::Pop`); the bell's flash fades out; the connection dot and the mark's cursor pulse while connecting. Entering takes 180 ms ease-out, leaving 120 ms ease-in, so closing feels quicker than opening.
- **What takes a while turns a spinner** (asked for on 2026-10-30, after removing a worktree said nothing for seconds): `ui::spinner` is Lucide's `loader-circle` turned once every 900 ms by `motion::spin`, since gpui 0.2.2 rotates only `svg` elements (`Transformation`). It comes in three shapes: `busy_button` takes the place of the button that started the work, in the same tone, with what it does (`Removing…`, `Installing…`) and no click; `busy` is a small line beside what it concerns (`saving…`, `measuring`); `loading` is a panel's note while its first answer comes. A row whose work runs dims, so the rest of the list stays readable. They replace the `…`, `◐` and plain `Loading…` texts, which did not say that anything moved. The status bar names the newest job (`design/connection.md`).
- **An agent's status is an icon of the window's own, not the TUI's glyph** (asked for on 2026-10-30: the `◐ ! ✓ ✗ ● ○` the TUI draws looked plain here). `ui::status_badge` gives a status its icon and colour, and `ui::badge` draws it wherever a status shows (the tab bar, the sidebar's rows, Search, TODO). One family of circles: idle is a ring; working is the same ring, faint, with a bright dot and a fading tail orbiting it; waiting, failed and done, which ask for you, are solid discs with `!`, `×` and `✓` cut out (an SVG `mask`, so the row shows through); pending is a dot in a ring. gpui renders an SVG to an alpha mask tinted with the text colour, so the tail's dots fade by opacity. The orbit turns smoothly, a turn in 1.2 s, at the angle the wall clock gives when the window draws, so every orbit points the same way; how often it draws is under "A working agent's orbit" below.
- **Leaving is kept by `Root`**: gpui draws only what the state holds, so closing would cut the element at once. `Leaving<T>` remembers the closed sheet, dialog or dock for `LEAVE`, and `Root` draws it animating out under a transparent layer that takes the clicks, so a second click cannot press a button that is going away (a dialog's "Delete", say). Reopening cancels the leave, and a timer from an older close never ends a newer one. A leaving dock is drawn over the terminal, so the terminal takes its width back at once.
- **Nothing animates forever while idle**: a repeating animation asks for a frame on every frame, which redraws the whole window, terminal included. Only the "connecting…" dot and the mark's cursor in the terminal's place pulse, and only while connecting (not while disconnected, which can last). A spinner turns only while its command runs, and stops with it.
- **A working agent's orbit draws about 30 times a second, on the display's frames** (asked for on 2026-10-31: the working animation was not smooth). It is the one thing that moves for long, so it does not use `with_animation`, which draws on every display frame. While some agent works (`Session::anyone_working`), `motion::Beat` follows the display's frames (`on_next_frame`) and redraws `Root` on the frame nearest a thirtieth of a second after the window last drew: every 4th frame at 120 Hz, every 2nd at 60, so each position stays on screen as long as the others. A window that already draws for another reason (a pane's output, a spinner) gets no extra frame. It rests as soon as a frame drew no orbit (`motion::orbits_drawn`: the working agents are folded away or out of sight), and a covered or minimised window draws nothing at all, since gpui stops its display link.
  - Why the old orbit stuttered: it stepped 30° ten times a second (its head jumped 2 points), and the steps came from a wall-clock timer, which fires anywhere between two display frames: 30 to 40 % of them showed a 120 Hz frame early or late, so a step lasted 92 to 108 ms instead of 100. Now 98 % of the orbit's frames are exactly 4 display frames apart (the rest are other redraws, or the measure's own jitter), and its head moves 0.7 point a frame. Every other moving thing already drew on every display frame: spinners, the connecting pulse, sheets and toasts while they come and go, the Flows diagram's one-shot rise and spark. Flows draws a working member as a still dot, so nothing else repeats.
  - Measured on 2026-10-31 (release build, cornercase 0.12.230, MacBook Pro M5 at 120 Hz, a 1280×800 window, agents faked working through a `CORNERCASE_BIN` wrapper that rewrites `view`'s statuses; CPU of the app over 20 s, then roughly what WindowServer added; noisy, since other builds shared the machine). With a terminal full of text: the old steps 5.5 to 6.6 % with one agent working and 6.9 % with four; now 10.5 to 14.7 % and 16.9 % (+5 to 10 %); 0.5 % with none working, and 0.45 % with one working out of sight, neither drawing a frame. Four cost more than one because the sidebar holds more rows to lay out: the price is the window's frame (3 to 5 ms here, mostly gpui laying the whole tree out again and painting the terminal), not the badges. Options compared back to back with a nearly empty terminal: the old steps 5.2 %; 30 a second on display frames 8 to 11 % (+5 to 10 %); 60 a second 17 to 20 % (+15 to 20 %); every display frame (120) 25 % (+40 %); a wall-clock timer at 30 a second about 5.7 %, but 1 to 23 % of its frames landed a display frame off, and 30 % at 60 a second (12.3 %).
  - Rejected: gpui's animation scoped to the badges (a frame asked from inside a view redraws every view above it, and `Root` always, so it costs a whole window at the display's rate, the 120 row); a faster wall-clock timer (uneven, above); 60 a second (twice the cost of 30, for a 12 px icon whose dots already move under a point a frame at 30); slowing the orbit while the window is in the background (a glance at it would see the old stutter); a cheaper frame through cached views (`Root` draws the badges itself, so the window would have to be split into cached views, the terminal first, each told of every change it draws; WindowServer's share of each frame would stay). That last one is the way to make every frame cheaper, spinners and scrolling included, if the cost matters later.
  - Not measured: a covered or minimised window. gpui 0.2.2 stops a window's display link when macOS says it is occluded, so no display frame calls the beat (read in its source).
- **Moving uses relative offsets** (`relative().left/top`), since gpui 0.2.2 has no transforms for `div`s: layout does not change, so the terminal is not resized while something moves. Nothing scales. Hover colours change at once, since gpui has no transitions for styles.
- **macOS's "Reduce motion" is not read**: gpui 0.2.2 does not expose it.
