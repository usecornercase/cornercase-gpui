# Widgets

Code: `src/ui/`, `src/theme.rs`, `src/dialogs.rs`

- **One set of building blocks** (`ui/mod.rs`) every panel uses, so the window reads as one thing: buttons (plain, primary for a form's main action, danger for what cannot be undone, icon buttons for one glyph, and an icon beside a label in any of the three tones), rows, sections, notes, fields, input boxes, search fields, checkboxes, segments (`icon_segment` with its picture), titles, bars, one-line texts, the undo bar (a removal's text and its Undo button, which the TODO and Queue panels show for a few seconds instead of asking first) and the emblem (a panel's icon in a cobalt disc, at the top of a page that says what the panel is for when it has nothing to show: Issues without a tracker, the empty Queue and Machines; `emblem_page` lays it out with its heading, `emblem_line` a sentence under them). They return gpui `Div`s the caller finishes with `.on_click(…)`.
- **Signs** (`ui/signs.rs`): chips (`accent_chip` for what is chosen, `quiet_chip` for a fact, `tinted_chip` in a status colour), the status `dot` (filled in a colour, or a faint ring for unknown), `error_line`, `warning_line` and `done_line` (an icon and a sentence), `callout` (a tinted card with an alert, a title and a body) and `row_action` (a faint icon with a tooltip, in a row's fixed slot, red on hover when it removes) with `resting_action` (its place while it cannot be pressed), and `field_action` (a small icon button inside a field, with a tooltip: Settings' search clear, a setting's Save and Revert). The Accounts sheet drew them first; they moved here on 2026-10-31 when Settings took the same look, so both sheets share one set. `resting_button` is a button shown before it can be pressed, dimmed and inert, so it does not appear from nowhere (Settings' Connect until a token is typed).
- **Pop-ups** (`ui/menu.rs`): a dropdown (the value, a chevron, a cobalt edge while open) that opens a menu under it on the press, as macOS pop-up buttons do: a glass card holding the focus, its entries with a check on the value in use and a cobalt pill on the highlighted one, which the pointer and ↑ ↓ share (kept in the owner's state, since hover cannot recolour text, below), Enter choosing and Escape closing only the menu. Settings' choices drew it first; its pieces moved here on 2026-11-02 when a flow's start dialog took it for its project (`design/flows.md`), so the two read alike. `ui/account_picker.rs` is the third, a whole widget since four forms use it (`design/accounts.md`). In those two a window-sized backdrop under the menu takes the press that closes it (`menu::backdrop`): that press does nothing else, as on macOS, the wheel cannot scroll a form from under the menu, and a dialog with both cannot have both open. Settings' still closes on the press its panel sees.
- **`TextField` is adapted from gpui 0.2.2's own `input` example (Apache-2.0, `LICENSE-GPUI`)**: gpui has no text field. Text goes through macOS's input method (`EntityInputHandler`), so dead keys, ⌥ characters and composition (marked text, underlined) work. Pasted newlines become spaces in a field of one line, a Windows line end (`\r\n`) one space and a lone `\r` one too (`one_line`): X11's primary selection hands CRLF text over as it is, and the field had kept its `\r` (found in review, 2026-11-04). `masked()` shows dots for secrets. Enter and escape are actions in the `TextField` key context, emitted as `Submit` and `Cancel`; every edit emits `Changed`. `clears_on_escape()` makes escape clear the text instead, and pass on when it is already empty; `in_tab_order()` makes the field a tab stop (`design/terminal.md`). `reverts_on_escape()` makes a field remember the value it was saved with (`keep_saved`, which also fills an unedited field with a newer value): escape puts that value back when the text differs (and emits `Cancel`), and passes on to `Root` when it does not, so a settings field never keeps the sheet from closing; `edited()` tells whether the text differs (2026-10-31, `design/settings.md`).
- **A text field's keys follow the platform** (`text_field::bindings`): on macOS ⌘A, ⌘C, ⌘X, ⌘V, ⌥⌫ and ⌘⌫ by word, ⌘← and ⌘→ to the ends, ⌃⌘Space the character palette; on Linux GTK's, which are Windows' own too (`control_bindings`): Ctrl+A, Ctrl+C, Ctrl+X, Ctrl+V, Ctrl+⌫ and Ctrl+Delete by word, Ctrl+← and Ctrl+→ by word, Home and End, plus Ctrl+Shift+C and Ctrl+Shift+V, the window's copy and paste there (`design/terminal.md`, Keys on Linux), so the terminal's habit works in a field too. A word ends at a blank. The field has no undo, so Ctrl+Z does nothing. Moving by word was added for Linux, where GTK users expect it; macOS kept its keys (2026-11-04). Checked live on Linux (X11) on 2026-11-04 in the new workspace dialog: Ctrl+⌫, Ctrl+← twice, Ctrl+Delete, Ctrl+A with Ctrl+X, Ctrl+V and Ctrl+Shift+V each did what is listed.
- **`wraps()` makes a field a textarea in looks, not in content**: the text stays one line (Enter still submits, pasted newlines still become spaces), but it breaks into rows at the field's width and the field grows a row at a time, instead of running out of its box. The height is measured from the width at layout (`request_measured_layout`), the way gpui's own text element does it; clicks, the caret, the selection (one band per row) and the input method's rectangles follow the rows. Every field is drawn as `WrappedLine`s (`text_field/element.rs`), with no wrap width when it does not wrap, so every kind shares one path. A text set from outside (`set_text`) can hold line breaks, such as a queue entry's prompt or an issue's task: such a field draws them all, where it used to draw the first line and leave room for the rest (checked live on 2026-11-06 in the Queue's form). It is opt-in because a one-line field (filters, settings, names) should stay one row high. A wrapping field must not sit in a flex column that scrolls itself (`overflow_y_scroll` on the column): in the queue's form it was laid out at no width and drew one letter per row (2026-10-31). The scroll goes on a plain container around the column, as in the Issues start form and the queue's form. There is no ↑/↓ between rows and no inner scroll, which `multiline` adds: a very long text makes the field tall. Checked live on 2026-10-30 (gpui 0.2.2) in the TODO panel: typing, a selection across a wrap, a click on a middle row.
- **`multiline(rows)` makes a field hold several lines** (2026-11-06, for a flow's prompts, `design/flows.md`; `text_field/rows.rs` holds the plain numbers, `text_field/element.rs` the drawing). gpui's `shape_text` gives one `WrappedLine` per line, and `Rows` lists every row on screen with its offsets, so clicks, the caret, the selection and the input method's rectangles read one table, with no window in its tests. Enter and ⇧Enter break the line, and ⌘Enter (Ctrl+Enter on Linux and Windows) submits; a paste keeps its lines (`\r\n` and a lone `\r` become `\n`, as in the TUI's fields); ↑ and ↓ move between rows and keep the column they started from (`goal_x`), and past the first or last row go to the text's end, as native fields do; ⇧ with ↑ ↓ Home End selects, and the selection goes to the primary selection like any other; Home and End reach the ends of the row, as ⌘← and ⌘→ do; ⌘↑ and ⌘↓, or Ctrl+Home and Ctrl+End on Linux and Windows, reach the ends of the text. Tab still moves the focus: a form is walked with it, and prompts have no use for a tab character. A word still ends at a blank, so Ctrl+⌫ at the start of a line takes the line break and the word before it.
  - **A second key context, `Multiline`**, only on these fields (`LINES_CONTEXT`), holds the new keys, so ↑ and ↓ still reach the parents of a field of one line, such as a menu over its filter. Enter is bound in both, and of two bindings at one depth gpui runs the later first, so these come after the plain ones (a test holds it).
  - **A caret at a wrap belongs to the next row** (`Rows::row_of`). gpui's `position_for_index` draws it at the end of the row before, and a field with vertical moves cannot live with that: ↓ onto the start of a row would seem not to move and the next ↓ would go nowhere, and Home on a row would jump to the row above. Keeping which side it is on (an affinity) was the other way, and more state for one case; so End and a click past a row's end stop before the row's last grapheme (`Row::last_caret`), usually the blank it wrapped at.
  - **It grows with its rows up to the limit, then scrolls inside itself**, clipped to its box, with a thumb in the box's padding (the wheel and the caret move it; it cannot be dragged). The scroll is the field's own (`View::scroll_top`) rather than an `overflow_y_scroll` around the element, for two reasons found in gpui 0.2.2's `paint_scroll_listener`: it never stops the wheel, so the sheet would scroll along with the field; and a handle's new offset only applies to the next frame, so the caret would be out of view for one. At its top or bottom the field lets the wheel go on to what scrolls around it. A drag selection follows the pointer past the box (a `MouseMoveEvent` of its own: gpui's `on_mouse_move` only fires while hovered), one step per mouse move, as the TUI's does, with no timer.
  - **`inside(scroller)` names the `ScrollHandle` of the form around a field.** gpui's divs do not follow a caret (only its `List` honours `request_autoscroll`), so a field growing at the bottom of a form typed out of sight, and Tab went to fields below the fold. When the caret moves or the field takes the focus, the field moves that scroller by what it takes to show the caret, in the next frame (`request_animation_frame`), which cannot be seen. It works for a field of any shape; only the flow editor passes it so far.
  - **An offset is put back on the text before it is used** (`floor_char_boundary` in `move_to` and `select_to`): hits and vertical moves read the layout of the last frame, and two keys can land before the next one, so the offset may be past a text that just got shorter or inside a character. A masked field's bullets have other offsets than its text: a click past the end of a typed secret gave an offset past the text, and the next key closed the window; its caret is still drawn off, as it was.
  - A tab or a carriage return in the text, from a prompt written by hand, is drawn as a space of the same length (`shown_without_controls`), so offsets hold, the text itself stays as it was and an untouched flow saves unchanged. `set_text` leaves the caret at the start, so a long prompt opens at its top, where a field of one line leaves it at the end.
  - **A selection is drawn only in the field that has the focus**, as the caret is (every field): with several large fields on one form, a selection left in one looked as if it would take what is typed in another.
  - Left out: undo, as in every field here; Page Up and Page Down; dragging the thumb.
  - Checked live on 2026-11-06 (debug build, gpui 0.2.2, cornercase 0.13.1, Linux x86_64 under Xvfb with lavapipe) in the flow editor: a prompt of 30 lines and the wrapped paragraphs of a built-in's; Enter, ⇧Enter, Ctrl+Enter, a click, a click past a row's end, ↑ ↓ keeping the column through short lines, Home, End, Ctrl+Home, Ctrl+End, ⇧ with each, Ctrl+C and Ctrl+V of three lines; the wheel over a full field moving it and not the form, then the form once the field is at its end; the caret, typing and Tab moving the form; a drag past the field's bottom; an empty field taking all those keys; and in Settings, a click past a typed token and a key, which closed the build before this (`end byte index 15 is out of bounds`). Not checked: macOS's keys and input method, Windows.
- **A text that can hold line breaks is clamped by its height** (`ui::clamped`: as many lines as asked, the rest hidden), not with gpui's `line_clamp`, which in gpui 0.2.2 counts only the lines it wraps. A text's own line breaks did not count, so a collapsed message holding a list showed every item and a run's task every line; and once the count was spent, the lines left were no longer wrapped but ran on in one row, which the clamp's own hidden overflow cut at the edge, mid-word. Cut by height, the text wraps as when shown whole and stops between two lines. Titles, which hold no line breaks, keep `line_clamp`: with `text_ellipsis` a cut title ends in an ellipsis, which a cut by height cannot draw. Checked live on 2026-10-31 with a fake flow run's task and messages (lists, blank lines, a long paragraph), expanded and collapsed.
- **A text kept to one line is drawn by `ui::one_line`**, an element of its own, and ends in "…" where its box ends. It measures the whole line, takes the width its box gives it, and cuts the text only when painting, keeping its highlights (a search's match, a file's colours) up to the cut; its narrowest width is nothing, so a full row shrinks it rather than the figures beside it. Line breaks and tabs read as spaces. gpui 0.2.2's own ways both failed. `truncate()` (`whitespace_nowrap` with `text_ellipsis`) keeps a text's first measure, taken at its full width before its box has one, so the sidebar's names, the status bar, Changes and Files clipped long texts mid-letter with no ellipsis; `clippy.toml` disallows it. `line_clamp(1)` with `text_ellipsis` measures again at each new width but cuts the text's styled runs in place, so the next measure in the same frame shaped the text with runs that no longer fit it: the window crashed (`not a char boundary`) on Search's "In sessions" results on 2026-10-31. The two- and three-line titles of Issues still take that cut, so they share the risk. Checked live on 2026-10-31 at 700, 980 and 1280 px wide: the sidebar, the status bar, Changes, Files (tree, viewer, search), Search (names and sessions, with matches), Processes, Ports and the server dialog. **A box that takes its width from the text must be a flex container** (`.flex()`, as the Files panel's `ellipsis`); a box with a share of its row (`flex_1`, a list row's full width) can stay a block. In a block box sized by the text, the text was left 0 px wide although the box had its width, so the Files viewer's title and tree header showed no names (found later on 2026-10-31 by logging the element's layout), nor did the Changes panel's open file (its file list's names, in the same kind of box, happened to show), nor, on 2026-11-01, the names in the Flows sheet's lists (`design/flows.md`): taffy 0.9 also lays a block box's children out while measuring the box at its narrowest, where this text measures nothing, and when the box then ends at a width its cache already holds a final layout for (the text fits, so the box is as wide as before), taffy reuses that layout without laying the text out again. So only a text that fits disappears: one cut to a narrower width gets a new layout and draws, which is why a long flow name cut beside its tags showed while the short names beside it did not. A flex container measured for its size lays nothing out. Whether a block box is hit depends on the order taffy measures the tree in (a run member's branch and the import check's agents, in such boxes, draw), so follow the rule rather than what shows today.
- **Selecting in a text that is no field** (`ui/selection.rs`, 2026-11-06): the Files viewer and the Changes diff share one `Selection<S>`, over whatever names a line there (a line number, a hunk's line), one `Press<S>` for what a press, a drag and a release do, and `overlay`, which paints a range over a line's styles. They are plain and tested without a window. `ui/selection/pointer.rs` holds the rest: `Selecting<S>` in each panel, `Laid<S>` (the rows of the last frame, for hit tests, written as they are laid out, read between frames), `layer` (a last child of the body that listens to the pointer and places the floating bar) and `action` and `action_bar`, the small buttons a hunk's header and the bar share. A panel implements `Selects` for the few things that differ. `ui::one_line` reports what it laid out through `on_laid`, since only it knows where it cut; the rest of its callers pay nothing. `ui/selection/code.rs` holds the code cell both panels draw, wrapped or cut (`Fit`, `code_cell`, the setting's button, `design/files-panel.md`).
- **Markdown** (`ui/markdown.rs` reads it, `ui/markdown/text.rs` draws it): the Issues sheet's bodies and comments (`design/issues.md`), a Recap (`design/recap.md`) and the notes of both update dialogs, cornercase's and the window's own (`design/notifications.md`, `design/self-update.md`), are one Markdown, so they read alike. The two files were Issues', and Recap took them second; they moved here on 2026-11-09, when the update dialogs became the third user, whose notes showed as raw Markdown (`**`, backticks and `- `) line by line. cornercase's own window draws those notes as Markdown too. It is a small reader, enough to read issue bodies and comments, a Recap and release notes as formatted text (headings, setext headings, paragraphs, lists, task boxes, quotes, fenced and indented code, tables, rules, emphasis, inline code, links, images as `[image: alt]`, autolinks, bare URLs), not a full CommonMark parser: unknown syntax stays as its text. HTML comments are dropped, `<br>` becomes a space and other tags vanish. `_` does not open emphasis inside a word, for snake_case; an opening marker is kept as text until it is closed, so a lone `*` stays. A bare URL leaves trailing punctuation out. **Runs, not nested marks**: gpui's text highlights cannot overlap, so `Inline::runs` cuts the marks into sorted ranges, each with every mark that covers it (nested emphasis, a bold link). Code is drawn in the terminal's font; a code block is one text (a div per line cost a layout node each), keeps blank lines' height and turns tabs into four spaces. A link opens its address, unless the caller gives its own `OnLink` (Recap's goes to what an id names; the update dialogs' opens only web addresses, `design/notifications.md`). Checked live on 2026-11-09 in both update dialogs: a fake release's heading, bold, italic, struck text, inline code, a link, nested and numbered items, a quote and a code block, and cornercase 0.13.20's real notes.
- **`input_box` is a flex column** (2026-10-31): a block box laid out as a flex item lays its children out at their narrowest in gpui 0.2.2 (taffy 0.9, the same trap as the block box under "A text kept to one line"), so a field's inner row (the search icon, the text, a clear button) was as narrow as the icon: the clear button was drawn over the text, and Settings' Save and Revert inside a field would have been too. As a flex column the row stretches to the box. The same holds for any wrapper of a full-width row inside a flex column: Settings' navigation stacks its rows in flex columns, not in plain boxes, or the selected row's tint and the search field hugged their text.
- **Hover cannot recolour text** in gpui 0.2.2: text is shaped with its colour while the element is laid out, and hover styles are only known when it is painted (a group's hover is even pushed only during paint), so `hover(|s| s.text_color(…))` and `group_hover` change backgrounds and icons (SVGs are tinted at paint) but leave text as it was. For the same reason they cannot change the layout: the layout is computed without hitboxes, so a size or margin set under hover is ignored; what must make room on hover keeps the hovered element in its state (`on_hover`), as the sidebar's rows do (`design/sidebar.md`). Light text on the cobalt pill hid it, since `text` and `on_brand` are nearly the same white; a faint note stayed faint on cobalt. A menu that recolours text on hover keeps the hovered row in its state (`on_hover`) and draws every colour from it, as Settings' choice popover does, where the mouse and the arrows share one highlight. Checked in gpui's source (`Interactivity::paint` pushes `GroupHitboxes`; `compute_style` applies hover only with a hitbox) and live on 2026-10-31.
- **Dialogs** (`dialogs.rs`) share `frame`, `cancel_and` and `show` (open and focus), and their fields sit in `ui::boxed`. `frame` has no height of its own, so a dialog whose body can outgrow the window scrolls it within `body_height` (the window's height less 240, from 200 to 560 px), leaving the title and the buttons in view: the pull request dialog, the Context dialog and a flow's start dialog, whose body from an issue passed an 800 px window once it gained the task (2026-11-01). Anything that cannot be undone asks first through `confirm(Question::new(title, message, button, command), …)`, which runs the command with `Store::cmd` on enter or the danger button. No caller needed `--view` (they pass ids, and `--yes` where the command asks), so the dialog runs the command as given and takes no flag for it. A caller that must know the answer (the Changes panel, to read a file again when cornercase refuses a stale discard) adds `on_reply`: the command then goes through the same queue with `store::queued`, and its error reaches the caller instead of a toast. A question that must say more than a sentence, or offer a choice with what it risks (the Worktrees sheet's, `design/worktrees.md`), adds `body`, scrolled within `body_height`, and `Tick`: a box that redraws the body, relabels the button and runs its own closure, so the answer stays one button and one place that asks, rather than a dialog of its own per caller.
- **The look described here is cornercase dark, the default theme** (`design/theme.md`): the terminal's palette, the chrome's colours, the glass's opacities and the shapes below are the values of its preset, and a person can change any of them. The reasons stay here.
- **The terminal's palette is Tokyo Night**, the dark theme cornercase's own fixtures use: the same 16 ANSI colours (the bright ones equal the normal ones, except bright black, and bright white is the foreground) are given to cornercase with `theme -`, with the xterm 256-colour cube and grey ramp built from them, so programs pick a look that matches what the window draws. A pane's program can override the palette, foreground, background and cursor; `Painter` applies its overrides first.
- **The chrome takes usecornercase.dev's colours** (its dark theme, read from the site's stylesheet on 2026-10-23), so the site, the TUI and this window draw one brand (cornercase's `design/website.md`, "The brand"): neutral greys for the ground and surfaces (`glass` `#0b0c0e`, cards `#15171b`, `raised` `#1d2025`), four greys for text (`text`, `soft`, `muted`, `faint`: `#eceef1`, `#b6bcc4`, `#8b929b`, `#6b727c`), cobalt `#005fff` (xterm colour 27, the brand's one accent) for fills, bars and focus, its ink `#74a3ff` (`accent`) for accent text and icons, and the site's status colours: yellow working, orange waiting, red failed, green done. The terminal keeps Tokyo Night, as the site's own terminal pictures do. Placeholders take the third grey and text fields a darker edge, as the site's fields do for contrast.
- **Icons are [Lucide](https://lucide.dev) 0.460.0 SVGs (ISC, `assets/icons/LICENSE`)** with the stroke thinned from 2 to 1.75, closer to SF Symbols at 14–18 px. SF Symbols' licence allows them only through Apple's system APIs, which gpui 0.2.2 does not reach. They are embedded in the binary, so the app needs no files beside it; a new icon is a file in `assets/icons/` and a line in `Icon` (its variant, `ALL` and its group's match), and a test fails when two icons share a file. `play-filled` and `star-filled` are Lucide's `play` and `star` filled with `currentColor`: a start button and a default read better solid. The `status-*` icons are drawn here, not taken from Lucide.
- **A file's icon tells its type, as the TUI's does** (`ui/file_icons.rs`, asked for on 2026-10-30): the glyphs are the TUI's own, Seti UI's file-type icons and Nerd Fonts' folders, taken as SVGs from Nerd Fonts 3.5.1's `src/svgs` (MIT, `assets/file-icons/LICENSE`, which also lists the renames), and the table is the TUI's `ui/icons/kinds.rs` copied: a known name first (`Cargo.toml`, `Dockerfile`, `README.md`), then the extension, ignoring case, else a generic file. Each is tinted with the palette's ANSI colour the TUI gives it, so a type looks alike in both. They are filled glyphs drawn at 16 px, beside Lucide's outlines at 12–14, since Seti's glyphs sit inside their square with room around them. Rejected: Lucide's generic `file-code` and the like (they do not tell Rust from TypeScript) and full-colour sets such as Material Icon Theme (gpui 0.2.2 draws an `svg` as one tinted mask, and an `img` of an SVG would be a second path for icons; it would not match the TUI either). Keep the table in step with the TUI's when it changes.
- **The whole window is glass in layers** (the values below are cornercase dark's, the default theme; `design/theme.md` holds what a theme can change; asked for on 2026-10-26, after a translucent macOS app with a see-through sidebar and darker content): it is `Blurred`, and `Root` paints `glass` (the site's ground at 55 %) once, under everything, so the blurred desktop shows through the whole window; each surface is a further translucent layer on it, never an opaque block. Each layer adds opacity, so the panes' colour is worked out to look, over the ground, as Tokyo Night at `terminal_opacity()` (0.65, or `CORNERCASE_GPUI_OPACITY`, kept between 0.3 and 1) would over the desktop (`theme::over_ground`, exact since gpui 0.2.2 blends in the colours' own space, `BGRA8Unorm`). The terminal keeps the translucency that was asked for, but it cannot be more see-through than the ground: below 0.55 it shows the ground alone. The ground's 55 % keeps the chrome's faint text readable over a bright desktop (50 % lost the status bar's, checked by eye over a bright checkerboard). Painting the ground everywhere but under the panes was rejected: the corners outside a rounded pane would need paths, and where a path's edge meets a pane's, each covers only part of the edge pixels, which would leave a lighter seam (reasoned, not tried). The cards (`surface`, a lighter grey at 30 %: the rail's, the sidebar's, the dock) read lighter than the ground and stay see-through, as the reference's sidebar; the boxes inside a panel (`panel`) are white at 4 %, one more lighter layer. Lines and hovers are white at low alpha (`border`, `edge`, `hover`, `selected`), so they read the same over any backdrop.
- **Linux is opaque** (`theme::ground`, 2026-11-04): compositors there do not blur (KDE's Wayland can, but gpui 0.2.2 cannot tell whether it will), and X11 without a compositor has no transparency at all, so a see-through ground would show the desktop, sharp, under the text. The ground is the site's `#0b0c0e` at full strength, and every layer over it keeps its colour and alpha, so the cards, the boxes in panels and the panes still read as lighter layers. With nothing to see through, `over_ground` gives the wanted colour back as it is when the ground is opaque (its formula would divide by zero there), so a pane is Tokyo Night at `terminal_opacity()` over the ground: at the default 0.65 it looks as it does on a Mac over a dark desktop, and `CORNERCASE_GPUI_OPACITY=1` gives Tokyo Night at full strength; there is no floor at the ground's opacity, as there is on a Mac, since the ground hides nothing. Rejected: Tokyo Night at full strength by default (lighter than a Mac ever shows it, and the panes would stand out from the cards beside them). The window itself is still `Transparent` on Linux, for the margin and the rounded corners of the frame it draws (`design/window.md`), with the opaque ground painted inside them. **Windows is glass over acrylic** (asked for on 2026-11-04, once the window ran on a Windows 11 desktop): the Mac's ground at 55 % over Windows 11's acrylic backdrop, which blurs the desktop behind the window as a Mac's `Blurred` does, so the window reads as it does there (`theme::ground` takes whether the backdrop was granted; `design/window.md`). The backdrop is DWM's own (`DwmSetWindowAttribute(DWMWA_SYSTEMBACKDROP_TYPE)`, Windows 11 22H2 and later): it follows "Transparency effects", turns solid while the window is inactive, as Windows' own windows do, and moves with the window, and gpui's DirectComposition swap chain, premultiplied, lets it through where the ground is translucent. Where DWM refuses it (Windows 10, Windows 11 before 22H2) the ground is opaque, as on Linux, since nothing would be behind it. Rejected: gpui's `Blurred`, `SetWindowCompositionAttribute`'s undocumented acrylic accent, widely reported to make a window lag behind the pointer while it moves or resizes, deaf to "Transparency effects" and blurred while inactive; Mica (`DWMSBT_MAINWINDOW`), which tints with the wallpaper and shows nothing of the windows behind, so it reads flat beside a Mac's glass. Checked on 2026-11-04 on Windows 11 build 26200: DWM reports the window's backdrop as acrylic in dark mode.
- **Floating cards stay nearly opaque** (`ui/glass.rs` `card(radius)`: sheets, dialogs, menus, toasts, at 88 to 91 %; `popover` for tooltips): gpui 0.2.2 blurs only the desktop behind the window, not the window's own content, so a more see-through card would show the text under it, unblurred. At about 90 % it shows only a hint of what is under it, enough to read as one more layer. Depth comes from the card instead: a sheen (lighter at the top), a light top edge fading from the left (inset by the radius, so it stays on the straight part), a 1 px line and a deep shadow, over the site's dimming veil (`#0a0b10` at 62 %). Translucent surfaces (panes, the dock, the rail's and the sidebar's cards) take no shadow: gpui draws a shadow under the whole element, so it would darken them from inside.
- **Rounded corners and more air, as macOS and iOS draw them** (asked for on 2026-10-23; the site's square corners were used until then). One scale, `theme::radius`: `CHIP` (5) for tags, counters, key caps, checkboxes and a row's buttons; `CONTROL` (8) for buttons, fields, rows, tabs, menu entries and the rail's icons; `CARD` (12) for the floating surfaces (the rail's and the sidebar's cards, the panes, the dock, menus, toasts and the boxes inside panels); `SHEET` (16) for sheets and dialogs. Switches, bars, dots and swatches are capsules or circles. A shape inside another takes the outer radius less the space between them (a segment in its track, an entry in its menu), so the curves stay parallel. The spacing grew with it: rows are 4 to 6 px taller, panels sit 12 to 16 px in from their edges, and 8 px (`GAP`) separate the floating surfaces from each other and from the window's edges. Code and diff lines keep square, full-width bands. gpui 0.2.2 clips a child to a rectangle, not to its parent's rounded shape, so a child that paints a background into a corner rounds that corner itself (the Files viewer, the Settings page list, the queue's form, a table's header row).
- **Cobalt marks what is chosen, without bars** (`ui/glass.rs`): a selected row is a rounded cobalt tint (`lit`), as macOS fills a selected sidebar row; the shown tab and segment are a lighter rounded fill, as the system's segmented controls; the highlighted menu entry is a cobalt pill. The 2 px glowing bars and underlines they had went with the square shapes. Primary buttons, checked boxes and switches stay a cobalt gradient with a soft glow (`cobalt`, `glow`); a focused field takes a 3 px cobalt ring (`ring`), as macOS draws focus; the shown panel's rail icon is tinted, without a glow; a cobalt wash lights the top of the rail's and the sidebar's cards. The site draws no glows or glass; this window does because it is a native window over the desktop, where translucency is the platform's look and depth tells what floats from what is docked. The colours and the mark stay the site's.
- **The mark** (`ui/brand.rs`) is the site's corner and cursor on its 12-unit grid, drawn with `div`s: small beside the wordmark in the title row, right of the traffic lights on a Mac and in their corner, over the rail, on Linux and Windows (`design/sidebar.md`), and large in the terminal's place while there is no terminal to show.
- **Widgets that measure a track** (`ui/slider.rs`, `ui/colour_picker.rs`) read its bounds from `ui/track.rs`, a thread-local map a canvas fills on every frame, since a mouse-down handler has no bounds. It holds one entry per fixed id (the five sliders, the three picker parts), so it never grows.
- **Every border between two parts can be dragged** (`ui/split.rs`): the sidebar's and the dock's (`design/window.md`), the list columns of Issues and Flows, the Settings page list, the queue's form, the Changes file list (`design/changes-panel.md`) and the terminal's dividers (`design/terminal.md`). A `Split` holds the size chosen by a drag, none until then so the default applies, within its limits and always leaving room for the other side; a double click on the border goes back to the default, as a double click evens a terminal split. Sizes last for the session, as the zoom does: they are not saved.
- **A split's handle is an invisible 8 px strip centred on the border** (a card's edge, or the line between a list and its page), with the resize cursor and nothing drawn on hover: gpui has no hover delay, so a highlight would flash whenever the pointer crosses a border. It is drawn after both sides, in their container at the line's offset, and `occlude`s them, so a press on its half over the terminal cannot start a selection there. Inside one side it would lie under the other, which is drawn later; `deferred` would draw it over sheets and dialogs too. The drag is gpui's `on_drag` with a blank preview, and the container's `on_drag_move`, called for every move of that drag wherever the pointer is, measures from the container's fixed edge, so the side follows the pointer. Each split has its own drag type: a docked panel and a sheet are drawn together, and both would follow one drag of a shared type.
- **A hover style is set once per element**: gpui 0.2.2 asserts in debug builds when `hover` is called twice, so the builders take what decides it (`row_base(target, lit)`, the menu row's danger flag) and a lit row does not hover.
- **`FONT_FAMILY`** lives in `theme.rs`, not `app.rs`, so panels need not import the window (`design/code-layout.md`).
- **Fonts on Linux** (`theme/fonts.rs`, 2026-11-04): a Mac draws Menlo and the system font (`.SystemUIFont`). Linux has neither: gpui 0.2.2 maps `.SystemUIFont` to IBM Plex Sans, rarely installed, and a family it cannot find falls back to its own list, whose first installed member is a proportional sans (DejaVu Sans on Debian). The terminal's cell is measured from that font's "M", so a pane about 120 columns wide got 78, each glyph drawn on a too-wide grid. So the window chooses at start, from what is installed: for code, DejaVu Sans Mono first (Menlo was made from it, so the grid and the glyphs match a Mac's), then Adwaita Mono (GNOME 48), Noto Sans Mono (Fedora, KDE), Ubuntu Mono and Ubuntu Sans Mono, Liberation Mono, JetBrains Mono, Source Code Pro, Noto Mono, then any family with a word ending in "Mono" (Nimbus Mono PS, GNU FreeFont's FreeMono; not Monotype Corsiva, nor gpui's own `.ZedMono`); for the chrome, the desktops' own sans first (Ubuntu Sans, Ubuntu, Adwaita Sans, Cantarell), then Noto Sans (KDE's, and on most systems), Inter, DejaVu Sans, Liberation Sans, else gpui's own fallbacks. **With no monospace font at all** the terminal takes the chrome's font, measured as any other, and a toast at start says to install DejaVu Sans Mono or Noto Sans Mono: the name used to stay DejaVu Sans Mono unchecked, which gpui drew in its first fallback with no word why (found in review, 2026-11-04). **gpui 0.2.2 panics when neither a family nor any of its own fallbacks loads** (`resolve_font`; its list is Lilex, IBM Plex Sans, Helvetica, Segoe UI, Ubuntu, Adwaita Sans, Cantarell, Noto Sans, DejaVu Sans, Arial), and it has no lookup that fails softly, so asking it whether DejaVu Sans Mono was installed aborted the start on a system with only other fonts (only Liberation, URW's or GNU FreeFont, as a minimal Arch can be): reproduced on 2026-11-04 with only URW's fonts left. The probe now resolves only names `all_font_names` lists and catches that panic, with the panic hook silenced around it (`quietly`); it first asks whether gpui can fall back at all (it resolves `.SystemUIFont`), and where it cannot, the chrome takes an installed family (a family with a "Sans" word first, then any that is not monospace, then the monospace one), so nothing names a font gpui cannot load. The panic cannot be avoided: `TextSystem::resolve_font` is gpui 0.2.2's only public lookup (`font_id` is private and the platform's text system crate-private, `all_font_names` mixes the fallbacks in, `get_font_for_id` knows only fonts already resolved). The panic hook is the whole process's, so a panic on another thread while it is silenced would print nothing: the probes therefore run in `main`, after `Application::new` and before the app runs (`theme::settle_fonts`), when no code of this app runs on another thread and gpui's own threads are idle (its workers and timer have no task yet, and X11's clipboard thread owns no selection), and each silence lasts one probe (CodeRabbit's review, 2026-11-04; they had run in `Root::new`, with the window open). **Where no font loads at all** (none installed, or only Type 1 or bitmap fonts, which gpui does not read), gpui panics at the first text it lays out, so the window could never say so: the start aborted with gpui's own `failed to resolve font '.SystemUIFont' or any of the fallbacks` before the toast could show. Now the start stops before any window opens, with `cornercase-gpui: no font that can draw text was found: install a TrueType or OpenType font, such as DejaVu Sans Mono or Noto Sans Mono` on standard error and status 1. Limit: started from a launcher, standard error goes to the session's log, so the launcher seems to do nothing; a desktop with no font cannot draw its own text either. `FONT_FAMILY` and `UI_FAMILY` are handles (`theme::Family`) that turn into the chosen name, so the call sites read the same on both platforms; `Root`, tooltips (`glass::popover`), drag previews (`glass::dragged`) and the pane move's caption name `UI_FAMILY`, since gpui gives a tooltip or a drag preview the default family rather than the window's. Whether a family is installed is asked of gpui itself (it resolves the name, then says which family it resolved to): `all_font_names` also lists gpui's fallbacks whether they are installed or not, and gpui reads the fonts fontconfig points at, so `fc-list` could name fonts gpui does not load. Rejected: reading the desktop's chosen font (GNOME's `font-name`, KDE's `kdeglobals`, the settings portal), one source per desktop and a process or a D-Bus call before the first frame; bundling a font (Zed bundles its own), megabytes for a look a Mac does not share. Checked live on 2026-11-04 in Debian trixie (DejaVu, Noto and JetBrains Mono installed): DejaVu Sans Mono and Noto Sans are chosen, the pane that measured 78 columns measures 118, `W`, `i` and digits keep their columns, and the semibold headers and bold wordmark have their weights (the fallback had drawn them regular). Checked again on 2026-11-04 with fonts moved out of `/usr/share/fonts`: with only URW's left the previous build aborted at start (`failed to resolve font 'DejaVu Sans Mono' or any of the fallbacks`) and this one opened with Nimbus Mono PS and Nimbus Sans, 118 columns, `iiiii` and `WWWWW` the same width; with no monospace font the terminal drew in Noto Sans at 78 columns and the toast showed. Checked on 2026-11-04 too, after the probes moved to `main`: with no font at all, and with only URW's Type 1 fonts (`fc-list` listed 70, gpui loaded none), the previous build aborted with gpui's panic (status 101) and this one printed the line above and exited 1 without a window; with only URW's OpenType fonts it opened as before, at 118 columns; with only Noto Sans the toast about the missing monospace font still showed.
- **Fonts on Windows** (`theme/fonts.rs`, 2026-11-04): the same choice at start, from Windows' own fonts: Cascadia Mono for the terminal (Windows 11's and Windows Terminal's), else Consolas (every Windows since Vista), Lucida Console or Courier New, then any installed family named "Mono"; Segoe UI for the chrome (what gpui 0.2.2 resolves `.SystemUIFont` to there), else Tahoma. Rejected: Segoe UI Variable, Windows 11's, a variable font whose named instances DirectWrite lists under family names gpui does not resolve the same way everywhere. Checked on the Windows runner (`design/windows.md`): the terminal kept its columns and the chrome drew.
- **Motion uses gpui 0.2.2's own `with_animation`** (`ui/motion.rs`), not [gpui-motion](https://github.com/1bye/gpui-motion) (`gpui-ce-motion`): that crate is built on `gpui-ce`, a fork whose element types do not mix with Zed's `gpui`, so adopting it would mean moving the whole app to the fork (checked 2026-10-23, gpui-ce-motion 0.4.0). gpui's tweens are enough for what the window needs. Springs that can be interrupted would need that crate or a port of its math.
- **What moves**: sheets and dialogs rise 14 and 10 px and fade in over a fading backdrop; the dock slides 24 px in from the right; toasts slide in from the right; context menus drop 4 px quickly (`Way::Pop`); the bell's flash fades out; a row Settings lands on holds a cobalt tint, then fades (`design/settings.md`); the connection dot and the mark's cursor pulse while connecting. Entering takes 180 ms ease-out, leaving 120 ms ease-in, so closing feels quicker than opening.
- **What takes a while turns a spinner** (asked for on 2026-10-30, after removing a worktree said nothing for seconds): `ui::spinner` is Lucide's `loader-circle` turned once every 900 ms by `motion::spin`, since gpui 0.2.2 rotates only `svg` elements (`Transformation`). It comes in three shapes: `busy_button` takes the place of the button that started the work, in the same tone, with what it does (`Removing…`, `Installing…`) and no click; `busy` is a small line beside what it concerns (`saving…`, `measuring`); `loading` is a panel's note while its first answer comes. A row whose work runs dims, so the rest of the list stays readable. They replace the `…`, `◐` and plain `Loading…` texts, which did not say that anything moved. The status bar names the newest job (`design/connection.md`).
- **An agent's status is an icon of the window's own, not the TUI's glyph** (asked for on 2026-10-30: the `◐ ! ✓ ✗ ● ○` the TUI draws looked plain here). `ui::status_badge` gives a status its icon and colour, and `ui::badge` draws it wherever a status shows (the tab bar, the sidebar's rows, Search, TODO). One family of circles: idle is a ring; working is the same ring, faint, with a bright dot and a fading tail orbiting it; waiting, failed and done, which ask for you, are solid discs with `!`, `×` and `✓` cut out (an SVG `mask`, so the row shows through); pending is a dot in a ring. gpui renders an SVG to an alpha mask tinted with the text colour, so the tail's dots fade by opacity. The orbit turns smoothly, a turn in 1.2 s, at the angle the wall clock gives when the window draws, so every orbit points the same way; how often it draws is under "A working agent's orbit" below.
- **Leaving is kept by `Root`**: gpui draws only what the state holds, so closing would cut the element at once. `Leaving<T>` remembers the closed sheet, dialog or dock for `LEAVE`, and `Root` draws it animating out under a transparent layer that takes the clicks, so a second click cannot press a button that is going away (a dialog's "Delete", say). Reopening cancels the leave, and a timer from an older close never ends a newer one. A leaving dock is drawn over the terminal, so the terminal takes its width back at once.
- **Nothing animates forever while idle**: a repeating animation asks for a frame on every frame, which redraws the whole window, terminal included. Only the "connecting…" dot and the mark's cursor in the terminal's place pulse, and only while connecting (not while disconnected, which can last). A spinner turns only while its command runs, and stops with it.
- **A working agent's orbit draws about 30 times a second, on the display's frames** (asked for on 2026-10-31: the working animation was not smooth). It is the one thing that moves for long, so it does not use `with_animation`, which draws on every display frame. While some agent works (`Session::anyone_working`), `motion::Beat` follows the display's frames (`on_next_frame`) and redraws `Root` on the frame nearest a thirtieth of a second after the window last drew: every 4th frame at 120 Hz, every 2nd at 60, so each position stays on screen as long as the others. A window that already draws for another reason (a pane's output, a spinner) gets no extra frame. It rests as soon as a frame drew no orbit (`motion::orbits_drawn`: the working agents are folded away or out of sight), and a covered or minimised window draws nothing at all, since gpui stops its display link.
  - Why the old orbit stuttered: it stepped 30° ten times a second (its head jumped 2 points), and the steps came from a wall-clock timer, which fires anywhere between two display frames: 30 to 40 % of them showed a 120 Hz frame early or late, so a step lasted 92 to 108 ms instead of 100. Now 98 % of the orbit's frames are exactly 4 display frames apart (the rest are other redraws, or the measure's own jitter), and its head moves 0.7 point a frame. Every other moving thing already drew on every display frame: spinners, the connecting pulse, sheets and toasts while they come and go, the Flows diagram's one-shot rise and spark. Flows draws a working member as a still dot, so nothing else repeats.
  - Measured on 2026-10-31 (release build, cornercase 0.12.230, MacBook Pro M5 at 120 Hz, a 1280×800 window, agents faked working through a `CORNERCASE_BIN` wrapper that rewrites `view`'s statuses; CPU of the app over 20 s, then roughly what WindowServer added; noisy, since other builds shared the machine). With a terminal full of text: the old steps 5.5 to 6.6 % with one agent working and 6.9 % with four; now 10.5 to 14.7 % and 16.9 % (+5 to 10 %); 0.5 % with none working, and 0.45 % with one working out of sight, neither drawing a frame. Four cost more than one because the sidebar holds more rows to lay out: the price is the window's frame (3 to 5 ms here, mostly gpui laying the whole tree out again and painting the terminal), not the badges. Options compared back to back with a nearly empty terminal: the old steps 5.2 %; 30 a second on display frames 8 to 11 % (+5 to 10 %); 60 a second 17 to 20 % (+15 to 20 %); every display frame (120) 25 % (+40 %); a wall-clock timer at 30 a second about 5.7 %, but 1 to 23 % of its frames landed a display frame off, and 30 % at 60 a second (12.3 %).
  - Rejected: gpui's animation scoped to the badges (a frame asked from inside a view redraws every view above it, and `Root` always, so it costs a whole window at the display's rate, the 120 row); a faster wall-clock timer (uneven, above); 60 a second (twice the cost of 30, for a 12 px icon whose dots already move under a point a frame at 30); slowing the orbit while the window is in the background (a glance at it would see the old stutter); a cheaper frame through cached views (`Root` draws the badges itself, so the window would have to be split into cached views, the terminal first, each told of every change it draws; WindowServer's share of each frame would stay). That last one is the way to make every frame cheaper, spinners and scrolling included, if the cost matters later.
  - Not measured: a covered or minimised window. gpui 0.2.2 stops a window's display link when macOS says it is occluded, so no display frame calls the beat (read in its source).
- **Moving uses relative offsets** (`relative().left/top`), since gpui 0.2.2 has no transforms for `div`s: layout does not change, so the terminal is not resized while something moves. Nothing scales. Hover colours change at once, since gpui has no transitions for styles.
- **macOS's "Reduce motion" is not read**: gpui 0.2.2 does not expose it.
