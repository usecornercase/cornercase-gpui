# Widgets

Code: `src/ui/`, `src/app/part.rs`, `src/app/status.rs`, `src/app/status/`, `src/app/revised.rs`, `src/theme.rs`, `src/dialogs.rs`

- **One set of building blocks** (`ui/mod.rs`) every panel uses, so the window reads as one thing: buttons (plain, primary for a form's main action, danger for what cannot be undone, icon buttons for one glyph, and an icon beside a label in any of the three tones), rows, sections, notes, fields, input boxes, search fields, checkboxes, segments (`icon_segment` with its picture), titles, bars, one-line texts, the undo bar (a removal's text and its Undo button, which the TODO and Queue panels show for a few seconds instead of asking first) and the emblem (a panel's icon in a cobalt disc, at the top of a page that says what the panel is for when it has nothing to show: Issues without a tracker, the empty Queue and Machines; `emblem_page` lays it out with its heading, `emblem_line` a sentence under them). They return gpui `Div`s the caller finishes with `.on_click(…)`.
- **Signs** (`ui/signs.rs`): `copy_button` (a message's small copy icon: Flows' messages, the Queue's conversation cards), chips (`accent_chip` for what is chosen, `quiet_chip` for a fact, `tinted_chip` in a status colour), the status `dot` (filled in a colour, or a faint ring for unknown), `error_line`, `warning_line` and `done_line` (an icon and a sentence), `callout` (a tinted card with an alert, a title and a body) and `row_action` (a faint icon with a tooltip, in a row's fixed slot, red on hover when it removes) with `resting_action` (its place while it cannot be pressed), and `field_action` (a small icon button inside a field, with a tooltip: Settings' search clear, a setting's Save and Revert). The Accounts sheet drew them first; they moved here on 2026-10-31 when Settings took the same look, so both sheets share one set. `resting_button` is a button shown before it can be pressed, dimmed and inert, so it does not appear from nowhere (Settings' Connect until a token is typed).
- **Pop-ups** (`ui/menu.rs`): a dropdown (the value, a chevron, a cobalt edge while open) that opens a menu under it on the press, as macOS pop-up buttons do: a glass card holding the focus, its entries with a check on the value in use and a cobalt pill on the highlighted one, which the pointer and ↑ ↓ share (kept in the owner's state, since hover cannot recolour text, below), Enter choosing and Escape closing only the menu. Settings' choices drew it first; its pieces moved here on 2026-11-02 when a flow's start dialog took it for its project (`design/flows.md`), so the two read alike. `ui/account_picker.rs` is the third, a whole widget since four forms use it (`design/accounts.md`). In those two a window-sized backdrop under the menu takes the press that closes it (`menu::backdrop`): that press does nothing else, as on macOS, the wheel cannot scroll a form from under the menu, and a dialog with both cannot have both open. Settings' still closes on the press its panel sees. Settings' fields with suggestions open the same popover under the field (`design/settings.md`).
- **`TextField` is adapted from gpui 0.2.2's own `input` example (Apache-2.0, `LICENSE-GPUI`)**: gpui has no text field. Text goes through macOS's input method (`EntityInputHandler`), so dead keys, ⌥ characters and composition (marked text, underlined) work. Pasted newlines become spaces in a field of one line, a Windows line end (`\r\n`) one space and a lone `\r` one too (`one_line`): X11's primary selection hands CRLF text over as it is, and the field had kept its `\r` (found in review, 2026-11-04). `masked()` shows a bullet per grapheme for secrets and hands the input method nothing (below). Enter and escape are actions in the `TextField` key context, emitted as `Submit` and `Cancel`; every edit emits `Changed`. `clears_on_escape()` makes escape clear the text instead, and pass on when it is already empty; `in_tab_order()` makes the field a tab stop (`design/terminal.md`). `reverts_on_escape()` makes a field remember the value it was saved with (`keep_saved`, which also fills an unedited field with a newer value): escape puts that value back when the text differs (and emits `Cancel`), and passes on to `Root` when it does not, so a settings field never keeps the sheet from closing; `edited()` tells whether the text differs (2026-10-31, `design/settings.md`).
- **A text field's keys follow the platform** (`text_field::bindings`): on macOS ⌘A, ⌘C, ⌘X, ⌘V, ⌥⌫ and ⌘⌫ by word, ⌘← and ⌘→ to the ends, ⌃⌘Space the character palette; on Linux GTK's, which are Windows' own too (`control_bindings`): Ctrl+A, Ctrl+C, Ctrl+X, Ctrl+V, Ctrl+⌫ and Ctrl+Delete by word, Ctrl+← and Ctrl+→ by word, Home and End, plus Ctrl+Shift+C and Ctrl+Shift+V, the window's copy and paste there (`design/terminal.md`, Keys on Linux), so the terminal's habit works in a field too. A word ends at a blank. The field has no undo, so Ctrl+Z does nothing. Moving by word was added for Linux, where GTK users expect it; macOS kept its keys (2026-11-04). Checked live on Linux (X11) on 2026-11-04 in the new workspace dialog: Ctrl+⌫, Ctrl+← twice, Ctrl+Delete, Ctrl+A with Ctrl+X, Ctrl+V and Ctrl+Shift+V each did what is listed.
- **`wraps()` makes a field a textarea in looks, not in content**: the text stays one line (Enter still submits, pasted newlines still become spaces), but it breaks into rows at the field's width and the field grows a row at a time, instead of running out of its box. The height is measured from the width at layout (`request_measured_layout`), the way gpui's own text element does it; clicks, the caret, the selection (one band per row) and the input method's rectangles follow the rows. Every field is drawn as `WrappedLine`s (`text_field/element.rs`), with no wrap width when it does not wrap, so every kind shares one path. A text set from outside (`set_text`) can hold line breaks: such a field draws them all, where it used to draw the first line and leave room for the rest (checked live on 2026-11-06 in the Queue's form, whose prompt was such a field until 2026-11-09). It is opt-in because a one-line field (filters, settings, names) should stay one row high. A wrapping field must not sit in a flex column that scrolls itself (`overflow_y_scroll` on the column): in the queue's form it was laid out at no width and drew one letter per row (2026-10-31). The scroll goes on a plain container around the column, as in the Issues start form, the queue's form and both columns of the flow editor. There is no ↑/↓ between rows and no inner scroll, which `multiline` adds: a very long text makes the field tall. Checked live on 2026-10-30 (gpui 0.2.2) in the TODO panel: typing, a selection across a wrap, a click on a middle row.
- **A field of one line clips to its box and scrolls sideways to keep its caret in view** (#166, #169, 2026-11-13). Before, only a multi-row field clipped: a one-line field painted its text from its left edge with no mask and no scroll, so a rename's old name ran over the tabs beside it (the field of a 140 px tab holding a 800-character name, its caret thousands of pixels out of view) and Plugins' Install placeholder ran under the buttons next to it. The scroll is `View::scroll_left`, computed in `settled` by `rows::sideways` (plain numbers, tested): the least scroll that shows the caret on every frame while the field has the focus (nothing but the caret moves a one-line field's scroll, so a text set under a focused field, a revert on Escape or a narrower box keep it in view too), never leaving room after the end of the text. A field without the focus shows its text from the start, as a browser's does, and the next focus reveals the caret; `set_text` starts the scroll over. An inline rename's box (`sidebar::rename_box`, shared by the tab and the sidebar's rows) stops the left press (`stop_propagation`) so that a press or a drag inside it reaches the field and neither the tab's click, which gave the focus back to the terminal, nor the tab's or row's drag starts (found in review on 2026-11-13; the same on `main`). Painting, the mouse mapping (`Layout::index_at`) and the input method's rectangles subtract it. The mask is the field's box exactly (a multi-row field keeps `clip()` with its caret margins, which would show a 2 px sliver of the glyph scrolled out on the left), and a selection dragged past the box follows the pointer (`follow_drag`, which only multi-row fields had). The placeholder is clipped too. A wrapping field grows instead and keeps 0. A field laid out at no width draws nothing since this clip (#189: see "A field in a row sits in a flex box" below). The TUI's rename is the precedent: its editor puts the cursor at the end with nothing selected and shows the part around it (`design/text-fields.md` upstream). So a rename opens with the caret at the end and the end of a long name in view, ⌘← (Home on Linux and Windows) shows the start, and ⌘A then typing replaces the name; selecting all on open, as the Finder does, was rejected since it would part every inline rename here from the TUI's. Checked live on 2026-11-13 (debug build of 0.1.73, gpui 0.2.2, cornercase 0.13.39, macOS 26.6.2, Apple silicon, a private server): a tab named with 817 characters at 1280 wide (the end shows with the caret, ⌘← shows the start, ⌘→ and `z` the end, Escape left the name, ⌘A, `short` and Return renamed it), a workspace named with 115 characters (the sidebar's field stays inside the row with its caret), and Plugins at 640 wide (the placeholder ends inside its field). After the review's fixes (same build): a press inside the scrolled tab field put the caret under the pointer and typing went in at it, a drag inside it selected text without lifting the tab (the window itself moved when the drag started 26 pt from the top: the title-bar band, #176), the names of 132 characters with no space and `api` (a short name) looked right, and at 640 wide the rename of the shown long tab showed the end with the caret and ⌘← the start. A drag inside a sidebar row's rename field selected text and moved no row, and Escape in Settings' Worktrees folder field holding a long saved value showed the value's end with the caret (checked after the second review). A press on the box's border, outside the text line, does nothing (it no longer gives the focus back to the terminal). The rename field of a tab that is not the shown one and sits at the strip's edge is cut by the strip, as before. Not checked: the input method's candidate window over a scrolled field, a dragged selection past the box's edge, Linux, Windows. A masked field's caret was off then (#177, below).
- **A masked field draws a bullet per grapheme, and every offset crosses one table** (#177, 2026-11-13). On 0.1.76 (the release), in Linear's token field in the window, a typed secret of 40 letters had its caret at about dot 14, ⇧→ ×6 from the start banded 2 dots, ⌘A banded about a third, and a dead key (´) closed the window: `panicked at gpui-0.2.2/src/platform/mac/text_system.rs:448`, "end byte index 41 is not a char boundary; it is inside '•'". The cause: the caret and bands took a content offset as an offset into the bullets (3 bytes each); a press did the reverse, so typing went in at character 3k; and composed text cut the shaping runs at the content's marked range, inside a bullet.
  - **Where**: `text_field/shown.rs`, `Shown`, built with the shown text in `shaping` and kept in `Layout`, whose rows are private. So the caret, the bands, presses and drags, the input method's rectangles and hits, the composed text's underline, the sideways scroll and the row moves all go through `to_shown`, `to_content`, `row_ends` and `runs`. A field that is not masked carries `Itself`, builds nothing and returns its argument. The cost is one grapheme walk per shaping where `chars().count()` was, then a binary search or an index per reader.
  - **Why a grapheme per bullet**: caret, ⌫ and ⌦ already move by extended grapheme, so each step is one bullet and a press cannot land inside a flag or a family. Native fields do not agree (GTK 3.24 and Firefox mask per character or code point, WebKit per UTF-16 unit; AppKit's secure field was not checked), so none settles it.
  - **The caret while composing** is read within the composed text (`composed_selection`): macOS's selection is relative to the text it sends, and `replace_and_mark_text_in_range` (gpui's example code) read it against the whole content, which put a masked caret before the underlined dot, and after a 4-byte character past the text. A plain field hid it, since an offset past its last glyph draws at the end.
  - **Several rows** (`masked().wraps()` or `multiline`): right by construction, since rows come from the bullets' layout and every offset crosses `Layout`; a line break is a bullet like any other. No such field exists and none was checked.
  - **Copy and cut do nothing in a masked field** (`shared`, which already kept it out of the primary selection), as secure fields in AppKit and GTK do; paste works. **Word moves and deletes go to the secret's ends**, so they tell nothing of its blanks. What a masked field hands the input method and macOS's secure event input are the next bullet (#188).
  - **Rejected**: caching the table on `TextField` (hits read the last frame's layout, which an edit makes older than the table); a mask of the same byte length as each character (no 1-byte bullet); mapping at each call site (one missed reader leaves the field half right).
  - **Checked** in a window on 2026-11-13 (macOS, cornercase 0.13.57, a debug build of 0.1.78 with gpui 0.2.2, private servers, made-up text, dark and light themes): the end and the caret with 40 and 120 letters, ← ⌘← ⌘→, ⇧← and ⇧→, ⌘A, one dot and one ← step for `ñ`, `€`, `😀`, flags, families and a decomposed `é`, ⌥⌫ (everything before the caret goes), ⌥← (not bound on macOS, does nothing), presses in the middle and past the end, a drag inside and past the box, a dead key (one underlined dot, then one plain dot, the window stays open), with the caret right after the underlined dot (seen again on the build with `composed_selection`: after `abc`, after two `😀`, at the end of a scrolled 40-letter secret, and in a plain field, which is as before), ⌘C and ⌘X (the clipboard's change count did not move, its contents were never read), and a plain field and a prompt as before. **Not checked**: Linux, Windows, ⌘V, an input method's candidate window, a masked field of several rows, a narrower window, AppKit's secure field. Tests: each `Shown` test is a table of offsets or cuts; taking the marked-range mapping out of `runs` fails both composed-text tests.
  - **Outside this change**: Settings' search field draws nothing, on 0.1.76 too (#189): see "A field in a row sits in a flex box" below.
- **A masked field hands the input method nothing, and on macOS keeps its keys from other programs while it holds them** (#188, 2026-11-13). Before, `text_for_range` answered with the real content, masked or not; on macOS gpui 0.2.2 calls it from `attributedSubstringForProposedRange:`, so the input method, and whatever it shows or logs, was handed the secret. Nothing turned on secure event input, so another process's event tap could read the keys.
  - **What it hands**: `None` for every range (`handed`, `text_field.rs`), the whole secret, a part, and the text being composed too; gpui then answers nil. A field that is not masked answers as before, the same text and the same actual range (`handed`'s two mappings are the ones the method used).
  - **Press-and-hold is off in a masked field** (`text_field/handler.rs`, a wrapper of gpui's `ElementInputHandler` that answers `apple_press_and_hold_enabled() == false` for a masked field; the trait method has no `EntityInputHandler` counterpart): with it on, the popup draws the held letter's variants over the field, which shows which letter of the secret is being typed, the one thing the screen would otherwise draw of it. With it off, a held key's repeats reach the field as the letter (`replace_text_in_range`), except a text of control characters only, which a masked field drops (an empty text, which deletes a pre-edit, still goes through): gpui gives Enter and Tab a `key_char` whatever the modifiers, and an unbound ⇧↩ or ⌥⇥ held would write line breaks or tabs into the token, where 0.1.80 wrote nothing. AppKit's secure field is reported to offer no popup either (second-hand: a 2016 cocoa-dev post, 1Password's forum; not read from a source). A plain field keeps its popup. Accepted cost: no accented letter by holding a key in a token (dead keys and ⌥ characters work; tokens are ASCII).
  - **What the other answers tell, and why they stay**: `selected_text_range` and `character_index_for_point` give offsets in UTF-16 units of the content, so the secret's length (the bullets on screen already show it in graphemes); `marked_text_range` says where the composition the input method gave sits; `bounds_for_range` gives the bullets' rectangles, which the screen shows. All four are needed: macOS's `selectedRange` and `markedRange`, the candidate window's place, a click in the composed text, X11's and Windows' caret spots; gpui sends keys to the input method first while a marked range is set. `unmark_text`, `replace_text_in_range` and `replace_and_mark_text_in_range` only take text in.
  - **Who asks, in gpui 0.2.2**: only macOS reads text (`attributedSubstringForProposedRange:`); `selectedRange`, `markedRange`, `firstRectForCharacterRange:` and `characterIndexForPoint:` are the others. X11, Wayland and Windows never call `text_for_range` (it is `allow(dead_code)` there) and read only the caret's place (`get_ime_area`, IMM32's composition and candidate windows) and the marked range; Wayland's `set_content_type` is always `Normal`, so a Wayland input method is never told a field is a password (gpui's limit). The leak was macOS's alone, and the change is inert elsewhere.
  - **AppKit and GTK** (read 2026-11-13, macOS 26.6.2): an `NSSecureTextField`'s editor, `NSSecureTextView`, answers `attributedSubstring(forProposedRange:)` with the real text, but its input context allows only Roman input sources (`allowedInputSourceLocales`), so no non-Roman input method runs in it, and it turns secure event input on. GTK's password entry hands the input method its display text, one invisible character per character (`gtk_entry_retrieve_surrounding_cb` on `gtk-3-24`, `gtk_text_retrieve_surrounding_cb` in GTK 4, both with the comment "does this even make sense when text is not visible?"). This follows GTK in never handing the real text and keeping input methods running, hands nothing instead of bullets, and follows AppKit in turning secure event input on. It does not follow AppKit's real-text answer, which is safe only with its Roman-only sources; restricting them is #203.
  - **Secure event input** (Carbon's `EnableSecureEventInput` and `DisableSecureEventInput`, not deprecated; TN2150): process-wide and counted, and any process holding it, in the background too, blocks every other process's event taps. `text_field/secure.rs`: `guarded(os, masked, focused, front)` is true only on macOS, for a masked field that is the focused element of the last frame, in a window that is key. A `Guard` takes one count when made and gives it back when dropped (`secure/carbon.rs`; `secure/no_carbon.rs` elsewhere), and the field makes or drops it only when the rule changes, so no path enables twice or leaves a count behind and no counter is shared. Three watchers, made in `render` (`SettingsPanel::field` has no `Window`) and dropped with the field: `on_focus` and `on_blur` (the field's focus as the frame's focus path has it; `is_focused` stays true for a field a closing sheet took away, since ⌘W and Escape leave `window.focus` alone) and `observe_window_activation` (called from AppKit's key-status callback at once, not at the next frame: a hidden window draws none).
  - **Each way out**: the focus moving, the sheet closing or its page changing (`on_blur`); the window losing the front, ⌘H, ⌘M, a system panel taking the key (the activation observer); the window closing or the app quitting (the field, then its `Guard`, drops); a crash (Apple's header: it is turned off when the process dies and nobody else holds it).
  - **Not covered**: the terminal's keys (a terminal's "secure keyboard entry" is a feature of its own, #202); another process's panel that takes the keys while this window stays key (Spotlight; TN2150's rule is the window's key status, as for AppKit's field). **Linux and Windows** have nothing to turn on for a window like this: Wayland keeps one client from reading another's keys by design, X11 has only a keyboard grab (xterm's Secure Keyboard) that gpui 0.2.2 does not expose, and Windows lets any process of the session see keys through a low-level hook that no call of an ordinary window turns off.
  - **Rejected**: handing bullets (they serve no input method, and a reconversion or transliteration of what it read would write bullets into the secret; GTK's own comment doubts it); leaving press-and-hold on (the popup draws the held letter's variants over the secret); handing only the marked text (leaks nothing new but no input method here asks, the terminal's handler answers `None` for every range and composes dead keys and ⌥ characters; the fallback if one is found that needs it); handing the real text (AppKit's, which is safe only with Roman-only sources gpui gives no way to ask for); not doing secure event input (gpui 0.2.2 has the hooks it needs); keeping it on for the sheet's life or the app's (TN2150 says never, and it breaks other apps' keys); deciding from paint each frame (a hidden window draws none); `is_focused` for "focused" (above); a process-wide counter (ownership balances each field's count); `IsSecureEventInputEnabled` to decide anything (it answers for every process: the app never calls it, and the check reads the registry through `ioreg`).
  - **Checked** in a window on 2026-11-13 (macOS 26.6.2, Spanish ISO layout, cornercase 0.13.57, a debug build of 0.1.82, gpui 0.2.2, a private server, made-up text; an instrumented build logged each handler method and its ranges, never the text, removed before the commit): `ioreg` named the window's pid while Linear's token field had the focus with the window in front, and nobody with it behind or after any way out. **Never asked, in any scene: `text_for_range`.** Dead key (´ then a): `replace_and_mark` of 2 bytes with the selection at 1, one underlined bullet with the caret after it, then one plain bullet. ⌥a: one bullet. `paste` of 17 made-up characters: 17 more bullets. Ways out, each with the field focused and the window in front: Tab (off), ⇧Tab (on), ⌘H (off) then `front` (on again), Escape (the field reverts, still on), Escape with the sheet closing (off), ⌘W (off), `kill` (off), `kill -KILL` (off). **Against the released 0.1.80** (the UI review): typing, a dead key, ⌥ characters, paste and composed text are pixel-identical in the token field, in a plain Settings field and in ⌘G's prompt. With press-and-hold off, a posted `hold` in the token field opens no popup and repeats the letter (where a posted hold opens one: `design/manual-check.md`).
  - **Not checked**: Linux and Windows; the import file picker or another app taking the front (⌘H stood for them); a real held key (an agent cannot hold one) and choosing a variant in the popup that existed before press-and-hold was turned off (`text` posts the character, not the digit key, and the helper has no digits); a light theme; a non-Roman input method (never added on this Mac, #203); the watchers, the `Guard` and the handler's wiring have no unit test, and a held ⇧↩ or ⌥⇥ in a token field was not seen in a window (the helper posts no modified holds, and a hold of letters cannot reach that path), so the control-only drop is read from gpui's sources and pinned only by `taken`'s table, as they need a window and the system call, so the checks above are theirs. Tests: `handed`, `press_and_hold`, `taken` and the four terms of `guarded` are plain tables; taking out `handed`'s masked branch, the `front` term, the `focused` term, `os == Mac`, the masked answer of `press_and_hold`, or `taken`'s masked branch fails one.
- **`multiline(rows)` makes a field hold several lines** (2026-11-06, for a flow's prompts, `design/flows.md`, and since 2026-11-09 for every prompt typed for an agent, #87: the Queue's form, Start a flow and ⌘G's Start an agent, all through `TextField::prompt()` (`multiline` with 3 to 12 rows, the flow editor's too); `text_field/rows.rs` holds the plain numbers, `text_field/element.rs` the drawing). gpui's `shape_text` gives one `WrappedLine` per line, and `Rows` lists every row on screen with its offsets, so clicks, the caret, the selection and the input method's rectangles read one table, with no window in its tests. Enter and ⇧Enter break the line, and ⌘Enter (Ctrl+Enter on Linux and Windows) submits; a paste keeps its lines (`\r\n` and a lone `\r` become `\n`, as in the TUI's fields); ↑ and ↓ move between rows and keep the column they started from (`goal_x`), and past the first or last row go to the text's end, as native fields do; ⇧ with ↑ ↓ Home End selects, and the selection goes to the primary selection like any other; Home and End reach the ends of the row, as ⌘← and ⌘→ do; ⌘↑ and ⌘↓, or Ctrl+Home and Ctrl+End on Linux and Windows, reach the ends of the text. Tab still moves the focus: a form is walked with it, and prompts have no use for a tab character. A word still ends at a blank, so Ctrl+⌫ at the start of a line takes the line break and the word before it.
  - **A prompt says how it is sent** (`ui::prompt_box`, `text_field::prompt_keys`): a line under the field in the muted colour (the faint one was about 3:1 at 11 px), `↩ for a new line, ⌘↩ to schedule` on macOS and `Enter for a new line, Ctrl+Enter to start` on Linux and Windows, with the verb of the form's button (schedule, save, start). Its words come from `send_key`, the pair the binding uses, so the two cannot drift (a test holds it). It sits under the field rather than in the placeholder because a placeholder goes with the first letter, and an edited entry or an issue's task opens with text, so it would never be seen. The flow editor's fields do not take it: a form of several of them, the notes and every role's prompt, would repeat it. cornercase pastes a prompt whole to an agent that asked for bracketed paste and on one line to one that did not (its `agents/launch.rs`, read on 2026-11-09), so the lines reach agents of the first kind.
  - **A second key context, `Multiline`**, only on these fields (`LINES_CONTEXT`), holds the new keys, so ↑ and ↓ still reach the parents of a field of one line, such as a menu over its filter. Enter is bound in both, and of two bindings at one depth gpui runs the later first, so these come after the plain ones (a test holds it).
  - **A caret at a wrap belongs to the next row** (`Rows::row_of`). gpui's `position_for_index` draws it at the end of the row before, and a field with vertical moves cannot live with that: ↓ onto the start of a row would seem not to move and the next ↓ would go nowhere, and Home on a row would jump to the row above. Keeping which side it is on (an affinity) was the other way, and more state for one case; so End and a click past a row's end stop before the row's last grapheme (`Row::last_caret`), usually the blank it wrapped at.
  - **A field of several lines keeps room below the caret when `inside` follows it** (`PROMPT_MARGIN`, 32 px), so a prompt's key line is not out of view just when a long prompt is done. Every `multiline` field gets it, the flow editor's included, which draws no such line: its caret keeps 32 px instead of 12, a small change accepted for one rule. In a view too short for the caret and its margins (the Queue's form with a long error under it), the margins shrink, the caret's row first (`scroll_to_show_with_margins`), so the caret is never scrolled out.
  - **It grows with its rows up to the limit, then scrolls inside itself**, clipped to its box, with a thumb in the box's padding (the wheel and the caret move it; it cannot be dragged). The scroll is the field's own (`View::scroll_top`) rather than an `overflow_y_scroll` around the element, for two reasons found in gpui 0.2.2's `paint_scroll_listener`: it never stops the wheel, so the sheet would scroll along with the field; and a handle's new offset only applies to the next frame, so the caret would be out of view for one. At its top or bottom the field lets the wheel go on to what scrolls around it. A drag selection follows the pointer past the box (a `MouseMoveEvent` of its own: gpui's `on_mouse_move` only fires while hovered), one step per mouse move, as the TUI's does, with no timer.
  - **`inside(scroller)` names the `ScrollHandle` of the form around a field.** gpui's divs do not follow a caret (only its `List` honours `request_autoscroll`), so a field growing at the bottom of a form typed out of sight, and Tab went to fields below the fold. When the caret moves or the field takes the focus, the field moves that scroller by what it takes to show the caret, in the next frame (`request_animation_frame`), which cannot be seen. Opening a role from its box in the flow editor's plan focuses its name, which is not drawn until then, and the field is revealed on the frame it appears. That first-focus rule misses a field that kept `was_focused` from its last paint (a role's name focused when the role closed, then reopened), so `TextField::reveal` asks a field to bring its caret into view again on its next paint, and the flow editor calls it on the next frame after focusing a role's name. The panic cannot be avoided: `TextSystem::resolve_font` is gpui 0.2.2's only public lookup (`font_id` is private and the platform's text system crate-private, `all_font_names` mixes the fallbacks in, `get_font_for_id` knows only fonts already resolved). The panic hook is the whole process's, so a panic on another thread while it is silenced would print nothing: the probes therefore run in `main`, after `Application::new` and before the app runs (`theme::settle_fonts`), when no code of this app runs on another thread and gpui's own threads are idle (its workers and timer have no task yet, and X11's clipboard thread owns no selection), and each silence lasts one probe (CodeRabbit's review, 2026-11-04; they had run in `Root::new`, with the window open). **Where no font loads at all** (none installed, or only Type 1 or bitmap fonts, which gpui does not read), gpui panics at the first text it lays out, so the window could never say so: the start aborted with gpui's own `failed to resolve font '.SystemUIFont' or any of the fallbacks` before the toast could show. Limit: started from a launcher, standard error goes to the session's log, so the launcher seems to do nothing; a desktop with no font cannot draw its own text either. `FONT_FAMILY` and `UI_FAMILY` are handles (`theme::Family`) that turn into the chosen name, so the call sites read the same on both platforms; `Root`, tooltips (`glass::popover`), drag previews (`glass::dragged`) and the pane move's caption name `UI_FAMILY`, since gpui gives a tooltip or a drag preview the default family rather than the window's. Rejected: reading the desktop's chosen font (GNOME's `font-name`, KDE's `kdeglobals`, the settings portal), one source per desktop and a process or a D-Bus call before the first frame; bundling a font (Zed bundles its own), megabytes for a look a Mac does not share.   - **The rail, the tab strip and the status bar are parts too** (#115, 2026-11-10): each has a plain key like the sidebar's, told from `observe_self`: `RailKey` (`sidebar/rail/key.rs`: Store notifications, the session's revision, the look, an open menu, the machine's place, the panel a tour points at, which `Root` also learns of through an observer on the guide), `TabsKey` (`tabs/key.rs`: the session's revision, Store notifications, the look, the rename, the machine's place, whether a machine's tab shows, whether the sidebar steps aside for a panel) and `StatusKey` (`app/status/key.rs`: the connection's dot, words and reason, the pulse, the active pane's line, the size, Store notifications, and a count of the notifier's and updater's notifications). What the tab strip is and what `Root` keeps of the tab bar is in `design/terminal.md`. The backstop names the part (`rail`, `tab bar`, `status bar`) in the line it prints. The window `Frame` is left out of `TabsKey`: only `claimed()` reads it, and it changes with the window's bounds or its decorations; a resize refreshes every part, and so does the window-appearance observer (`app/looks.rs`), which gpui calls on a decoration change.
  - **Measured on 2026-11-10** (release builds 0.1.60 and 0.1.61, cornercase 0.13.32, an M5 MacBook Pro on battery, 22 agents with 5 working at 1512×912, window in front, three interleaved runs each): the frame median went from 1.01 to 0.81 ms with an idle shell shown (B), from 1.35 to 0.75 ms with a flow's tab shown (7 tabs, 2 working: T) and from 1.16 to 0.73 ms with a pane's output redrawn (C); the window's CPU from 5.5 to 4.6 %, 6.2 to 4.4 % and 6.9 to 5.2 % of a core. A `sample` of B and T shows `render_rail`, `tab_group` and `render_status` at about 0 samples (they draw only when a key moves), their content replayed by `reuse_prepaint` and `reuse_paint`, and in T `request_layout` and `compute_layout` fell to about a third, in B only `compute_layout` did and `request_layout` hardly moved. The provisional target (a frame median of 0.7 ms or less in B and T, and CPU a quarter lower) was missed on frame time in all three cells (0.81, 0.75 and 0.73 ms), and met on CPU for T (29 % lower) and, to within rounding, C (24.6 %); B's CPU fell by 16 %. What is left is `Root`'s own tree, the title row, the terminal and presenting the frame.
  - **An open docked panel is a cached view too** (#134, 2026-11-11: the Changes, Files, TODO, Recap and Flow panels; the Browser is not). Rule, written before any measure: cache a panel that adds 25 % of its baseline frame and 0.15 ms or more to a frame drawn for the orbits. Measured on `main` (release 0.1.61, cornercase 0.13.32, an M5 MacBook Pro on AC, 22 agents with 5 working at 1512×912, three interleaved runs per cell; the baseline B was 1.27 ms, T 1.24): Changes +4.4 ms (a diff open: +5.1), Files +2.2, TODO +3.4, Recap +1.2, Flow +2.6 against T, Browser (start page) +0.43. A `sample` put the cost in `compute_layout` and `prepaint`, not in the panels' own `render`: taffy laying out rows, cards and the diagram on every beat frame.
    - **How**: `app/dock.rs` `dock_view` wraps the panel's own view (`PanelKind::cached`, `AnyView::cached` with the full size), nothing new in the panels; `DockKey` (`app/dock/key.rs`: the shown dock, a count of Store notifications, the session's revision) is told from `observe_self` beside the parts' keys and notifies the dock's view, and the backstop names `dock`. Every Store field a panel reads is covered, as the parts' are, at the price of redrawing the dock on every Store notification; narrowing it per panel was rejected for now as the riskier path. The leaving dock stays uncached (it slides, so its bounds change every frame).
    - **What keeps each panel fresh**: its own `cx.notify()` after every change of what it draws (the audit, in each panel's note, added them where a toast's Store notify had been doing it by accident), child views (a notify marks the views above), Recap's 20 s and Flow's 1 s ticks for the wall clock they draw, and TODO drawn uncached while its Send to menu is open, since `ui::badge`'s orbit turns only at render (`design/todo-panel.md` has the options rejected). Rejected: a periodic safety redraw (it would hide a missed notify).
    - **The slide-in settles** (noticed in review, 2026-11-11): a cached dock kept the slide's last paint at about 0.99 opacity until something redrew it, since the slide fades the card while the cache's key ignores opacity. A shown dock that is new or changed notifies its view once `motion::ENTER` and 20 ms have passed (`Root::settle_dock` in `app/dock.rs`, told from `tell_dock`), so the last paint is at full opacity.
    - **`tests/layers.rs`** keeps it so (`CACHED`, `design/code-layout.md`); a debug build prints `the dock changed without a notify on the window` when `DockKey` moves without a tell.
    - **Measured after** (same bench, `before` and `after` interleaved, three runs each; frame median and CPU of a core): Changes 5.7 → 1.9 ms and 18.6 → 8.4 % (with a diff 6.5 → 2.1, 20.2 → 8.6), Files 3.3 → 1.7 and 12.6 → 7.7, TODO 4.4 → 2.1 and 15.6 → 8.2, Recap 2.5 → 1.7 and 9.4 → 7.2, Flow 4.0 → 2.1 and 14.4 → 9.1; B 1.30 → 1.20 and T 1.20 → 1.16 (no regression). A `sample` shows the panels' own `render` and `compute_layout` at about a tenth of before, and `reuse_prepaint` and `reuse_paint` up.
