# Queue

Code: `src/panels/queue.rs`, `src/panels/queue/`

- **The TUI's Queue tab, for every project**: the entries come live from `status --app` (its `queue`, the same as `queue list --json`'s `entries`). The panel never polls `queue list`; the app stream already carries every change.
- **Entries are read leniently** (`#[serde(default)]`, unknown fields ignored, an entry without an id dropped): a field a newer server adds or drops never hides an entry.
- **States** are the server's: `pending`, `starting`, `started`, `failed`, `missed`, and on a routine's runs `removed` and `kept`. Pending, failed and missed entries can be edited and started now (`runnable`), a routine's runs never; a starting one cannot be removed until it settles.
- **An empty queue explains itself** (asked for on 2026-10-31: with nothing in it, the sheet did not say what it was for, only a grey line under an empty filter). Until the queue holds an entry, the sheet is a centred page in the look of Issues' page for a tracker that is not connected (`ui::emblem`, shared with it): the Queue's emblem, "Start agents later, on their own", a line saying that nothing is queued yet and what the queue does, **Schedule an agent…** (the form) beside **Open Issues**, whose Schedule… queues an issue, and a card of five points. The buttons come before the card, so a short window shows them without scrolling. The points are what the form asks, in its order, with its icons: when (a time, a delay, a plan's reset), again and again (a routine, and its limits), what (a prompt or an issue), where (a new tab or a new worktree) and that it runs unattended. The toolbar is left out, since there is nothing to filter. While the form is open the page stays without its buttons, so the points explain the form beside them. The card of points sits in a full-width row that centres it, and grows to the row's width up to 520 (`flex_1`, `min_w(0)`, `max_w(520)`): in the page's column, taffy 0.9 measures an item's height at its width before `max_w` caps it, so a card given the page's width, or 520 capped by the page, ran its last point out of it; given no width, it took its texts' one-line width (gpui measures a text's narrowest width as its whole line) and spilled out of a narrow page. Along a row's main axis the cap applies first, so its height fits (all three seen live on 2026-10-31, at 1280 and 900 px wide).
- **Sections, then the server's order**: "Did not start" (failed and missed, which wait for Start now or another time), "Scheduled" (pending and starting), "Routines" and "Started", each in the server's order (chronological, ties by id). In the one chronological list the TUI draws, what started earlier pushed what starts next down the sheet, and a failed entry sat among the started ones. A state a newer server adds goes under "Other" rather than under a heading that would misname it. The headings carry the counts, which replaced "N pending · M in all" in the toolbar, and Clear started sits in the Started heading, beside what it clears. Without a filter "Scheduled" shows even when empty, and says when nothing is scheduled and how to schedule, unless a routine is listed, since then something is; a filter leaves out the sections it empties.
- **A row** is when it runs, the state's icon, the label (dimmer once started), the prompt's first line when it differs, and the state in its colour with agent, mode, place and accounts. The icons are the window's status family (`design/widgets.md`): pending a dot in a ring, a spinner while starting, a green check once started, a red cross for failed, the orange "!" for missed, since it waits for you. The TUI colours missed yellow, which reads as "working" here. A failed entry says why, and a missed one what happened and what to do, on a line of their colour under the row.
- **Actions show on the row under the pointer**, as Processes' Go and Stop and the TUI's buttons, which follow the selected row: otherwise Start now, Edit and Remove repeated on every row, a cobalt Start now on each. They stay on the row being edited, and `Starting…` stays while `queue run` answers. They are hidden (`invisible`), not transparent, so nothing hidden takes a click, and they keep their room while hidden, so a row does not change when the pointer reaches it. Edit keeps its slot while its row is in the form. A click on the row does what Enter does in the TUI: it edits an entry that can run and shows a started one's live pane (`data::Click`); it does nothing while the entry starts or is already in the form. Remove's tooltip on a started entry says that its agent keeps running, which a line under the list used to say.
- **The toolbar** is the filter, a search field with its clear button as in Issues and Processes, and **Schedule…**.
- **The form** says what happens under its title ("It starts by itself at the time you choose"; an edit, that only what changes is sent), and its sections take the empty page's icons. The lists that wrap (trackers, projects, workspaces, agents, modes) are chips, as in Issues' start form; the short fixed choices stay segments. Its fields wrap (`TextField::wraps`), so a long prompt or issue URL grows the field instead of running out of it. A footer stays while the form scrolls: the trust notice, the error with its icon, Cancel and Schedule (Save for an edit).
- **"Started · pane N" only while that pane exists**: an entry records the server token (`boot` in `status --app`) its pane belongs to. A pane id from another server run, or one the session no longer has, reads "pane closed" and offers no Open button, since pane ids are reused across restarts.
- **Places read as the TUI names them**: `project › branch`, else `project › workspace name`, else the worktree folder; a project the session no longer has falls back to its folder name.
- **Local time comes from `localtime_r`** (libc), so the panel needs no time-zone crate and agrees with the machine's zone. The `unsafe` is sound because `localtime_r` writes only the zeroed `tm` it is given, on the caller's stack. Day differences use Howard Hinnant's days-from-civil algorithm (`time::days`), which the search panel reuses for RFC 3339 times.
- **When a row runs reads from today** (`today 14:30`, `tomorrow`, `yesterday`, a weekday within the week, the date otherwise) plus a relative time (`in 2h 5m`, `3d 4h ago`). A 30-second timer redraws the panel so relative times move on by themselves.
- **The form builds `queue add` or `queue edit ID`** with `--json`, so the answer can be read and an error shown under the form (`cli::reason`, without the command's name or `Error: `). `--at` takes the texts the CLI documents (`14:30`, `tomorrow 9:00`, `2026-10-24 09:00`, `in 2h`, `claude reset`, `codex reset`). The entry starts from `--issue` (a URL or key) or `--prompt`; an issue may name its tracker (`--source`) for an ambiguous key or a self-hosted URL.
- **An edit sends only what changed**: the time stays unless another kind is chosen ("unchanged"), the place stays unless "somewhere else" is chosen, the agent stays unless one is picked, and the prompt and name are sent only when their text differs from the entry's.
- **A new entry starts where the window is**: the shown project and workspace, filled in once the session says where that is (it may arrive after the form opens). Choosing a project without a workspace means a new worktree on a branch, made when missing.
- **Agents and modes come from `config --json`** (setting `agent` and `agents.NAME.mode`), read once when the form first opens; `auto` has no modes. The mode chosen in the settings is marked with ✓.
- **An Account row follows the agent** (`design/accounts.md`, An account where agents start): a dropdown under Agent, for the chip chosen, else the entry's agent on an edit, else settings' (none for `auto`, which `queue add` refuses). Hidden when a routine runs a flow, as upstream's is: a team has several agents and the form asks for one. `--account` goes only when the dropdown differs from what the entry would get anyway, so an edit sends only what changed, as the rest of the form does. A new entry left alone follows the account in use when it starts, and a dim line says so. An entry's account that is gone reads `home (gone)` in red and saving it unchanged is refused by `queue edit`, in the form's error; a pick clears that error, as any change does. A row's `claude: work` names the folder, not the label: `status --app` gives the folder, and the row has no list to look it up in.
- **An entry that started or went away meanwhile closes its edit form**, since the server would refuse the edit.
- **Removing asks nothing and can be undone** (#463 upstream, checked with cornercase 0.12.225): `queue remove ID --json` and `queue clear-started --json` answer the removed entries (a routine's with its runs, which the bar says) and an `undo` number, and the panel offers Undo (`queue restore N`) for 6 seconds in an undo bar, as the TODO panel and the TUI's undo toast do. A later removal replaces the bar; the timer only clears the bar it was started for. The server keeps only its last few removals, so an old number can be refused, which becomes a toast. Removing a started entry only clears history: its agent keeps running.
- **The undo bar sits under the toolbar**, outside the list's scroll, and over the empty page too: removing the last entry empties the queue, and its Undo must stay in reach.
- **Why a bar and not a toast with an action**: a toast's action runs through `Store::act`, which adds `--view`, and `queue restore` refuses `--view`.
- **Queued agents accept the folder's trust prompt and submit the prompt by themselves**: that is cornercase's behaviour for unattended starts, and the form says it.
- **`open_pane` and `toast_outcome` live here and are shared** with the search and TODO panels (focus a pane and close the sheet; toast a command's result), so the three panels do not repeat them.
- **Start now** reads `Starting…` until `queue run` answers (it starts an agent, maybe in a new worktree), and the status bar names the entry; Save reads `Saving…` and Schedule `Scheduling…`.
- **Weeks in a delay**: `in 1w` is new in cornercase 0.13.1, so `in` shows the same four units as `every`.
- **Checked live** on 2026-10-31 with cornercase 0.12.230 (debug build, 1280×800 and 900×640) on a throwaway project: the empty page, with the form open beside it and opened from it, a long prompt growing its field, the form's error, Open Issues; and, through a `CORNERCASE_BIN` wrapper that answers `status --app` with made-up entries, the sections, a row in every state, the actions on hover, a click opening a missed entry's form, a notice wrapping in the narrowed list, and a queue holding only started entries. Start now, Remove, Undo and Open were not pressed on the made-up entries, and nothing was scheduled (`queue list` stayed empty).

## Routines

A routine is a queue entry that repeats (cornercase 0.13.1, #653 upstream, its `design/queue.md`): `repeat` is set, its state stays `pending`, and each time it fires a run is added, an ordinary entry whose `routine` names it. Its `next` is its next time; a paused routine has none, and its `at` is then stale, so it reads `paused` and `at` is never shown.

- **A section of its own, each run under its routine's label.** The TUI draws them in one chronological list, where a routine's runs sit among everything else; among "Scheduled" here a routine would swap places with one-off entries each time it fires, its history between them. The section says plainly, under its heading, that a routine only runs while cornercase's server runs, that each run gets a fresh worktree from the up-to-date default branch and that only git repositories can have routines, as the form does for a repeating kind and the empty page's card.
- **A run is one line under the label, in the label's column**: its icon, its time, its state, where it ran, and on a line of its state's colour under it what the TUI appends: why it failed, why it was kept, what a missed run means (no "Start it now", which is not on offer). `removed` and `kept` read "Workspace removed" and "Workspace kept", since "Removed" under a list with a Remove button says the wrong thing. Kept is the orange "!", since something waits for you there; removed a grey check.
- **Runs show newest first, at most 10.** The server keeps 10, and up to 20 while a run's cleanup counts down; the newest are the ones to see. A run whose routine is gone stays in its state's section, read as history. A filter that matches only a run keeps its routine above it.
- **A run is history**: no Edit, no Start now, a click only opens a live pane (a kept run has one too). Remove takes it from the list and leaves its agent and workspace, as the tooltip says. Clear started clears them too, never a routine; it sits in the Started heading, or in the Routines heading when only runs have something to clear (`clear_goes_in`), the same rule as the server's `clearable`.
- **Actions**: Start now, Pause or Resume, Edit, Remove, shown as the row's others are. Pause and Resume are icons with tooltips, as Edit and Remove are, so swapping one for the other moves nothing and a list beside the open form keeps room for its text; the reserved width of two more labelled buttons took it from the label. A spinner takes the icon's slot while `queue pause` or `queue resume` answers. Resume's icon is the repeat arrows rather than Start now's play. A routine cannot be removed while a run of it starts (the server refuses it), so Remove waits as it does on a starting entry.
- **A narrow list keeps its text.** With the form open in a 900 px window the list is about 320 px wide, and the room the hidden actions keep took all of the label's, four buttons now on a routine. A row wraps its actions to a line of their own rather than squeeze its text under 100 px (`flex_wrap`, with `ml_auto` to keep them on the right), and a run's indent gives way before its text does: it is a spacer beside the row, which has a minimum width, so the spacer shrinks. Seen live at 900×640.
- **In words**: `repeat.rs` reads the server's canonical texts (`2h`, `3d 01:25`, `day 09:00`, `weekday 09:00`, `monday 09:00`) into `↻ every 2 hours`, `every 3 days at 01:25`, `every Monday at 09:00`. A text it does not know reads `every <text>`, so a newer server's kind still says something true. A routine of days or weeks shows its clock, which the server captured when it was added.
- **The form offers one family on an edit**: the server refuses to turn a one-off entry into a routine or back, so a one-off's edit lists `unchanged` and the one-off kinds, and a routine's `unchanged` and the four repeating kinds (`When::offered`). `unchanged` on a routine shows its repeat in words, and the other kinds start from its values. `--every` goes only when another kind is chosen. A new entry lists both families, in two tracks, one above the other, their segments a little tighter than the form's others so that each fits a row at the form's default width. Widening the form to 460 instead left the list about 280 px in a 900 px window, too little for its toolbar.
- **The values go as typed, and the server's error is what shows**: below 30 minutes, above a year or a clock it cannot read are refused by `Repeat::parse` with its own words, in the form's error, so the limits live in one place. The form only asks for a value that is empty. A hint under `every` gives the limits beforehand.
- **A repeating kind changes the form**: What is the prompt alone (`--every` refuses an issue), and for a flow a line says it is the team's task. Where lists only repository roots and `Open in` says `new worktree`, with no branch and no choice, since a routine names its own worktrees (`--project` only). If the project in the form is not a repository, the form moves to the first that is, or says to open one (`repository_for`). Agent gains each flow as `<name> (flow)` (`--flow`; then Mode says it is set by the flow's roles), from `flow list --json` for the form's project, read once per project while a repeating kind is chosen: only those that can start, each name once, since a project's flow can share a name with yours.
- **A repository root is read from the session**: a workspace at the project's folder with a branch (a detached one reports its short hash, a plain folder none), or a linked worktree in the project. This panel does not read the disk (`AGENTS.md`). A project opened on a linked worktree passes here, though its `.git` is a file, and the server's refusal shows.
- **`remove the workspace when it finishes`** is off by default, sent as `--cleanup` or `--no-cleanup` on a new routine and on an edit only when changed. A line beside it says what it does and when the workspace stays, in the docs' terms. The TUI greys it for an agent whose status it cannot read. `config --json` does not say which those are (today they happen to be the ones without an `agents.NAME.mode` setting, which is no contract), so here the box stays and the server's refusal shows, in the form's error.
- **Checked live** on 2026-11-06 with cornercase 0.13.1, Linux x86_64 under Xvfb with lavapipe, on a bench server with a real bare remote and a fake agent script (no real agent ran; no macOS, no Windows): through the window: a routine of each kind from the form (`30m`, `3d`, `2w`, `day 09:00` with the checkbox, `weekday 08:15`, `friday 18:00` on the flow Quick, each read back with `queue list --json`), every 10 minutes and the agent `auto` refused with the server's words in the form, a plain folder left out of Where and the form moving to the repository; Pause and Resume, Start now with a run appearing under its routine (a real fetch from a bare remote), a flow routine's run with fake roles from the command line, Remove taking a routine and its run with Undo bringing both back, Clear started taking three finished runs and no routine, an edit from `every 30 minutes` to `every day at 07:45` with the checkbox, an edit from one flow to another and from a flow to an agent, a one-off's edit offering no repeating kind, a click on a run opening its pane, Remove on one run, the empty page, and 900×640 beside the form. Real `removed`, `kept` and `failed` runs were made on the same bench: the fake agent set Claude's working and idle titles, so its status went `done`, and after the 3 minutes one clean run was removed and one with an uncommitted file kept; a remote that could not be fetched failed one run (`tests/fixtures/queue/routines.json`, with the paths replaced). The server's refusal of `--cleanup` for an agent it cannot read shows in the form too (`amp`). Not seen live: a `missed` run (unit tests only, it needs a server down past an occurrence) and the cleanup of a flow's run.
