# Shared files and the merge check

Code: `src/model/shared.rs`, `src/dialogs/merge_check.rs`, `src/dialogs/merge_check/answer.rs`, the row's tag in `src/sidebar/workspace.rs`, the menu's entry in `src/sidebar/menus.rs`, the file's mark in `src/panels/changes/file_list.rs`

Two workspaces of a project are two git worktrees of one repository, and nothing stops two agents from changing the same file in them. cornercase says so before merge time (cornercase 0.12.218 and 0.12.220, its `design/shared-files.md`, #252 upstream): what counts as shared, the scan and the scratch copy are the server's. This window draws what `view` and `changes merge-check` answer, and only adds Ask agent.

## Shared files

- **`view` carries them**: each workspace's `shared` lists, for each other workspace, `workspace`, `count` and at most 100 `files`, and is left out when empty. `changes shared --json` prints the same object, read from `status`, so the window never runs it: it would be a process per row for what the stream already brought.
- **They follow the setting, off by default upstream** (Settings › Worktrees › shared files, `shared_files`): off, the server scans nothing and `view` lists nothing, so nothing shows, at once and with no setting of our own. The switch shows by itself, since the Settings sheet is built from `config --json`.
- **`⇄N` on the row** (`shared_tag`): the distinct files it shares with any other workspace, as the TUI's badge, not how many workspaces. In yellow (`colours::working`), the TUI's caution; orange stays for real conflicts and waiting agents, as it does for a pull request's. It sits where the TUI puts it, after the pull request's tags and before `↓N`, and is hidden while the row is being removed. A click opens the merge check for that workspace without selecting it; a right click still opens the row's menu.
- **The tooltip is the small list** (`Session::shared_tip`): each other workspace with how many files and the first six, then `… and N more`, since a tooltip cannot scroll. The dialog lists 20.
- **`⇄` on a file** (`shared_mark`), the first of a file row's right-hand tags, muted like the row when it is viewed or folded, in the project scope and in Every project. A rename counts by its new or its old path. Its tooltip names who else changes it (`Session::file_shared_tip`). It has no click of its own, as the TUI's: a click selects the file like the rest of the row.
- **Limits of 100 files a pair**: `files` stops at 100 (`SHARED_LISTED` upstream, so a formatter's run does not bloat every line of `view`). `count` is still whole, so a row with one pair cut short counts right; past that `shared_count` takes the larger of the distinct files listed and the largest `count`, a floor for several pairs cut short. A file past the 100th gets no mark. Nothing upstream gives more, and a run that shares more than 100 files has its tag and dialog to say so.

## The merge check

- **Where**: **Merge check…** in a workspace's menu, after the pull request's entry, for a workspace with a `branch` (upstream's `git::branch`, a detached HEAD's short hash included, so every git workspace), even with nothing shared, since the base check is useful alone; and a click on `⇄N`. No key, as in the TUI.
- **On demand only**: it checks as it opens and on **Check again** (Enter), as the TUI's. Automatic dry runs would be a snapshot per tick.
- **A job beside the queue** (`store::run_partial_busy`, key `merge-check:<workspace>`, `Checking how NAME merges…` in the status bar): it copies the index and writes objects in a scratch folder, up to the server's 30 s; in the queue it would hold every key and focus behind it. While it runs each merge says `Checking…` with a spinner and the button turns into `Checking…`. Each dialog runs one at a time, so no generations: Check again does nothing while one runs, and a dialog that closes drops its answer with its entity. A reopened one is a new dialog and checks again.
- **A partial answer is an answer**: `changes merge-check` exits 3 when any entry has an `error`, conflicts being an answer and not a failure, with the JSON printed all the same; `cli::run_partial` keeps it, so a base that does not exist shows as that entry's line and the pairs still show theirs.
- **The lines are plain data** (`answer.rs`, `Reading::lines`), tested without a window: `Into main`, or `Into the base branch` until an answer names it, since `view` does not carry `Workspace::base` (Check again keeps the name the last answer gave); `With mc/pricing` and `2 shared files`, then those files (at most 20, then `… and N more`, as the TUI); then the verdict: `Merges cleanly`, `1 conflict` with each path and git's kind (`contents`, `modify/delete`, `add/add`), or `Could not check: …` in cornercase's words. An answer with no base adds `Choose a base in the Changes panel.`. Paths are cut at their end with the rest of the window's text (`ui::one_line`), where the TUI cuts their start.
- **A pair that changes while the dialog is open**: the shared files follow `view`. One that appears after the check has no verdict until Check again; one that stops sharing keeps its verdict, since it was a true answer about that moment and is named by the workspace (`workspace N` if it left the session).
- **`Shared files are off`**: with nothing shared the dialog says `No other workspace of shop changes the same files.`, which claims a scan, only when the setting is on; off, `Shared files are off (Settings › Worktrees), so no other workspace was looked at.`, the TUI's two sentences. The setting comes from `config --json`, read once as the dialog opens; while unknown, or if that read fails, it says neither.
- **What fails shows in the dialog, in red, and no toast**: the dialog says it where you are looking, as the pull request's does. A refusal (`workspace 3 is not in a git repository`, a workspace that left) is cornercase's own text through `cli::reason`.
- **It closes itself** when its workspace leaves the session or starts being removed, as the TUI's.
- **Ask agent**, only here (cornercase's dialog left it out; this window has it in the pull request dialog already, and a conflict is what an agent can fix): shown only while the answer lists a conflict, through `Store::ask_agent`, so it pastes with no Enter, focuses the agent and toasts, and without an agent copies the text. The text names every merge that conflicts, at most 20 files each: `the merge check found conflicts into main: README.md (contents); with mc/pricing: README.md (contents) `, with a space at the end for a note to follow.
- **Left out, as in the TUI**: a key, a click on a pair to go to that workspace, and `changes merge-check --with` or `--base` from the dialog (a base is chosen in the Changes panel, and the next check follows it).

## Checked live

- On 2026-11-06 with cornercase 0.13.1 and git 2.53, on Linux x86_64 under Xvfb with lavapipe, on private servers with fake agents and a throwaway repository:
  - Two worktrees changing one file, committed on `main` too, and an untracked file both added: `⇄2` on both rows and their tooltips; the marks in Uncommitted and Every project and their tooltips; a mark muted on a viewed file; a rename marked by its old path; a click on a mark selecting the file. The setting turned off and on with the window open: the marks went and came back at once, and the dialog said so.
  - A real conflict, from a click on the row's mark and from the menu: `1 conflict`, `README.md`, `contents`, then `Merges cleanly` after both worktrees wrote the same text and Enter; the button checks again too. 25 `add/add` conflicts: `… and 5 more`, the body scrolling. A repository with no default branch: exit 3, `Could not check: no base branch to merge into`. A check slowed to 6 s by a wrapper: every merge's spinner, the busy button, `Checking how mc/pricing merges…` in the status bar.
  - Ask agent with a fake agent (pasted with no Enter, focused, toasted) and without one (the toast says it copied; the clipboard itself was not read back). The worktree removed with its dialog open: it closed. A plain folder's menu has no entry. Escape and Done.
- With `--remote`, through a fake ssh between two servers on one box and no real sshd: the dialog answered from the other server, and `changes merge-check` run by hand brought exit 3 and its JSON back as it does here.
- Not checked: macOS and Windows, where `⇄` comes from the fonts of each platform (U+21C4 is one cell in the TUI; here it is a glyph like the row's `↓` and `⎇`), and a pair past the 100 files `view` lists, whose counts and tooltips are covered by tests only.
