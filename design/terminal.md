## Keys and text

- **Keys reach the terminal only while its own focus handle is focused and no dialog or sheet is open**, never while a text field or a focused panel has the focus: a modal over the terminal must not type into the shell behind it. ⌘ shortcuts (their Linux keys are under Keys on Linux) are the exception and are read in `Root::shortcut` whatever has the focus (⌘C and ⌘V act on the terminal only when it is focused).
- **Every ⌘ shortcut is one row of `keymap::SHORTCUTS`**: a command, its keys and whether it needs ⇧. The same table gives the buttons' tooltips (`with_keys`) and the ⌘/ dialog, so a hint cannot drift from its key. On macOS a row without ⇧ also answers with ⇧ when no shifted row takes the key, so ⌘+ (⇧= on a US keyboard) and ⌘? work; Linux reads symbols back to their keys instead (Keys on Linux), so a chord there matches its row exactly. Only the app menu's system keys (⌘Q, ⌘H, ⌥⌘H, ⌘M, ⌃⌘F) are gpui actions in `main.rs`, so the menu bar shows them; the help lists them from `keymap::system_keys(os)`.
- **Why these keys**: they follow macOS terminals where one exists (⌘W closes the pane as in iTerm and Ghostty, ⌘[ ⌘] move between panes, ⌘9 is the last tab as in browsers, ⌘F finds). Panels without a mnemonic letter took a free one with ⇧ (⇧⌘S the scheduled queue, ⇧⌘G flows next to ⌘G, ⇧⌘X plugins as in editors, ⇧⌘H the Recap panel, the H of history, since Ctrl+Alt+Shift+R is the desktop's on Linux); ⇧⌘K connects to another server, as Terminal's New Remote Connection; ⇧⌘Q was avoided since macOS logs out on it. ⇧⌘P goes to a file (`design/files-panel.md`, asked for on 2026-10-31), the quick open editors put on ⌘P; Processes moved from it to ⇧⌘M, the M of Activity Monitor and of memory. ⌘P, free since the sidebar's filter went (2026-10-31, `design/sidebar.md`), shows the pull request of the workspace on screen since 2026-11-01, the P of the TUI's `g p` (`design/pull-requests.md`); making it a second key for ⌘F had been rejected, one shortcut per job. macOS keeps ⇧⌘Q, ⇧⌘3, ⇧⌘4 and ⇧⌘5 (screenshots) and ⌘? (the Help menu's search), and the app menu ⌘Q, ⌘H and ⌘M; a test fails when a row takes one of them, except ⌘?, which the ⌘/ dialog answers since the app has no Help menu. cornercase has no command to clear the scrollback or zoom a pane, so ⌘K and ⇧⌘↩ stay free.
- **⌘F has two meanings, by where the focus is** (`keymap::Focus`, 2026-11-06): Find in the Files viewer while the focus is in that panel on a text file, Search anywhere else, the terminal included, so what ⌘F does in a pane does not change, and no plain key is read for it. It is a row of its own in `SHORTCUTS` that answers only there, as the Browser's ⌘[ and ⌘] answer only in a page (`design/files-panel.md`). Rejected: another key for one of them, since ⌘F is what find is everywhere, and Search keeps it for all the places that have no text to find in. On Linux and Windows it is Ctrl+Shift+F, the same reading of ⌘; plain Ctrl+F still goes to the program.
- **⌘C in a docked panel copies what is selected there** (`Root::dock_copy`, 2026-11-06): the Files viewer's or the diff's selection, while the focus is in that panel. Before, it did nothing outside the terminal, and a text field still answers it first. The Queue sheet's run detail (`Root::sheet_copy`, #143) is the one sheet that copies this way: its Text view's selection, while the sheet shows and a selection exists (not tied to the panel's focus, since a sheet has no dock card), after a text field's own ⌘C.
- **⇧ with the arrows select in the Files viewer and the Changes diff** (`Root::dock_select`, 2026-11-09): read in `on_key` after the ⌘ shortcuts and before Escape, only while the dock card, or the Files panel's own handle, has the focus (the Changes panel has none: a click in it, but on the filter, focuses the card), so the terminal and text fields keep the key (`design/files-panel.md`, Selecting in the viewer; the diff from #94, `design/changes-panel.md`).
- **Getting around, the TUI's key menu without its prefix** (its 0.12.4 and `design/keyboard-shortcuts.md`; `terminal/steps.rs`, asked for on 2026-11-06): ⌘J and ⇧⌘J go to the next and previous workspace, ⌘Y and ⇧⌘Y to the next and previous project, ⌘B to the agent that needs you and ⌘R marks the agent in the active pane for review, or as reviewed. The rules are the TUI's: workspaces stay in the shown project and skip one being removed, projects follow the sidebar's order, both wrap, and the agent is the next in the agents section's order after the active pane, folds included, whose status needs you (waiting, failed, done, pending), or a toast says none does. They go through `focus --workspace`, `--project`, `--pane` and `mark --pane`; the mark's toast comes with its answer, so a refused mark says why and not that it was marked (CodeRabbit on #51). **The keys**: only three letters are free with and without ⇧ on every platform (J, Y, Z), and a level of the tree is a pair, so ⇧ is the way back, as in ⌘G and ⇧⌘G elsewhere. J because j goes down a list; workspaces are the level moved through most. Y has no mnemonic: it is the other free one, beside J under the same hand. B for the bell of an agent that needs you (the TUI's `a` is ⇧⌘A's letter here, and ⌘A is what a page in the Browser selects with). R for review: it answers Reload where it did before, in the Browser, as ⌘[ is Back there. **Rejected**: arrows (⌘← ⌘→ type line start and end in Ghostty and iTerm, a field and a page need them, and Ctrl+Alt+Shift+arrows are the desktop's on Linux, so projects would have none); ⌘; ⌘' under ⌘[ ⌘] (`;` takes Shift on a Spanish keyboard, the user's, and `⇧'` types `?`, so three of the four keys would be out of reach); ⌘K ⇧⌘K as vim's pair (⌘K clears the screen in every Mac terminal, so a habit would move the window, and ⇧⌘K is Connect); ⌘Z and ⌘S (undo and save, habits a page in the Browser also needs).
- **⌘W closes what is on top**: a dialog, else a sheet, else the docked panel when the focus is in it, else the active pane, asking first when it runs an agent (as its menu does). ⇧⌘W closes the shown tab the same way. On a machine's tab both act there, with the tab's `boot` (`design/machines.md`). While a dialog is open, every other shortcut is ignored, as macOS ignores menu keys under a sheet.
- **Escape is handled once, in `Root`, one step per press** (#199): it cancels a pane's drag, else closes the dialog, else the sheet, else, while the focus is in the docked panel (its page included), the topmost thing the panel has of its own (`escape::Top`, in this order: a `<select>` menu drawn by the window, a menu (the Browser's agents, screenshots, device and chooser menus, Files' menu, a TODO's send menu), a pick or the picked card, Files' find field, a selection in the viewer or the diff), else a file's full screen, wherever the focus is; else the place that has the focus takes it: the program in the active pane or a popup (vim needs it), the Browser's page, or, from a panel or the sidebar, the terminal, which gets the keys back. The order is plain data (`escape.rs`, `Scene::step`), tested as a table; `Root` reads the scene from the window and takes the step (`terminal/escape.rs`), and each docked panel lists what it has open (`tops`) and closes the one named (`close_top`). **No Escape closes a docked panel** (decided 2026-11-13, #199): once nothing of its own is on top, the keys go back to the terminal and the panel stays open; its key, ⌘W while it has the focus and its ✕ close it. Rejected: closing it, as the code did from 7b57811 (2026-10-31), where it came with the Browser panel unasked (this note said then that Escape "brings the focus back to the terminal"; the Files and Changes notes later described the code), and as cornercase's TUI does (its `design/todo-panel.md`, #174 upstream). A docked panel is meant to stay open while one works and closing it already has three ways, so a press too many (after a menu, a cleared filter, or one meant for a page while the toolbar had the focus) cost the whole panel, a page's screencast and what one was reading, where keeping it costs one more key. The TUI's reason does not carry over: its side panel never holds the keys, so there `Esc` can only close it, and it names giving the panel the keys on a click as the case to look at again; here a click does, and Escape is how they go back without one. Mac editors keep their side panels too: JetBrains IDEs send Escape from a tool window to the editor and hide it with ⇧Escape; VS Code's Escape dismisses widgets, not its side bar or panel. Dialogs and panels used to close themselves on Escape without stopping it, so a dialog over a sheet closed both; none of them handles it now. The Browser's menus had the opposite fault: nothing told `Root` they were open, so one press passed them by and closed their panel, leaving the menu's state open for the next time. A pick, the picked card and the Browser's menus answer only while the focus is in the Browser, so Escape in a pane is the program's even while a pick waits. A text field emits `Cancel` (rename fields undo, dialog fields close), except a search or filter field (`clears_on_escape`), which clears its text and, when already empty, lets Escape go on to `Root`, as Spotlight does, and a field with a saved value (`reverts_on_escape`: Settings' fields, the Browser's address), which puts it back when it differs and otherwise lets Escape go on.
- **A click on the veil closes the dialog or sheet**: the cards and toasts `occlude`, so a click on them never reaches the veil. The veil occludes too, so nothing behind it takes the pointer: a click that closed a sheet also reached the program in the pane under it, and the borders' resize handles showed their cursor through it.
- **Tab moves between a dialog's fields** (`TextField::in_tab_order`, gpui's `focus_next`). Only dialog fields are tab stops: gpui's tab order spans the whole window, so fields behind a dialog would be reached too. In other fields Tab goes on to the panel (the Search panel switches modes with it).
- **The context menu takes ↑ ↓ ↩** (and space): the highlight skips separators and notes and wraps; a submenu opens on its first entry.
- **A menu opened from a control low in the window grows upward from it** (`Root::open_menu_above`, used by the status bar's tunnels label and the pane account chips): its bottom-left corner is anchored 6 pt above the pointer (gpui's `anchored().anchor(Corner::BottomLeft)`), so no height is guessed and a submenu, which replaces the entries in place, grows upward too. Rejected: estimating the height from the rows and notes to place a top-anchored menu, which was off as soon as a note wrapped.
- **A menu can hold a note** (`Entry::Note`): a muted line that cannot be chosen, under the resting row of an action that waits upstream, naming the issue (`design/upstream-gaps.md`) or the cornercase an entry needs, such as `needs cornercase 0.13.30 or newer on this Mac` (a machine's pane menu, `design/machines.md`). A resting row stands for an item, and a note is the smaller remark. At the menu's 320 px a note such as `needs cornercase 0.13.30 or newer on this Mac` fits one line; a longer one, such as `Could not read vps's accounts: <reason>`, wraps. A note naming an issue once broke at the `/` and read as two words (seen live on 2026-11-06).
- **Printable text goes through the platform's input method** (`EntityInputHandler for Root`), which composes accents, emoji and ⌥ characters (⌥2 types `@` on a Spanish keyboard). `keys::key_event` takes only what is not text: named keys, and anything with Ctrl. Encoding text ourselves would break dead keys and every non-US layout. **That handler does not pass through `on_key`**, so it checks for an open dialog or sheet itself: with the terminal focused under a sheet with no field of its own, such as Accounts opened by its key, typed letters reached the shell behind it (found live on 2026-11-06, on Linux with cornercase 0.13.1). Since then, on the same bench, nothing reached the shell from under Accounts opened by its key or from Search, and typing with nothing open still did; not tried on macOS or Windows, where text takes the same handler.
- **Ctrl with a key** sends the key itself, lower case (ctrl+space, ctrl+letter, ctrl+[); cornercase encodes it for the program.
- **⌥ with a key that types nothing else is meta** (⌥← moves by words in the shell): the key goes as a named key with `alt` rather than as text. ⌥ with a key that types a character is left to the input method. On Linux Alt never types (AltGr does, and gpui does not report it as Alt), so Alt is always meta: Alt+Shift+A goes as `A` with `alt`, Alt+ñ as `ñ` (`keys::key_event`); gpui inserts text there only for keys with no modifier but Shift, so without this they were lost.
- **Control characters typed through the input method are dropped**; Enter, Tab and friends arrive as named keys instead, so they are not sent twice.
- **⌘V pastes text, else an image** (`terminal/pasting.rs`): text on the clipboard goes as an `input` paste; a clipboard with only an image (a screenshot taken with ⌃⇧⌘4) goes to `paste-file --pane P --name pasted.<kind> -` on standard input (#479 upstream), which keeps the file on the server's machine and pastes its path, so an agent there can open it. gpui reads the text first when both are there, as other terminals do. The name comes from gpui's format, since cornercase sniffs only some kinds (a TIFF would get no extension).
- **Dropping files on a pane pastes them** into the pane under the pointer (else the active one). On this Mac their paths are pasted as text, each followed by a space and quoted for the shell only when it needs it, as Terminal and Ghostty do: copying the file would cost a copy, a 32 MiB cap and refuse folders, for a path the agent can already read. On another machine each goes to `paste-file --pane P FILE`, which reads it here and pastes the path there; a folder or a file over 32 MiB is refused with cornercase's message. Checked live on 2026-10-29 (cornercase 0.12.225): pasting an image here and through `--remote`; dropping was not checked live (no tool here drags from Finder).
- **On Linux both work through gpui** (read in gpui 0.2.2's sources on 2026-11-04): the X11 and Wayland clipboards offer the image types (`image/png`, `image/jpeg`, WebP, GIF, SVG, BMP, TIFF) as `ClipboardEntry::Image`, and XDND on X11 and `wl_data_device` on Wayland deliver dropped `text/uri-list` files as `ExternalPaths`, so neither needed code of its own. Checked live on 2026-11-04 on X11 (Xvfb, openbox, cornercase 0.12.280): a PNG put on the clipboard with `xclip -t image/png` and pasted with the window's paste key (Super+V then) pasted the path of `pasted.png`. Not checked: dropping files (no tool there drags), Wayland.
- **⌘0 resets the font size to 13**, the size the window opens with; ⌘+ and ⌘- step by one point between 8 and 32. A new size drops the measured `Metrics`, which are measured again on the next draw.

## Keys on Linux

Code: `keymap.rs` (`chord`, `shift_held`, `shortcut`, the labels), `keys.rs`, `main.rs` (`system_bindings`), `ui/text_field.rs` (`bindings`), `panels/browser/keyboard.rs` and `typing.rs`.

- **Asked for on 2026-11-04**, with Linux support. gpui's `platform` modifier is the Super key there, and GNOME and KDE keep Super for themselves (Super+V, Super+1…9, Super+H, Super+L, Super+A, Super+S…), so the ⌘ shortcuts needed another home that leaves the terminal its keys.
- **⌘ is Ctrl+Shift, as in Linux terminals** (GNOME Terminal, Konsole, kitty, Ghostty, WezTerm): ⌘T is Ctrl+Shift+T, ⌘C and ⌘V copy and paste with Ctrl+Shift+C and Ctrl+Shift+V, ⌘W closes with Ctrl+Shift+W, ⌘/ is Ctrl+Shift+/ (Ctrl+?). **⇧⌘ is Ctrl+Alt+Shift**, since Ctrl+Shift is taken by the plain ones: ⇧⌘C (Changes) is Ctrl+Alt+Shift+C, ⇧⌘[ and ⇧⌘] are Ctrl+Alt+Shift+[ and ]. **⌘1…9 is Alt+1…9**, as GNOME Terminal, xfce4-terminal, Ghostty and browsers switch tabs on Linux. The table stays one table (`SHORTCUTS`, written in macOS terms); `keymap::chord` reads a Linux keystroke as the macOS chord it stands for, and the labels (`keys_label`, `Shortcut::label`, the tooltips, the ⌘/ dialog, `system_keys`, `other_keys`) are plain functions of an `Os`, so both platforms' are tested on any host.
- **One exception, Usage**: ⌘U would be Ctrl+Shift+U, which IBus, GNOME's input method (also the default on Ubuntu and Fedora), takes for typing a character by its code point (its `unicode-hotkey`), and gpui hands keys to the input method first. On Linux Usage is Ctrl+Alt+Shift+U (`SHIFTED_ON_LINUX`); ⇧⌘U is free on macOS, so the chord stays unambiguous. fcitx5's Unicode addon takes Ctrl+Alt+Shift+U where fcitx5 is the input method; Usage then opens from the rail only.
- **The window's own keys** (`main.rs`, gpui actions bound globally, which gpui dispatches before any key listener, so they never reach the program): Ctrl+Shift+Q quits, F11 is full screen (as GNOME Terminal and browsers), Ctrl+Shift+M minimises (gpui minimises on X11 and Wayland; ⌘M was already kept free in the table). There is no hide or hide-others on Linux, and gpui draws no app menu there. gpui dispatches a key binding while its window is taken out for the dispatch, so a global action handler cannot update that window there: the window's actions run deferred (`main.rs`, `on_window`), found live when F11 did nothing on Linux. macOS hands key equivalents to the window first too, so ⌘M and ⌃⌘F from the keyboard did nothing before either: checked on 2026-11-04 (macOS 26, cornercase 0.12.244, keys posted to the app's pid), a build of `main` ignored both while ⌘T opened a tab, and this one minimised and entered and left full screen. From the menu bar they worked, and deferring changes nothing there.
- **What reaches the program**: plain Ctrl and Alt keys (Ctrl+C interrupts, Alt+B moves by words), Alt+0, AltGr characters, and any Ctrl+Shift or Ctrl+Alt+Shift chord that is not a shortcut (Ctrl+Shift+Z goes on as Ctrl+Z, as Linux terminals pass it). Super is never bound and never reaches the program, as ⌘ on macOS. Ctrl+Shift+1…9 are never shortcuts (see below), so Ctrl+Shift+2 still sends NUL and Ctrl+Shift+6 the Ctrl+^ vim switches files with. **Ctrl+Shift+- is Smaller text**, as kitty's ctrl+shift+minus, so Ctrl+_ never reaches the program: readline's and Emacs's undo (`^_`) has Ctrl+- and Ctrl+7, which cornercase sends as `^_`, and nano's Go To Line has Alt+G. Ctrl+/, which xterm and VTE also send as `^_`, reaches the program as a plain `/`: cornercase's legacy encoder (`ctrl_char` in its `term/keys.rs`) maps only `_`, `-` and `7` to it (read on 2026-11-04 and seen with `cat -v`).
- **How gpui reports these keys** (gpui 0.2.2, `Keystroke::from_xkb`, read and checked live): a letter keeps Shift and comes lower case (Ctrl+Shift+T is `ctrl-shift-t`), but a symbol comes as the layout's shifted keysym with Shift cleared: Ctrl+Shift+[ is `ctrl-{`, Ctrl+Shift+/ `ctrl-?`, Ctrl+Shift+= `ctrl-+`, Ctrl+Shift+- `ctrl-_`, Ctrl+Shift+0 `ctrl-)`, Ctrl+Shift+, `ctrl-<`. `keymap::unshifted` maps those back with a US layout's table. **A symbol is a shortcut only with Shift held**, read from the window's modifier state since the keystroke lost it (`keymap::shift_held`: gpui's `Window::modifiers`, which X11's XkbStateNotify and Wayland's `wl_keyboard.modifiers` update before the key arrives): with Shift a US shifted symbol reads as its key and any other symbol as itself, and without Shift a Ctrl+symbol goes to the program. Until 2026-11-04 any Ctrl chord whose key was a US shifted symbol counted as Ctrl+Shift, which took keys that type such a symbol unshifted from the program: Ctrl+< opened Settings on a German or another ISO keyboard, Ctrl+8 (`_`) made the text smaller and Ctrl+) reset it on a French one. The keystroke has no physical key code, so the layout cannot be asked: **symbol shortcuts follow the symbol typed with Shift**. On another layout a shortcut needs the key that types its US symbol with Shift (Shift+0 types `=` on a Spanish or German keyboard, so Ctrl+Shift+0 zooms in there, as Ctrl+Shift+=; Shift+9 types `)`, so Ctrl+Shift+9 resets the size), and a shortcut whose symbol no shifted key types has no key there (Settings on Spanish, German and French keyboards, Smaller text on a French one), only its button. Letters follow the layout's letters (gpui maps a non-Latin layout's keys to the US letter in the same place).
- **Rejected**: Super as ⌘ (the desktop keeps it, and on Wayland the compositor never passes most of it on); Ctrl+Alt for ⇧⌘ (Ctrl+Alt+T opens a terminal, Ctrl+Alt+L locks, Ctrl+Alt+D shows the desktop, Ctrl+Alt+Del logs out, Ctrl+Alt+arrows switch workspaces on GNOME, KDE, Xfce and Ubuntu, and X11 keeps Ctrl+Alt+F1…F12 and Backspace); Ctrl+Shift+1…9 for tabs (the key comes as the layout's shifted symbol, `!` or `@`, `"` or `·` on a Spanish keyboard, which cannot be mapped back to its digit without the layout); plain Ctrl shortcuts (the shell needs every one of them).
- **Keys the desktop keeps** (`no_linux_shortcut_takes_a_key_the_desktop_keeps`, a test like macOS's): Ctrl+Shift+U (IBus), Ctrl+Alt+Shift+R (GNOME's and Cinnamon's screencast), Ctrl+Alt+Shift+Delete, Page Up and Page Down (KDE's log out, reboot and shut down without asking), Ctrl+Alt+Shift+arrows (moving a window to another workspace in GNOME, Xfce and Cinnamon), Ctrl+Alt+Shift+Tab, Ctrl+Alt+T, L, D, Delete and arrows, Alt+F2, F4, F7, F8, F10, Tab, Space and \`, and every Super key. The window's Ctrl+Shift+Q and Ctrl+Shift+M are in the list too, so no row takes them. No shortcut used Ctrl+Alt+Shift+R or the others, so none had to move but Usage; the Recap panel, which would have liked ⇧⌘R, took ⇧⌘H for it.
- **In the Browser panel**, Chrome's own keys work as on Linux: Ctrl+C, Ctrl+X and Ctrl+V copy, cut and paste with the window's clipboard, Ctrl+L goes to the address, Ctrl+R and F5 reload, Alt+← and Alt+→ go back and forward (`PAGE_KEYS`, only while the browser has the focus), besides their Ctrl+Shift forms; the ⌘/ dialog shows these. Other Ctrl keys go to the page, where Chrome edits from them itself (`design/browser.md`).
- **Labels read as Linux apps write them**: `Ctrl+Shift+T`, `Ctrl+Alt+Shift+C`, `Alt+1…9`, `F11`, `Ctrl+click`, the modifiers in KDE's and most apps' order, a symbol by its US key (`Ctrl+Shift+=`, `Ctrl+Alt+Shift+[`), Enter rather than ↩. Text fields take GTK's keys (`design/widgets.md`).
- **The ⌘/ dialog** (`dialogs/shortcuts.rs`) fits the longer Linux keys: 1120 px wide there (940 on macOS), never wider than the window less 64; descriptions wrap rather than end in "…" (on macOS too, where the Esc row used to be cut); and on Linux Window and Tabs and panes swap columns, so the shorter Window is what shares a column with the longer Everywhere else. The list is as tall as the window less 160 and scrolls past it (`body_height`, 216 until the Getting around and Viewer keys came), so at 1280 × 800 every row showed on Linux (seen on 2026-11-06); with the Files viewer's ⇧ arrows row (2026-11-09) the last row of Everywhere else is cut at the bottom there and the list scrolls to it (seen on Linux, not on Windows, which has the same rows). On macOS the same sums say it fits too, System's five keys included, but that was not seen; at 216 the last two rows of the first and third columns were below the fold. It never scrolled before: its columns stretched to the scroller's height, so nothing overflowed it and the rows past 480 px could not be reached (the System rows on macOS); they now keep their own height (found 2026-11-04). Checked live on Linux (X11 and Wayland) the same day: every row at 1280 × 800 with nothing cut, and at 960 × 680 the wrapped rows and the wheel scrolling to the last ones. On macOS (2026-11-04, opened with ⌘⇧7 on a Spanish keyboard): the wrapped Esc row and the cut rows above; the wheel was not checked there, since a scroll posted to the app's pid does not reach gpui.
- **Checked live on 2026-11-04** (cornercase 0.12.280, gpui 0.2.2, Debian trixie arm64 in a container, keys sent with xdotool 3.20160805, the keystrokes gpui reported logged from `Root::on_key` by a throwaway debug build). X11 (Xvfb, Openbox 3.6.1): Ctrl+Shift+T opened a tab; Alt+1 and Alt+2 switched tabs; Ctrl+C interrupted `sleep 100`; a word selected by a double click, Ctrl+Shift+C then Ctrl+Shift+V pasted it at the prompt; Ctrl+Alt+Shift+C opened and closed Changes; Ctrl+Shift+/ opened the ⌘/ dialog with the Linux labels; F11 entered and left full screen, Ctrl+Shift+M minimised, Ctrl+Shift+Q quit; Ctrl+click on a blank cell reached the link opener ("No link under the pointer"); `cat -v` got Alt+B as `^[b`, Alt+Shift+A as `^[A`, Ctrl+Shift+Y as `^Y` and Ctrl+Shift+2 as `^@`; typed text arrived once, and on a Spanish layout (`setxkbmap es`) AltGr+2, AltGr+3, the dead acute then e, ñ and the dead diaeresis then u arrived once each (`@#éñü`). gpui reported the keystrokes described above (`ctrl-{`, `ctrl-+`, `ctrl-_`, `ctrl-)`, `ctrl-<`, `ctrl-?`, `ctrl-alt-}`, `ctrl-@`, `ctrl-^`; on the Spanish layout Ctrl+Shift+0 as `ctrl-=`, Ctrl+Shift+9 as `ctrl-)`, Ctrl++ as `ctrl-+`, Ctrl+Shift+' as `ctrl-?`, which opened the dialog). Wayland (weston 14.0.2 nested in the X screen): Ctrl+Shift+T, Alt+1, Ctrl+Alt+Shift+C, typed text, AltGr, a dead key, F11 and Ctrl+Shift+Q. Once Shift came from the window's state (the same day, logged the same way, on both X11 and Wayland): the window reported Shift held at the key down of Ctrl+Shift+[, =, 0 and / (`ctrl-{` and the others with Shift cleared), which still moved between panes, zoomed, reset the size and opened the ⌘/ dialog; with `setxkbmap fr` Ctrl+8 and Ctrl+) reached `cat -v` as `^_` and `)`, with `setxkbmap de` Ctrl+< as `<`, and on a US layout Ctrl+- and Ctrl+7 as `^_` and Ctrl+/ as `/`. Not checked: GNOME, KDE and Sway themselves (the keys they keep are from their documented defaults, so whether IBus or fcitx5 take a chord first is not seen here), a non-Latin layout, and Ctrl+click on a real path or address (opening it is another change's).

## Keys on Windows

Code: `keymap.rs` (`chord`, `left_to_system`, `typed_with_alt_gr`, the labels and `WINDOWS_SYSTEM_KEYS`), `keys.rs`, `main.rs` (`system_bindings`), `ui/text_field.rs`, `panels/browser/keyboard.rs` and `typing.rs`.

- **Linux's keys** (asked for on 2026-11-04, with Windows support): ⌘ is Ctrl+Shift, ⇧⌘ Ctrl+Alt+Shift, ⌘1…9 Alt+1…9, Usage Ctrl+Alt+Shift+U, the page's own keys in the Browser, Ctrl+click, and text fields take the same Ctrl keys. Windows Terminal's own keys are Ctrl+Shift too (Ctrl+Shift+T, W, C, V), and gpui's `platform` modifier is the Windows key, which Windows keeps (Win+D, Win+L, Win+1…9), so the reasons that shaped Linux's keys hold. One scheme for both PCs keeps the README and the ⌘/ dialog one table; Usage keeps Linux's Ctrl+Alt+Shift+U though Windows has no IBus. Rejected: Ctrl+Alt+1…9 for tabs, as Windows Terminal has them: Windows types the AltGr character for Ctrl+Alt (`@` is Ctrl+Alt+2 on a Spanish layout).
- **How gpui reports these keys on Windows** (gpui 0.2.2, `keyboard.rs::get_keystroke_key`, read): a letter keeps Shift (Ctrl+Shift+T is `ctrl-shift-t`), and a digit or a symbol comes as the layout's shifted character with Shift cleared (Ctrl+Shift+[ is `ctrl-{`), as on Linux, so `keymap::unshifted` and `shift_held` read them unchanged.
- **The window's keys are Windows'**: Alt+F4 quits, F11 is full screen, Ctrl+Shift+M minimises (`system_bindings`, `WINDOWS_SYSTEM_KEYS`). gpui hands a system key to `DefWindowProc`, which closes the window, only when the app did not handle it, and the terminal and the page take every key: so both leave Alt+F4 alone on Windows (`keymap::left_to_system`; the window closes, and the last window closing quits). **Alt+Space stays the program's** (meta-space): gpui 0.2.2 translates only an unhandled `WM_KEYDOWN` into characters, never a `WM_SYSKEYDOWN`, so no `WM_SYSCHAR` reaches `DefWindowProc` and the window menu never opens from the keyboard (left to Windows on the runner, nothing opened). A right click on the title bar did not open it either (`design/window.md`, Windows). There is no Ctrl+Shift+Q there: it is not a Windows habit, and with three rows the System list fits the dialog's first column, where a fourth was cut at the bottom of an 800 px window (seen on the runner).
- **Alt with a key is meta**, as on Linux: Windows' Alt types nothing (`keys::meta_text`, the page's `route`).
- **AltGr** (`keymap::typed_with_alt_gr`): gpui reports AltGr without Ctrl and Alt only on the layouts it lists (`WindowsKeyboardLayout::uses_altgr`: German, French, Spanish and some fifteen more); on the others (US-International, UK Extended) it reports Ctrl+Alt, and Windows itself types the AltGr character for a Ctrl+Alt pressed on purpose. A Ctrl+Alt key whose character is printable and is not the key itself is therefore text: the terminal leaves it to the input handler (`keys::key_event` answers nothing, so gpui translates it), the page types it, and it never reads as a Ctrl+Alt+Shift shortcut, since text wins over a key there as `⌥` characters do on a Mac.
- **Limits**: Windows may keep Ctrl+Shift+0 to switch keyboard layouts (gpui 0.2.2 notes it cannot see that chord), and then Text back to its size does not arrive; a layout whose AltGr+Shift types a character on a letter takes that character rather than the shortcut.
- **Checked on Windows** (2026-11-04, `design/windows.md`): typing, Enter, Ctrl+Shift+/ with every Windows label, Ctrl+Shift+T, Alt+1, Ctrl+Alt+Shift+E and C opening Files and Changes, Ctrl+Alt+Shift+B the Browser, Ctrl+Shift+, Settings, Esc, Ctrl+Shift+E going to PowerShell as `^E`, Ctrl+click on a path, and Alt+F4 quitting. Not checked: AltGr on any layout and the Browser's keys.

## Drawing

- **The terminal is not a cached view**, unlike the sidebar, the rail, the tab strip and the status bar (#115, 2026-11-10): it is redrawn on every frame, since everything in it can change with a key, the pointer, the input method or a message. Its paint and layout were under 1 % of a frame in the bench (`design/widgets.md`), so a cached part with a rule for all of it was not worth the risk of a stale pane; a file's full screen puts it under `invisible`, whose children still prepaint, so a cached terminal would also have to be notified when that flips.

- **A canvas measures, then paints**: the prepaint step places the panes (`Layout::new`), fits as many whole cells as the space holds once the panes' padding and gaps are taken out (`Layout::extra`; at least 1, at most 1000 columns and 500 rows) and, when that differs from the size asked last, asks cornercase for it on the next frame (`set_size` deferred), so a resize never re-enters the window's update. The mouse and the input method read the layout the last prepaint kept.
- **Every pane floats on a card of its own**, rounded, with 12 px (`PADDING`) around its cells and 8 px (`GAP`) of ground between cards, as the tabs float in the title row. cornercase lays a tab out in cells, with two columns or one row between panes: about 16 px at 13 pt, no room for a gap and padding on both sides, so cards drawn over its cells would have their text touching the shared edge. The window places the panes itself instead: it walks the split tree the surface sends (`layout`), gives each pane its cells and its padding, puts the gap between the two sides of each split, and asks cornercase for fewer cells by what that adds. That extra depends only on the tree's shape, not on the size, so asking for it does not loop. The first side of a split takes what it needs and the second the rest, so the last cards absorb the fraction of a cell left over and a pane beside a stack takes the stack's whole height. A surface without a tree (older servers) keeps the panes on one grid. cornercase has no option for wider dividers.
- **Text sits on the grid whatever font a glyph falls back to**: words of single-width cells are shaped together with a forced advance of one cell; a wide cell (followed by an empty cell) or a composed one (several characters) is shaped alone at its column. Shaping whole lines without a forced advance would drift as soon as a glyph comes from a fallback font.
- **The block cursor goes under the text**, which is drawn over it in the pane's background colour; bar and underline cursors draw over the cell. An unfocused terminal, or the `block_hollow` shape, shows a hollow block.
- **A card's bottom padding names its account** once there is one, with a chip that switches it (`design/accounts.md`, The account of a running pane); it takes no row and covers no cell.
- **Only the active pane shows its cursor** when the tab has several; its card's edge is brighter, and the others fade (`theme::INACTIVE`, 55 %): their card, cell backgrounds, text and lines lose opacity, so they sink into the glass and the active pane reads as the one in front. A black wash, used until 2026-10-26, made the inactive panes the darkest and most solid surface on the glass, so they looked like the active one; gpui 0.2.2 keeps its element opacity to itself, so the fade is applied to each colour (`theme::faded`). Settings › UI › inactive panes (`dim_inactive_panes`, `design/sidebar.md`) turns the fade off; the cursor and the brighter edge stay, so the active pane can still be told.
- **What a pane says over its card is drawn in the canvas's prepaint** (`terminal/pane_notes.rs`, as the account chips are, `design/accounts.md`): the layout is known only there, and neither shows while a pane moves. Both reserve nothing, so no PTY ever changes size for them.
- **`↓ n more`** (the TUI's 0.12.31, its `design/scrollback.md`): a pane scrolled up says how many rows are under its view, from the frame's `scroll` (`total - offset - rows`, `PaneGrid::below`, and it grows while the program prints), in a small button at the end of the pane's last row, over the text as the TUI's badge is: it shows only while reading history, where a cell's end matters least, and the padding below is the chips' and the band's and too short for a target to aim at. In a pane narrower than the button, it is cut at the pane's width and starts at its first cell, rather than crossing into the next card (CodeRabbit on #51; seen live on the same day with `↓ 3175 more` in a pane dragged to its narrowest), where the TUI drops its badge: the click still works. A press there runs `scroll --pane P --bottom` through the ordered queue, after any wheel steps still going, starts no selection, sends the program nothing and leaves the focus and the active pane alone, as the wheel does. Keys and pastes bring the view back by themselves (`input`, in cornercase).
- **A message held for you is the TUI's bar** (its `design/commands-for-scripts-and-agents/held-sends.md`; #676 upstream, 0.13.9): `send` waits while you type to a pane, and `held_sends`, `held_from`, `held_queued` and `draft` on the pane in `view` tell it. A band in the card's bottom padding, left of the account chips, has the TUI's words and its two buttons at its right: `1 message waiting from claude (pane 9) · goes after yours`, `3 messages waiting, the first from claude (pane 9) · goes after yours`, no sender for one outside a pane; once `held_queued` is true, `queued: goes right after yours` or `2 queued: the first goes right after yours` behind a spinner. `goes out in a moment`, which this band said without a draft before #676, is gone: upstream's point is that two windows' bars read the same. It stays as long as anything is held and hides while the pane is `resuming`, where the TUI draws its resuming band and `--send-now` is refused, and while a machine's tab takes no input (`Root::takes_input`). A narrow card goes in the TUI's order: it cuts the words, drops them, then drops ` wait turn `; ` send now ` stays while it fits; the tooltip has the whole text and why it waits. **Not over the last row, unlike the TUI**: there the bar has no other place, but a prompt is usually on that row, and it would cover what you are typing, the reason the message waits; the padding covers no cell, as the chips' row found (`design/accounts.md`), and the buttons are as tall as the chips.
  - **Who sent it goes by the name the pane menu gives** (`pane_menu::pane_label`: `claude (pane 9)`, a shell's program otherwise, so a shell blocked in `cornercase send` reads `cornercase (pane 5)`), read from `Root::shown_session`, so on a machine's tab it is that server's pane 5. A sender since closed keeps its id, `pane 40`, as upstream's `held_from` does.
  - **The buttons run `held --pane P --send-now` and `--wait-turn` on `Root::shown()`'s queue**, the one way from a frame's pane id to its server (`design/machines.md`), so a machine's tab gets `--remote` and the same id here is not touched. Each is a job (`Store::cmd_busy_on`): the status bar names it, the button shows a spinner once it has run for 300 ms, a second press meanwhile does nothing, and a refusal, usually a message that went out between the last `view` line and the click, is the toast. The lines trail the answer by up to 500 ms, so the bar changes then.
  - **A press stays on the band**: a left press anywhere on it stops there (`cx.stop_propagation`), so `Root::on_mouse_down` never runs, the terminal's focus and the active pane stay, a selection does not start and the program gets nothing; the buttons act on release, so a press can slide off. Rejected: acting on `on_click` alone, whose press also reaches the terminal behind it and takes the focus.
  - **` wait turn ` reads as chosen** with a check mark on a brighter ground and takes no more presses, where the TUI drops the pill: the person sees what they picked, and the bar keeps its shape. `--wait-turn` covers the messages held so far, so one held later turns `held_queued` off and the button comes back, as upstream's does.
  - **` send now ` submits your half-written line with the message** (#708 upstream, filed 2026-11-07). `held --send-now` is `send --force`: it pastes after what you typed and presses Enter, so a pane with `half line` receives `half linefrom a shell` as one line. That is upstream's documented behaviour and its own bar's, and this window's click adds nothing to it: it sends one command and no key. While `draft` is true the tooltip says so and, when it fits, a faint line after the words: `send now takes your line with it · needs usecornercase/cornercase-terminal#708`. Rejected: clearing the line first with Ctrl+U or retyping it (a workaround upstream rejects too: the draft lives inside the agent and no agent has a safe key to clear its box), disabling the button while there is a draft (a message is held mostly because of one, so it would hardly ever work), and asking first through a dialog (it takes the keyboard from the pane, and the TUI's does not ask). `draft` also stays true after it until the 60 s bound, so a later message is held for a line already gone; #708 says that too.
  - **Checked live** on 2026-11-07 with cornercase 0.13.19, Linux x86_64 under Xvfb with lavapipe, a fake `ssh` between two servers on one box, with a fake agent reading lines, on a local pane and on a machine's tab: half a line typed in the window, `cornercase send` from a shell pane so `held_from` was set, both buttons. ` wait turn `: `held_queued` true, the bar read as chosen, nothing reached the pane, the half line was still there, and more typing with no click on the pane joined it. ` send now `: the agent got `half line morefrom a shell`, the bar went, and typing went on in the pane. A press on an inactive pane's band acted on that pane and left the active pane and its keys alone. With the same pane id holding a message on both servers, the machine's buttons moved only the machine's. A refusal after `held --send-now` from a shell was the toast on both. A pane too narrow for ` wait turn ` showed `1 mes…` and ` send now `. With the bench's server frozen around a press, the button spun, the status bar named the job, and a second press sent nothing more. Not checked: a real agent's box, a real sshd, a pane `resuming` under a held message, macOS and Windows.
- **The default background is translucent** (`design/widgets.md`): a pane's card is `colours::pane()`, the theme's terminal background (Tokyo Night in cornercase dark) at the panes' opacity as it looks over the ground, and the pane paints nothing more where its program kept the default. What a program chose stays opaque, so its colours read as it chose them: a pane whose program set its own default background (OSC 11) is filled with it (`Painter::pane_fill`, which compares against the theme's background), and so is a cell with a background of its own (`Painter::cell_fill`), unless that background is the default colour itself, which programs often paint explicitly and which would otherwise leave opaque blocks on the glass. The colours given to cornercase with `theme -` stay opaque: programs never see the opacity.
- **Positions past a pane are allowed**: `Layout::cell_in` counts in the cells of the pane a drag started in, wherever the pointer is (negative cells included), so a drag that leaves its card still reaches its program or the selection, clamped to the pane. A press in a card's padding takes the nearest cell of that pane.

## No tab open (`no_tab.rs`)

- **Asked for on 2026-11-01** (cornercase's TODO list: no screen for a project with nothing open). A view that shows a project or workspace without tabs has no tab to stream: cornercase pauses its surface and sends no frame, so the window kept drawing the last tab it had shown, from another project, and typed into it; a window that started there said "The terminal cannot be shown" with cornercase's refusal (`view N streams nothing now: it shows no tab`), toasted it and asked again every 5 s.
- **The terminal's place says so instead, as the TUI's does** (its `ui/pane.rs`, "no tab open" and `+ Tab`): the emblem with a terminal, "No tab open", a line naming the place, and buttons. Start an agent… opens the start dialog (⌘G, as the sidebar's Agent button) and is the main action; New shell runs `new-tab --workspace W --focus` (⌘T). When the workspace has closed agents (`closed_agents`), Reopen N agents comes first and is the main one, as the TUI's reopen pill, with the sidebar menu's job (`sidebar::reopening`), so the menu and the page show one running job. A worktree being removed shows its removal running and no buttons, as the TUI drops its `+ Tab`. The place is a worktree's own name, or the project's for its main workspace, which cornercase names `default`.
- **No project at all is a welcome**, as the TUI's: the mark, the wordmark, the site's tagline and Open a project… (⌘O).
- **What counts as showing no tab**: the session's view shows no tab, and the frame on screen is older than that session. Frames carry the view's `projection`, which cornercase bumps whenever what the view shows changes, so a frame with a projection at least the session's came for a tab shown since (`Session::shows_no_tab`). Gating on the session alone was rejected: view lines reach the window up to 500 ms after a change (`design/sidebar.md`, folds), while the new tab's frame comes at once, so going from an empty project to a tab would show the page for half a second over a terminal that had arrived. While it shows no tab the panes are neither drawn nor hit, and keys reach no pane (`Root::frame_shown`); a drag in progress when it switches there (a pane held by its handle, a divider, a selection) is dropped, so a pane's ghost does not hang over the page until the button is released, and a program that got the press gets its release at the last cell it was sent, so it is not left mid-drag (`Root::drop_drags_without_tab`, both found by Greptile on #10).
- Checked live on 2026-11-01 with cornercase 0.12.235 on an isolated server (`CORNERCASE_SOCKET`): the welcome with no project, a project whose only tab was closed (from another tab, and closing the shown tab), back to a tab (its terminal drawn within 0.3 s), a window started on a project with nothing open (no toast, no surface asked for until a tab showed), New shell clicked (a tab opened there and drew), and two closed agents faked into `view` through a `CORNERCASE_BIN` wrapper (Reopen was not pressed). Not checked live: a worktree being removed, and Start an agent… (the dialog is the sidebar's).

- **Shared by the pages of this area** (`no_tab.rs`): `page()` for a page that never scrolls, and `scrolled()` for the missing and older pages, which keep the scroll on an outer flex column whose content has `flex_shrink_0` and auto vertical margins: free space centres it, and a page taller than a small window starts at its top and scrolls, instead of being cut above and below as a centred, scrolling `page()` is (gpui clamps the scroll offset at the top; `min_h_full` inside a block scroll div did not centre). A "Try again" button, and `ask_then` and `run_answered` (ask first, then run a job and keep its answer under the buttons, kept by the job's key so a page draws only its own answer).

## cornercase missing (`missing.rs`)

- **Asked for in #21**: a window started from the Finder or an app menu used to say "Lost cornercase / could not run `cornercase`" and retry every 1.5 s forever. Now it finds cornercase (`design/connection.md`) and, when it cannot use one, draws a page in the terminal's place, as it does for the welcome and "No tab open" (the window has nothing else to show then).
- **The cases**: none found (with where it looked, the home as `~`), CORNERCASE_BIN or a chosen file that is not a program, a binary older than the minimum (naming its version and the path), one that does not start (with the system's reason), and one whose `--version` is not cornercase's. The status bar says the same in two or three words.
- **Buttons**: Installation guide (usecornercase.dev/docs/installation/), Try again and Choose cornercase… (a file picker; hidden under CORNERCASE_BIN, which would still win, and the page says to fix or unset it). For a binary older than the minimum a first button, Update cornercase…, asks first (the question names the binary, home as `~`, and says it may only name the command to run), runs `<that binary> update` on this computer as a job with a busy button, keeps its answer on the page (the command to run when cornercase cannot update itself: Homebrew, a folder it cannot write) and starts again on exit 0; the guide button turns plain there, so there is one primary. The lead says "Update it here, or as the installation guide says". It updates the binary the page names, CORNERCASE_BIN's included, with `cli::answer_at`, never with `--remote`; a server already running keeps its release, which the update chip offers to restart as after any install (`design/notifications.md`).
- **No retry of its own**, unlike a lost connection: the lookup can run the user's rc files and an install needs the user. Try again and a pick set the connection to starting, so the page becomes the "Connecting to cornercase…" note with the pulsing mark and the status bar's dot, which is how it shows that it runs. A pick that fails stays on the page with its reason and is not saved (nor is one whose path is not valid text); a file picker that cannot open is toasted. The page scrolls, so its buttons stay reachable in a small window.
- **Checked live** on 2026-11-10 (macOS 26, gpui 0.2.2) with a copy of cornercase 0.13.18 as CORNERCASE_BIN: the page shows Update cornercase… first, and `cornercase update` from a shell on that copy installed 0.13.28 (exit 0), while a copy under a Homebrew-like folder printed the `brew` command (exit 1). The click on the button could not be posted to the window, so the question and busy button were not seen.
- **Not checked**: the page on Windows and the not-found case on this Mac (cornercase is installed here); both are covered by plain tests of the texts and of the lookup.

## Mouse

- **The left button selects**, with cornercase's own selection (`selection --from --to`), unless the program reads the mouse; Shift forces a selection even then. The key that opens links (⌘, Ctrl on Linux) wins over Shift: ⌘⇧-click and Ctrl+Shift+click open the link as ⌘-click and Ctrl+click do, as kitty opens a link on Ctrl+Shift+click in a program that takes the mouse, and Shift alone selects (`keymap::opens_with_system`, kept after review on 2026-11-04). A finished selection is copied on macOS, as the TUI does, and goes to the primary selection on Linux (below); a click without a drag clears it.
- **A double click selects a word, a triple click the line**. A word is a run of cells of one class: blank, word (letters, digits and `_-./~:@%+=#?&`, and `\` when the server runs Windows, so paths and links select whole) or other punctuation. The empty cell after a wide character belongs to it.
- **On Linux a finished selection goes to the primary selection, not the clipboard** (`desktop::selection_board`, asked for on 2026-11-04), as X11 and Wayland terminals do (xterm, GNOME Terminal, Konsole, Ghostty by default): a released drag, a double or a triple click reads the text with `selection --pane P --json` and writes it with gpui's `write_to_primary`, without a toast. `--copy` is left out, since it would also copy the text in cornercase's own window (OSC 52 to the terminal it runs in). Ctrl+Shift+C still copies the selection to the clipboard, with its toast, so the two stay apart. The read goes through the ordered queue, as copying does, because it must come after the `selection --from --to` that made the selection; it answers on a callback, so nothing waits on it, and a read that fails becomes a toast (`selection::kept`), on macOS's copy too, where it had been dropped; so does an answer that cannot be read (not JSON, or a `text` that is not a string; CodeRabbit's review, 2026-11-04), while an answer without `text` is cornercase saying nothing is selected (it leaves the field out), so the board is left alone without a word. Rejected: copying to both (each selection would replace what Ctrl+Shift+C put on the clipboard, which keeping them apart is for, with a toast each time). macOS has no primary selection and keeps copying a finished selection.
- **The middle button pastes the primary selection on Linux** into the pane under the pointer, which it makes active, as an `input` paste like Ctrl+Shift+V (bracketed where the program asked for it); an empty primary selection pastes nothing. In a program that reads the mouse the press goes to the program, and Shift+middle pastes, as xterm and VTE do (`mouse::press_for`); its release and drags carry the middle button (`Drag::Program` keeps the button, where every release used to say left). A middle press on a divider does nothing. macOS still listens to the left and right buttons only (`mouse::buttons`), so its middle button does nothing, as before. Not done: a plugin's popup, which pastes with Ctrl+Shift+V only.
- **Text fields do the same on Linux** (`ui/text_field.rs`): a selection made with the mouse, Shift+arrows or Ctrl+A goes to the primary selection, unless the field is masked, and a middle click pastes it where it lands, newlines as spaces as Ctrl+V does. Only a selection the field's own press started counts on release, so a click elsewhere leaves the primary selection alone.
- **On Wayland it depends on gpui 0.2.2 and the compositor**: the compositor must offer `zwp_primary_selection_device_manager_v1` (GNOME, KDE and the wlroots compositors do; weston 14 does not, so a middle click pastes nothing there), and gpui claims the selection with the serial of the window's last key press, so until a key has been pressed in the window a compositor that checks serials (sway) refuses it and nothing is pasted.
- **Checked live on 2026-11-04** (cornercase 0.12.280, gpui 0.2.2, Debian trixie arm64 in a container, xdotool, xclip). X11 under openbox: a double-clicked word in the shell reached `xclip -o -selection primary` while the clipboard kept what xclip had put there, and a middle click typed it at the prompt; a word dragged over in one pane and middle-clicked into the other pasted there and made it active; text xclip put in the primary selection pasted too; Ctrl+Shift+C still copied to the clipboard with its toast; with mouse reporting on (`printf '\033[?1000h\033[?1006h'; cat -v`) a middle click reached the program as `^[[<1;31;21M^[[<1;31;21m`, a press and a release of the middle button, and Shift+middle pasted; in `vim -u NONE -N -c 'set mouse=a'` a middle click reached vim, which put its own register, and Shift+middle inserted the primary selection; in the Search field a middle click pasted it, a drag and Ctrl+A put the field's selection in it, and a click elsewhere left it alone. Wayland under sway 1.10 nested in the X screen: a word double-clicked in one pane pasted into the other once a key had been typed in the window, and not before. Not checked: GNOME and KDE themselves, a program with bracketed paste reached by a middle click (it is the Ctrl+Shift+V path), macOS live (its paths did not change: the same `selection --copy`, the same two buttons; the tests cover its side of each decision).
- **The right button is cornercase's in every pane**, even one whose program reads the mouse, since almost no program uses it: a click opens the pane's menu, a drag onto another pane moves it there (`move-pane`; how it is drawn is under Moving panes). The menu offers "Send the right click to the program" for the rare program that wants it.
- **Where a dropped pane goes**: the middle third of the target's card both ways swaps the two; elsewhere the nearest edge takes that side (`--place left|right|above|below`), measured in points on the card rather than in its cells, so its padding counts too.
- **Dividers are the gaps between cards**: a press there, or 4 px into either card, takes the split. A drag sets its ratio so that the gap lands under the pointer (`Along::ratio`: the first side's cells are what lies between the split's start and the pointer, less that side's padding and half the gap), kept between 0.1 and 0.9 and coalesced so only the latest reaches cornercase; a double click evens the split out, as on the TUI's borders. The pointer is a resize arrow over a gap, so the drag can be found: the canvas inserts a hitbox per gap in its prepaint and asks for the cursor over it in its paint, after the terminal's own I-beam, so it wins there. While a divider is dragged the whole terminal keeps the arrow, since the gap reaches the pointer only once cornercase answers. Checked live on 2026-10-24 (cornercase 0.12.190): a 100 pt drag moved the split by 13 columns, with the gap under the pointer.
- **The wheel** accumulates fractional lines and acts per whole line, at most 25 at once. A program that reads the mouse gets wheel events; a full-screen program (alternate screen) with alternate scroll gets arrow keys, and without it nothing; anything else scrolls cornercase's scrollback (`scroll --up/--down`).

## Paths and web addresses under the pointer (`links.rs`, `model/link.rs`)

- **A path a program printed is a link, as in the TUI** (its `design/keys-and-mouse.md` and `design/files-panel.md`): cornercase decides what is a path and which file it is (`link --pane P --cell X,Y --json`: the canonical path, whether it is inside the workspace, its relative path, its lines and the cells it takes), so the rules (`:12`, `:12-30`, `#L12`, `~/`, the foreground program's folder, then the workspace's root) stay in one place; the command exists for programs that draw cornercase's terminals themselves.
- **Asked only when the pointer enters another word**: the run of word cells under it (the double click's classes, so `src/main.rs:12` is one word and brackets end it) is the key; moving inside it asks nothing, a blank cell or the padding asks nothing and forgets the link. One question at a time, run beside the queue (it only reads, and hovering must not wait behind typing); a word entered meanwhile is asked when it answers, and an answer for a word the pointer has left is dropped.
- **On a Windows server a backslash is part of the word** (decided 2026-11-04): cornercase there takes `C:\src\app\main.rs:10` and `src\x.rs:3` as paths (its `design/files-panel.md`, Paths in panes), so with `\` outside the word the pointer crossing such a path entered a new word at every folder, dropped the underline and the card, and asked again. The key may be no wider than cornercase's path, or a link inside it would never be asked, so on Unix it stays as it was. Checked only by unit tests on macOS.

The wheel and typing drop it; leaving the terminal forgets it.

A click with a modifier, a double click and Shift keep their meaning. After the click the link stays off until the pointer leaves the word, so the card does not come back over the panel just opened.
- **Resting on it shows the file in a card** (`design/files-panel.md`, Peeking at a path).
- **A web address is a link too, found here** (asked for on 2026-11-01: addresses should open in the Browser panel). cornercase leaves them out of `link` on purpose (its `files/link.rs` skips any word holding `://`): in the TUI the terminal it runs in finds them, and here this window is that terminal, so finding them is drawing, not server logic. An `http` or `https` hyperlink the program printed (OSC 8) takes all the cells of that address in the row, blanks and brackets included, so it is one spot, which keeps its destination: a label redrawn with another address is another spot, and a click checks the address under it again, so it never opens the old one; otherwise the address inside the word under the pointer counts, from its `http://` or `https://` to the word's end, less a `.`, `:` or `?` that ends a sentence. It is found without asking cornercase, so it is underlined at once, with the hand, as a path is. What counts as a web address is `link::is_web`: an `http` or `https` scheme in any case, a host, and no blank or control character (tightened on 2026-11-02, when a pull request's check links took the same rule, `design/pull-requests.md`). Limits: an address the program wrapped onto the next row is cut at the row's end (`surface` does not say which rows go on, #701 upstream; no line says so, since it would sit on every address), and one holding a character outside the word class (`(`, `,`, `!`, `'`) stops there.
- **A plain click opens a web address where Settings › Links says** (asked for on 2026-11-01: "configurable in settings, whether it opens in your default browser or in cornercase's"): the default browser by default, what a terminal does, or the Browser panel (`Store::open_in_browser`, `design/browser.md`), docking it. The click is held back like a path's, so a drag still reaches the program. A `localhost` address while the window shows another machine, or a machine's tab, always opens in the panel, the one place that reaches that machine's servers (through its ssh tunnel); the system browser would open this Mac's. The setting is the window's own, kept on this Mac (`prefs.rs`, `design/settings.md`): cornercase's TUI has no browser of its own, so cornercase's settings have nothing to say about it.
- **Resting on a web address shows the page in a card**, as resting on a path shows the file (asked for on the same day: "preview it like a file, keep the default behaviour, and offer to open it in cornercase's browser in the preview"). The Browser panel's Chrome loads it in a page of its own, 1280 × 800 at one device pixel per CSS pixel (a crisp picture at the card's width on a Retina screen), waits for `document.readyState` to be complete (at most 8 s) and half a second more for scripts to draw, and takes a JPEG; the header names the page's title and its address. Clicking the picture opens the page as a click on the address would; the header has Open in the Browser panel and, unless the address is another machine's `localhost`, Open in your default browser.
  - **Which pages load at once** is the second setting of Settings › Links, local addresses by default (`localhost`, `*.localhost`, an IPv4 loopback address, `[::1]`, `0.0.0.0`: a dev server, the case the panel exists for; the host is parsed as an address, so `127.example.com` is not local, found by CodeRabbit and Greptile on #11). The host is read by the `url` crate, which follows the WHATWG URL standard as Chrome does, rather than by hand: Chrome reads `HTTP://LOCALHOST`, `%6cocalhost`, `localhost.`, `127.1`, `0x7f.0.0.1`, `2130706433` and `[::ffff:127.0.0.1]` as this machine, and a hand-made parser that missed one would have loaded this Mac's own port for an address meant for the other machine's tunnel (found by CodeRabbit on #12, once `is_web` took a scheme in any case), else every address, or none. The others show a card that says why and has Show the page. Loading a page is a GET, and a GET can act: a one-time sign-in link printed by a CLI would be used up by the pointer crossing it. Rejected: loading every page on hover (that risk, and a request to any site the pointer passes over), and a card with only the address (it would not be a preview).
  - **Previews load apart from the panel's tabs**: in a browser context of their own (`Target.createBrowserContext`, disposed when the window's connection to Chrome ends), so they carry none of the profile's cookies, and with downloads denied for it (a link to a file shows "it may be a download"). Their pages never show as tabs: the panel skips any target of that context. `alert`, `confirm`, `prompt` and `print` are stubbed before the page's scripts run, since a dialog would block the page and the picture. Each step waits at most 5 s for Chrome (8 s for the navigation), so a page that never answers ends in a note rather than a card that loads forever. Hovering a local address starts the panel's Chrome if it was not running; that start is the slow part of the first preview (a second or two).
  - **On another machine** a `localhost` address goes through a tunnel to that port, waiting at most 15 s for it: cornercase's hold from 0.13.50 on both computers, which a preview never starts (it loads through one that is up or opening and otherwise says the port is not tunnelled and that opening it tunnels it), else the ssh tunnel the panel opens (`tunnels.rs`), where a tunnel that is retrying is waited for, not started again. One parser (`model::link::loopback_port`) decides both what counts as local and which port the tunnel forwards, so nothing local can slip past the tunnel to this Mac: an address without a port takes its scheme's (80, 443), and a `*.localhost` name is kept in the tunnelled address so a server that routes by host still sees it (two parsers had let `http://localhost/` and `app.localhost` load this Mac's pages, found on #11).
  - **A preview the card no longer wants stops**: its task belongs to the card, so hovering another address or closing the card drops it, and its page is closed when dropped (`Opened`), rather than loading and taking a picture nobody sees. The page is created by a task of its own that outlives the preview: a preview dropped while Chrome is still creating the page would otherwise lose the reply that names it, and leave it open (found by Greptile on #11).
  - Limits: each hover of another address loads the page again (no cache, so a dev server's page is never stale); a second window on the same Chrome profile sees the first one's preview pages as an agent's tabs for the second or two they live.

Not checked: a click into the default browser, Every address and When asked, and a machine reached over ssh.
- **⌘-click always opens with the system** (macOS, or the Linux desktop with Ctrl+click, as Linux terminals open links, `keymap::opens_with_system`), whatever the setting, as it does for paths: the setting chooses only the plain click.
- **⌘-click opens a hyperlink the program printed** (OSC 8) or a web address in the text with the system browser, or else a path cornercase recognises under the pointer (`link --cell`), opened with its default app (`desktop::open`: macOS's `open`, else `xdg-open` or `gio open` on Linux, on a thread of its own so the queue never waits; its failure is a toast, a missing `xdg-open` included); on another machine (`design/remote.md`) the path is copied instead, since it is not on this machine, and so is the path of a `file://` hyperlink (its host is dropped and its `%` escapes read, and `file:///C:/x/y.rs` from a Windows server reads as `C:\x\y.rs`, the path as Windows writes it); other hyperlinks open here. Paths, which gpui opens the same way without saying why it failed, go through `desktop.rs`. Checked live on 2026-11-04 (X11 in a container with no portal): the Browser's "Open in the system browser" ran `xdg-open http://localhost:8765/`, and a click with the platform key (Super then, before Ctrl+click took its place) on a path a shell printed ran `xdg-open /tmp/demo/clip.mp4`.

## Moving panes

Code: `src/terminal/pane_drag.rs` (the handle, pressing, dragging, dropping), `src/render/moving.rs` (the move as data over time), `src/render/ghost.rs` (its painting).

- **Asked for on 2026-10-31**: dragging panes, "with good transitions and a wow effect", and visible that a pane can be dragged, as other apps show it. Until then only the right button moved a pane, with nothing drawn until it landed, which nobody could guess.
- **A handle, as Ghostty does**: Ghostty 1.3 shows a grab handle when the pointer nears the top of a split (1.3.1 shows it only then, after people found handles everywhere distracting); Warp drags a pane by its header. Here a pill sits in the top padding of a card, centred, while the pointer is within 44 px of that card's top and the tab has more than one pane (a pane alone has nowhere to go: `move-pane` moves within a tab). It fades in, widens and brightens under the pointer, the pointer turns an open hand, and its tooltip says "Drag to move this pane". It spans 4 to 14 px below the card's top, clear of the 4 px a divider's grip reaches into the card under it, and stops at the first row of text.
- **Rejected**: handles always shown (one on every pane, all the time, for a rare action); a header bar on each pane (a row taken from every pane); press and hold anywhere to lift the pane (pausing before dragging a selection, a common way to select, would lift the pane, and a program that reads the mouse gets the press at once); gpui's own drag and drop (`on_drag` answers the left button only, so the right-button drag would need a second path, and it says nothing when a drag ends without a drop, which the ghost needs to fly home).
- **Lifting**: past 5 points from the press the pane lifts. Its card turns hollow (fill and text faded, a dashed cobalt edge) while a ghost, the pane's own text drawn live at a smaller size (at most 42 %, 300 by 220 points), shrinks out of the card toward the pointer over 240 ms and hangs from its grip under it, with the floating cards' shadow and a cobalt glow. It is drawn `deferred`, over everything, so it can cross the sidebar or the dock. The pointer is a closed hand over the whole window.
- **Aiming**: over another pane a drop zone grows in, the part of the card the pane would take (the half toward the nearest edge, or the whole card for a swap), as a cobalt wash with a bright edge. Moving to another place or pane glides it there in 170 ms instead of jumping; over a gap between cards it stays where it was; over its own card or outside the panes it shrinks away. A caption under the ghost names the place (Swap, Left, Right, Top, Bottom) with its arrow: drawn in the zone's middle it was hidden by the ghost, which hangs right where the pointer is.
- **Landing**: a drop sends `move-pane … --json` (on a machine's tab through `Root::shown()` and the tab's own queue with `--boot`, `design/machines.md`). The frame with the new layout arrives about 20 ms later (measured on 2026-10-31 with 0.12.234, before the command had even returned), and the window waits for it with the card still hollow. The answer carries the tab's layout (`--json`, #112: `move-pane` has taken it since upstream #360, release 0.12.137, so the minimum 0.13.19 needs no gate; a line of `requests --follow` gives the printed JSON as its `json`, `cli/requests.rs`, so the machine tab's queue and this computer's read the same text); a changed one leaves the ghost waiting for its frame, which on a machine's tab can come after the answer, since the two travel on different connections, so the order does not matter. Then every other card slides from where it was to its new place, eased over 380 ms (the bounds from before the change are kept and drawn moving to the new ones, the text clipped by the moving card), while the ghost flies into the moved pane's new card, growing back to full size, and fades into it over the last 30 %; the pane then glows cobalt for 0.9 s. Move pane in the pane's menu slides the cards the same way, without a ghost. Only a move the window started slides: sliding every new layout would make a divider drag and a window resize trail behind the pointer.
- **Going home**: a release over its own card or outside the panes, or Escape, flies the ghost back into its card, which fills in again. A refused move (cornercase refuses when the tab would have no room for every pane) toasts cornercase's reason and turns the zone red as the ghost goes home. A move that changes nothing (the layout in the answer is the one it was dropped on) goes home as soon as cornercase answers: `move-pane` is sent with `--json` (Landing). A drop that sees no new layout within 1.5 s goes home too, for an answer that never comes or cannot be read. A refusal always arrives as an error and goes home at once. Unchanged means the layout is equal to the one dropped on, a split's share (`Branch::ratio`, `Share`) included: cornercase re-inserts the moved pane at an even split, so dropping a pane on the side it already holds after a divider was dragged changes the share, and that move waits for its frame and slides. Fixtures from cornercase 0.13.32 on 2026-11-10 (`tests/fixtures/move_pane/`) pin the printed JSON, the same JSON in a line, and a refusal in both forms: a refusal exits 1 with nothing on stdout even with `--json`, and a line gives `{"status":1,"error":…}`. A refusal for lack of room (`tab N has no room for every pane after that move`) could not be made on the bench in a short try, so the fixture is a pane moved onto itself, which is refused the same way.
- **On a machine's tab** the handle shows on a live tab whose command line takes `--boot` (cornercase 0.13.30 or newer here), and the drag, the right-button drag and Move pane read the machine tab's grid and layout and send on its queue; a refused move, or a stale `boot` (`vps restarted: nothing was sent`), goes home red with a toast.
- **The right button** lifts a pane only once the pointer leaves its card, so a release on its own pane still opens its menu, as before. gpui 0.2.2's macOS view takes `mouseDragged:` but not `rightMouseDragged:` (found live on 2026-10-31), so the window hears nothing between a right press and its release: no ghost or zone shows during a right-button drag, the pane is drawn moving only as it lands (the ghost flies from its old card to the new one), and a release outside the panes leaves nothing behind. The handle, held with the left button, shows the whole drag. Reading the pointer from the system while the right button is held was not done: a second path for a gesture the handle already shows.
- **The drag takes the mouse**: while a pane is pressed, the window listens to every move and release in the capture phase and stops them there, so the ghost follows outside the terminal and nothing under the pointer reacts. A move that arrives with the button up (released outside the window) cancels it.
- **Frames**: the canvas asks for the next frame only while something moves (a lift, a gliding zone, a flight, a slide, a glow); a still pointer over a settled zone draws nothing more, as the rule for idle animations asks (`design/widgets.md`).
- **Not done**: dropping a pane on another tab or on the tab bar, as Warp does: `move-pane` moves a pane within its tab only (0.12.234).
- Checked live on 2026-10-31 with cornercase 0.12.234, on a throwaway tab of three panes: the handle and its tooltip on hover, the open hand over it, a drag from it (the lift, the ghost over the sidebar, the zone gliding from Swap to Left, the caption under the ghost), the drop (the cards sliding into three columns, the ghost growing into the moved pane, which became active), Escape (the ghost flying back into its card, the layout unchanged) and a right-button drag onto another pane (moved and drawn as it landed, with nothing during the drag, which is how the right-button gap above was found). Not checked live: a refused move, and the menu's moves.
- Checked live on 2026-11-10 with cornercase 0.13.32 on this computer and on a machine, a debug build of 0.1.57 on macOS (Apple silicon), the drop timed from the release time `drag` prints (`design/manual-check.md`): a pane dropped on a place that leaves the layout as it was, on this computer's tab and on a machine's tab, was filled in with no ghost by about 0.5 s (at about 0.25 s the ghost was still flying home, a flight takes 0.3 s), where holding the ghost hollow until 1.5 s and then flying home was the old path; a move that changed the layout landed on both, and the layout read back with `status --json` was the new one. Not checked: a refused move in the window (no tab of three panes could be made to refuse for lack of room, as the split itself is refused in a small window, so a refusal's text comes from the fixtures), a stale move on a machine's tab, a drag with the old build to compare timings, that the move's line carries `--json` (it goes through the running `requests --follow`, which no log shows: that rests on the unit tests that fail without it), a move that changes only a split's share (a unit test, not the window), Linux and Windows, and a real machine.

## Plugin popups

- **What shows one**: the `app` feed's `popup` (`status --app --follow`, kept in `Store::app`) says a popup is open anywhere; while it does, `Popup` (one entity per `Store`, a global, so `app.rs` holds nothing for it) follows `surface --popup --patches` and draws its one pane. The stream ends when that popup closes (and a later popup needs a new one), so an ended stream is followed again after 500 ms while the feed still names a popup, after 5 s when it failed the same way twice; the card says why meanwhile.
- **A floating card over the terminal**, not the window: the glass card of sheets with the action and plugin as its title and a `✕`, the popup's terminal drawn as a pane card by the same painter as the panes (`render::popup::paint_popup`), on a veil over the terminal area that occludes it, so the panes behind take no pointer. The popup keeps the size cornercase gives it (cornercase's own window's while one is attached, since it follows the shared size, else this window's view's, as `plugin run --view` asks; `design/plugins.md`); larger than the terminal area, it is cropped to what is left within a 24 px margin, measured by a probe the size of that area.
- **Keys and text go to the popup while it is open**, through the same path as the pane's (the terminal's focus, `Root::on_key`, the input method), so dead keys and ⌥ characters work there too; `type_in` sends them with `input --popup --pane ID`, the id from its frames, so nothing reaches a popup opened since. **Escape reaches the popup's program**, as in the TUI: popups host fzf and curses menus that use it, so it stays handled once in `Root`, which passes it on when the terminal is focused and no dialog or sheet is open. **⌘W closes it** (`plugin popup-close`), after a dialog or sheet and before the docked panel or the pane, as does its `✕`; ⌘V pastes into it. A click in the popup gives the terminal the focus back; the mouse reaches the program only when it asked for it (presses, releases, the wheel as for a pane).
- **Each event is its own `input` command** on the ordered queue (`Store::cmd`), since the queue batches input by pane only; a popup takes a few keys at a time, so a process per key is acceptable.

## Tabs

- The tab bar shows the shown workspace's tabs as rounded pills floating on the ground of the title row, the shown one filled lighter, with its status, name, other panes, model, account (`design/accounts.md`) and context, and a close button (always on the shown tab, on hover on the others). A tab renames in place on a double click, drags to reorder (`move --tab`, landing before or after by the drag's direction, outlined in cobalt, thicker on the side it lands; dropped on `+` it goes last) and opens its menu on a right click.
- **A tab's details read as the TUI's** (its `design/memory.md`, 0.12.181, 0.12.186): `Opus 5.5 · 23%`, with `compacted` where the percentage goes once the conversation was compacted, until the next reply (without a model too, as the sidebar's row has it; a bare percentage without a model stays out), and `1.2 GB` at the end, what all the tab's panes use (`Tab::memory`, `memory_size`: whole MB, then GB with one decimal, never less than 1 MB). A shell tab shows the memory alone. The window does not read the `memory` setting for this: `view` carries `memory` only while it is on. It carries it only for panes on screen, so a tab just shown has none for up to 2 s. `model` and `context` in Settings › UI take their parts away, and `compacted` follows `context` (`design/sidebar.md`).
- **Closing a tab that runs an agent asks first**, since closing it stops the agent; its worktree and branch stay. A shell tab closes at once, like closing a pane without an agent.
- **The tab strip is a cached part** (#115, `design/widgets.md`): what `tab_group` draws (tabs, arrows, `+`, the watcher) is the part `Parts::tabs`, redrawn when `TabsKey` moves. The title row (its drag area on Windows, the grip on Linux), the split buttons and the window's own controls stay in `Root` and are laid out on every frame: gpui 0.2.2 does not replay a reused view's window control areas, so inside a part the caption would stop dragging and its buttons would stop acting as the system's. Working badges are painted by the strip's orbit layer (`design/widgets.md`), so a working tab scrolled out of the strip draws nothing and counts for nothing. `strip::watcher` notifies the part, not `Root`: what it changes (the scroll, the arrows) is drawn only there. The tab bar's actions and menu are in `tabs/acts.rs` (`design/code-layout.md`).
- `+` offers a shell, the default agent (`dialogs::start_in`) or the start dialog.
- **Every start here answers as soon as its tab is open** (`--focus --placed`: `+`, ⌘G's dialog and a row's `Start agent here`, the Issues sheet's in `design/issues.md`). Without `--placed` a `start` holds its answer while the agent asks to trust the folder, with a prompt or without one, and these run through the ordered queue, which holds the keys behind it: on 2026-11-07, on `main`, `Start agent here` showed the tab with the question, and `Starting an agent…` stayed while `1` and Enter never reached it. Nothing these commands need is lost: the account (`--account`) is set when the tab is made and the worktree made before the answer, the prompt follows the launch, and what is refused before the tab (no default agent, a worktree that fails) still answers with an error, a toast. What fails after the answer shows in the tab (`design/machines.md`). They send nothing right after it, the one thing upstream's help warns against, so no caller needs the wait. A machine reached with `--remote` older than 0.13.0 refuses the flag, and that is the toast.
- Checked live on 2026-11-07 (cornercase 0.13.19, Linux x86_64 under Xvfb with lavapipe, a private server and a fake agent that asks to trust the folder before it reads its prompt; no macOS, no Windows): `+`'s default agent, a workspace's and a project's `Start agent here`, and ⌘G with a prompt, a worktree and an account: the tab with the question within a second, no job left in the status bar, a typed answer reached it and the prompt followed, on that account in that worktree.
- **Tabs past the edge scroll** (`tabs/strip.rs`, the TUI's 0.11.16): the strip is a horizontal scroller (`overflow_x_scroll`), so the wheel moves it as gpui gives, and `‹` `›` appear at its ends when the tabs do not fit, each scrolling to the next tab that is cut (`stepped`), and fainter at the end of the row; before them the row held only what fit and the rest could not be reached by mouse. Whether they show is known after a layout, so a zero-size canvas after the strip (`watcher`) looks at the `ScrollHandle` and asks for another draw if it is wrong. The arrows take room, so once shown they leave only when the tabs would fit without them (`overflows`), which cannot flip back and forth.
- **The active tab stays in view** (`followed_scroll`): another tab or a narrower row brings it in by the least it takes, another workspace starts over at the first tab, as the TUI's `follow` does, and a tab that grows past the edge (a new tab's details arrive after it was followed) is kept in view, unless you scrolled away from it: the wheel and the arrows are left alone until the active tab changes. The watcher computes this after the layout rather than `ScrollHandle::scroll_to_item`, which gpui 0.2.2 applies with the strip's bounds of the frame before: back from a project with one tab, whose strip was one tab wide, it scrolled a tab too far.
- **A long tab name ends in "…"** (#156, 2026-11-13). A tab's name is at most 200 px (`NAME_MAX` in `tabs.rs`, about 30 characters), cut by `ui::one_line` in a box that shrinks, the whole name in its tooltip. Both kinds of tab share it (`tab_label`, from `tab_name` and `machine_tab`). As a `whitespace_nowrap` text in a `flex_none` pill, a long name made one tab as wide as its whole name, its ✕ far out of view; a routine's run names its tab with its whole prompt, about 900 characters (usecornercase/cornercase-terminal#774). 200 px is a little more than the TUI's cut at 24 cells (`MAX_NAME` in its `ui/tab_bar.rs`) and about what a browser gives a tab's title. The tab itself is not capped at the strip's width, so a tab wider than the strip (an agent's model, account, context and memory) stays wider than it, as every tab did, and the strip scrolls to it. A cap at the strip's width (`max_w` of 100 %) was tried and dropped: taffy also caps the tab's least width by it, so a tab whose status, `+N`, details and ✕ are wider than the strip is cut to the strip while those parts keep their width, and they are drawn over the next tab; gpui 0.2.2 has no least width of "what the parts need". The tooltip lives in the strip's part as the `+` button's does: one showing refreshes the window (`design/widgets.md`), and gpui draws none during a drag. ## Context menu

- **One menu for the whole window**: a right click or a row's `⋯` opens it at the pointer, drawn over everything (deferred, snapped inside the window). Escape, a click outside or any entry closes it, and focus returns to the terminal.
- **A submenu takes the menu's place**, as the TUI's *move to group* does, instead of opening beside it: no hover timing, and it fits a narrow window.
- **A heading names what follows** (`Entry::Heading`, a plugin's name over its entries, `design/plugins.md`): the keys skip it, as they do a line, and it takes no click.
- **Separators come from optional entries left out**, so the menu drops separators at either end and doubled ones rather than every caller checking.
- **An entry runs on the window after the menu has closed**, so it can open a dialog or another menu.
- Entries that stop or remove something are red (`danger`); one of several choices can carry a check at its end (`choice`).
- **A long label ends in "…" inside the menu** (#152, 2026-11-12). `menu_row` holds its label in `ui::one_line`, in a box that shrinks (`min_w_0`), and a heading (`menu_heading`, a plugin's name) is cut the same way. So a long group name in Move to group ›, a plugin's name or run, a pane's program or a page's `<select>` option (`panels/browser/select.rs` draws its rows with `menu_row`, up to 420 px) stops at the menu's edge, and a submenu's `›` and a chosen entry's tick stay at the row's end. As text that would not wrap (`whitespace_nowrap`), a long label ran past the card. The menu keeps its width, 200 to 320 px, the width its notes are written for. Cut, as menus are on macOS, rather than wrapped: an entry of several lines reads as several entries, and `above` places a menu over the pointer by counting one line per row. Rejected: a wider menu (group names have no limit upstream, so it only moves the cut and covers more of the terminal for one name); a tooltip on the rows (it would show on every short entry, and `Entry` cannot tell a name from an action). A group's whole name is in its own menu's Rename group, Icon and colour (#145) and Delete group…; the sidebar's row cuts it too. Checked live on 2026-11-12 (debug builds of 0.1.65 before and 0.1.67 after, gpui 0.2.2, cornercase 0.13.39 on macOS 26.6.2, Apple silicon, a private server): groups of 120 characters with spaces and 102 with none, the project's menu and Move to group › opened by a right press and keys; before, both ran past the card; after, both end in "…" at the card's edge; the project's whole menu with short labels, `›` included, is pixel-identical before and after. Not checked: `›` or a tick beside a cut label, a plugin's heading, the Browser's `<select>` popup, Linux, Windows.

## A machine's tab

Code: `Root::shown` and `Root::input` in `app/machine.rs`, and `terminal/` and `tabs.rs` reading through them. Everything else about it is in `design/machines.md`.

- **The same code with the other queue**: drawing, the layout, keys, pastes, the wheel, a selection, dividers and a click on a pane read `self.shown()`, the connection the frame came on, so a pane id only ever goes back to its own server. Whose session a pane is looked up in goes the same way (`shown_session`): the status bar reads `vps · zsh · ~/code/shop`, with the home there, and a word's path rules are that server's.
- **Keys** (`keys_go`, plain): a live tab's active pane; while another tab arrives they wait for it; before the first frame and while it is down a toast says `vps unreachable: nothing was sent` (or what else holds it), and nothing is kept. With no machine shown, no frame means nowhere, as before.
- **`takes_input`** is what the mouse and the wheel ask, and `frame_shown` what the painter asks (the handle is drawn with `takes_input`, as it is an affordance for input): a tab that is down still draws its last frame, and the layout it leaves behind must not reach a pane.
- **Selections are read and never copied there** (`selection --pane P --json`, without `--copy`, which would use the machine's own clipboard and toast), and reach this computer's clipboard (or the primary selection on Linux) cleaned of control and hidden characters, line breaks and tabs kept, since they come from another machine (`selection::cleaned`).
- **The right button** lifts as here when its program does not read the mouse or Shift is held (`right_lifts`, `press_right`): a release over the same pane opens the machine's pane menu, a drag onto another moves it (`design/machines.md`), and it never focuses. A program that reads the mouse gets it, focusing its pane first, and its release too, which a local right press, whose release the menu takes, does not need.
- **What a local path means differs**: no underline, no peek and no ⌘-click on a path there (`spot_under` keeps only web addresses; ⌘-click selects as a plain press), rather than opening a file here by mistake; a web address there is underlined, previewed and opened (`design/machines.md`, "A machine's page in the Browser panel"). A file dropped or a picture pasted goes through `paste-file` on the machine's queue, as for a window on another server, so its path is there.
- **Keys that act on the tab's structure**: splitting there works, ⌘[ ⌘] and the tab keys (⌘1…9, ⇧⌘[ ⇧⌘]) move there, ⌘T and the keys that walk workspaces, projects and agents go back and act here, as they name what is here, ⌘W and ⇧⌘W close there, and ⌘R marks the active agent there with `--boot`, or says what it needs on this computer (`Marking an agent on vps needs cornercase 0.13.30 or newer on this Mac`). A pane's `↓ n more` and its held messages read the machine's frame and session like the rest, and the click that goes back to the bottom goes on its queue.
- **Dimmed** (`Surface::dimmed`, 40 % over each pane's own fade, no cursor) while it is not live, with the card over it (`terminal/machine_card.rs`). The handle is off (`hover_handle`), as it is below cornercase 0.13.30 here, and `drop_drags` releases a press before the connection it belongs to is left.
