# Terminal

Code: `src/terminal.rs` (keys, ⌘ shortcuts, the surface element), `src/terminal/` (`mouse.rs`, `selection.rs`, `links.rs`, `pane_menu.rs`, `pane_drag.rs`, `input.rs`, `pasting.rs`, `popup.rs`, `no_tab.rs`), `src/render.rs`, `src/render/layout.rs`, `src/render/popup.rs`, `src/keys.rs`, `src/tabs.rs`, `src/context_menu.rs`

## Keys and text

- **Keys reach the terminal only while its own focus handle is focused and no dialog or sheet is open**, never while a text field or a focused panel has the focus: a modal over the terminal must not type into the shell behind it. ⌘ shortcuts are the exception and are read in `Root::shortcut` whatever has the focus (⌘C and ⌘V act on the terminal only when it is focused).
- **Every ⌘ shortcut is one row of `keymap::SHORTCUTS`**: a command, its keys and whether it needs ⇧. The same table gives the buttons' tooltips (`with_keys`) and the ⌘/ dialog, so a hint cannot drift from its key. A row without ⇧ also answers with ⇧ when no shifted row takes the key, so ⌘+ (⇧= on a US keyboard) and ⌘? work. Only the app menu's system keys (⌘Q, ⌘H, ⌥⌘H, ⌘M, ⌃⌘F) are gpui actions in `main.rs`, so the menu bar shows them; the help lists them from `SYSTEM_KEYS`.
- **Why these keys**: they follow macOS terminals where one exists (⌘W closes the pane as in iTerm and Ghostty, ⌘[ ⌘] move between panes, ⌘9 is the last tab as in browsers, ⌘F finds). Panels without a mnemonic letter took a free one with ⇧ (⇧⌘S the scheduled queue, ⇧⌘G flows next to ⌘G, ⇧⌘X plugins as in editors); ⇧⌘K connects to another server, as Terminal's New Remote Connection; ⇧⌘Q was avoided since macOS logs out on it. ⇧⌘P goes to a file (`design/files-panel.md`, asked for on 2026-10-31), the quick open editors put on ⌘P; Processes moved from it to ⇧⌘M, the M of Activity Monitor and of memory. ⌘P, free since the sidebar's filter went (2026-10-31, `design/sidebar.md`), shows the pull request of the workspace on screen since 2026-11-01, the P of the TUI's `g p` (`design/pull-requests.md`); making it a second key for ⌘F had been rejected, one shortcut per job. macOS keeps ⇧⌘Q, ⇧⌘3, ⇧⌘4 and ⇧⌘5 (screenshots) and ⌘? (the Help menu's search), and the app menu ⌘Q, ⌘H and ⌘M; a test fails when a row takes one of them, except ⌘?, which the ⌘/ dialog answers since the app has no Help menu. cornercase has no command to clear the scrollback or zoom a pane, so ⌘K and ⇧⌘↩ stay free.
- **⌘W closes what is on top**: a dialog, else a sheet, else the docked panel when the focus is in it, else the active pane, asking first when it runs an agent (as its menu does). ⇧⌘W closes the shown tab the same way. While a dialog is open, every other shortcut is ignored, as macOS ignores menu keys under a sheet.
- **Escape is handled once, in `Root`**: it closes the dialog, else the sheet, else brings the focus back to the terminal from a panel or the sidebar; only with the terminal focused and nothing open does it reach the program (vim needs it). Dialogs and panels used to close themselves on Escape without stopping it, so a dialog over a sheet closed both; none of them handles it now. A text field emits `Cancel` (rename fields undo, dialog fields close), except a search or filter field (`clears_on_escape`), which clears its text and, when already empty, lets Escape go on to `Root`, as Spotlight does.
- **A click on the veil closes the dialog or sheet**: the cards and toasts `occlude`, so a click on them never reaches the veil. The veil occludes too, so nothing behind it takes the pointer: a click that closed a sheet also reached the program in the pane under it, and the borders' resize handles showed their cursor through it.
- **Tab moves between a dialog's fields** (`TextField::in_tab_order`, gpui's `focus_next`). Only dialog fields are tab stops: gpui's tab order spans the whole window, so fields behind a dialog would be reached too. In other fields Tab goes on to the panel (the Search panel switches modes with it).
- **The context menu takes ↑ ↓ ↩** (and space): the highlight skips separators and wraps; a submenu opens on its first entry.
- **Printable text goes through the platform's input method** (`EntityInputHandler for Root`), which composes accents, emoji and ⌥ characters (⌥2 types `@` on a Spanish keyboard). `keys::key_event` takes only what is not text: named keys, and anything with Ctrl. Encoding text ourselves would break dead keys and every non-US layout.
- **Ctrl with a key** sends the key itself, lower case (ctrl+space, ctrl+letter, ctrl+[); cornercase encodes it for the program.
- **⌥ with a key that types nothing else is meta** (⌥← moves by words in the shell): the key goes as a named key with `alt` rather than as text. ⌥ with a key that types a character is left to the input method.
- **Control characters typed through the input method are dropped**; Enter, Tab and friends arrive as named keys instead, so they are not sent twice.
- **⌘V pastes text, else an image** (`terminal/pasting.rs`): text on the clipboard goes as an `input` paste; a clipboard with only an image (a screenshot taken with ⌃⇧⌘4) goes to `paste-file --pane P --name pasted.<kind> -` on standard input (#479 upstream), which keeps the file on the server's machine and pastes its path, so an agent there can open it. gpui reads the text first when both are there, as other terminals do. The name comes from gpui's format, since cornercase sniffs only some kinds (a TIFF would get no extension).
- **Dropping files on a pane pastes them** into the pane under the pointer (else the active one). On this Mac their paths are pasted as text, each followed by a space and quoted for the shell only when it needs it, as Terminal and Ghostty do: copying the file would cost a copy, a 32 MiB cap and refuse folders, for a path the agent can already read. On another machine each goes to `paste-file --pane P FILE`, which reads it here and pastes the path there; a folder or a file over 32 MiB is refused with cornercase's message. Checked live on 2026-10-29 (cornercase 0.12.225): pasting an image here and through `--remote`; dropping was not checked live (no tool here drags from Finder).
- **⌘0 resets the font size to 13**, the size the window opens with; ⌘+ and ⌘- step by one point between 8 and 32. A new size drops the measured `Metrics`, which are measured again on the next draw.

## Drawing

- **A canvas measures, then paints**: the prepaint step places the panes (`Layout::new`), fits as many whole cells as the space holds once the panes' padding and gaps are taken out (`Layout::extra`; at least 1, at most 1000 columns and 500 rows) and, when that differs from the size asked last, asks cornercase for it on the next frame (`set_size` deferred), so a resize never re-enters the window's update. The mouse and the input method read the layout the last prepaint kept.
- **Every pane floats on a card of its own**, rounded, with 12 px (`PADDING`) around its cells and 8 px (`GAP`) of ground between cards, as the tabs float in the title row. cornercase lays a tab out in cells, with two columns or one row between panes: about 16 px at 13 pt, no room for a gap and padding on both sides, so cards drawn over its cells would have their text touching the shared edge. The window places the panes itself instead: it walks the split tree the surface sends (`layout`), gives each pane its cells and its padding, puts the gap between the two sides of each split, and asks cornercase for fewer cells by what that adds. That extra depends only on the tree's shape, not on the size, so asking for it does not loop. The first side of a split takes what it needs and the second the rest, so the last cards absorb the fraction of a cell left over and a pane beside a stack takes the stack's whole height. A surface without a tree (older servers) keeps the panes on one grid. cornercase has no option for wider dividers.
- **Text sits on the grid whatever font a glyph falls back to**: words of single-width cells are shaped together with a forced advance of one cell; a wide cell (followed by an empty cell) or a composed one (several characters) is shaped alone at its column. Shaping whole lines without a forced advance would drift as soon as a glyph comes from a fallback font.
- **The block cursor goes under the text**, which is drawn over it in the pane's background colour; bar and underline cursors draw over the cell. An unfocused terminal, or the `block_hollow` shape, shows a hollow block.
- **Only the active pane shows its cursor** when the tab has several; its card's edge is brighter, and the others fade (`theme::INACTIVE`, 55 %): their card, cell backgrounds, text and lines lose opacity, so they sink into the glass and the active pane reads as the one in front. A black wash, used until 2026-10-26, made the inactive panes the darkest and most solid surface on the glass, so they looked like the active one; gpui 0.2.2 keeps its element opacity to itself, so the fade is applied to each colour (`theme::faded`).
- **The default background is translucent** (`design/widgets.md`): a pane's card is `colours::pane()`, Tokyo Night at the window's opacity as it looks over the ground, and the pane paints nothing more where its program kept the default. What a program chose stays opaque, so its colours read as it chose them: a pane whose program set its own default background (OSC 11) is filled with it (`Painter::pane_fill`), and so is a cell with a background of its own (`Painter::cell_fill`), unless that background is the default colour itself, which programs often paint explicitly and which would otherwise leave opaque blocks on the glass. The colours given to cornercase with `theme -` stay opaque: programs never see the opacity.
- **Positions past a pane are allowed**: `Layout::cell_in` counts in the cells of the pane a drag started in, wherever the pointer is (negative cells included), so a drag that leaves its card still reaches its program or the selection, clamped to the pane. A press in a card's padding takes the nearest cell of that pane.

## No tab open (`no_tab.rs`)

- **Asked for on 2026-11-01** (cornercase's TODO list: no screen for a project with nothing open). A view that shows a project or workspace without tabs has no tab to stream: cornercase pauses its surface and sends no frame, so the window kept drawing the last tab it had shown, from another project, and typed into it; a window that started there said "The terminal cannot be shown" with cornercase's refusal (`view N streams nothing now: it shows no tab`), toasted it and asked again every 5 s.
- **The terminal's place says so instead, as the TUI's does** (its `ui/pane.rs`, "no tab open" and `+ Tab`): the emblem with a terminal, "No tab open", a line naming the place, and buttons. Start an agent… opens the start dialog (⌘G, as the sidebar's Agent button) and is the main action; New shell runs `new-tab --workspace W --focus` (⌘T). When the workspace has closed agents (`closed_agents`), Reopen N agents comes first and is the main one, as the TUI's reopen pill, with the sidebar menu's job (`sidebar::reopening`), so the menu and the page show one running job. A worktree being removed shows its removal running and no buttons, as the TUI drops its `+ Tab`. The place is a worktree's own name, or the project's for its main workspace, which cornercase names `default`.
- **No project at all is a welcome**, as the TUI's: the mark, the wordmark, the site's tagline and Open a project… (⌘O).
- **What counts as showing no tab**: the session's view shows no tab, and the frame on screen is older than that session. Frames carry the view's `projection`, which cornercase bumps whenever what the view shows changes, so a frame with a projection at least the session's came for a tab shown since (`Session::shows_no_tab`). Gating on the session alone was rejected: view lines reach the window up to 500 ms after a change (`design/sidebar.md`, folds), while the new tab's frame comes at once, so going from an empty project to a tab would show the page for half a second over a terminal that had arrived. While it shows no tab the panes are neither drawn nor hit, and keys reach no pane (`Root::frame_shown`); a drag in progress when it switches there (a pane held by its handle, a divider, a selection) is dropped, so a pane's ghost does not hang over the page until the button is released, and a program that got the press gets its release at the last cell it was sent, so it is not left mid-drag (`Root::drop_drags_without_tab`, both found by Greptile on #10).
- Checked live on 2026-11-01 with cornercase 0.12.235 on an isolated server (`CORNERCASE_SOCKET`): the welcome with no project, a project whose only tab was closed (from another tab, and closing the shown tab), back to a tab (its terminal drawn within 0.3 s), a window started on a project with nothing open (no toast, no surface asked for until a tab showed), New shell clicked (a tab opened there and drew), and two closed agents faked into `view` through a `CORNERCASE_BIN` wrapper (Reopen was not pressed). Not checked live: a worktree being removed, and Start an agent… (the dialog is the sidebar's).

## Mouse

- **The left button selects**, with cornercase's own selection (`selection --from --to`), unless the program reads the mouse; Shift forces a selection even then. A finished selection is copied, as the TUI does; a click without a drag clears it.
- **A double click selects a word, a triple click the line**. A word is a run of cells of one class: blank, word (letters, digits and `_-./~:@%+=#?&`, so paths and links select whole) or other punctuation. The empty cell after a wide character belongs to it.
- **The right button is cornercase's in every pane**, even one whose program reads the mouse, since almost no program uses it: a click opens the pane's menu, a drag onto another pane moves it there (`move-pane`; how it is drawn is under Moving panes). The menu offers "Send the right click to the program" for the rare program that wants it.
- **Where a dropped pane goes**: the middle third of the target's card both ways swaps the two; elsewhere the nearest edge takes that side (`--place left|right|above|below`), measured in points on the card rather than in its cells, so its padding counts too.
- **Dividers are the gaps between cards**: a press there, or 4 px into either card, takes the split. A drag sets its ratio so that the gap lands under the pointer (`Along::ratio`: the first side's cells are what lies between the split's start and the pointer, less that side's padding and half the gap), kept between 0.1 and 0.9 and coalesced so only the latest reaches cornercase; a double click evens the split out, as on the TUI's borders. The pointer is a resize arrow over a gap, so the drag can be found: the canvas inserts a hitbox per gap in its prepaint and asks for the cursor over it in its paint, after the terminal's own I-beam, so it wins there. While a divider is dragged the whole terminal keeps the arrow, since the gap reaches the pointer only once cornercase answers. Checked live on 2026-10-24 (cornercase 0.12.190): a 100 pt drag moved the split by 13 columns, with the gap under the pointer.
- **The wheel** accumulates fractional lines and acts per whole line, at most 25 at once. A program that reads the mouse gets wheel events; a full-screen program (alternate screen) with alternate scroll gets arrow keys, and without it nothing; anything else scrolls cornercase's scrollback (`scroll --up/--down`).

## Paths and web addresses under the pointer (`links.rs`, `model/link.rs`)

- **A path a program printed is a link, as in the TUI** (its `design/keys-and-mouse.md` and `design/files-panel.md`): cornercase decides what is a path and which file it is (`link --pane P --cell X,Y --json`: the canonical path, whether it is inside the workspace, its relative path, its lines and the cells it takes), so the rules (`:12`, `:12-30`, `#L12`, `~/`, the foreground program's folder, then the workspace's root) stay in one place; the command exists for programs that draw cornercase's terminals themselves.
- **Asked only when the pointer enters another word**: the run of word cells under it (the double click's classes, so `src/main.rs:12` is one word and brackets end it) is the key; moving inside it asks nothing, a blank cell or the padding asks nothing and forgets the link. One question at a time, run beside the queue (it only reads, and hovering must not wait behind typing); a word entered meanwhile is asked when it answers, and an answer for a word the pointer has left is dropped.
- **The link is underlined in cobalt with a faint tint, and the pointer is a hand**, only while the pointer is inside the span cornercase answered (`row`, `start`, `end`) and the row still shows the text it had when it answered (`Hovered::shown_in`): a program that redraws or scrolls under a still pointer must not leave an underline on other text, nor open what is no longer there. The wheel and typing drop it; leaving the terminal forgets it.
- **A plain click opens it in the Files panel**, at its lines (`files::open_link`), docking the panel, as the TUI does, even in a program that reads the mouse: the press on a link is held back (`Drag::Link`), a release on the same cell opens it, and moving to another cell first sends the held press to the program or starts a selection from it, so a drag that starts on a path still reaches the program. A click with a modifier, a double click and Shift keep their meaning. After the click the link stays off until the pointer leaves the word, so the card does not come back over the panel just opened.
- **Resting on it shows the file in a card** (`design/files-panel.md`, Peeking at a path).
- **A web address is a link too, found here** (asked for on 2026-11-01: addresses should open in the Browser panel). cornercase leaves them out of `link` on purpose (its `files/link.rs` skips any word holding `://`): in the TUI the terminal it runs in finds them, and here this window is that terminal, so finding them is drawing, not server logic. An `http` or `https` hyperlink the program printed (OSC 8) takes all the cells of that address in the row, blanks and brackets included, so it is one spot; otherwise the address inside the word under the pointer counts, from its `http://` or `https://` to the word's end, less a `.`, `:` or `?` that ends a sentence. It is found without asking cornercase, so it is underlined at once, with the hand, as a path is. Limits: an address the program wrapped onto the next row is cut at the row's end, and one holding a character outside the word class (`(`, `,`, `!`, `'`) stops there.
- **A plain click opens a web address where Settings › Links says** (asked for on 2026-11-01: "configurable in settings, whether it opens in your default browser or in cornercase's"): the default browser by default, what a terminal does, or the Browser panel (`Store::open_in_browser`, `design/browser.md`), docking it. The click is held back like a path's, so a drag still reaches the program. A `localhost` address while the window shows another machine always opens in the panel, the one place that reaches that machine's servers (through its ssh tunnel); the system browser would open this Mac's. The setting is the window's own, kept on this Mac (`prefs.rs`, `design/settings.md`): cornercase's TUI has no browser of its own, so cornercase's settings have nothing to say about it.
- **Resting on a web address shows the page in a card**, as resting on a path shows the file (asked for on the same day: "preview it like a file, keep the default behaviour, and offer to open it in cornercase's browser in the preview"). The Browser panel's Chrome loads it in a page of its own, 1280 × 800 at one device pixel per CSS pixel (a crisp picture at the card's width on a Retina screen), waits for `document.readyState` to be complete (at most 8 s) and half a second more for scripts to draw, and takes a JPEG; the header names the page's title and its address. Clicking the picture opens the page as a click on the address would; the header has Open in the Browser panel and, unless the address is another machine's `localhost`, Open in your default browser.
  - **Which pages load at once** is the second setting of Settings › Links, local addresses by default (`localhost`, `127.*`, `[::1]`, `0.0.0.0`, `*.localhost`: a dev server, the case the panel exists for), else every address, or none. The others show a card that says why and has Show the page. Loading a page is a GET, and a GET can act: a one-time sign-in link printed by a CLI would be used up by the pointer crossing it. Rejected: loading every page on hover (that risk, and a request to any site the pointer passes over), and a card with only the address (it would not be a preview).
  - **Previews load apart from the panel's tabs**: in a browser context of their own (`Target.createBrowserContext`, disposed when the window's connection to Chrome ends), so they carry none of the profile's cookies, and with downloads denied for it (a link to a file shows "it may be a download"). Their pages never show as tabs: the panel skips any target of that context. `alert`, `confirm`, `prompt` and `print` are stubbed before the page's scripts run, since a dialog would block the page and the picture. Each step waits at most 5 s for Chrome (8 s for the navigation), so a page that never answers ends in a note rather than a card that loads forever. Hovering a local address starts the panel's Chrome if it was not running; that start is the slow part of the first preview (a second or two).
  - **On another machine** a `localhost` address goes through the ssh tunnel the panel opens for that port (`tunnels.rs`), waiting at most 15 s for it; a tunnel that is retrying is waited for, not started again.
  - Limits: each hover of another address loads the page again (no cache, so a dev server's page is never stale); a second window on the same Chrome profile sees the first one's preview pages as an agent's tabs for the second or two they live.
  - Checked live on 2026-11-01 with cornercase 0.12.235 on an isolated server, its own Chrome profile and its own settings file: resting on `http://localhost:8765/page.html` showed its title and its picture within the first second; `https://example.com/` showed Show the page, and pressing it (this machine could not reach that site) ended after 8 s in "The page did not answer within 8 seconds"; Settings › Links listed both settings after the line, choosing Browser panel wrote the file, and a click then docked the panel on that page with no tab left by the previews. Not checked: a click into the default browser, Every address and When asked, and a machine reached over ssh.
- **⌘-click always opens with macOS**, whatever the setting, as it does for paths: the setting chooses only the plain click.
- **⌘-click opens a hyperlink the program printed** (OSC 8) or a web address in the text with the system browser, or else a path cornercase recognises under the pointer (`link --cell`), opened with macOS's `open`; on another machine (`design/remote.md`) the path is copied instead, since it is not on this Mac, and so is the path of a `file://` hyperlink (its host is dropped and its `%` escapes read); other hyperlinks open here. Nothing under the pointer is a toast.
- Checked live on 2026-10-31 with cornercase 0.12.234 on a throwaway project: the underline and the card for code, a PNG, a GIF, an MP4, an MP3, a PDF and Markdown, the card beside the path while a list of paths stays free below it.
- Web addresses checked live on 2026-11-01 with cornercase 0.12.235 on an isolated server and its own Chrome profile: a plain address was underlined without the period after it, an OSC 8 hyperlink `[the page]` as one span, brackets and blank included, and a click on `http://localhost:8765/page.html` docked the Browser panel, which opened that page once its Chrome had started. Opening the dock narrowed the pane and the address wrapped onto the next row: the surface stream does not say that a row goes on in the next one, so such an address is cut at the row's end. Not checked: ⌘-click into the system browser, and a click while the window shows another machine.

## Moving panes

Code: `src/terminal/pane_drag.rs` (the handle, pressing, dragging, dropping), `src/render/moving.rs` (the move as data over time), `src/render/ghost.rs` (its painting).

- **Asked for on 2026-10-31**: dragging panes, "with good transitions and a wow effect", and visible that a pane can be dragged, as other apps show it. Until then only the right button moved a pane, with nothing drawn until it landed, which nobody could guess.
- **A handle, as Ghostty does**: Ghostty 1.3 shows a grab handle when the pointer nears the top of a split (1.3.1 shows it only then, after people found handles everywhere distracting); Warp drags a pane by its header. Here a pill sits in the top padding of a card, centred, while the pointer is within 44 px of that card's top and the tab has more than one pane (a pane alone has nowhere to go: `move-pane` moves within a tab). It fades in, widens and brightens under the pointer, the pointer turns an open hand, and its tooltip says "Drag to move this pane". It spans 4 to 14 px below the card's top, clear of the 4 px a divider's grip reaches into the card under it, and stops at the first row of text.
- **Rejected**: handles always shown (one on every pane, all the time, for a rare action); a header bar on each pane (a row taken from every pane); press and hold anywhere to lift the pane (pausing before dragging a selection, a common way to select, would lift the pane, and a program that reads the mouse gets the press at once); gpui's own drag and drop (`on_drag` answers the left button only, so the right-button drag would need a second path, and it says nothing when a drag ends without a drop, which the ghost needs to fly home).
- **Lifting**: past 5 points from the press the pane lifts. Its card turns hollow (fill and text faded, a dashed cobalt edge) while a ghost, the pane's own text drawn live at a smaller size (at most 42 %, 300 by 220 points), shrinks out of the card toward the pointer over 240 ms and hangs from its grip under it, with the floating cards' shadow and a cobalt glow. It is drawn `deferred`, over everything, so it can cross the sidebar or the dock. The pointer is a closed hand over the whole window.
- **Aiming**: over another pane a drop zone grows in, the part of the card the pane would take (the half toward the nearest edge, or the whole card for a swap), as a cobalt wash with a bright edge. Moving to another place or pane glides it there in 170 ms instead of jumping; over a gap between cards it stays where it was; over its own card or outside the panes it shrinks away. A caption under the ghost names the place (Swap, Left, Right, Top, Bottom) with its arrow: drawn in the zone's middle it was hidden by the ghost, which hangs right where the pointer is.
- **Landing**: a drop sends `move-pane`. The frame with the new layout arrives about 20 ms later (measured on 2026-10-31 with 0.12.234, before the command had even returned), and the window waits for it with the card still hollow. Then every other card slides from where it was to its new place, eased over 380 ms (the bounds from before the change are kept and drawn moving to the new ones, the text clipped by the moving card), while the ghost flies into the moved pane's new card, growing back to full size, and fades into it over the last 30 %; the pane then glows cobalt for 0.9 s. Move pane in the pane's menu slides the cards the same way, without a ghost. Only a move the window started slides: sliding every new layout would make a divider drag and a window resize trail behind the pointer.
- **Going home**: a release over its own card or outside the panes, or Escape, flies the ghost back into its card, which fills in again. A refused move (cornercase refuses when the tab would have no room for every pane) toasts cornercase's reason and turns the zone red as the ghost goes home. A move that changes nothing (the layout in the answer is the one it was dropped on) goes home at once, and so does a drop that sees no new layout within 1.5 s.
- **The right button** lifts a pane only once the pointer leaves its card, so a release on its own pane still opens its menu, as before. gpui 0.2.2's macOS view takes `mouseDragged:` but not `rightMouseDragged:` (found live on 2026-10-31), so the window hears nothing between a right press and its release: no ghost or zone shows during a right-button drag, the pane is drawn moving only as it lands (the ghost flies from its old card to the new one), and a release outside the panes leaves nothing behind. The handle, held with the left button, shows the whole drag. Reading the pointer from the system while the right button is held was not done: a second path for a gesture the handle already shows.
- **The drag takes the mouse**: while a pane is pressed, the window listens to every move and release in the capture phase and stops them there, so the ghost follows outside the terminal and nothing under the pointer reacts. A move that arrives with the button up (released outside the window) cancels it.
- **Frames**: the canvas asks for the next frame only while something moves (a lift, a gliding zone, a flight, a slide, a glow); a still pointer over a settled zone draws nothing more, as the rule for idle animations asks (`design/widgets.md`).
- **Not done**: dropping a pane on another tab or on the tab bar, as Warp does: `move-pane` moves a pane within its tab only (0.12.234).
- Checked live on 2026-10-31 with cornercase 0.12.234, on a throwaway tab of three panes: the handle and its tooltip on hover, the open hand over it, a drag from it (the lift, the ghost over the sidebar, the zone gliding from Swap to Left, the caption under the ghost), the drop (the cards sliding into three columns, the ghost growing into the moved pane, which became active), Escape (the ghost flying back into its card, the layout unchanged) and a right-button drag onto another pane (moved and drawn as it landed, with nothing during the drag, which is how the right-button gap above was found). Not checked live: a refused move, and the menu's moves.

## Plugin popups

- **What shows one**: the `app` feed's `popup` (`status --app --follow`, kept in `Store::app`) says a popup is open anywhere; while it does, `Popup` (one entity per `Store`, a global, so `app.rs` holds nothing for it) follows `surface --popup --patches` and draws its one pane. The stream ends when that popup closes (and a later popup needs a new one), so an ended stream is followed again after 500 ms while the feed still names a popup, after 5 s when it failed the same way twice; the card says why meanwhile.
- **A floating card over the terminal**, not the window: the glass card of sheets with the action and plugin as its title and a `✕`, the popup's terminal drawn as a pane card by the same painter as the panes (`render::popup::paint_popup`), on a veil over the terminal area that occludes it, so the panes behind take no pointer. The popup keeps the size cornercase gives it (the TUI window's, since it follows the shared size); larger than the terminal area, it is cropped to what is left within a 24 px margin, measured by a probe the size of that area.
- **Keys and text go to the popup while it is open**, through the same path as the pane's (the terminal's focus, `Root::on_key`, the input method), so dead keys and ⌥ characters work there too; `type_in` sends them with `input --popup --pane ID`, the id from its frames, so nothing reaches a popup opened since. **Escape reaches the popup's program**, as in the TUI: popups host fzf and curses menus that use it, so it stays handled once in `Root`, which passes it on when the terminal is focused and no dialog or sheet is open. **⌘W closes it** (`plugin popup-close`), after a dialog or sheet and before the docked panel or the pane, as does its `✕`; ⌘V pastes into it. A click in the popup gives the terminal the focus back; the mouse reaches the program only when it asked for it (presses, releases, the wheel as for a pane).
- **Each event is its own `input` command** on the ordered queue (`Store::cmd`), since the queue batches input by pane only; a popup takes a few keys at a time, so a process per key is acceptable.

## Tabs

- The tab bar shows the shown workspace's tabs as rounded pills floating on the ground of the title row, the shown one filled lighter, with its status, name, other panes, model and context, and a close button (always on the shown tab, on hover on the others). A tab renames in place on a double click, drags to reorder (`move --tab`, landing before or after by the drag's direction, outlined in cobalt, thicker on the side it lands; dropped on `+` it goes last) and opens its menu on a right click.
- **Closing a tab that runs an agent asks first**, since closing it stops the agent; its worktree and branch stay. A shell tab closes at once, like closing a pane without an agent.
- `+` offers a shell, the default agent (`start --focus`) or the start dialog.

## Context menu

- **One menu for the whole window**: a right click or a row's `⋯` opens it at the pointer, drawn over everything (deferred, snapped inside the window). Escape, a click outside or any entry closes it, and focus returns to the terminal.
- **A submenu takes the menu's place**, as the TUI's *move to group* does, instead of opening beside it: no hover timing, and it fits a narrow window.
- **Separators come from optional entries left out**, so the menu drops separators at either end and doubled ones rather than every caller checking.
- **An entry runs on the window after the menu has closed**, so it can open a dialog or another menu.
- Entries that stop or remove something are red (`danger`).
