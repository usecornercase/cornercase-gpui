## The data

- **The list** comes from the app stream (`Store::take_app` reads `bots` as it reads `machines`), never from a poll of `bot list`. It is read leniently: a `bots` that is missing or not a list is no bots, and an entry that does not read is left out while the others stay. A bot with no line yet has `last: null`; the window does not read `last` or `created`. It reads `folder` and `access` since 2a-ii, leniently: absent or of another type is empty and the bot stays in the list (a field only a menu and the form read must not take a bot out of the list, which would close its chat with a `was removed` toast), and neither is in `shown_alike`, since nothing drawn shows them: a menu and the form read them at the press, and a change of only these would redraw the cached sidebar and chat for nothing.
- **A chat** reads `bot history ID --json --last 1000` once, then follows the `bot` events of the notifier's stream, which is already open for the whole server run (`events --notices --host --json`): `Event::Bot` is read beside the others and `Store::bot_heard` takes it, so the stream has a second reader and no process more. A stream of the chat's own was rejected: one more process per window for the same events.
- **Lines of bots whose chat does not show** are also heard from the notifier's stream, only to tell an answer (`model/bots/told.rs`, `Answers`); nothing of them is kept.
- **The merge** keeps the lines by id, sorted, the newest 1,000 (upstream's own limit); an `Earlier messages are left out` note says so. A line that arrives twice is kept once, and lines out of order are put in order. Once the history is read, a line whose id skips past the last one asks `bot history --after LAST` for the lines between (one such read at a time). A late answer of an earlier ask, or for another bot, is dropped (`Chat::asked`).
- **A failed read keeps what is shown**: with lines already in the chat the failure shows above them, and the next line heard, an app line that settles the bot, or showing the chat again reads it whole; a catch-up asked while another read runs is kept (the earliest cursor) and asked when that one ends. A line whose fields have the wrong type (a `text` that is a number, no `kind`) is left out, never turned into a blank line.
- **A new server run** (`boot` changes in the app line) reads the chat again whole; the notifier's stream starting again reads what follows the last line (`Store::bot_stream_started`).
- **A `state` event** updates that bot's state until the next app line replaces it, so the row and the turn's row never disagree with the chat for longer than a line. A `change: removed` leaves the chat; `created` and `edited` are heard as nothing, since the list changes with the app line. Unknown kinds show as plain text; an event with none of `line`, `state`, `change`, or with a bad line, changes nothing.
- **Held** is read from the lines with upstream's own replay rule, not from the list's `held` count: a `you` line with `held: true` after the last line that ends a turn (a `bot` answer, an `error`, or a notice whose text is `stopped`, `interrupted by a restart`, `1 held message dropped` or `N held messages dropped`) is still held. So it ends with the very line that ends the turn and never trails by an app line. Those texts are upstream's fixed words.

## Routines

#267, part 1, for cornercase 0.13.85 and newer (usecornercase/cornercase-terminal#846 and #874; #888, #875 and #896 since). Cornercase's own design is upstream's `design/bots/routines.md`, read at `610feefa`; #267's text was written before it shipped, and this follows what shipped.

- **The data.** A run's lines carry `routine`, the id of the run's queue entry (a one-off entry is its own run): a `notice` `↻ <label> · <time>` first, then `step` lines, then a `bot` or `error` line, or a notice `stopped` or `interrupted by a restart`. `Line::routine` is read only when it is a number and the line has no `ask` (upstream's `groups`: an asking line is the chat's, #346); any other type reads as none and the line stays. A bot's entries in the app line's `queue` have `place.bot` (its id) and an empty `project`; a run copies it, and its state can be `answered`. `Bot` reads `routines` (a count) and `next` (UTC seconds or null), leniently, as `folder`; `next` is in `shown_alike` since the row draws it, `routines` is not, since nothing draws it. `Runs` (`model/bots/runs.rs`) is the queue read for the chat, made in `take_bots` from the same app line and compared, so the cached chat and sidebar move only when it changes: by entry, its bot, label, whether it answers (`starting`) and what Run again starts; by bot, what it scheduled (the entries that are not runs).
- **A run is one block where its header is**, even when chat lines come between (upstream's `groups`): the header as the server wrote it (`↻ a routine` when its first line is not one), its steps folded under `+N steps` with none kept in view, then the answer as a chat's (same head, copy button, Markdown kept by line id), or the error with Run again, or the end notice, a line of a kind this window does not know as plain text (the chat's rule; upstream's block leaves it out), and `Answering…` with the working spinner while its entry starts. A chat step after a block starts a run of steps of its own. Why at its header and not at its newest line: the block would jump down the chat each time a line joined it, and upstream draws it there. The cost, upstream's too: a run's answer can land above lines read since, with no `New messages`. A line that joins the chat's last block is new, as a new row is (`entries::arrived` reads the newest line's id, `tail`, which a block keeps past its head), so a reader scrolled up gets `New messages` for it. A block's key holds its newest line's id (`tail`), how many lines it holds (so a line that a catch-up read puts before its newest, a step between its header and its answer, measures it again), whether it answers and whether it offers Run again, so a growing block splices its own row alone and keeps its first and last at its head, which the splices' order needs.
- **A run's lines never touch the chat's turn.** `held`, `asked`, `turn` and `retry` read only the lines without `routine` (`entries::own`), so a run's `bot` line does not end the chat's turn or release its held messages, a run's `stopped` between a stop and its `N held messages dropped` does not lose what was dropped, and Retry shows for a chat error with a run's lines after it and never for a run's error. `bot list`'s `state` stays the chat's during a run (upstream), so the turn's row and Stop are the chat's alone; a run's spinner is on its block and its row.
- **Run again** is offered under a run's error when its entry is still in the queue and its routine still exists, or, for a one-off, when it failed or was missed (upstream's `runs_again`), and sends `queue run` with the routine's id, else the entry's own, as a job (`Starting a run of “Review PRs”…`, the button `Starting…` until it answers). A run gone from the queue offers nothing; a press that finds it gone says `That run is no longer in the queue` (upstream's words). It is a tab stop (`ui::press`, a handle per run kept by `BotChat`), and the keys reaching it reveal its row, since a run's error can be far above the end; a row past the list's overdraw is not laid out, so Tab reaches it once PgUp brought it near (the limit Retry has, `design/widgets.md`). No Stop for a run: upstream's window has none, `bot stop` from a shell ends it and a run lasts at most 15 minutes.
- **Landing on a block.** A toast's Show, a banner's click and a click on a run in the routines sheet show the chat with the block's top in view: `Store::show_bot_at` sets `Bots::anchor` (the bot, the run, a serial) and `BotChat::take_aim` asks `aim` on each render before `re_anchor`. While the chat's history is still read, the block is gone to once, as soon as the rows hold it (`Aimed::early`), and a scroll the person makes meanwhile is left alone. Once the read has settled, `Done` or `Failed` (`Chat::settled`), the block is gone to once more, since the read can move its row, and the anchor counts as applied (`Aimed::done`); a read chat without the block takes the anchor and moves nothing. Going to it on every render until the read was `Done` was CodeRabbit's suggestion on #390, and it kept a chat whose read failed snapped to the block (the reviewer's finding). The chat never writes to the `Store` for it, so the cached view keeps reading only.
- **The routines sheet is the Queue panel scoped to the bot**, titled `Routines › PRs` (`Store::sheet_title`): `Routines` in the chat's header (a tab stop, before New conversation, `What PRs does on a schedule`) and `Routines…` in the bot's menu after Edit bot… set `Bots::queue_of` after `open_sheet`, which clears it, so every other way into the Queue opens the projects' queue; it is not cleared on close, so the sheet that slides out keeps its list. The Queue's key while the routines show opens the projects' queue (`closes`). **Routines gives way in a narrow chat** (upstream's rule: its header button goes when it would leave the name under 12 cells, and `⋯` always has `routines…`): the button is drawn while the name and the facts keep at least 116 pt (96 pt for the name, about 12 cells, and the two 10 pt gaps), measured from the header's own children at prepaint (`on_children_prepainted`, the name's left edge to the first fixed control's) and handed to the chat through a deferred update, since the cached chat has no width of its own to read and is drawn again when its bounds change. The phone a chat shows while its answers reach a chat app (#269) sits before Routines: the room still ends at the first fixed control, the phone when it shows, and the button's width is read where the button sits (`at`, one place later then). A hidden button comes back only once the room holds it, its 10 pt gap and 8 pt more (`routines_fit`), so a width at the edge never flips it, and the button's width is the one last measured. At 640 × 360 the room with the button is 26 pt, which left the name `..`; without it the name has about 91 pt, as before #267. A chat first drawn narrow shows the button for one frame. **A button that goes while it has the keys hands them to the field itself**: the header's prepaint, deciding it goes, defers a focus of the field when the button's handle (`BotChat::routines_stop`, kept by the chat so it can be asked) has the keys. `Root::focus_lost` (`design/widgets.md`) was expected to do it, as for Stop, and does not: seen live on 0.1.134, a letter typed after the button went landed nowhere, while Stop leaving with the keys still handed them to the field. The difference is that Stop goes with a `Store` change and Routines with the chat's own deferred notify; why gpui's lost focus does not reach `Root` then was not found. Rejected: leaving the name squeezed (a regression at the least window), a floor for the name (it pushes the controls past the card's edge), an icon button (it hides the word, and `Icon::Repeat` already means Resume in the Queue sheet), and the room depending on the name's own length (the header cannot measure a squeezed name, and upstream's 12 cells are fixed too). The panel keeps only the bot's entries (`data::scoped`), drops its form, detail, undo bar and filter when the scope changes, shows the filter alone in its toolbar (Schedule… comes with the form in part 2), no Clear started (the request clears every project's), a Routines note that says each run is a new conversation of the bot answering in its chat, and `No routines yet` with the scheduling example when the bot has none. Start now, Pause, Resume and Remove with Undo are the Queue's own. A click on a run that left a block (`starting`, `answered` or `failed`: upstream's `left_a_block`), or on a routine whose newest run did, closes the sheet and shows the chat at it, in one update as Search does, so the keys land in the chat's field; a missed run, a run not made yet and a pending reminder do nothing. The sheet closes when its bot leaves the list. **Why the Queue panel and not upstream's dialog**: upstream's view is a dialog of the queue modal's size that opens the schedule form; here the Queue is a sheet with its form in its right column, so the same panel scoped to one bot is the like-for-like, and it reuses the list, the actions, the undo bar and, in part 2, the form. Rejected: a strip under the chat's header (it takes the chat's height, a tab stop per routine, and still needs the Queue's form), a dialog (capped at 560 px), a `PanelKind` of its own (a ⌘ key and a rail or gear entry for a view of one bot). The sheet's rows are not tab stops, as the Queue's are not (#326's table).
- **The row** reads `next 09:00` (the chat's clock, `time_label`) while the bot is idle, no run of it answers and `next` is set, in place of `claude · opus` (upstream's); the chat's header keeps the facts. It is read at render, so `tomorrow 09:00` can stay past midnight until the next app line (the chat's times have that limit). The status slot's spinner turns while the bot thinks or a run of it answers, and so does the folded section's.
- **Remove bot…** names what the bot scheduled, since cornercase removes a bot's routines, their runs and its reminders with it: `Its chat, its memory, its folder and what it scheduled (Review PRs, Morning brief) are deleted. Agents it started keep running.`, at most three names and then `and N more`, read from `Runs` at the press. It rests while a run answers (cornercase refuses `bot remove` then), with the menu's reason line first; New conversation… does not, since a run has its own session. **No Undo**: cornercase's request answers an `undo`, but its own window offers none, on purpose (`design/bots/routines.md`): the chat and the folder are gone, so restored entries of a missing bot would only fail when they run. So `bot remove` keeps no `--json`.
- **The gate** is `Feature::BotRoutines` (0.13.85) on the server's release only: Routines, Routines… and the fourth example need it, and nothing in part 1 sends a command an older command line cannot parse (`queue run`, `pause`, `resume`, `remove` and `restore` take a bot's entry unchanged). This computer's half comes with `queue add --bot` in part 2. An older server has no `routine`, no `place.bot` and no `next`, so nothing else changes there.
- **What waits for part 2**: the schedule form for a bot and Edit on a bot's entry (neither sheet offers Edit on one now: the form would build a project's entry), a bot's entries leaving the Queue sheet with upstream's dim line, Clear started and the bots' runs (`queue clear-started` clears them too; only upstream's window leaves them, with no flag for it), and a `queue-failed` toast of a bot's run opening the bot. The bot's card and its routine rows' `⋯` (upstream #875) are part 2b-iii of #266.
- **What rests on reading** (no test makes a gpui entity): `take_bots` → `Runs::of` and `close_routines_if_gone`; `show_bot_at`; `BotChat::take_aim`, `keep_again_stops` and the reveal in `reveal_stops`; `run_block::run` and Run again's press → `Store::run_again`; the header's Routines and the menu's Routines… → `open_routines`; `QueuePanel::sync_scope`, `Click::Chat` and Open chat → `open_chat`; `render_sheet`'s title. The rules are plain functions with tests: `Runs`, `aim`, `entries` and `keys`, `own`'s effect on the turn's state, `row_detail`, `empty_lines`, `remove_words`, the menu, `closes`, and the Queue's `chat_block`, `bot_click`, `scoped`, `sections`, `remove_tip` and `status_label`.

## The shown place

The shown place is one value, `Showing` (`Local`, `Machine(place)` or `Bot(id)`, in `model/place.rs`), kept in `Store` (`store/place.rs`, with its writer `place()`, `show_local` and the readers `machine_place()`, `shown_bot()` and `shows_local()`), so no two flags can both be set. `Showing::after(Moved)` is the rule, a plain function: a move to a local place, a machine's place or another bot sets that place; a removed bot, or a list that no longer holds the shown bot, leaves the chat; anything else keeps what shows. The writers are `select_there`, `show_bot`, `show_local` (which every command that moves the view reaches through `cli::moves_view`, and a press on a project, workspace, tab or agent row, a toast's Show, Search's choice, ⌘1…9 and ⇧⌘[ ⇧⌘]), `follow_machines` and the bot's removal (with the toast `<name> was removed`). The readers outside `store/` are those three methods. Root mirrors the bot in `SideState::bot` as it mirrors a machine's place (`app/bot_place.rs`): entering pauses the own surface, leaving resumes it, and `view-set --hidden` goes while a chat covers the tab, so agents there notify. After the window restarts it shows the panes, as upstream does and as a machine's place does.

Tab strip while a chat shows: the workspace's tabs with none marked; a press on one goes back to it. The title stays as it is; the status bar keeps the connection and the size and drops the pane's name and folder, since `active_pane()` is none (as for a machine's place). A docked panel follows the workspace behind the chat, as it does with no chat. A bell in the tab behind a chat is a toast, not a flash.

**`shown_bot` is read nowhere** (part 2b-i). It names the chat cornercase's own window shows, only from 0.13.80, and a view of this window's kind keeps a selection of its own and never shows a bot: nothing in cornercase's window moves this one, and this one cannot answer in kind, since nothing sets `shown_bot` from outside. Following it while running, at launch (a restart shows the panes; a `--bot` argument was rejected) or for "was it read there" (`unread` already says that) and a `cli::Feature` for it were rejected; `design/machines.md`'s `shown_remote` is the precedent. **`show_bot` leaves the keys with a dialog or a sheet** (`keys_go_to_chat`): it asked for them whatever was open, which would have put them in a field a sheet hides; closing the overlay gives them to the chat (`keys_after`). Search's choice still lands in the field, since it closes its sheet in the same update.

## The keys while a chat shows

⌘E (New bot) acts while a chat shows: it opens a dialog, and the keys come back to the chat's field when it closes. While a chat shows, its field has the keys (`Root::keys_rest`), so typing, a dead key, ⌥ characters and the input method go to it, and ↑ ↓ PgUp PgDn scroll the chat when the field holds one row or none (with more rows ↑ ↓ move between rows; PgUp PgDn always scroll). ⌘A ⌘C ⌘X ⌘V are the field's, as in every field of this window; ⌘Z does nothing (no field has undo); Tab and ⇧Tab walk the chat's buttons and its field, in the order they are drawn: Routines (on a server with routines, while the chat is wide enough for it: "Routines"), New conversation, `⋯`, then the examples (an empty chat), or the Run again of each failed run drawn and Retry (a failed turn), in the lines' order, then Stop (a running turn), then the field, and round again; Return and Space press the button that has the ring ("With keys alone"). The field and the buttons are tab stops only while no dialog or sheet is open and no file shows full screen (`Store::chat_takes_keys`), so Tab in a form never reaches the chat behind it. The terminal element is not drawn, so no click, wheel, drop or input-method text reaches a pane, and `takes_input()` is false, so `active_pane()` is none: close, split, panes, mark, copy and paste find no pane. `keymap::in_chat` answers each command: **Acts** as always (panels and sheets, ⌘F, the finder, ⌘N, ⌘O, ⇧⌘K, ⌘P, ⌘G, ⌘/, zoom, ⌘C, and the Browser's own keys); **Leaves** because it moves the view (next and previous workspace and project, ⌘B when an agent needs you, ⌘T, ⌘1…9 and ⇧⌘[ ⇧⌘], a number past the last tab does nothing); **OnTop** (⌘W closes a dialog, a sheet or a docked panel, never a pane); **Rests** (⌘R, ⇧⌘W, ⌘D, ⇧⌘D, ⌘[ ⌘], ⌘V: they would act on a tab or pane nobody sees; ⌘V is `InChat::Field`: the field's own binding takes it before `Root` asks, so a ⌘V that reaches `Root` comes from a place that is not the field and does nothing, and a docked Browser's page that has the focus is still asked first). A test keeps one answer for every command of `SHORTCUTS`. Escape clears the field when it holds text (and the draft); with none it closes what is on top, one per press, and with nothing on top does nothing, the keys staying in the field (upstream's rule: a stray Escape never drops what you read). Linux and Windows send the same commands through `keymap::chord`.

**⇧⌘I** (Ctrl+Alt+Shift+I on Linux and Windows; `Command::Bots`, Getting around, `in_chat` answers Acts) goes to a bot with an answer not read yet: the first after the shown chat in the list's order, wrapping, and from the top with no chat shown, as ⌘B walks agents. With none unread, while a chat shows it goes to the next bot (wrapping; with one bot it stays), and otherwise to the bot shown last in this run of the window (`Bots::last_shown`, set by `show_bot`) if it is still listed, else the first. All of it is the plain function `key_goes`. With no bot it says `No bot yet: ⌘E makes one`; below the gate it says the section's sentence, or ⌘E's for an older server. Under a dialog it does nothing (every move rests there); under a sheet the chat shows behind it and the sheet keeps the keys (see "The shown place"). Why I: without ⇧ every free letter is a habit (⌘A, ⌘K, ⌘S, ⌘Z, ⌘L, ⌘X); with ⇧, R, U, V, Z and Q are taken on a platform or by the desktop, punctuation is out of reach on a Spanish keyboard (#319) and digits come as symbols on Linux; I is beside ⌘I (Issues), as ⇧⌘E Files is beside ⌘E. Taking ⇧⌘I also takes away the fallback that made ⇧⌘I open Issues. Rejected: extending ⌘B (it says `No agent needs you` and walks agents) and a picker (Search is one).

## The section

Below the projects and above the Agents section in every arrangement (in side by side, at the bottom of the projects' column); #266 says "after the projects", and in the one-column arrangements that would split the projects from their workspaces. It shows only when the server lists at least one bot, at most half its column (its rows scroll past that), and never when there are none, so a server without bots draws the window as before. The header folds it (`Bots`, with the spinner and the rail's disc when folded); the fold is kept in memory in `SideState`, as the sidebar's other folds are, since cornercase has no command for its own saved fold and each client keeps its own layout. Rows are in `bot list`'s order, never by state, since rows that move are hard to press: the status slot (a faint message glyph, or the status family's spinner while it thinks), the name and `claude · opus` (the agent alone when no model is set), and at the end the rail's disc with the unread count, hidden while that chat is on screen in the active window. No avatar: every sidebar row has one status slot, and an initials disc would make bot rows heavier than the others (the TUI draws none). No local row is marked while a chat shows. The sidebar's cached part moves with `Bots::revision` (a name, state or unread count, the fold, a shown bot).

## The chat

One card the size of the terminal area. A header (the name, then `agent · model · effort · account` for what is set), the lines, the turn's row while the bot thinks (`Thinking · 42s · 3 steps`, the time left out under 5 s), and the field below it ("Talking"). Lines: `you` a bubble on the right with its time, or `Held`; `bot` with `name · time` above its Markdown and a copy button, which answers `Copied the answer` (`design/widgets.md`, The small copy icon says what it copied); steps dim, a run past 3 folded under `+N steps` that a press opens (the last 3 stay in view); `error` in the danger colour; `notice` centred, the server's words as they come; an unknown kind in plain muted text. Times are the Queue's clock (`14:02`, else `yesterday 14:02`, `Mon 14:02`, a date): #278 will move them. The empty state is two lines in the Queue's empty page's look; on a server with routines (0.13.85) its second line says a bot also answers on a schedule it sets itself, and a fourth example sets one (upstream's), and on an older server it promises no schedule and offers three.

- **Scrolling** uses gpui's `list` anchored by `scroll_to` the end, as the Browser's console does. A sync splices only the entries that changed (`entries::spliced` and `row_splices`: entries that overlap the first new one tell what was dropped at the front, then each position that differs, then the tail; the `Earlier messages` row is spliced on its own so a chat at its 1,000 lines does not move a reader who scrolled up), the Markdown of an answer is parsed once and kept by line id, and a frame lays out only what is in view. A line arriving at the bottom stays at the bottom; scrolled up, what is read stays put and a `New messages` button shows, cleared by a press or by reaching the end. It shows only when the newest line's id grew (`entries::arrived`), not whenever the last entry's key changed: the key carries a run's open state, so opening the last run of a turn that still ran, while scrolled up, raised it with nothing new (seen on 2026-11-21 by a press, #320). Measured on 2026-11-15 on a debug build (dependencies optimised) with 1,000 lines of long answers, scrolling by ↑ held about 60 frames: median 2.0 ms, worst 5.5 ms.
- **The chat is a cached view** (`AnyView::cached`), drawn from itself and the `Store`: `tests/layers.rs` checks it as it checks the docked panels (`ALSO_CACHED`), except `global.rs`, which holds the entity. It reads the clock at render, so a time of day written before midnight reads as today's until the next redraw; only a turn's row redraws by itself.
- **The chat entity follows the `Store`**: `BotChat::get` makes it again when the global's `Store` is not the current one (after ⇧⌘K to another server), as `Popup::get` does; no test makes an entity here, so that rule rests on reading.
- **Links** in an answer open when a web address is clicked, as in Recap and the Queue, and anything else is a toast: the click is the person's own, in this window, and no server makes the window open anything. Upstream copies a link because its server draws its own window (#863).
- **A dropped message** (#333): a `you` bubble that a stop or a restart dropped (`entries::asked`, the first N held when `N held messages dropped` came) reads `Dropped`, the word of the notice under it, in place of its time, and is drawn at half opacity, so it no longer reads as sent. A message held while the stop was on its way is not dropped: the server held it again and the next turn took it, so it keeps its time. Nothing offers to send a dropped message again: the stop was the person's own act and its notice says how many went, and a button per bubble would be a tab stop per bubble and a second way to send; its text can be read and typed again. A bubble that turns dropped is measured again (`EntryKey` kind 6).
- **Selecting** Markdown is not possible anywhere in this window (gpui's text cannot be selected), so each answer has a copy button, and selecting goes to part 2. **Code highlighting** is #312.

## Talking

**The field** is `TextField::chat()` (`ui/text_field`, `Enter::Sends`, key context `TextField Chat`): Return sends, ⇧Return breaks the line, ⌘↩ (Ctrl+Enter on Linux and Windows) sends too, one to 6 rows then it scrolls inside, a paste keeps its line breaks. It is the third way a field reads Return (a line: submit; several lines: a break and ⌘↩ submits; the chat: submit and ⇧Return breaks) and one rule with a parameter, not a copy of the bindings. Return while the input method composes (`marked_range`) accepts the composition and sends nothing: on macOS gpui hands the key to the method first, and the guard (`submits`) covers a platform that lets the binding run with marked text left. A dead key followed by Return is committed by the method, so the text goes with its accent. The field is not inside the cached chat: gpui marks every ancestor view dirty when a view notifies, so a key typed in a field inside the chat would lay its lines out again. `ChatField` is a view of its own below the cached chat, inside one card that `bot_chat::view` draws.

**How a text travels.** `bot say ID --json -` as a line of the ordered queue, the text in the line's `stdin` (`Queue::cmd_with_stdin_then`, the one call that has a reply and standard input): the only form where `-`, a text that starts with `-` and line breaks arrive whole. Seen on a 0.13.80 server: `-`, `-x starts with a dash`, `two\nlines\n`, `año ñ 😀` and 20,000 characters reached the agent to the character, 20,001 was refused by cornercase (`the message is 20001 characters; a bot takes at most 20000`) and a text of blanks too (`the message is empty`); it answers in 1 to 3 ms with the line (`id`, `held` when a turn runs), and the `you` line reaches the notifier's stream in the same millisecond, so the bubble comes from the event as every line does (one source) and the answer is only the receipt. `bot say` also takes `-` and `--json` at 0.13.77, the release of the gate, so talking needs no newer cornercase than reading. Never `--wait` in the queue. It is a job that shows it runs (`Sending to PRs…` in the status bar, Send as `ui::busy_button`).

**When the field empties, never lost, never twice.** The field empties at Return, and one message to a bot is on its way at a time (a second Return waits on Send's spinner, `on_return`). A refused or failed message goes back into that bot's draft **before** what was typed since, with the toast `Could not send to PRs: <cornercase's words>`; for a bot that is gone it is in the toast, which offers **Copy message**; a failed Retry leaves the draft alone. A reply that never comes counts as a failure. The ordered queue keeps two messages in order. Only blanks: Return does nothing and Send rests. At 20,000 characters the window leaves it to cornercase's refusal, with the text kept: the limit is cornercase's to change. Rejected: emptying when the command answers (two Returns, and typing mixed with the text on its way), several messages on their way (a failure's text out of order), a count before 20,000, a hint row under the field.

**Held, Stop, Retry, New conversation.** A message sent while a turn runs is held by the server and its bubble says `Held` (1a draws it from the lines). **Stop** (`bot stop`, on the turn's row) never asks: it ends a turn the person is watching and keeps the conversation; the row reads `Stopping…` until the bot is idle, and `stopped` and `1 held message dropped` come as lines. If it fails, a toast and the button is back. **Retry** shows under an error that is the last line while no turn runs, and sends again what the failed turn was asked, through the same path as Send, never touching the field (#333). A turn is asked one message, or every message held while the turn before it ran, which cornercase's server joins with a blank line (`bot_next` → `bot_start` → `turn::joined`): so Retry sends those messages joined the same way, as one message. `entries::asked` replays the lines in the server's order to know which `you` lines the turn that ended last took (a message starts a turn; held ones wait; a `bot`, an `error`, `stopped` or `interrupted by a restart` ends it; the waiting ones start the next, but for the first N a `N held messages dropped` notice names, which a stop dropped). A turn that a `setting up` notice opened is the bot's setup, and Retry runs the setup again (see "A bot's setup turn"). With no `you` line that the failed turn took (it is past the newest 1,000 lines, or the turn was not started by a message or a setup) Retry does not show; before, it sent the last `you` line before the error, which after held messages was only the last of them, and could be an older turn's. Two held messages can pass cornercase's 20,000-character limit together: Retry is then refused with cornercase's words, as a typed message that long would be. Upstream's own window has the same fault (`send_again` sends `chat::prompt_of`, the last opener before the error, read at `610feefa` on 2026-11-21), which is reported upstream with this part; this window does not wait on it, since the lines already say what a turn took. **New conversation** (header) asks first (`dialogs::confirm`): a reset forgets the agent's conversation for good (its session id goes) though the chat's lines, `bot.md` and `memory.md` stay, and this window asks for what cannot be undone (cornercase's own window does not); it rests, dim, with `PRs is answering: stop it first` while a turn runs, so the question never stands between a person and a running agent, and a `busy` from a race shows the server's words.

**Drafts** live in `Store` (`Bots::drafts`), one per bot, kept on every key without a notify (so the sidebar's cached part is not drawn per key) and dropped with the bot (`take_app`) and with the server: ⇧⌘K makes the entities again with the new `Store`. Showing another bot, a tab or a machine's place and coming back finds the text; back from a tab the caret is where it was, after another bot it is at the text's end. A removed bot's draft goes with it, and when its chat was showing its `was removed` toast offers Copy message.

**The chat keeps following its end while the field grows.** A list keeps its top offset when its viewport shrinks, so a second row in the field would have hidden the newest line. gpui calls a list's scroll handler only for a wheel event, so the chat remembers whether it followed (`following`, set from where the reader is after a wheel or a key) and `BotChat::render` scrolls to the end while it does (`re_anchor`): the cached chat is drawn again when its bounds change, which a row added to the field does and a typed key does not. A placeholder is one row (`design/widgets.md`).

**The examples** of the empty state are upstream's questions under `Try one of these:`: three, and on a server with routines a fourth that sets one (`Every weekday at 9, tell me which of my PRs are blocked.`, upstream's words). A press, or Return or Space on the one with the ring, fills an empty field, or adds the example after the text on a line of its own (upstream replaces the draft; this window loses nothing typed), sends nothing and gives the field the keys (`global::keys_to_field`: the press no longer falls through to `press_rests`, and a key never did). On the frame the keys reach an example, from outside or from another example, the page moves as little as it takes to show that example whole (`example_to_reveal`, then the examples' column's `on_children_prepainted` hands its children's bounds to `text_field::show_box`, as the account picker reveals its first row); on later frames nothing moves it, so the wheel still scrolls the page while an example has the keys. Scrolling to the page's end was the first try and was rejected: in the least window (640 × 360) the three do not fit, and example 1, with the ring, was mostly out of view.

**Where the keys rest.** `Root::keys_rest` answers it (the chat's field while a chat shows, else the terminal's handle) and every place that gives the keys back asks it: `keys_changed` for `Keys::Root` and a noted terminal, Escape's `Step::KeysBack`, `close_shortcut` (⌘W on a docked panel), `close_menu`, `finish_rename` and the title row's presses. `keep_the_keys` is the one place that still parks the keys on `Root`'s own handle, on purpose: it runs only while a dialog or sheet is open, and the field must not type under it. `focus_lost` is the net under the chat's buttons: a button that has the keys and leaves the frame (Stop turning into `Stopping…`, the turn ending, Retry into `Sending…`) gives them to `keys_rest`, since the handle noted last was in the window (`lost_goes`, `design/widgets.md`). A press that nothing took (the sidebar's blank area, a fold, the status bar, the gutter around the card) would give the keys to `Root`'s handle, where typing goes nowhere, so `Root`'s own press asks the rule (`press_goes_to_rest`: a chat shows, no dialog or sheet, nothing prevented it) and focuses the field, so a press in the card's lines is covered too. A press on one of the chat's five buttons prevents it (`ui::press`), so it acts and leaves the keys where they were, normally the field; with a sidebar rename open, a press on Stop no longer ends the rename. That press also ends an open rename unsaved (`finish_rename(false)`), as a press in the panes does: no rename in this window ends on its field's blur, and while a chat shows there are no panes. `keys_after` gained no case; the field is noted as `Place::Window`, so a dialog that closes over the chat gives it back by `Back`, and a sheet by `Root`. `keys_follow` moves the keys with the place when a chat shows or leaves. A docked panel that has the keys (the Browser's page, the Files finder) keeps them. A removed bot's text is forgotten (`Refill::Forget`), so a bot made again with the same id starts empty.

**With keys alone** (part 2b-ii) a person can do in a chat everything its buttons do: Stop, Retry, New conversation, the examples and the bot's menu are tab stops (`ui::press`, the window's rule in `design/widgets.md`, "A button takes the keys"), Tab and ⇧Tab walk them and the field, the one that has the keys shows the field's ring, and Return or Space presses it on the key's release. No ⌘ shortcut was added (`design/widgets.md` says why). New conversation's question answers Return on its key down; the button acts only on the release of a key that went down on it, so a held Return opens the question once and does not answer it, and the Return that answers it does not open it again. Escape on a button gives the keys back to the field (`Step::KeysBack`). Not stops, by the rule's third clause: Send (Return in the field), `New messages` (↓ and PgDn), the resting and busy forms of each button; not made stops in this part, and listed on #326: `+N steps`, an answer's copy icon and its links. No key shows a toast's Show either: ⇧⌘I is how a person without a pointer reaches the answer a toast told. Rejected: Escape stopping a turn (a stray Escape would stop an agent's work) and a typed `/stop` (text goes to the bot).

**The field's cost.** A key typed in the field must not lay the chat's lines out again, so the field is a view of its own and a key notifies only it (drafts are kept without a `Store` notify). Measured on 2026-11-15 (a debug build with optimised dependencies, window 1280 × 800, `ZED_MEASUREMENTS=1`, a chat of the newest 1,000 lines of a fake agent's answers, 21 letters per run, nothing else building): the median frame was 0.8 ms (the worst 0.9 ms) over that chat and 0.72 ms over an empty one, and 0.6 ms typing into a shell with no chat. About one run in six had a median of 4.3 ms (once 8.2 ms): that happens equally over an empty chat, over a shell and with no change of ours (with a temporary counter `BotChat::render` ran 0 times in such a run, so the cached lines were not drawn again), in steps of about 4.2 ms, so it is frame pacing of this Mac and not a cost of the field. 1a's scroll measure was a median of 2.0 ms.

## A bot's setup turn

**What cornercase does** from 0.13.89 (usecornercase/cornercase-terminal#887, contract feature `bot-setup`; read at upstream's `610feefa`): `bot new` with a non-blank `--about` starts the bot's first turn by itself, a new conversation that reads what cornercase tells the bot about itself, `bot.md` and `memory.md` and asks it to schedule what `bot.md` asks for and say what it will do. Its first line is a notice, `setting up` (upstream's `chat::SETTING_UP`), then the turn's steps and its answer, as for any turn. Upstream's `bot_made` publishes `created`, then `start_setup` publishes the `thinking` state, appends the `setting up` line and begins the turn, all before `bot new` answers (`--json` then says `state: thinking`). With `--about` empty nothing starts. `bot setup ID --json` runs the setup again (it prints `{"bot", "line"}`); it is refused while a turn runs (`busy`) and when `bot.md` is empty (`conflict`: `<id> has nothing in bot.md to set up from; say what it is for first: cornercase bot edit <id> --about TEXT`).

**A setup opens a turn here too.** Upstream's replay takes `setting up` as a `you` that is not held: it starts a turn (`chat::opens_turn`). This window's replay does the same (`entries::opens_a_turn`, used by `Walk::step` and `turn`), with no second replay, so the turn row reads `Thinking · 42s · 3 steps` timed from the notice's `at` and counting the steps after it, where it read `Thinking` alone for the whole setup (one took 412 s and 38 tool calls on 0.13.86). A message sent during the setup is held as during any turn and starts the next one; a stop during it drops what was held, as for a message's turn. `held()` and `ends_a_turn` (upstream's rule for Held) do not change: the notice ends nothing. The row keeps the word `Thinking` (upstream's says `thinking` for a setup too), and the notice is drawn centred as any notice. The window's `Line` keeps no `routine`, so `is_setup` asks only the notice's text, where upstream also asks for no `routine`; no routine's line has that text (#267 adds the condition with `routine` on the line).

**Retry under a failed setup** (`entries::Retry { error, again }`, `Again::Setup`): when the error that ends the chat ended a turn whose only opener was `setting up`, Retry sends `bot setup ID --json` (`Store::set_up_bot`), never the text `setting up` to the bot; upstream's `send_again` does the same (`bot_setup` when the opener is a setup). A turn that held messages during a setup and failed still sends those messages, as before. It is a job on **the same busy key as Send** (`say_key`): one thing on its way to a bot at a time, Send and Retry both show it runs (`Setting up…` on Retry, `Setting PRs up…` in the status bar), a second press sends nothing, and `BotChat::moved` needs no new flag. It never touches the draft. A refusal is a toast, `Could not set PRs up: <cornercase's words>`. It is sent with `--json` (the rule), though its answer is not read: the second `setting up` line comes from the notifier's stream as every line does. Retry shows only under an error that is the last line, as in upstream's window: after a stopped or interrupted setup there is none, and `bot setup` from a shell is the way.

**The gate.** Retry sends `bot setup`, a subcommand this computer's command line parses and that came in the feature's own release, so it asks both halves (`Store::bot_setup_offered`: `Releases::lacks(Feature::BotSetup)`, `design/connection.md`); without it no Retry shows under a failed setup, as before this change, and nothing says why (see Rejected). The form's note only says what the server does with `--about`, a flag as old as bots, so it asks the server alone (`Store::server_has`). Reading the `setting up` line needs no gate: only a server with the feature writes it, as the list is the server's half for `Feature::Bots`. `BotChat`'s `Controls` holds `bot_setup_offered`, so a command line's release read after the chat showed draws Retry again.

**The order that shows the new chat.** The window shows the chat at or after `bot new`'s answer (`bot_created` → `follow_made` → `show_bot`), and upstream appends the `setting up` line before it answers, so the history read that `show_bot` starts holds it. Until that read answers `body` draws `Reading the chat…` (`Read::Asking` with no lines comes before the empty page), and afterwards the lines are not empty: the empty page cannot show for a bot that sets itself up, whichever of the history, the app line or the events comes first. The `thinking` state event that comes before the app line listing the bot is dropped (`Bots::state_heard`: the bot is not in the list yet); the app line that lists it carries `state: thinking`, so the row and the turn row follow from it. Between showing the chat and the history's answer the turn row is `controls::turn_row`'s fallback, `Thinking` with no time, then it gains its time and steps.

**Telling the answer.** The setup's answer is a `bot` line like any other, so "Never told twice" applies unchanged: told when the chat is not on screen here, once; nothing for the chat shown in the active window.

**The form's sentence** (`model/bots/form.rs`, `about_note`, `SETS_ITSELF_UP`), under What it's for in New bot… only, dim, below the field's keys hint: `Once made, the bot sets itself up from it at once: it schedules what this asks for and says in its chat what it will do. Left empty, it starts nothing and spends no tokens until you write to it.` Upstream's own form says nothing of it (its placeholder is `optional: what the bot is for`), so the words are this window's wording of upstream's `bot new --help` ("the bot sets itself up for it at once", "schedules what that asks for and says in its chat what it will do", "it starts nothing and spends no tokens until you write to it"). Edit bot… keeps its line (`ABOUT_WAITS`): what a bot is for is not shown or changed there yet.

## Making, editing and removing a bot

**What the form sends and why.** `bot new --json` with the agent and the access always sent (the form sends what it shows and depends on no server default), every other option only when set, each in the `=` form (`--model=opus`) and `--` before the name, so a name or a value that starts with `-` arrives whole (seen on 0.13.80: without `--` clap refuses `-x`; with it the bot is named `-x`, its id `x`). The name and the model go trimmed, what it is for as typed unless it is only blanks; a name of only blanks sends nothing, as New workspace and New group. Nothing is sent until the agents are read, and a second Return while the job runs sends nothing (the form's guard and the store's, on the dialog's start key).

**The form** (`dialogs/bot_form.rs`, the plain data in `model/bots/form.rs`) is upstream's fields in its order: Name, Agent, Model, Effort, Account, Access, Chat apps, What it's for. Agent comes from `bot agents --json`, never a list of names here, so the agents upstream made bots later showed with no change: usecornercase/cornercase-terminal#849 shipped in 0.13.86 (Gemini CLI, opencode, Cursor CLI and GitHub Copilot CLI can be bots), and their chips, accesses and reasons came from the list with nothing changed here (`tests/fixtures/bots/agents-reads.json`, 0.13.109's answer with fakes for six agents); one that cannot be a bot is a resting chip with the server's own `why` (`Codex · not installed`), readable with no pointer. The agent chosen at open is the server's default agent (`config --json`'s `agent`, as every other form takes it) when it can be a bot **and offers access through cornercase**, else the first agent that does, else the first that can be a bot. **This departs from #266's task ("the server's default agent when it can be a bot")**: with a default that offers full access only (Codex today), the form would open with no access chosen, so a name and Return could only say `Choose its access.` and a person without a pointer could not make a bot at all (no key reaches the chips or the segment, #326). The default agent stays one press away, and the access is still never chosen for the person. Model is a field with the agent's suggestions as chips that fill it (no combobox exists in this window; the Machines form's host chips are the pattern), Effort chips only for an agent that has `efforts`, Account the shared picker only for an agent that has accounts and starting on the agent's own login, which is cornercase's default for a bot. Both access lines show always, the full-access one in the danger colour, so the warning is read before choosing (as upstream's form does), and a line says when an agent can be a bot with full access only. **The first line follows the chosen agent's `reads`** (0.13.86, upstream's feature `bot-reads`, #361): `Through cornercase, it reads and writes only in its own folder.` for `reads: "folder"` (Gemini CLI and GitHub Copilot CLI, whose tools refuse a path outside their folder), `Through cornercase, it reads anything and writes only in its own folder.` for every other agent. `reads` is read leniently (`text_or_empty`, as a bot's folder): absent, another type or another value means anything, and the agent stays in the list, so there is no gate and an older server draws as before. The line does not change with the chosen access: it says what access through cornercase is, and upstream's brief holds such a bot to its folder only then (`REACH_FOLDER`; full access gets `FULL`), so with Full access chosen the danger line below it says the rest. On Windows those two agents offer full access only and the line still says what access through cornercase would be, beside the full-only line. **Access is never chosen for the person when `cornercase` is not offered**: Create then says `Choose its access.` under the form and sends nothing, since full access lets an agent change any file and run anything, unattended, and only the person may pick it. Chips, segments and buttons are no tab stops (#326), except the Chat apps row's choices and its line (#269, "Chat apps" below); Tab goes through Name, Model, the Chat apps row and What it's for. Under What it's for, on a server with `bot-setup` (0.13.89), a dim line says what filling it in starts ("A bot's setup turn"). Return in Name creates, so a name and Return give a bot with every other field at its default, with keys alone, **when some agent can be a bot through cornercase** (the form opens on it). If only an agent with full access only can be a bot (Codex today), a name and Return says `Choose its access.` and keys alone cannot make a bot, since no key reaches the access segment (#326); in What it's for Return breaks the line and ⌘↩ creates.

**The agents' list** is read when the form opens, beside the queue (it only reads), and shows `Reading the agents…`; a failure says `Could not read the agents: <words>` with Try again, never an empty list; Create rests until it is read.

**A refusal** (a taken name, 50 bots, a name of 41 characters) is cornercase's, shown under the form in cornercase's words; the form stays open with everything typed, and the line goes at the next change. The 40-character limit is cornercase's to change, so the window counts nothing (as 1b decided for 20,000 characters). A refusal that comes after the form was closed is a toast.

The other forms keep both faults until #341 and #342 decide for them.

**The order that shows the new chat.** Seen on 0.13.80 (five makings): the `bot` event `change: created` and the answer arrive in the same millisecond, and the app line that lists the bot arrives within a few milliseconds of them, before or after (once about 470 ms after). So the dialog closes at the answer and the chat shows once the list holds the bot (`Made`, `Bots::can_show` still refuses a bot the list does not hold), whichever comes first, **if the form was still the shown dialog at the answer** (`place::awaits`, the rule a machine's start follows too: `design/machines.md`): a form closed before it (Escape, a press outside) moves nothing, and a person who moved meanwhile would otherwise have the chat take the view and the keys later, so then no chat shows and the row comes with the list. The wait ends at a person's move (the same three places that end a machine's started tab: `forget_awaited`), at another `boot` and after 30 s (the machine's own constant), and then nothing shows: the row is there when the list has it. Rejected: keeping the dialog open until the chat shows (Create would come back and a second press would send a second `bot new`).

**The first bot and the `+`.** 1a's rule stays: with no bot the section is not drawn (upstream draws none either), so New bot… is in the Projects header's `+` after New group…, always while the gate allows it, and the Bots header has a `+` once the section shows. **⌘E** (Ctrl+Shift+E on Linux and Windows) opens New bot… (why this key: `design/terminal.md`, Why these keys). It acts while a chat shows and the keys come back to the chat's field when the form closes. On a server without bots it toasts the gate's sentence, never silence; without a session it does nothing, as ⌘N.

**The row's menu** is one function (`sidebar/bot_menu.rs`) offered by the row's `⋯` on hover and a right press: New conversation… (1b's question, shared) and Remove bot…. While the bot answers both rest under `<name> is answering: stop it first`, 1b's words. What a hovered row adds moves `SidebarKey` through `side.hovered` and nothing else.

**Remove bot…** asks first (`Remove the bot PRs?`, its chat, its memory and its folder are deleted, agents it started keep running), then runs `bot remove` as a job. It rests while the bot answers, as New conversation does, so the question never stands between a person and a running agent and Stop stays on the turn's row; upstream's button inside the question that stops the turn is rejected (a second place that stops a turn, whose label would change while it is open). ## Never told twice

**Who posts cornercase's own notification** (read in its sources at 0.13.80 and 0.13.86, and seen): its server queues one for an answer and sends it only to its own attached windows, as an escape sequence the terminal around that window shows (OSC 9 seen on the bench); it runs no program, so with no window of its own attached nothing is posted, and `desktop_notifications` `off` posts none.

**The order.** cornercase publishes the `bot` line on `events` first and counts it unread after; the count reaches this window with the next app line, 0 to about 500 ms later (seen: 0 to 520 ms). It counts as seen, with no rise, a turn a `say --wait` client waits on and an answer read on screen in its own window (seen: both).

**The rule.** An answer is told when the app line shows that bot's `unread` rose, in the words of the `bot` or `error` line heard for it (`Answers`: pairs the two within 2 s, in either order). Telling at the line was rejected: it would toast what cornercase counts as seen and the row's count would disagree for good. On top comes this window's own rule, `tells`: nothing for the chat shown in the active window (cornercase does not know it shows it: #869), and nothing for a run's error (a line with `routine`), which its `queue-failed` message already tells. Nothing is told below the gate (`tells` holds it) or for a linked machine's bots (none is heard).

**The toast.** `<name>: <first line>`, Done, 15 s; an error `<name> could not answer: <first line>`, NeedsYou (it waits for the person; Error would read as "your press failed"); a button Show (`ToastGo::Bot` → `go_to_bot` → `show_bot`); two bots give two toasts, the same text while it stands counts `×2`. The first line of an answer (`first_line`) is read over the window's Markdown parser, so it reads as the chat draws it; an error's is its first non-blank line as plain text, as the chat draws an error and as cornercase's own toast takes it; both are cut at 100 characters with `…` as cornercase cuts it. A removed bot's toasts go, and so do a bot's toasts when its chat is read: at once when this window counts it as read (`mind_seen`, with `bot seen`), and with the app line that zeroes the count when it was read elsewhere (cornercase's own window, a script's `bot seen`): a toast is not a reading, a reading takes the toasts away; a click on a banner of a removed bot says `<name> is gone`.

**The notification.** Only while the window is behind, with `desktop_notifications` read on each one; headline `<name> answered` or `<name> could not answer`, body the first line, no sound (cornercase plays none); a click does what Show does.

| Setup | cornercase tells | This window tells | Banners for one answer |
|---|---|---|---|

| Its window attached, the chat not on screen there, notifications on | its toast and its terminal's notification | a toast; a banner while behind | two, as for an agent's notice |

Cases: (b) read in its window or waited on: not told (no rise; seen); (c) a message sent from here, then a move to a tab: told; (d) the chat shown in the active window: nothing, `bot seen` follows; (e) a line that came while the stream was not followed: never replayed, the row's count is what is left; (f) a line heard twice: told once (`told` ids); (g) a routine's failure: told once, by its message; its answer is told with the routine's label (`PRs · Review PRs: …`, headline `PRs · Review PRs answered`), read from the queue's entry the line's `routine` names, and without it when the entry is gone (#267).

## A bot's secrets in its form

The first read shows `Reading the secrets…`; a later one keeps the list drawn. The form reads again when the bot's count or `unreadable` moved and the list it holds does not already have that many (or the file stopped opening), so a change made in a shell, in the ask dialog or in another window shows. A replacement keeps the count, so the store also raises a counter after each `set` or `remove` of its own (`Managing::secret_saved`), and the form reads again when it moved. A count the list already has reads nothing more, but an add or a remove of one's own can still read twice: its answer and the app line cross while the first read is in flight, and the second event finds the old list. It costs one `bot secret list`, and was not worth a count kept per read. **A replacement made elsewhere** shows its new date only at the next read: the app line carries a count, not dates. One read runs at a time; a change heard during it reads once more after it (`again`), and an answer to an older read is dropped (`serial`).
