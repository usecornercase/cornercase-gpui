# Bots

The Bots section of the sidebar and a bot's chat, for cornercase 0.13.77 and newer (usecornercase/cornercase-terminal#844, #845; this window's #266). Cornercase's own design is upstream's `design/bots.md` and `design/bots/window.md`; this file says what this window does and why.

## The cut

Writing is not here: the window has no field in a chat, so no key typed there is sent anywhere.

- **Part 2a-i, here** (see "Making and removing a bot"): New bot… (the form, built from `bot agents`), the Bots header's `+`, the first bot, ⌘E, the row's `⋯` and right-press menu with New conversation… and Remove bot…, and Remove… itself. Editing and renaming a bot and opening its folder still happen in cornercase's own window or with `cornercase bot edit`.

## The data

- **The list** comes from the app stream (`Store::take_app` reads `bots` as it reads `machines`), never from a poll of `bot list`. It is read leniently: a `bots` that is missing or not a list is no bots, and an entry that does not read is left out while the others stay. A bot with no line yet has `last: null`; the window does not read `last`, `folder`, `created`, `access`.
- **A chat** reads `bot history ID --json --last 1000` once, then follows the `bot` events of the notifier's stream, which is already open for the whole server run (`events --notices --host --json`): `Event::Bot` is read beside the others and `Store::bot_heard` takes it, so the stream has a second reader and no process more. A stream of the chat's own was rejected: one more process per window for the same events.
- **The merge** keeps the lines by id, sorted, the newest 1,000 (upstream's own limit); an `Earlier messages are left out` note says so. A line that arrives twice is kept once, and lines out of order are put in order. Once the history is read, a line whose id skips past the last one asks `bot history --after LAST` for the lines between (one such read at a time). A late answer of an earlier ask, or for another bot, is dropped (`Chat::asked`).
- **A failed read keeps what is shown**: with lines already in the chat the failure shows above them, and the next line heard, an app line that settles the bot, or showing the chat again reads it whole; a catch-up asked while another read runs is kept (the earliest cursor) and asked when that one ends. A line whose fields have the wrong type (a `text` that is a number, no `kind`) is left out, never turned into a blank line.
- **A new server run** (`boot` changes in the app line) reads the chat again whole; the notifier's stream starting again reads what follows the last line (`Store::bot_stream_started`).
- **A `state` event** updates that bot's state until the next app line replaces it, so the row and the turn's row never disagree with the chat for longer than a line. A `change: removed` leaves the chat; `created` and `edited` are heard as nothing, since the list changes with the app line. Unknown kinds show as plain text; an event with none of `line`, `state`, `change`, or with a bad line, changes nothing.
- **Held** is read from the lines with upstream's own replay rule, not from the list's `held` count: a `you` line with `held: true` after the last line that ends a turn (a `bot` answer, an `error`, or a notice whose text is `stopped`, `interrupted by a restart`, `1 held message dropped` or `N held messages dropped`) is still held. So it ends with the very line that ends the turn and never trails by an app line. Those texts are upstream's fixed words.

## The shown place

The shown place is one value, `Showing` (`Local`, `Machine(place)` or `Bot(id)`, in `model/place.rs`), kept in `Store` (`store/place.rs`, with its writer `place()`, `show_local` and the readers `machine_place()`, `shown_bot()` and `shows_local()`), so no two flags can both be set. `Showing::after(Moved)` is the rule, a plain function: a move to a local place, a machine's place or another bot sets that place; a removed bot, or a list that no longer holds the shown bot, leaves the chat; anything else keeps what shows. The writers are `select_there`, `show_bot`, `show_local` (which every command that moves the view reaches through `cli::moves_view`, and a press on a project, workspace, tab or agent row, a toast's Show, Search's choice, ⌘1…9 and ⇧⌘[ ⇧⌘]), `follow_machines` and the bot's removal (with the toast `<name> was removed`). The readers outside `store/` are those three methods. Root mirrors the bot in `SideState::bot` as it mirrors a machine's place (`app/bot_place.rs`): entering pauses the own surface, leaving resumes it, and `view-set --hidden` goes while a chat covers the tab, so agents there notify. After the window restarts it shows the panes, as upstream does and as a machine's place does.

Tab strip while a chat shows: the workspace's tabs with none marked; a press on one goes back to it. The title stays as it is; the status bar keeps the connection and the size and drops the pane's name and folder, since `active_pane()` is none (as for a machine's place). A docked panel follows the workspace behind the chat, as it does with no chat. A bell in the tab behind a chat is a toast, not a flash.

## The keys while a chat shows

⌘E (New bot) acts while a chat shows: it opens a dialog, and the keys come back to the chat's field when it closes. While a chat shows, its field has the keys (`Root::keys_rest`), so typing, a dead key, ⌥ characters and the input method go to it, and ↑ ↓ PgUp PgDn scroll the chat when the field holds one row or none (with more rows ↑ ↓ move between rows; PgUp PgDn always scroll). ⌘A ⌘C ⌘X ⌘V are the field's, as in every field of this window; ⌘Z does nothing (no field has undo); Tab does nothing (the field is not a tab stop and no button can take the focus). The terminal element is not drawn, so no click, wheel, drop or input-method text reaches a pane, and `takes_input()` is false, so `active_pane()` is none: close, split, panes, mark, copy and paste find no pane. `keymap::in_chat` answers each command: **Acts** as always (panels and sheets, ⌘F, the finder, ⌘N, ⌘O, ⇧⌘K, ⌘P, ⌘G, ⌘/, zoom, ⌘C, and the Browser's own keys); **Leaves** because it moves the view (next and previous workspace and project, ⌘B when an agent needs you, ⌘T, ⌘1…9 and ⇧⌘[ ⇧⌘], a number past the last tab does nothing); **OnTop** (⌘W closes a dialog, a sheet or a docked panel, never a pane); **Rests** (⌘R, ⇧⌘W, ⌘D, ⇧⌘D, ⌘[ ⌘], ⌘V: they would act on a tab or pane nobody sees; ⌘V is `InChat::Field`: the field's own binding takes it before `Root` asks, so a ⌘V that reaches `Root` comes from a place that is not the field and does nothing, and a docked Browser's page that has the focus is still asked first). A test keeps one answer for every command of `SHORTCUTS`. Escape clears the field when it holds text (and the draft); with none it closes what is on top, one per press, and with nothing on top does nothing, the keys staying in the field (upstream's rule: a stray Escape never drops what you read). Linux and Windows send the same commands through `keymap::chord`.

## The section

Below the projects and above the Agents section in every arrangement (in side by side, at the bottom of the projects' column); #266 says "after the projects", and in the one-column arrangements that would split the projects from their workspaces. It shows only when the server lists at least one bot, at most half its column (its rows scroll past that), and never when there are none, so a server without bots draws the window as before. The header folds it (`Bots`, with the spinner and the rail's disc when folded); the fold is kept in memory in `SideState`, as the sidebar's other folds are, since cornercase has no command for its own saved fold and each client keeps its own layout. Rows are in `bot list`'s order, never by state, since rows that move are hard to press: the status slot (a faint message glyph, or the status family's spinner while it thinks), the name and `claude · opus` (the agent alone when no model is set), and at the end the rail's disc with the unread count, hidden while that chat is on screen in the active window. No avatar: every sidebar row has one status slot, and an initials disc would make bot rows heavier than the others (the TUI draws none). No local row is marked while a chat shows. The sidebar's cached part moves with `Bots::revision` (a name, state or unread count, the fold, a shown bot).

## The chat

One card the size of the terminal area. A header (the name, then `agent · model · effort · account` for what is set), the lines, the turn's row while the bot thinks (`Thinking · 42s · 3 steps`, the time left out under 5 s), and the field below it ("Talking"). Lines: `you` a bubble on the right with its time, or `Held`; `bot` with `name · time` above its Markdown and a copy button; steps dim, a run past 3 folded under `+N steps` that a press opens (the last 3 stay in view); `error` in the danger colour; `notice` centred, the server's words as they come; an unknown kind in plain muted text. Times are the Queue's clock (`14:02`, else `yesterday 14:02`, `Mon 14:02`, a date): #278 will move them. The empty state is two lines in the Queue's empty page's look, and promises no schedule.

- **Scrolling** uses gpui's `list` anchored by `scroll_to` the end, as the Browser's console does. A sync splices only the entries that changed (`entries::spliced` and `row_splices`: entries that overlap the first new one tell what was dropped at the front, then each position that differs, then the tail; the `Earlier messages` row is spliced on its own so a chat at its 1,000 lines does not move a reader who scrolled up), the Markdown of an answer is parsed once and kept by line id, and a frame lays out only what is in view. A line arriving at the bottom stays at the bottom; scrolled up, what is read stays put and a `New messages` button shows, cleared by a press or by reaching the end. Measured on 2026-11-15 on a debug build (dependencies optimised) with 1,000 lines of long answers, scrolling by ↑ held about 60 frames: median 2.0 ms, worst 5.5 ms.
- **The chat is a cached view** (`AnyView::cached`), drawn from itself and the `Store`: `tests/layers.rs` checks it as it checks the docked panels (`ALSO_CACHED`), except `global.rs`, which holds the entity. It reads the clock at render, so a time of day written before midnight reads as today's until the next redraw; only a turn's row redraws by itself.
- **The chat entity follows the `Store`**: `BotChat::get` makes it again when the global's `Store` is not the current one (after ⇧⌘K to another server), as `Popup::get` does; no test makes an entity here, so that rule rests on reading.
- **Links** in an answer open when a web address is clicked, as in Recap and the Queue, and anything else is a toast: the click is the person's own, in this window, and no server makes the window open anything. Upstream copies a link because its server draws its own window (#863).
- **Selecting** Markdown is not possible anywhere in this window (gpui's text cannot be selected), so each answer has a copy button, and selecting goes to part 2. **Code highlighting** is #312.

## Talking

**The field** is `TextField::chat()` (`ui/text_field`, `Enter::Sends`, key context `TextField Chat`): Return sends, ⇧Return breaks the line, ⌘↩ (Ctrl+Enter on Linux and Windows) sends too, one to 6 rows then it scrolls inside, a paste keeps its line breaks. It is the third way a field reads Return (a line: submit; several lines: a break and ⌘↩ submits; the chat: submit and ⇧Return breaks) and one rule with a parameter, not a copy of the bindings. Return while the input method composes (`marked_range`) accepts the composition and sends nothing: on macOS gpui hands the key to the method first, and the guard (`submits`) covers a platform that lets the binding run with marked text left. A dead key followed by Return is committed by the method, so the text goes with its accent. The field is not inside the cached chat: gpui marks every ancestor view dirty when a view notifies, so a key typed in a field inside the chat would lay its lines out again. `ChatField` is a view of its own below the cached chat, inside one card that `bot_chat::view` draws.

**How a text travels.** `bot say ID --json -` as a line of the ordered queue, the text in the line's `stdin` (`Queue::cmd_with_stdin_then`, the one call that has a reply and standard input): the only form where `-`, a text that starts with `-` and line breaks arrive whole. Seen on a 0.13.80 server: `-`, `-x starts with a dash`, `two\nlines\n`, `año ñ 😀` and 20,000 characters reached the agent to the character, 20,001 was refused by cornercase (`the message is 20001 characters; a bot takes at most 20000`) and a text of blanks too (`the message is empty`); it answers in 1 to 3 ms with the line (`id`, `held` when a turn runs), and the `you` line reaches the notifier's stream in the same millisecond, so the bubble comes from the event as every line does (one source) and the answer is only the receipt. `bot say` also takes `-` and `--json` at 0.13.77, the release of the gate, so talking needs no newer cornercase than reading. Never `--wait` in the queue. It is a job that shows it runs (`Sending to PRs…` in the status bar, Send as `ui::busy_button`).

**When the field empties, never lost, never twice.** The field empties at Return, and one message to a bot is on its way at a time (a second Return waits on Send's spinner, `on_return`). A refused or failed message goes back into that bot's draft **before** what was typed since, with the toast `Could not send to PRs: <cornercase's words>`; for a bot that is gone it is in the toast, which offers **Copy message**; a failed Retry leaves the draft alone. A reply that never comes counts as a failure. The ordered queue keeps two messages in order. Only blanks: Return does nothing and Send rests. At 20,000 characters the window leaves it to cornercase's refusal, with the text kept: the limit is cornercase's to change. Rejected: emptying when the command answers (two Returns, and typing mixed with the text on its way), several messages on their way (a failure's text out of order), a count before 20,000, a hint row under the field.

**Held, Stop, Retry, New conversation.** A message sent while a turn runs is held by the server and its bubble says `Held` (1a draws it from the lines). **Stop** (`bot stop`, on the turn's row) never asks: it ends a turn the person is watching and keeps the conversation; the row reads `Stopping…` until the bot is idle, and `stopped` and `1 held message dropped` come as lines. If it fails, a toast and the button is back. **Retry** shows under an error that is the last line while no turn runs and a `you` line is kept before it; it sends that text again through the same path as Send and never touches the field. With no `you` line kept it does not show (upstream shows it and does nothing). **New conversation** (header) asks first (`dialogs::confirm`): a reset forgets the agent's conversation for good (its session id goes) though the chat's lines, `bot.md` and `memory.md` stay, and this window asks for what cannot be undone (cornercase's own window does not); it rests, dim, with `PRs is answering: stop it first` while a turn runs, so the question never stands between a person and a running agent, and a `busy` from a race shows the server's words.

**Drafts** live in `Store` (`Bots::drafts`), one per bot, kept on every key without a notify (so the sidebar's cached part is not drawn per key) and dropped with the bot (`take_app`) and with the server: ⇧⌘K makes the entities again with the new `Store`. Showing another bot, a tab or a machine's place and coming back finds the text; back from a tab the caret is where it was, after another bot it is at the text's end. A removed bot's draft goes with it, and when its chat was showing its `was removed` toast offers Copy message.

**The chat keeps following its end while the field grows.** A list keeps its top offset when its viewport shrinks, so a second row in the field would have hidden the newest line. gpui calls a list's scroll handler only for a wheel event, so the chat remembers whether it followed (`following`, set from where the reader is after a wheel or a key) and `BotChat::render` scrolls to the end while it does (`re_anchor`): the cached chat is drawn again when its bounds change, which a row added to the field does and a typed key does not. A placeholder is one row (`design/widgets.md`).

**The examples** of the empty state are upstream's three questions under `Try one of these:` (none promises a schedule: routines are #267). A press fills an empty field, or adds the example after the text on a line of its own (upstream replaces the draft; this window loses nothing typed), sends nothing and gives the field the keys.

**Where the keys rest.** `Root::keys_rest` answers it (the chat's field while a chat shows, else the terminal's handle) and every place that gives the keys back asks it: `keys_changed` for `Keys::Root` and a noted terminal, Escape's `Step::KeysBack`, `close_shortcut` (⌘W on a docked panel), `close_menu`, `finish_rename` and the title row's presses. `keep_the_keys` is the one place that still parks the keys on `Root`'s own handle, on purpose: it runs only while a dialog or sheet is open, and the field must not type under it. `focus_lost` is unchanged. A press that nothing took (the sidebar's blank area, a fold, the status bar, the gutter around the card) would give the keys to `Root`'s handle, where typing goes nowhere, so `Root`'s own press asks the rule (`press_goes_to_rest`: a chat shows, no dialog or sheet, nothing prevented it) and focuses the field, so a press in the card, whose buttons and lines prevent nothing, is covered too. `keys_after` gained no case; the field is noted as `Place::Window`, so a dialog that closes over the chat gives it back by `Back`, and a sheet by `Root`. `keys_follow` moves the keys with the place when a chat shows or leaves. A docked panel that has the keys (the Browser's page, the Files finder) keeps them. A removed bot's text is forgotten (`Refill::Forget`), so a bot made again with the same id starts empty.

**With keys alone** a person can write and send. Stop, Retry, New conversation and the examples are not reachable: no button in this window can take the focus (`ui::button` has no focus handle, and Tab does nothing in the chat), so that waits for a decision about buttons for every panel, and part 2's ⌘ shortcut. Rejected: Escape stopping a turn (a stray Escape would stop an agent's work) and a typed `/stop` (text goes to the bot).

**The field's cost.** A key typed in the field must not lay the chat's lines out again, so the field is a view of its own and a key notifies only it (drafts are kept without a `Store` notify). Measured on 2026-11-15 (a debug build with optimised dependencies, window 1280 × 800, `ZED_MEASUREMENTS=1`, a chat of the newest 1,000 lines of a fake agent's answers, 21 letters per run, nothing else building): the median frame was 0.8 ms (the worst 0.9 ms) over that chat and 0.72 ms over an empty one, and 0.6 ms typing into a shell with no chat. About one run in six had a median of 4.3 ms (once 8.2 ms): that happens equally over an empty chat, over a shell and with no change of ours (with a temporary counter `BotChat::render` ran 0 times in such a run, so the cached lines were not drawn again), in steps of about 4.2 ms, so it is frame pacing of this Mac and not a cost of the field. 1a's scroll measure was a median of 2.0 ms.

## Making and removing a bot

**What the form sends and why.** `bot new --json` with the agent and the access always sent (the form sends what it shows and depends on no server default), every other option only when set, each in the `=` form (`--model=opus`) and `--` before the name, so a name or a value that starts with `-` arrives whole (seen on 0.13.80: without `--` clap refuses `-x`; with it the bot is named `-x`, its id `x`). The name and the model go trimmed, what it is for as typed unless it is only blanks; a name of only blanks sends nothing, as New workspace and New group. Nothing is sent until the agents are read, and a second Return while the job runs sends nothing (the form's guard and the store's, on the dialog's start key).

**The form** (`dialogs/bot_form.rs`, the plain data in `model/bots/form.rs`) is upstream's fields in its order: Name, Agent, Model, Effort, Account, Access, What it's for. Agent comes from `bot agents --json`, never a list of names here, so an agent upstream makes a bot later (usecornercase/cornercase-terminal#849) shows with no change; one that cannot be a bot is a resting chip with the server's own `why` (`Codex · not installed`), readable with no pointer. The agent chosen at open is the server's default agent (`config --json`'s `agent`, as every other form takes it) when it can be a bot **and offers access through cornercase**, else the first agent that does, else the first that can be a bot. **This departs from #266's task ("the server's default agent when it can be a bot")**: with a default that offers full access only (Codex today), the form would open with no access chosen, so a name and Return could only say `Choose its access.` and a person without a pointer could not make a bot at all (no key reaches the chips or the segment, #326). The default agent stays one press away, and the access is still never chosen for the person. Model is a field with the agent's suggestions as chips that fill it (no combobox exists in this window; the Machines form's host chips are the pattern), Effort chips only for an agent that has `efforts`, Account the shared picker only for an agent that has accounts and starting on the agent's own login, which is cornercase's default for a bot. Both access lines show always, the full-access one in the danger colour, so the warning is read before choosing (as upstream's form does), and a line says when an agent can be a bot with full access only. **Access is never chosen for the person when `cornercase` is not offered**: Create then says `Choose its access.` under the form and sends nothing, since full access lets an agent change any file and run anything, unattended, and only the person may pick it. Chips, segments and buttons are no tab stops (#326); Tab goes through Name, Model and What it's for. Return in Name creates, so a name and Return give a bot with every other field at its default, with keys alone, **when some agent can be a bot through cornercase** (the form opens on it). If only an agent with full access only can be a bot (Codex today), a name and Return says `Choose its access.` and keys alone cannot make a bot, since no key reaches the access segment (#326); in What it's for Return breaks the line and ⌘↩ creates.

**The agents' list** is read when the form opens, beside the queue (it only reads), and shows `Reading the agents…`; a failure says `Could not read the agents: <words>` with Try again, never an empty list; Create rests until it is read.

**A refusal** (a taken name, 50 bots, a name of 41 characters) is cornercase's, shown under the form in cornercase's words; the form stays open with everything typed, and the line goes at the next change. The 40-character limit is cornercase's to change, so the window counts nothing (as 1b decided for 20,000 characters). A refusal that comes after the form was closed is a toast.

**At 640 × 360** the title and the buttons stay in view and the body scrolls: Name and the agents' chips show at open. Tab reveals Model and What it's for; the last field ends the form (`set_ends_form`, #342's rule), so its hint is whole. The form passes its scroller to its account pickers (`design/widgets.md` says how a picker reveals itself, #341) and tells its last field (#342). The other forms keep both faults until #341 and #342 decide for them.

**The order that shows the new chat.** Seen on 0.13.80 (five makings): the `bot` event `change: created` and the answer arrive in the same millisecond, and the app line that lists the bot arrives within a few milliseconds of them, before or after (once about 470 ms after). So the dialog closes at the answer and the chat shows once the list holds the bot (`Made`, `Bots::can_show` still refuses a bot the list does not hold), whichever comes first, **if the form was still the shown dialog at the answer**: a form closed before it (Escape, a press outside) moves nothing, and a person who moved meanwhile would otherwise have the chat take the view and the keys later, so then no chat shows and the row comes with the list. The `created` event is heard as nothing (it carries no bot, and the list is the one source). The wait ends at a person's move (the same three places that end a machine's started tab: `forget_awaited`), at another `boot` and after 30 s (the machine's own constant), and then nothing shows: the row is there when the list has it. Rejected: keeping the dialog open until the chat shows (Create would come back and a second press would send a second `bot new`).

**The first bot and the `+`.** 1a's rule stays: with no bot the section is not drawn (upstream draws none either), so New bot… is in the Projects header's `+` after New group…, always while the gate allows it, and the Bots header has a `+` once the section shows. The Projects `+`'s tooltip names bots only while one can be made, and the Bots header's `+` shows only when `Making` allows it too. **The gate for making is not `bots_offer`** (that is `Hidden` with no bot, so it cannot say whether the first can be made): `Making` asks the session's release and this computer's command line (`Feature::Bots`), and says why where a person would look: a resting New bot… with the sentence for an older command line here, and nothing new for an older server (⌘E toasts the sentence there).

**⌘E** (Ctrl+Shift+E on Linux and Windows) opens New bot… (why this key: `design/terminal.md`, Why these keys). It acts while a chat shows and the keys come back to the chat's field when the form closes. On a server without bots it toasts the gate's sentence, never silence; without a session it does nothing, as ⌘N.

**The row's menu** is one function (`sidebar/bot_menu.rs`) offered by the row's `⋯` on hover and a right press: New conversation… (1b's question, shared) and Remove bot…. While the bot answers both rest under `<name> is answering: stop it first`, 1b's words. What a hovered row adds moves `SidebarKey` through `side.hovered` and nothing else.

**Remove bot…** asks first (`Remove the bot PRs?`, its chat, its memory and its folder are deleted, agents it started keep running), then runs `bot remove` as a job. It rests while the bot answers, as New conversation does, so the question never stands between a person and a running agent and Stop stays on the turn's row; upstream's button inside the question that stops the turn is rejected (a second place that stops a turn, whose label would change while it is open). A turn that starts between the question and the press is cornercase's `busy` refusal (seen: `prs is answering; stop it first (cornercase bot stop prs)`), shown in a toast. The person who removed it gets no `<name> was removed` toast, since they just answered the question; a removal from elsewhere still tells when its chat showed. The mark is set when the command is sent, because cornercase publishes `removed` before it answers. The chat leaves and its draft goes, as in 1a and 1b. A dialog that names a removed bot closes (upstream's rule), on the `removed` event and when the list drops the bot (the list is the one source, since an event can be missed while the stream is down): the Remove question and 1b's New conversation question.

**What waits upstream.** `BotInfo` (`bot list --json`, `bot new --json`, `status --app`) has no `about`, and no command prints what a bot is for (usecornercase/cornercase-terminal#876; seen: no `about` in any answer; upstream's own window reads `bot.md` itself). The window may not read cornercase's private files, so Edit… (part 2a-ii) cannot show that text: it will not offer the field and will say so plainly.

## `bot seen`

Sent through the ordered queue when the shown chat has unread answers in the active window, once per unread count (a count that returns to none may ask again): showing a chat, an answer arriving while it shows, the window becoming active. A step changes no count, so none sends it; an answer or an error heard in the shown chat, and showing a chat, forget what was sent, so the next answer is told again even at the same count. When an app line shows the shown bot stopped thinking or got more unread, the chat reads what follows its last line once (`bot history --after`), so a line missed while the notifier's stream was down or starting cannot stay missing; an empty chat reads from the start. A sheet over the chat still counts as on screen. The row hides its count meanwhile so the app line between an answer and its `seen` shows no flash.

`Feature::Bots` (0.13.77). A release that could not be read counts as older. `cli::MINIMUM` does not move. A linked machine's bots are upstream's to add; nothing is drawn for them.
