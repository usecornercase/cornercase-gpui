# Releases

Code: `.github/workflows/release.yml`, `.github/workflows/version.yml`, the version step of `ci.yml`, `.github/release/` (`release.sh`, `keychain.sh`, `about.toml`, `about.hbs`), `tools/macos/` (`bundle.sh`, `notarize.sh`), `tools/icon.py`, `assets/macos/`, `.cargo/config.toml`, `CHANGELOG.md`; the README's Install says how to use the downloads

- **Every merge that changes the app releases it**, as cornercase's do (its `design/releases.md`; asked for on 2026-11-05). (1) The pull request bumps `Cargo.toml`'s version (then `cargo check`, so `Cargo.lock` follows) and adds its `## X.Y.Z` section to `CHANGELOG.md` (`AGENTS.md`); CI's guardrails refuse it otherwise (`release.sh pull-request`: the version above the last tag, the section there). "The app" is `app_changed`'s list in `release.sh`: what a release builds or packs, so a change to the signing ships too; docs, tests and CI alone need no bump. (2) On the push to `main`, `version.yml` runs `release.sh tag`: a new version is tagged through the API and `release.yml` dispatched on the tag, since a tag made with `GITHUB_TOKEN` starts no workflow; a version already tagged does nothing, and fails when the app changed since it. (3) The release run checks the tag, builds the three downloads and publishes them; a version with a `-` (`0.2.0-rc.1`) is a pre-release, and the bundle's `CFBundle*Version` takes only its numeric part. A maintainer pushing a tag by hand starts it too. (4) If it fails, re-run the failed jobs when the cause has passed (a runner, Apple's service); otherwise fix it in a pull request with the next version, and delete the failed tag (and the draft release, if one exists). Dependabot's pull requests change `Cargo.lock`, so a bump must be pushed to their branch before they merge. Rejected: a maintainer tagging by hand when it is time, which left merged changes unreleased.
- **The tag is checked before anything is built** (`release.sh check`): it equals `v` plus `Cargo.toml`'s version, the tagged commit is on `origin/main`, and `CHANGELOG.md` has a `## X.Y.Z` section. A release from a side branch or without notes is refused. `release.sh version` validates the version, since a fork's pull request controls `Cargo.toml`.
- **By hand, not cargo-dist**: cornercase uses dist, but dist makes neither a `.app` nor a DMG, and a hand-written workflow keeps the bundle and the Linux build image in our hands.
- **Dry runs**: a pull request that touches what a release builds (the workflow, `.github/release/`, `tools/macos/`, the platform assets, `.cargo/`, `Cargo.toml`, `Cargo.lock`, `build.rs`, `rust-toolchain.toml`) and `workflow_dispatch` run everything except `publish`. Some failures show only in a release build: fxc on Windows (debug builds compile shaders at run time), the x86_64 macOS slice, Ubuntu 22.04's libraries. A new workflow cannot be dispatched before it is on `main`, so the pull request trigger is the only way to run it before merging. The pull request filter also lists the licence files, the icons and `tools/icon.py`, which a release reads; a change only under `src/` does not start it (CI builds that), and the tag check and the changelog section are exercised only by a release. The action majors (`upload-artifact@v7`, `download-artifact@v8`) and `cargo-about@0.9.3` through `install-action` are confirmed by the first dry run. The Linux job fails if the binary needs more than glibc 2.35, which the README promises. No `rust-cache`: a tag cannot reuse a pull request's cache, `main`'s is the debug profile, and a clean build is reproducible and safe from cache poisoning. The only secrets are macOS's signing ones, in the `release` environment, which a pull request never reaches (below); `publish` alone has `contents: write`; every checkout drops its credentials; values reach scripts through `env:`; releases are made with `gh release create` (a draft, then the upload, then published, so a failed upload leaves no half release), not a third-party action.
- **What is published**: unversioned assets named by target, as cornercase's dist names them (`cornercase-gpui-universal-apple-darwin.dmg`, `…-x86_64-pc-windows-msvc.zip`, `…-x86_64-unknown-linux-gnu.tar.gz`), each with a `.sha256`, plus `sha256.sum` of every file and `CHANGELOG.md`. Unversioned, so `releases/latest/download/<name>` links in the README never go stale, and the app's own update (#22) can pick an asset by target and show the changelog's sections. Installed windows read these names, the `.sha256` files and `CHANGELOG.md`, so renaming one breaks the update of every copy already installed (`design/self-update.md`). The three build jobs set `CORNERCASE_GPUI_RELEASE=1`, which is how a build knows it may replace itself with a release. The sums are made in the publish job, verifiable with `sha256sum -c` or `shasum -a 256 -c`. The release's notes are the changelog section plus a line pointing to the README's Install. Rejected: `gh --generate-notes`, whose text is written for developers.
- **macOS**: one `macos-15` job builds `aarch64-apple-darwin` and `x86_64-apple-darwin` and `lipo`s them into one binary (`tools/macos/bundle.sh`, which runs the same on any Mac); Apple's toolchain cross-compiles both ways. Rejected: x86_64 natively on `macos-15-intel`, the last Intel image, as a second job to join.
  - **Built for macOS 12** (`MACOSX_DEPLOYMENT_TARGET` in `.cargo/config.toml`, so every build, and `LSMinimumSystemVersion`): Zed's floor, the one gpui is exercised on; Rust's defaults (11.0 on arm64, 10.12 on x86_64) are untested with gpui. The script asserts `minos 12.0` on both slices. It was not tried on macOS 12.
  - **The bundle** is `cornercase.app`: the app calls itself "cornercase" everywhere (title, menus, the Linux desktop entry, Windows' product name), the executable stays `cornercase-gpui`, the id is `dev.usecornercase.gpui` (permanent: notification and privacy grants, notarization and a cask key on it), the category is developer tools. No `NSPrincipalClass` (gpui does not go through `NSApplicationMain`) and no `LSEnvironment` (it cannot name the home folder, and finding `cornercase` is #21's job).
  - **The icon** (`assets/macos/cornercase-gpui.icns`, from `tools/icon.py`) uses Apple's grid: on a 1024 canvas the tile is 824 px at a 100 px margin, with the Windows icon's corners, mark and colours and no baked shadow. A full-bleed tile looks about a quarter too big in the Dock, and macOS 26 puts an icon that does not fill the rounded square on a grey plate. The `.icns` holds PNG entries from 16 to 1024 px, written directly, with no `iconutil`. At 16 px the 12-px tile is filled by the mark.
  - **A release is signed with Developer ID and notarized** (#23): `bundle.sh` signs the app with the hardened runtime, a secure timestamp and `assets/macos/cornercase-gpui.entitlements`, then signs the DMG; `notarize.sh` sends the DMG to Apple's notary service (`notarytool submit --wait`), prints Apple's log (which can hold warnings even when accepted) and fails unless it is Accepted, staples the ticket to the DMG, and fails unless `spctl` says `source=Notarized Developer ID` for the DMG and for the app inside it. Gatekeeper then asks only whether to open an app downloaded from the internet. Only the DMG is stapled, as Zed does: its ticket lists the app inside, so one submission covers both, and stapling the app too would need a second one before the DMG is made.
  - **The identity** is team `P7C3YXZT2N`, an individual account, so macOS names its holder as the developer; an organization account would show Cornercase, but moving to one changes the team, and with it the identity installed copies and privacy grants recognise. The certificate expires on 2027-12-05: a new one must be in the secrets before then, and releases signed with the old one keep opening, since their signatures carry Apple's timestamp.
  - **Secrets** live in the `release` environment, which only `main` and `v*` tags can use: `MACOS_CERTIFICATE` (a base64 `.p12` with the key, the certificate and Apple's Developer ID G2 intermediate), `MACOS_CERTIFICATE_PASSWORD`, and an App Store Connect team key with the Developer role (`APPLE_API_KEY`, the `.p8`'s text, `APPLE_API_KEY_ID`, `APPLE_API_ISSUER`). A pull request's job has no environment, so it signs ad hoc, as before, and its dry run still checks the bundle, the entitlements and the DMG; `workflow_dispatch` on `main` signs and notarizes without publishing, which is how to try the real thing; a run on `main` or a tag without the certificate fails (`keychain.sh`), so a release is never unsigned and a dry run never passes unsigned by mistake. Rejected: notarizing with an Apple ID and an app-specific password, which belong to a person and break with their password.
  - **Two jobs**: `macos-build` compiles both slices with no secrets and uploads them; `macos`, the one job in the environment, runs no `cargo`, only `lipo`, `codesign`, `hdiutil` and `notarytool`. Every build script and proc macro of a dependency runs during the build, so none ever runs on the machine that holds the key. The key goes in a keychain made for the job, with a random password and on the search list (without that, `find-identity` does not count the identity as valid and `codesign` does not find it), and deleted at the end; the `.p8` goes in a temporary file `notarize.sh` removes.
  - **Entitlements**: none of the code-execution exceptions (JIT, unsigned memory, library validation): gpui compiles its Metal shaders through the system and loads only system frameworks. The seven resource entitlements (Apple Events, microphone, camera, contacts, calendars, location, photos), with their usage strings in `Info.plist`, are for the programs in the panes, as Ghostty and iTerm2 declare them: a server the window starts counts the window as its responsible process for privacy prompts (cornercase's `setsid` does not change that), so a shell or an agent asks in the window's name, and under the hardened runtime a missing entitlement is a refusal without a prompt.
  - **Without an identity** (`MACOS_SIGNING_IDENTITY` unset: pull requests, a local run) the bundle is signed ad hoc, with the same runtime and entitlements. Not leaving it unsigned matters: the linker signs only the arm64 binary and seals no resources, and a quarantined bundle without a valid seal is reported as "damaged", with no way to open it but `xattr`. With the seal, Gatekeeper says "Apple could not verify "cornercase" is free of malware", which System Settings › Privacy & Security › Open Anyway gets past.
  - **On a Mac** with the identity in the login keychain: `MACOS_SIGNING_IDENTITY="Developer ID Application: … (P7C3YXZT2N)" tools/macos/bundle.sh …`, then `NOTARY_PROFILE=<name> tools/macos/notarize.sh <dmg>`, the profile saved once with `xcrun notarytool store-credentials`.
  - **The DMG** is HFS+ with `cornercase.app` and an `Applications` link, volume `cornercase`; `hdiutil create` is retried three times, since runners fail it intermittently with "Resource busy". The licences sit inside the app's `Resources`, so they stay with it once installed. No background picture, no `create-dmg`.
  - **Privacy grants**: the app is the process macOS asks for folder access (Files panel), and a grant is tied to the signature's team and bundle id, so a release keeps it across updates; an ad-hoc identity changes with every build, so a local build's grants may not survive the next one.
- **Windows**: a `windows-2025` job and a flat zip (as dist's) of `cornercase-gpui.exe` and the licences.
  - **The C runtime is linked statically** (`-C target-feature=+crt-static`, `.cargo/config.toml`, `cfg(target_os = "windows")` rather than the triple so a `CARGO_TARGET_*_RUSTFLAGS` set by a tool cannot replace it): a zip is copied and run anywhere, and without `vcruntime140.dll` (the Visual C++ redistributable, which a fresh Windows may lack) the exe dies before `main`, so not even our message box shows. It costs a few hundred KB; Zed does the same. Set for every build, so CI, `cargo install` and the release link alike. **Never set `RUSTFLAGS`**, which replaces config `rustflags`. The job fails if the exe imports `VCRUNTIME*` or `api-ms-win-crt-*`. Rejected: shipping the DLL beside the exe, and requiring the redistributable (an installer's job, #24).
  - **fxc**: gpui's `build.rs` compiles HLSL with `fxc.exe`, found through `GPUI_FXC_PATH`, `where.exe`, then one hardcoded SDK version that breaks when the runner image moves; the job exports the newest one it finds.
  - **Limits until #24**: SmartScreen shows "unknown publisher" (More info › Run anyway), and Smart App Control on Windows 11 blocks unsigned programs outright, with no per-app override.
- **Linux**: `container: ubuntu:22.04` on an `ubuntu-24.04` runner, rustup installing the pinned toolchain, so the glibc it needs is 2.35's at most and the build does not depend on GitHub's runner-image lifecycle (`ubuntu-22.04` runners will be retired). The job prints the highest `GLIBC_x.y` the binary needs and its `NEEDED` libraries. It links `freetype`, `xcb`, `xkbcommon` and `xkbcommon-x11`; gpui opens Wayland's client library, Fontconfig and the Vulkan loader at run time (`design/linux.md`). The `.tar.gz` has a top folder with the binary, the desktop file, the icon and the licences. Packages wait on #25.
- **Licences and notices**: every archive carries `LICENSE-MIT`, `LICENSE-APACHE`, `LICENSE-GPUI`, the Lucide and file-icon licences (the icons are compiled into the binary) and `THIRD-PARTY-NOTICES.txt` from cargo-about 0.9.3, with our own text template (cargo-about's example is code from another project). It takes the four targets, ignores build and dev dependencies, and accepts Apache-2.0, MIT, BSD-2-Clause, BSD-3-Clause, ISC, Zlib, Unicode-3.0, MPL-2.0 and CC0-1.0 in that order, so `X OR Y` picks Apache or MIT. The list was computed from `cargo metadata` for those targets (638 crates, no GPL-only crate). The MPL-2.0 crates (`nucleo-matcher`, `dwrote`, `option-ext`) show their repository, where their source is. cargo-about needed no workaround for `ring`. **CI's guardrails run it too**, so a dependency bump that brings an unaccepted licence fails its pull request, not the release; `release.sh notices` is the one place the command lives, and `release.sh licences` the one place the file list lives.
- **Notes**: each version's section holds a line for every change users see (`AGENTS.md`), in cornercase's heading style (`## X.Y.Z`, no brackets or dates).
- **Waits on**: native notifications on macOS, which a signed bundle makes possible (a follow-up to #23, `design/notifications.md`), #24 (signing Windows, an installer), #25 (`.deb`, `.rpm`, AppImage), #26 (Homebrew, winget, Scoop, the AUR). No Linux arm64 or Windows on Arm build: not asked.
- **Checked** (2026-11-05, this Mac: macOS 26.6.2, Xcode 26.2, `cornercase` 0.12.287): both macOS targets built in release and `bundle.sh` made the DMG (`lipo -archs` x86_64 and arm64, `minos 12.0` per slice, `plutil -lint`, `codesign --verify --deep --strict`, `hdiutil verify`, mounted: the app and the `Applications` link); a quarantined copy was refused with "Apple could not verify…", not "damaged", `syspolicy_check distribution` complained only about the ad-hoc signature and the missing notarization ticket, never integrity, and `spctl -a` said "rejected"; the `.ico` regenerated by `tools/icon.py` is byte-identical, and the `.icns` round-trips through `iconutil`; `release.sh notices` produced the notices, failed when `MPL-2.0` was removed from the accepted list; `actionlint` and `shellcheck` pass; `cargo xwin clippy` for Windows passes with `+crt-static`, and the debug exe it builds imports no `vcruntime` or `api-ms-win-crt` DLL; fmt, clippy, the 1,338 tests, `cargo-machete` and `jscpd` pass. **Not checked**: the workflow itself (it runs on a pull request or a tag), the Windows and Linux jobs' output, the glibc the Linux build needs, opening the bundle (the quarantine could not be cleared here, so no run from `/Applications`), the icon on macOS 26's Dock, macOS 12 to 25, an Intel Mac, a real Windows 10 or 11, and real Linux distributions.
- **Checked for signing** (2026-11-05, this Mac: macOS 26.6.2, Xcode 26.2, `cornercase` 0.13.0): `keychain.sh` run with a runner's variables made up (`RUNNER_TEMP`, `GITHUB_ENV`, `GITHUB_EVENT_NAME`) left a pull request ad hoc, failed a tag without the certificate, and with the real `.p12` wrote the identity; `bundle.sh` with that identity signed the app (`flags=0x10000(runtime)`, Apple's timestamp, `TeamIdentifier=P7C3YXZT2N`, the resources sealed) and the DMG, both `--verify --strict`; without one it signed ad hoc with the runtime and the seven entitlements, and that bundle's window opened on a tab, drew the terminal and connected to the server; `actionlint`, `shellcheck` and `plutil -lint` pass. **Not checked**: the workflow's signing job (only `main` and tags reach the environment), a program in a pane asking for the camera or the microphone, and launching a quarantined copy from `/Applications`.
