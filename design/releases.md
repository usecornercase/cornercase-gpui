# Releases

Code: `.github/workflows/release.yml`, `.github/workflows/version.yml`, `.github/workflows/release-watch.yml`, `tools/release-watch.sh`, `tools/release-watch-test.sh`, `tools/release-test.sh`, `tests/fixtures/release-watch/`, the version step of `ci.yml`, `.github/dependabot.yml`, `.github/release/` (`release.sh`, `keychain.sh`, `about.toml`, `about.hbs`), `tools/macos/` (`bundle.sh`, `notarize.sh`), `tools/icon.py`, `assets/macos/`, `.cargo/config.toml`, `CHANGELOG.md`; the README's Install says how to use the downloads

- **Every merge that changes the app releases it**, as cornercase's do (its `design/releases.md`; asked for on 2026-11-05). (1) The pull request bumps `Cargo.toml`'s version (then `cargo check`, so `Cargo.lock` follows) and adds its `## X.Y.Z` section to `CHANGELOG.md` (`AGENTS.md`); CI's guardrails refuse it otherwise (`release.sh pull-request`: the version above the last tag, the section there); that step is the job's last and runs unless the run is cancelled, after the tools are installed and the other checks ran, so a missing bump is one red step (#122: when it came first, its failure skipped the installs, so `machete` and `licences` failed too and `fmt` never ran). "The app" is `app_changed`'s list in `release.sh`: what a release builds or packs (the root licences too), so a change to the signing ships too; its section must hold text, or the release would have no notes; docs, tests and CI alone need no bump. (2) On the push to `main`, `version.yml` runs `release.sh tag`: a new version is tagged through the API and `release.yml` dispatched on the tag, since a tag made with `GITHUB_TOKEN` starts no workflow; a version already tagged does nothing, fails when the app changed since it, and is dispatched again when it has neither a release nor a release run (the dispatch failed after the tag was made). The job runs one at a time (`concurrency`); GitHub keeps one waiting run per group, so a third push while one runs replaces the waiting one, whose version is then skipped: its changes ship in the next one, and the update dialog still shows its notes, read from `CHANGELOG.md`. The job takes seconds, so only merges landing together skip a number. Rejected: no `concurrency`, where two runs on the same version race to make its tag. Versions compare with a pre-release below its release (`0.2.0-rc.1` < `0.2.0`). (3) The release run checks the tag, builds the three downloads and publishes them; a version with a `-` (`0.2.0-rc.1`) is a pre-release, and the bundle's `CFBundle*Version` takes only its numeric part. A maintainer pushing a tag by hand starts it too. (4) A job no runner took is re-run by the release watch (below), with nobody waiting for it. Any other failure of the newest tag's run opens an issue, "Release vX failed", which says what to do: re-run the failed jobs when the cause has passed (Apple's service); otherwise fix it in a pull request with the next version, and delete the failed tag (and the draft release, if one exists). Dependabot's pull requests change `Cargo.lock`, so a bump must be pushed to their branch before they merge. Rejected: a maintainer tagging by hand when it is time, which left merged changes unreleased.
- **Release watch** (`.github/workflows/release-watch.yml`, `tools/release-watch.sh`, #229, after cornercase's own, its #818). Before it, a release that lost a job for lack of a runner stayed a tag with no release until a person or an agent re-ran it: v0.1.82 (run 43441808932, 2026-11-13) was re-run by hand 37 minutes after its merge, v0.1.64 (run 43300275797, 2026-11-12) never was and has no release. Its rules and reasons are cornercase's; no code was taken from it.
  - **What it does**: on a 5-minute schedule (The schedule) it takes the newest `v*` tag (`git ls-remote`, sorted as `release.sh` sorts) and that tag's last Release run, and does one of three things, each in one plain line of its log: re-runs the failed jobs (`gh run rerun <id> --failed`, which keeps the jobs that passed and their artifacts), opens or comments on the issue "Release vX failed", or does nothing.
  - **It re-runs only when** the run was started by the Version workflow (`workflow_dispatch`), ended in `failure`, has at least one job that did not pass (a conclusion other than success, skipped or neutral), every such job has no step (that is how a job no runner took looks: v0.1.82's signing job was `cancelled` with none, annotated "The job was not acquired by Runner of type hosted even after multiple attempts"), and the run's `run_attempt` is below 3.
  - **Three attempts in all**, counted by the run's own `run_attempt`: GitHub's counter needs no state of the watch's, and it counts a person's re-runs too, so the watch never adds two on top of a person's three. A drop costs 15 to 25 minutes in the queue, so two re-runs cover about an hour of shortage; past that it is no blip, and a person should know.
  - **It never re-runs, and tells instead** (the issue, once per attempt): a job that ran a step and failed, a run that was cancelled or ended any other way, a failure with no job listed as failed, and the attempts running out (the issue then says no runner took them on attempt 3, the last the watch re-runs: it cannot say none took them earlier, since a person's re-runs count too). **It does nothing, and says so**: a tag that is released; a run that has not ended (any Release run of the tag, so a person's re-run in progress is never doubled); any tag but the newest (Later releases, below), and, asked with `--dry-run --tag`, a tag with a later version released; a tag pushed by hand (run event `push`: its actor is the person who pushed it, whom GitHub tells of a failed run, which it does not for Version's dispatch by `github-actions[bot]`; pushing a tag is taking the release in hand, as a pull request's dry run is its author's); a pull request's run (never looked at). A pre-release is handled like a release, against the first reading: Version makes them through the same unattended flow, and GitHub never makes a pre-release Latest.
  - **A tag with no Release run is left to `release.sh tag`**, which dispatches it on the next push to `main`. The watch never dispatches: every new tag has no run for the seconds between Version's tag and its dispatch, and a second dispatch would wait in `release.yml`'s group and then fail at `gh release create`; a tag made through the API carries no date, so "old enough" would be a guess; one owner per act (Version tags and dispatches, the watch re-runs).
  - **What a person hears**: one issue per tag, "Release vX failed", with one comment per attempt, never two for the same attempt (the link `…/attempts/<n>)` in the issue or a comment, open or closed: closing it is how a person says they saw it; a new attempt after a closed issue opens a new one). The text says what ran and what to do in commands to paste, and the watch never closes it. The issues are looked up in the 100 newest, by exact title, not by search, which lags behind an issue just made. Rejected: failing the watch's run (it would notify whoever last changed the cron line, every 5 minutes, until a newer tag), and a job summary or annotation (nobody reads them). A failure of the watch itself (`gh` or `git` failing) ends the run with status 1 and an `::error::` line, never "nothing to do".
  - **Where the logic lives**: `tools/release-watch.sh`, outside `app_changed`'s list and `release.yml`'s pull request paths, so adding or changing it releases nothing, with no version and no dry run, for something no user of the window sees. CI's Linux job already runs shellcheck on `tools/*.sh` and every `tools/*-test.sh` under two shells. `tools/` already holds scripts a workflow runs (`tools/macos/`). It calls no word of `release.sh`; it takes two of its rules as copies, the version pattern (`version`) with a `v` and the tag order (`latest`: `versionsort.suffix=-`, `-v:refname`), so a change to either there changes `tools/release-watch.sh` too. Rejected: a word in `release.sh` or a file in `.github/release/` (a release for nothing users see), `.github/release-watch.sh` beside the workflows (CI's shellcheck and test loops would need its path, and the scripts would live in two places), and the logic inline in the workflow (no tests, no dry run).
  - **Why a workflow on a schedule, of its own**: a job inside `release.yml` is the app, and a run cannot re-run its own failed jobs while it is in progress. `workflow_run` on Release makes no run for a run dispatched with `GITHUB_TOKEN` (cornercase's had 124 runs, all skipped). Waiting inside Version fails its 5-minute limit and holds its group. A personal or App token is a secret to make and renew. Its concurrency group is `release-watch`, not `version`: a group keeps one pending run, so a watch run could replace a pending Version run and leave a version untagged; `cancel-in-progress` is off, so a run by hand and a scheduled one wait for each other.
  - **Permissions**: `permissions: {}` at the top; the job has `actions: write` (read runs and jobs, re-run), `contents: read` and `issues: write`. The checkout keeps no credentials; the token and `GH_REPO` reach the script through `env:`. The triggers are `schedule` and `workflow_dispatch`, which no pull request or fork reaches, and the job runs only on `refs/heads/main`: a dispatch by hand on another ref does nothing, since a branch's copy of the script is unreviewed code acting with the repository's token on the release. The script refuses to act (exit 2, no call) unless `GITHUB_ACTIONS=true`, or with `--dry-run`, so nobody re-runs a release or opens an issue from a Mac with their own credentials by mistake. The tags are read anonymously from `https://github.com/$GH_REPO.git`: no history is cloned every 5 minutes, and a private repository would make it fail loudly.
  - **The `release` environment and a re-run by the bot**: its only rule is its branch policy (`main` and `v*`, no reviewers, no wait), and GitHub says re-runs use "the privileges of the actor who initially triggered the workflow"; for a tag's run that actor is already `github-actions[bot]` (Version's dispatch), whose first attempts sign every release (v0.1.88, run 43519241123). So by the rules the watch's re-run reaches the signing secrets as v0.1.82's re-run by a person did. Not seen yet (below).
  - **The schedule**: `2-59/5 * * * *`, GitHub's shortest interval, off the start of the hour, which GitHub names its busiest. The reason is the drop rate measured on cornercase's hourly Pages cron (2026-10-16 to 2026-11-13): GitHub ran about one slot in five and none of its watch's first slots. At that rate a 15-minute cron waits about 75 minutes for a run and a 5-minute one about 25, near a release's own 15 to 45. Cost: up to 288 runs a day on the Actions page, a few seconds each on a Linux runner (free on a public repository, no macOS runner: #162 is untouched), a `git ls-remote` and one API request per hundred releases each while the newest tag is released. Seen on 2026-11-14: GitHub ran none of this watch's slots in the four hours after its merge (its one run was the dispatch by hand), cornercase's 15-minute watch one in its first eight hours, and cornercase's hourly Pages cron about one slot in six over the two days before. So the real wait is hours, not 25 minutes. Whether the watch needs another trigger is #252. Limits: GitHub delays and drops scheduled runs; they run `main`'s latest commit; a public repository's schedule is turned off after 60 days without activity and stays off until `gh workflow enable release-watch.yml`; a failed run notifies the user who last changed the cron line; artifacts are kept 7 days, so a re-run after that (by anyone) fails at the download; a person re-running at the moment the watch does makes the watch's re-run fail, shown as a failed run, and the next run sees the attempt running.
  - **Later releases** (#246): only the newest tag is ever re-run or told; an older tag whose jobs no runner took stays a tag with no release once a newer one exists. An older release gives users nothing a newer one does not: the window's update check and the README's and the site's downloads ask only `releases/latest` (Which release is Latest), and the update dialog lists every section after the running version from that release's `CHANGELOG.md`, which holds the older version's too (`design/self-update.md`); nothing reads the list of releases as a history (`latest-flag` looks only for the highest, `release.sh tag` only at the current version). At GitHub's real cadence (The schedule) a newer tag is usually there before the watch first looks at a dropped one, which is then never published, as v0.1.64: the newer release is what users get, as after a version Version skips (above) or a stapling that fails (macOS, below). The rule was first made so that a late release could not take Latest; since #239 a release published below a higher one is not Latest (Which release is Latest), which also covers cornercase's "Accepted" case, a newer version published while the watch's re-run of the newest tag waits for its runner. Rejected: re-running older tags as well, within the 7 days a run's artifacts are kept: each re-run takes a macOS runner (#162) for a release no update check or link offers, it needs a rule of its own, an age limit on the run, to keep the first days' tags (failed runs a week old or more) out, and the first run after such a change would have re-run v0.1.64's `macOS (build)` (run 43300275797) and published it with the first real `--latest=false`. Accepted: when the newest tag fails for real, an older tag that only lost a runner is never released, and its changes reach users with the fix's version; the issue names only the newest tag, so a person who wants the older one out sooner finds it (`gh release list` against the tags) and re-runs it by hand. A release's body on GitHub holds only its own section, so a version left without a release has its notes only in `CHANGELOG.md` and the update dialog (#253).
  - **`--dry-run --tag` with an older tag**: `--tag` alone looks at TAG in place of the newest tag, and the tags above it still count: once a later version is released, it says the tag is left alone and why (`later_released`), which is what the watch does with that tag. On a schedule the check decides nothing, since no version above the newest tag can be released; without it, the dry run would decide on the tag's last run and print a re-run or an issue the watch never makes (v0.1.64; v0.1.1, v0.1.19). `--attempt N` skips it on purpose: it asks what the rules decide had attempt N of TAG, taken as the newest tag, just ended, which is how the real cases are shown (v0.1.82 and v0.1.64 in Checked).
  - **Every page of releases**: the watch lists the published releases on every page (`gh api --paginate`), as `latest-flag` does, for the reason it gives (Which release is Latest). The order seen is newest commit first (a release's `created_at` is "the date of the commit used for the release", in "Get the latest release"), so one page holds every release until the 101st (77 on 2026-11-14, about ten a day) and the newest one after that; past it, `--dry-run --tag` of an old tag would call it unreleased, and nothing documented keeps the newest on the first page. It costs one request per hundred releases. A page that fails ends the run with status 1 and its `::error::` line, as any failed read, so nothing is decided on part of the list. Rejected: one page (above); `releases/tags/<tag>`, whose 404 for a tag with no release ends `gh api` as a failure does; stopping at the page that holds the tag, a loop of pages to save one request per hundred.
  - **Using it**: `GH_REPO=usecornercase/cornercase-gpui tools/release-watch.sh --dry-run` reads and prints what it would do. `--tag TAG`, alone or with `--attempt N`, looks at TAG in place of the newest tag (`--dry-run --tag` with an older tag, above), which is how it is shown the real cases. Tests (`tools/release-watch-test.sh`): `gh` and `git` are stubs, `gh api`'s `--jq` is answered by the real `jq`, the real case's jobs are a fixture (`tests/fixtures/release-watch/`), every rule above has a test that fails without it (the "Checked" line lists the rules taken out), and CI's Linux job runs them under dash and bash as `sh`. `actionlint` and the release scripts' shellcheck: `design/linux.md`.
  - **Checked** on 2026-11-14 (gh 2.97.0, shellcheck 0.11.0, actionlint 1.7.12, dash and bash 3.2 as `sh`, `jq` 1.7.1): the tests pass under both shells; with each rule taken out in turn (the cap, "every job", "at least one", failure only, the not-ended gate, the later-release gate and its reason, every page of the releases, a failed page, the newest tag only, the push rule, the event filter, the exact title, a one-step job not counting as dropped, the attempt link's closing parenthesis, the refusal outside a runner, open versus closed, the wording after a decision) the test for it failed. Dry runs against this repository decided each real case as the rules say: the newest tag, mid-release, nothing yet; v0.1.92 released; v0.1.64, v0.1.19 and v0.1.1 left alone behind a later release; attempt 1 of v0.1.82 and of v0.1.64 a re-run of the job no runner took; v0.1.19 an issue for a job that ran and failed. `gh api --paginate` read the releases 30 to a page as one page of 100 holds them (77 each). Off a runner without `--dry-run` it exited 2 and called nothing. Git's sort, on a throwaway repository, put a release above its pre-release and 0.1.10 above 0.1.9.
  - **Not checked**: a scheduled run of this watch (none by 04:53 UTC on 2026-11-14: The schedule); a re-run and an issue made with the workflow's token (that `GITHUB_TOKEN` may call `rerun-failed-jobs` at all); a re-run by the bot reaching the `release` environment's secrets; the first real `--latest=false` (Which release is Latest, Not checked); more than 100 real releases (paging was seen with pages of 30); a pre-release tag through git's sort on GitHub (none exists).
- **Dependabot's cargo updates** (`.github/dependabot.yml`, monthly, #122): the `cargo` group takes only patch updates and every other update comes alone, so one that needs code changes or a newer gpui waits without holding the safe ones back. Dependabot reads a version as major.minor.patch whatever its first number, so `0.22` to `0.23`, a break for Cargo, is a minor to it: a group of minors would take those in again; the price of patches only is that a minor of a crate at 1.0 or above, which is safe, also comes alone. `core-video` takes only patches: the Files panel's video peek hands its frames to gpui's `surface` element as core-video 0.4's `CVPixelBuffer` (`design/files-panel.md`), the type gpui 0.2.2 takes, so 0.6 does not build (`SurfaceSource: From<CVPixelBuffer>` is not satisfied) and it moves with gpui's manual bump (`AGENTS.md`). `libc`'s ignore is in `design/linux.md`. The `cargo` entry raises `open-pull-requests-limit` from its default 5 to 10: the breaking updates that wait (base64, parking_lot, sha2 and windows) plus the patch group fill five at the first run, and at the limit Dependabot opens no further pull request, so a safe update or a fix released as a 0.x minor would not come, and security updates are off here, so version updates are the only route a fix takes. Rejected: exempting Dependabot from the version check (`main`'s release would then fail, or the update would ship in nobody's notes) and turning the cargo updates off (no security updates either).
- **The tag is checked before anything is built** (`release.sh check`): it equals `v` plus `Cargo.toml`'s version, the tagged commit is on `origin/main`, and `CHANGELOG.md` has a `## X.Y.Z` section. A release from a side branch or without notes is refused. `release.sh version` validates the version, since a fork's pull request controls `Cargo.toml`.
- **By hand, not cargo-dist**: cornercase uses dist, but dist makes neither a `.app` nor a DMG, and a hand-written workflow keeps the bundle and the Linux build image in our hands.
- **Dry runs**: a pull request that touches what a release builds (the workflow, `.github/release/`, `tools/macos/`, the platform assets, `.cargo/`, `Cargo.toml`, `Cargo.lock`, `build.rs`, `rust-toolchain.toml`) and `workflow_dispatch` on `main` run everything except `publish`; a dispatch on a `v*` tag publishes that version. Some failures show only in a release build: fxc on Windows (debug builds compile shaders at run time), the x86_64 macOS slice, Ubuntu 22.04's libraries. A new workflow cannot be dispatched before it is on `main`, so the pull request trigger is the only way to run it before merging. The pull request filter also lists the licence files, the icons and `tools/icon.py`, which a release reads; a change only under `src/` does not start it (CI builds that), and the tag check and the changelog section are exercised only by a release. The action majors (`upload-artifact@v7`, `download-artifact@v8`) and `cargo-about@0.9.3` through `install-action` are confirmed by the first dry run. The Linux job fails if the binary needs more than glibc 2.35, which the README promises. No `rust-cache`: a tag cannot reuse a pull request's cache, `main`'s is the debug profile, and a clean build is reproducible and safe from cache poisoning. The only secrets are macOS's signing ones, in the `release` environment, which a pull request never reaches (below); `publish` alone has `contents: write`; every checkout drops its credentials; values reach scripts through `env:`; releases are made with `gh release create` (a draft, then the upload, then published, so a failed upload leaves no half release), not a third-party action.
- **What is published**: unversioned assets named by target, as cornercase's dist names them (`cornercase-gpui-universal-apple-darwin.dmg`, `…-x86_64-pc-windows-msvc.zip`, `…-x86_64-unknown-linux-gnu.tar.gz`), each with a `.sha256`, plus `sha256.sum` of every file and `CHANGELOG.md`. Unversioned, so `releases/latest/download/<name>` links in the README never go stale, and the app's own update (#22) can pick an asset by target and show the changelog's sections. Installed windows read these names, the `.sha256` files and `CHANGELOG.md`, so renaming one breaks the update of every copy already installed (`design/self-update.md`). The three build jobs set `CORNERCASE_GPUI_RELEASE=1`, which is how a build knows it may replace itself with a release. The sums are made in the publish job, verifiable with `sha256sum -c` or `shasum -a 256 -c`. The release's notes are the changelog section plus a line pointing to the README's Install. Rejected: `gh --generate-notes`, whose text is written for developers.
- **Which release is Latest** (`publish` in `release.yml`, `release.sh latest-flag`, `tools/release-test.sh`, #239). `releases/latest` is what the window's update check asks (`src/self_update.rs`, which offers only a newer version), what the README's and the site's download links serve, and what the site asks for the version it shows. Before #239 `publish` passed no `--latest`, so GitHub chose: its documentation says `make_latest` "defaults to true for newly published releases" without saying whether that holds for a draft published by an update, so an older version published after a newer one could have become Latest (it came close on 2026-11-13: v0.1.87 waited 23.5 minutes for a runner and was published 13 minutes before v0.1.88).
  - **What it does**: before making the draft, `publish` asks `release.sh latest-flag "$VERSION"`, which prints `--latest` or `--latest=false` and, on standard error, one line saying why; the edit that publishes the draft passes it. The highest version published stays Latest and one published below it is not, whichever default GitHub takes.
  - **The rule**: it lists the published releases (`gh api --paginate …/releases`: every page, since the documentation gives no order); drafts, pre-releases and tags that are not versions do not count. `--latest=false` when one of them is above the version (`newer`, the order `pull-request` uses), otherwise `--latest`, also with none published and when the version itself is the highest published. A pre-release (a `-`, as the step's `--prerelease`) gets `--latest=false` without listing anything: GitHub never makes one Latest.
  - **A draft does not count**: one may never be published (a release whose publish failed; a draft written by hand for a future version), and counting it would keep the highest published release from being Latest as long as it stays.
  - **A failed listing publishes nothing**: the word prints no flag and fails, before the draft is made, so a re-run of the failed jobs runs `publish` again with no draft left to clean up. A wrong Latest would reach every window's update check; a late release reaches nobody until it is re-run.
  - **On the edit, not the create**: drafts cannot be Latest, and the documentation does not say what a draft does with `make_latest`; the edit publishes the draft and sets it in one request (`draft: false` with `make_latest`), as `gh` publishes its own drafts (`publishRelease`, gh 2.103.3). Rejected: both commands; `make_latest=legacy` through `gh api` ("the release creation date and higher semantic version", without saying which wins, and it needs the release's id); no flag.
  - **The same version again**: a re-run of `publish` once its release exists makes a second draft (`gh` checks for a release only without `--draft`) and edits whichever release it finds by the tag, as before; the flag is `--latest` unless a higher version is published.
  - **Not built, not covered**: a Latest that is wrong already is put right by the next highest release's `--latest`. Two versions publishing within the same few seconds (the listing comes before the uploads, 4.7 s for v0.1.89) can leave the older one Latest until the next release.
  - **Where it lives**: a word of `release.sh`, so changing it is a release, like everything `publish` runs; its test, `tools/release-test.sh`, is outside `app_changed` and `release.yml`'s paths, and CI's Linux job shellchecks it and runs it under dash and bash as `sh` with no line of `ci.yml`: `gh` is a stub, `--jq` is answered by the real `jq`. `release.sh`'s errors go to standard error, so the error of a word whose output a step reads (`latest-flag`, `version`) reaches the log, not the variable. Rejected: lines in the step (no test can run them), a test beside the script in `.github/release/` (every change to it would be a release, and CI's loops would need its path) and a Rust test in `tests/` (none there runs a shell script).
  - **gh on the runner**: 2.103.3, inferred from the notes of the `ubuntu24` images of 2026-11-01 and 2026-11-11 (the link of the run's own image is a 404); the step prints `gh --version`, so each release's log names it. `release edit --latest` and `--latest=false` and `api --paginate --jq` are in it and in 2.97.0.
  - **Checked** on 2026-11-14 (shellcheck 0.11.0, actionlint 1.7.12, dash and bash 3.2 as `sh`, `jq` 1.7.1): the tests pass under both shells, and with each rule taken out in turn (the draft and pre-release filters, the pre-release order, `--paginate`, the failed-listing stop, the version filter on tags, the strict comparison, `fail` on standard error, the pre-release branch, the `GH_REPO` and argument checks) the test for it failed. Read-only against this repository the word answered `--latest` for 0.1.999, `--latest=false` for 0.1.5 and for `0.2.0-rc.1` without a call. The step's lines ran under `bash -e -o pipefail` with a stub `gh`: a failed listing stopped before `release create`, and `release edit … --draft=false` ended with the flag. **Not checked**: GitHub's answer to `make_latest` on the edit that publishes, until v0.1.91; a release published after a newer one; a pre-release through the step; two in the same seconds.
- **macOS**: one `macos-15` job builds `aarch64-apple-darwin` and `x86_64-apple-darwin` and `lipo`s them into one binary (`tools/macos/bundle.sh`, which runs the same on any Mac); Apple's toolchain cross-compiles both ways. Rejected: x86_64 natively on `macos-15-intel`, the last Intel image, as a second job to join.
  - **Built for macOS 12** (`MACOSX_DEPLOYMENT_TARGET` in `.cargo/config.toml`, so every build, and `LSMinimumSystemVersion`): Zed's floor, the one gpui is exercised on; Rust's defaults (11.0 on arm64, 10.12 on x86_64) are untested with gpui. The script asserts `minos 12.0` on both slices. It was not tried on macOS 12.
  - **The bundle** is `cornercase.app`: the app calls itself "cornercase" everywhere (title, menus, the Linux desktop entry, Windows' product name), the executable stays `cornercase-gpui`, the id is `dev.usecornercase.gpui` (permanent: notification and privacy grants, notarization and a cask key on it), the category is developer tools. No `NSPrincipalClass` (gpui does not go through `NSApplicationMain`) and no `LSEnvironment` (it cannot name the home folder, and finding `cornercase` is #21's job).
  - **The icon** (`assets/macos/cornercase-gpui.icns`, from `tools/icon.py`) uses Apple's grid: on a 1024 canvas the tile is 824 px at a 100 px margin, with the Windows icon's corners, mark and colours and no baked shadow. A full-bleed tile looks about a quarter too big in the Dock, and macOS 26 puts an icon that does not fill the rounded square on a grey plate. The `.icns` holds PNG entries from 16 to 1024 px, written directly, with no `iconutil`. At 16 px the 12-px tile is filled by the mark.
  - **A release is signed with Developer ID and notarized** (#23): `bundle.sh` signs the app with the hardened runtime, a secure timestamp and `assets/macos/cornercase-gpui.entitlements`, and, with `MACOS_NOTARIZE` set, notarizes it before the DMG is made; then it signs the DMG and notarizes that. `notarize.sh` sends one of them to Apple's notary service (`notarytool submit --wait`; the app as a zip), prints Apple's log (which can hold warnings even when accepted), fails unless it is Accepted, staples the ticket, and fails unless `spctl` says `source=Notarized Developer ID` (for a DMG, also of the app inside it, whose ticket it checks too). Gatekeeper then asks only whether to open an app downloaded from the internet. **Both are stapled**, so two submissions: with only the DMG's ticket, `syspolicy_check distribution` failed the app copied out of it ("Notary Ticket Missing", fatal), and its first launch would need the network to find the ticket. Rejected: stapling only the DMG, as Zed does.
  - **The identity** is team `P7C3YXZT2N`, an individual account, so macOS names its holder as the developer; an organization account would show Cornercase, but moving to one changes the team, and with it the identity installed copies and privacy grants recognise. The certificate expires on 2027-12-05: a new one must be in the secrets before then, and releases signed with the old one keep opening, since their signatures carry Apple's timestamp.
  - **Secrets** live in the `release` environment, which only `main` and `v*` tags can use: `MACOS_CERTIFICATE` (a base64 `.p12` with the key, the certificate and Apple's Developer ID G2 intermediate), `MACOS_CERTIFICATE_PASSWORD`, and an App Store Connect team key with the Developer role (`APPLE_API_KEY`, the `.p8`'s text, `APPLE_API_KEY_ID`, `APPLE_API_ISSUER`). A pull request's job has no environment, so it signs ad hoc, as before, and its dry run still checks the bundle, the entitlements and the DMG; `workflow_dispatch` on `main` signs and notarizes without publishing, which is how to try the real thing; a run on `main` or a tag without the certificate fails (`keychain.sh`), so a release is never unsigned and a dry run never passes unsigned by mistake. Rejected: notarizing with an Apple ID and an app-specific password, which belong to a person and break with their password.
  - **Stapling asks again** (`stapler` in `notarize.sh`, since 2026-11-06): `stapler staple` and `validate` read the ticket from Apple's CloudKit, and on 2026-11-06 three releases in a row failed there with `NSURLErrorDomain -1005`, after notarization itself had been accepted. Up to five tries, 20 s more apart each time; a ticket that truly isn't there still fails, a few minutes later. The tag then has no release, and the next one's notes in the update dialog cover it.
  - **Two jobs**: `macos-build` compiles both slices with no secrets and uploads them; `macos`, the one job in the environment, runs no `cargo`, only `lipo`, `codesign`, `hdiutil`, `notarytool` and `stapler`; `keychain.sh` sets `MACOS_NOTARIZE` whenever it finds the identity, so a signed build is always notarized there. Every build script and proc macro of a dependency runs during the build, so none ever runs on the machine that holds the key. The key goes in a keychain made for the job, with a random password and on the search list (without that, `find-identity` does not count the identity as valid and `codesign` does not find it), and deleted at the end; the `.p8` goes in a temporary file `notarize.sh` removes.
  - **Entitlements**: none of the code-execution exceptions (JIT, unsigned memory, library validation): gpui compiles its Metal shaders through the system and loads only system frameworks. The seven resource entitlements (Apple Events, microphone, camera, contacts, calendars, location, photos), with their usage strings in `Info.plist`, are for the programs in the panes, as Ghostty and iTerm2 declare them: a server the window starts counts the window as its responsible process for privacy prompts (cornercase's `setsid` does not change that), so a shell or an agent asks in the window's name, and under the hardened runtime a missing entitlement is a refusal without a prompt.
  - **Without an identity** (`MACOS_SIGNING_IDENTITY` unset: pull requests, a local run) the bundle is signed ad hoc, with the same runtime and entitlements. Not leaving it unsigned matters: the linker signs only the arm64 binary and seals no resources, and a quarantined bundle without a valid seal is reported as "damaged", with no way to open it but `xattr`. With the seal, Gatekeeper says "Apple could not verify "cornercase" is free of malware", which System Settings › Privacy & Security › Open Anyway gets past.
  - **On a Mac** with the identity in the login keychain: `MACOS_SIGNING_IDENTITY="Developer ID Application: … (P7C3YXZT2N)" tools/macos/bundle.sh …`, with `MACOS_NOTARIZE=1 NOTARY_PROFILE=<name>` to notarize both, the profile saved once with `xcrun notarytool store-credentials`.
  - **The DMG** is HFS+ with `cornercase.app` and an `Applications` link, volume `cornercase`; `hdiutil create` is retried three times, since runners fail it intermittently with "Resource busy". The licences sit inside the app's `Resources`, so they stay with it once installed. No background picture, no `create-dmg`.
  - **Privacy grants**: the app is the process macOS asks for folder access (Files panel), and a grant is tied to the signature's team and bundle id, so a release keeps it across updates; an ad-hoc identity changes with every build, so a local build's grants may not survive the next one.
- **Windows**: a `windows-2025` job and a flat zip (as dist's) of `cornercase-gpui.exe` and the licences.
  - **The C runtime is linked statically** (`-C target-feature=+crt-static`, `.cargo/config.toml`, `cfg(target_os = "windows")` rather than the triple so a `CARGO_TARGET_*_RUSTFLAGS` set by a tool cannot replace it): a zip is copied and run anywhere, and without `vcruntime140.dll` (the Visual C++ redistributable, which a fresh Windows may lack) the exe dies before `main`, so not even our message box shows. It costs a few hundred KB; Zed does the same. Set for every build, so CI, `cargo install` and the release link alike. **Never set `RUSTFLAGS`**, which replaces config `rustflags`. The job fails if the exe imports `VCRUNTIME*` or `api-ms-win-crt-*`. Rejected: shipping the DLL beside the exe, and requiring the redistributable (an installer's job, #24).
  - **fxc**: gpui's `build.rs` compiles HLSL with `fxc.exe`, found through `GPUI_FXC_PATH`, `where.exe`, then one hardcoded SDK version that breaks when the runner image moves; the job exports the newest one it finds.
  - **Limits until #24**: SmartScreen shows "unknown publisher" (More info › Run anyway), and Smart App Control on Windows 11 blocks unsigned programs outright, with no per-app override.
- **Linux**: `container: ubuntu:22.04` on an `ubuntu-24.04` runner, rustup installing the pinned toolchain, so the glibc it needs is 2.35's at most and the build does not depend on GitHub's runner-image lifecycle (`ubuntu-22.04` runners will be retired). The job prints the highest `GLIBC_x.y` the binary needs and its `NEEDED` libraries. It links `freetype`, `xcb`, `xkbcommon` and `xkbcommon-x11`; gpui opens Wayland's client library, Fontconfig and the Vulkan loader at run time (`design/linux.md`). The `.tar.gz` has a top folder with the binary, the desktop file, the icon and the licences. Packages wait on #25.
- **Licences and notices**: every archive carries `LICENSE-MIT`, `LICENSE-APACHE`, `LICENSE-GPUI`, the Lucide and file-icon licences (the icons are compiled into the binary) and `THIRD-PARTY-NOTICES.txt` from cargo-about 0.9.3, with our own text template (cargo-about's example is code from another project). It takes the four targets, ignores build and dev dependencies, and accepts Apache-2.0, MIT, BSD-2-Clause, BSD-3-Clause, ISC, Zlib, Unicode-3.0, MPL-2.0 and CC0-1.0 in that order, so `X OR Y` picks Apache or MIT. The list was computed from `cargo metadata` for those targets (638 crates, no GPL-only crate). The MPL-2.0 crates (`nucleo-matcher`, `dwrote`, `option-ext`) show their repository, where their source is. cargo-about needed no workaround for `ring`. **CI's guardrails run it too**, so a dependency bump that brings an unaccepted licence fails its pull request, not the release; `release.sh notices` is the one place the command lives, and `release.sh licences` the one place the file list lives.
- **Notes**: each version's section holds a line for every change users see (`AGENTS.md`), in cornercase's heading style (`## X.Y.Z`, no brackets or dates).
