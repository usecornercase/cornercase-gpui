# Plugins

Code: `src/panels/plugins.rs`, `src/panels/plugins/`, `src/cli/window_processes.rs`, `src/cli/kept/`; in the window, `src/sidebar/menus.rs`, `src/sidebar/rail.rs`

- **Like the TUI's Settings › Plugins, with no catalogue**: what is installed or linked, whether it is on, what it asks for and runs, its actions and its log; turning each on and off, linking a folder, installing, updating and removing. Finding plugins is the website's job.
- **The list is read again each time the sheet opens**: `plugin list --json` reads the plugins from the files, `plugin actions --json` asks the server for their actions and `plugin status --json` (#469 upstream) for what each service is doing. Without a server, or with an older one, there are no actions and no service states, a toast says why, and the list stays. `list` stays the source of the cards rather than `status`, which carries the same plugins, because it works with no server. The last two are the store's (`Store::plugins`, `plugins/offers.rs`), since the menus and the rail draw from them too.
- **A plugin's source is kept as JSON** (`{"kind":"link","path"}` or `{"kind":"git","repo","url","ref","subdir","commit","path"}`), so a kind added later still reads; an unknown kind is shown by name.
- **Turning one on is the explicit step**, so it asks first and says plainly what that means: it runs as you, what it asks for is shown, not enforced, and what it runs. Turning off asks nothing. Plugins start off.
- **Removing an installed plugin deletes its copy; unlinking a linked one only forgets it**: both ask, with the difference spelled out, and settings and data stay.
- **The confirmation is this sheet's own small dialog** (`plugins/ask.rs`), since `dialogs::confirm` runs a command and these steps run a closure that marks the plugin busy and reloads. It can carry a scrolled block of monospaced lines, for a preview, drawn as the log is.
- **Linking on another machine asks for the folder's path** (`dialogs::ask_path`): the folder picker shows this Mac's disk (`design/remote.md`).
- **Install and update are previewed and confirmed in the window** (#468 upstream; `plugins/fetch.rs`, `plugins/install.rs`): `plugin install SOURCE --preview --json` fetches and prints what installing runs, installing nothing; the dialog shows its `lines` as cornercase writes them (the same preview the terminal prints, with hidden characters already escaped), so the app never words its own version of what a plugin runs. Yes runs `plugin install SOURCE --commit SHA --yes` with the commit the preview printed: cornercase refuses when the source gives another commit by then, so what installs is what was read. `--yes` is still needed beside `--commit`, since there is no terminal to ask in (cornercase 0.12.225). Nothing needs a terminal tab any more, so the old tab and its shell quoting are gone.
- **The toast after installing or updating is the app's own** (`installed Notch 0.1.1, turned off`), from the preview: without `--preview` the command prints `fetching…`, the whole preview and then the outcome on stdout, with no `--json`, and its first line is the fetch.
- **Updating previews every plugin first**: `plugin update ID --preview --json` takes one ID (`--json` and `--commit` require it), so Update all previews each installed plugin, all at once, and asks once with every changed plugin's preview under a `name: old → new` line; one up to date prints only `id`, `commit` and `up_to_date`, and is told in a toast. A failed preview (a linked plugin, no network) is its own toast and does not hold the others. On yes the updates run one after another, each `plugin update ID --commit SHA --yes`, since each rewrites `plugins.json`. The single Update… takes the same path with one ID.
- **The preview's shape** was read on cornercase 0.12.225 with `plugin install jacogaz/cornercase-notch --preview --json` (October 2026; `tests/fixtures/plugins/install-preview.json`). The update and status fixtures follow `Details`, `UpdatePreview` and `PluginsInfo` in cornercase's sources, since getting real ones means installing or turning on a plugin on this machine.
- **Service states come from `plugin status --json`**: a card of a plugin that is on and has services shows a chip per service, `running, pid N` in green, `stopped, restarting in N s` in red, `starting` (or a state added later, by name) in amber. Without a server the card says that the state needs it. `problem` (`plugins.json` cannot be read) is shown above the list.
- **The sheet's actions run on what the window shows**: a `button` action takes no target; otherwise the most precise of its contexts the window shows (pane, tab, workspace, project), and none when it shows none. `plugin run` gets the revision the actions were listed at and refuses a stale one.
- **A failed action exits with 1 but still prints its outcome**, which the toast reads (`cli::run_printed`: `cli::run` drops standard output on a failure, so until 2026-11-06 the toast said only `cornercase plugin: failed`); an error before it ran (a stale revision, no server) prints nothing, and the error is shown instead.
- **Popup actions run from the sheet too** (#456 upstream): running one closes the sheet so the popup shows over the terminal (`design/terminal.md`), and the button stays busy until it closes, since `plugin run` answers only then. Its end is toasted as any action's, except a popup closed by its `✕` or `popup-close`, which says nothing, as the TUI's: `ended: closed` comes with an `error` and exit 1, but the person did it. It opens for this window's view (`--view`, below), with or without cornercase's own window.

- **What runs is a job in the store** (`plugin:` keys, `design/connection.md`): the card's on/off chip turns into a spinner, and an action, Update, Install, Link folder and Update all become busy buttons that say what they do (`Fetching…`, `Installing…`, `Checking…`, `Linking…`); the status bar names it, so a popup action that closed the sheet still shows. Checking for updates has its own key: it shared the plugin's, so Update read `Checking…` while the plugin turned on or off.
- **The log shows the last 60 lines** (`plugin logs ID -n 60`) and is read again with the list.
- **On another machine the sheet only reads and runs**: cornercase's `plugin` commands that install, update, remove, link, turn on or off, list or show logs act on the files of the machine they run on and refuse `--remote`; only `plugin status`, `actions` and `run` ask the server. So there the list comes from `plugin status --json` (it carries every plugin's fields), the switches and the install, update, remove and log buttons are gone, and a note says to run `cornercase plugin …` on that machine and that doing it from here needs #703 upstream.

## Window processes

`plugin windows` (#674 upstream, cornercase 0.13.15; its `design/plugins/running.md`), `cli/window_processes.rs` the process, `cli/kept.rs` the keeper of children that must end gracefully (shared with the tunnel holds, `design/browser.md`) and `cli/kept/win32.rs` its Job object on Windows, `plugins/window_processes.rs` what its lines say.

- **The window keeps one `cornercase plugin windows --json` for as long as it is open**, so what plugins declare as `[[window]]` runs beside it, with cornercase's own environment, restarts, `running/` files and lock. It starts when the window has found cornercase (`Msg::Started`, whether the server started or not, since the command needs none) and has no version gate, as the minimum has it.
- **It runs only while the window's own connection is on this computer** (`cli::host()` is none, `WindowProcesses::step`), as upstream's window does (its `design/remote-windows/switching-machines.md`): started when the window comes to this machine and stopped when it leaves, since those processes talk to this machine's socket. A window on another server must not run this computer's plugins out of sight, whose card it does not show, and a plugin calling `$CORNERCASE_BIN` would reach or start a server here that the person is not using. So a start with `--remote` runs none, and `Root::switch` stops it as the quit path does, with nothing said, since that end is expected: a stopped run's lines and end are dropped by its number, so it neither toasts nor retries, and a retry due meanwhile asks the same decision and starts nothing. Coming back starts a new one. A machine's tab or place is a second connection and leaves `cli::host()` alone, so it is not leaving and they keep running. `CORNERCASE_REMOTE` in the window's own environment names nothing here: the window ignores it and takes it from every child (`cli::CALLER`), so its connection is on this computer and they run. The command itself always goes through `Target::Local`, since cornercase refuses `--remote` on it. Its state is a global entity of its own (`WindowProcesses`) rather than in `Store`, which a switch replaces, and it is not among the streams `kill_all` kills.
- **Stopping it** is the part that can go wrong, since a plugin's processes must not outlive the window. The command stops what it runs on a signal it can catch or when the reader of its output goes.
  - `Child::kill` is `SIGKILL`, which it cannot catch, and what it runs would be orphaned: so it is not in `cli`'s list of children, it has no `Stream`, and `main.rs`'s `leave`, on both ways out (quit and the relaunch after an update), and a switch to another server, send `SIGTERM` (`stop_window_processes`). The window does not wait for it: the command stops them by itself within its 2 s, and nothing here needs it gone. Its reader thread reaps it at the end of its output, by its own id, since a switch back within those 2 s starts a new one beside it, and two for a moment are what two windows are. Rejected: closing the pipe from the app, since the read end is held by a thread blocked in `read`, and closing a file another thread is reading neither wakes it nor closes the pipe.
  - On Linux and macOS a window that dies, by a plain `kill` or a crash, runs no quit path: its end of the pipe closes with it, which the command sees within 200 ms. So the pipe is what covers those, and it needs nothing here. The read end must stay ours alone, which Rust's close-on-exec gives.
  - **On Windows** a reader that left is seen only at the next line it cannot write, and `SIGTERM` does not exist: `leave` uses `Child::kill`, which there takes them along, through the `KILL_ON_JOB_CLOSE` of cornercase's job objects. Rejected: `taskkill` without `/f`, which would give their windows a `WM_CLOSE` but which cornercase's own notes list as not checked with this command, for a failure that would leave them running. The rest of the stopping path (`Child::kill` taking the window processes along through cornercase's own jobs) is still compiled by CI only; what was checked on Windows is in `design/windows.md`.
  - **A window that dies on Windows** would leave the command and its processes running until a line fails, as upstream says of any client, so the command is held by a Job object, the way out upstream names.
    - **The job** has `KILL_ON_JOB_CLOSE | BREAKAWAY_OK`, the flags upstream gives its own jobs. The window keeps its only handle (made with no security attributes, so no child inherits it) in `Kept` beside the `Child`, until the reader reaps the command. When the window dies Windows closes the handle, which ends the command, every process in the job and every job nested in it; cornercase's own jobs end their trees too when the command goes, two independent paths.
    - **Only `plugin windows` and the tunnel holds are in a job** (the holds: `design/browser.md`, which says why theirs is dropped without letting go). `plugin windows` is the child that runs programs of its own, which a person sees and which `plugin remove` waits for, and it may never write again. The streams run nothing and end at their next write; the typist and `requests` end at the end of their input, which a crash closes. Rejected: a job for every child, which would reach every way one ends (`Stream`'s drop, `kill_all`, one-shots such as `theme --clear`) for a limit nobody reported. Rejected: the window putting itself in a kill-on-close job, which would end files opened in their apps and Chrome, which the next window adopts (`design/browser.md`).
    - **What the children inherit**: Windows puts each child in its parent's jobs, so the window processes and what they start are in ours, and each window process's own job nests in it. `BREAKAWAY_OK` lets out only a process created with `CREATE_BREAKAWAY_FROM_JOB`, which upstream uses only for its server, so a server a plugin's process starts outlives the window; without it that server would leave the plugin's job but stay in ours, and a crash would end every shell and agent. Rejected: `SILENT_BREAKAWAY_OK`, which would leave everything the command starts outside our job, so a grandchild started before its own job is assigned would escape.
    - **A window already in a job** (a terminal's, an IDE's, a CI runner's) gets its own job nested under it, which Windows allows since 8 for a new, empty job with no UI limits; the launcher keeps its say. Rejected: `CREATE_BREAKAWAY_FROM_JOB` for the command, which takes it out of the launcher's job against what the launcher asked and is refused where that job does not allow breakaway.
    - **A normal end lets go**: `stop` (quit, the relaunch, a switch) and the reap set the limits back to `BREAKAWAY_OK` alone, as upstream's `Grouped` does when dropped, so a quit is exactly as before. A `Job` dropped without letting go behaves as a crash, which the tests use. Rejected: a job that always kills on close, which at every quit would end what a plugin's earlier process left running on purpose.
    - **The moment before the command joins**: it runs for microseconds before `AssignProcessToJobObject`, as upstream's children do, since std's `Child` gives no main thread to start it suspended and `PROC_THREAD_ATTRIBUTE_JOB_LIST` needs the nightly `spawn_with_attributes`. It is harmless: the command starts nothing before reading the plugin files. A tunnel hold shares the gap (`design/browser.md`).
    - **A job Windows refuses** (making it, setting its limits, putting the command in it): the command still runs as before, and one toast says so once per window run (`told_untied`, which `stopped()` does not clear), never at the backoff's restarts. Rejected: silence, since a person would believe a crash is covered.
- **What it prints goes on the plugin's card**, this computer's only (on another server the cards are that server's plugins, which this command does not run): one chip per process, `panel running, pid 4242` and `panel stopped, restarting in 2 s`, with `Service`'s words and colours, since a line carries what `plugin status` gives of a service. The line's seconds count down from when it came, or they would stand for up to a minute, with the sheet redrawn each second while something counts. `stopped` with no `restart_in` (the plugin turned off, its entry gone) leaves the card, as upstream asks, or it would show a process that is gone. A plugin that is on with no line yet reads `starting`, which lasts under half a second.
- **If the command ends by itself** the card says `not running, trying again` with the last line of its error output, every process is taken as gone (its output ends once everything has stopped), a toast says so once, and it starts again after `cli::backoff`, without a toast until a line has come in between. A line that cannot be read is a toast.
- **An update says nothing new**: the command stays the version it started as until the window restarts, and what it starts meanwhile gets the new binary as `CORNERCASE_BIN` from cornercase. Restarting it would stop and start every plugin's processes for no reason.

## Menu entries and buttons

The TUI's 0.12.115 (entries) and 0.12.187 (buttons), `plugins/offers.rs` the model and the run, `sidebar/menus.rs` the entries, `sidebar/rail.rs` the slots.

- **Read when it can change, never on a draw**: `plugin actions --json` (all of them, once, rather than one call per kind of row) and `plugin status --json` (the buttons' titles and icons) when the window connects (`Root::open_view`, so also after a reconnect or on another server), whenever the sheet reloads (it opened, or anything in it changed) and after a refused run. Drawing and opening a menu only filter what the store holds. A failed read offers nothing and toasts why, as the accounts' list does; a newer read drops the answers of an older one (`Offers::ask`), so a read that lost the race over ssh cannot bring back a plugin just turned off. The sheet opened before the server answers, which only `CORNERCASE_GPUI_OPEN` does in practice, toasts once and is right when the window connects.
- **A plugin changed outside the window shows late**: one turned on from a shell appears once the sheet opens or the window reconnects, and an entry or button listed before a change is refused by its revision, whose error is the toast, and the list is read again, so the next try is right. The TUI notices within a second because it reads the files itself; there is no stream of this. Rejected: reading on every menu (upstream's design says a client lists when it opens a menu, but that is one process per right click, a round trip over ssh, and a button has no such moment) and polling, for a change that happens while someone writes a plugin.
- **Entries come below the built-in ones, under a line and the plugin's name** (`Entry::Heading`, which the keys skip): the TUI puts them at the bottom of those menus too, with the title alone. They stay in the menu rather than in a submenu per plugin, as upstream rejected for its `⋯`: a plugin's entries would hide one click deeper for no reason. With no plugin nothing is added, not even the line.
- **Which menus**: a project's, a workspace's and a tab's (their rows' right click and `⋯`, and the tab bar's), and a pane's right click, each with its `--project`, `--workspace`, `--tab` or `--pane`. A group has none, as cornercase refuses one. An agent row's menu has none either, as the TUI's: its pane's menu has them.
- **Buttons are slots of the rail**, after the docked panels and above its line, where the TUI's icon bar puts them, after Flow. The TUI's other place, a row at the foot of the projects column, belongs to a TUI whose tools sit in a footer; here the rail is that footer (`design/sidebar.md`). One slot per plugin with a `button` action, in the list's order; a plugin off has no action listed, so no slot, though `status` still gives it a `button`.
- **A short rail scrolls** (`design/sidebar.md`), so no slot is ever out of reach and the TUI's `⋯` for what does not fit has nothing to do; the rail's own icons just fit the window's opening size, so a plugin's slot pushes the last sheets into the scroll. The sheets have their keys and a button has none, so they give way, the opposite of the TUI's short bar, which leaves the buttons out first. Rejected: the slots after the sheets, the end of the top group as in the TUI's bar, which would start out of view at the opening size with nothing to say so; and pinned above Help, which keeps every icon in place but needs its own limit and scroll once a few plugins have buttons.
- **A slot draws the manifest's `icon`, the title as its tooltip** (`status`'s `button`, which fills both in; the plugin's name and its initial without an answer). An icon from a private use area gives way to the title's initial: plugins for the TUI may use a Nerd Font's glyph, and the window ships no such font, so it would draw a box.
- **One action runs on the click, several open a menu on the press** in the manifest's order, as `+` does. While an action of the plugin runs the slot spins; a slot with one action takes no click meanwhile, and one with several keeps its menu, as nothing limits how many run at once. So a popup action's slot spins until it closes. While a menu is open the slots have no tooltip: gpui would otherwise show one that was waiting, from a press within its half a second, over the menu it just opened at the pointer (occluding the slot does not stop it, as gpui's own comment says).
- **A run is the sheet's**: `offers::run_action`, with the revision the entry was listed at, the same job key (so the sheet's button spins for a run started from a menu, and the status bar names it), a popup closing any sheet, and the same toast.
- **A run acts for this window's view**: every run the sheet, the menus and the slots make passes `--view` (#666 upstream, cornercase 0.13.11), so a `button` action gets the ids and folder of what this window shows, and a popup opens with no cornercase window attached, sized from the view (`width`×`height` when they fit, else 80 % of it). An item named next to it keeps its target, and the view only answers for the popup. With no view (the connection fell) a run is refused with a toast rather than sent without one, which would act on what cornercase's own window shows.
- **Over a machine's tab the view is still this window's own** (`Store::view_id`, never `MachineTab`'s): the list and the run go to this window's server, and a machine's view id means nothing there, or another view of the same number. So a button acts on the local tab resting behind, and its tooltip says so (`Notes board: acts on the tab behind vps's`), since it is not what the person is looking at; a popup, which draws only over a local tab (`design/machines.md`), goes back to it first, as a sheet closes for it. Rejected: running the machine's plugin of the same id through its connection, since these slots list this server's plugins.
- **Checked live on 2026-11-06** (cornercase 0.13.1, Linux x86_64 under Xvfb with lavapipe, a debug build, on a private server with three linked plugins: one with four actions and a `[button]`, one with one action and none, one with neither; no macOS, no Windows, no real sshd): the entries under each plugin's name in a project's and a workspace's row, a tab's sidebar row and a pane's right click, each run reaching the plugin with its own `CORNERCASE_CONTEXT`, ids and folder (the tab bar's menu is the same `open_target_menu`, not tried, as this bench lists tabs in the sidebar); a failed action's toast with its exit status; ↑ ↓ skipping the name; a slot with the manifest's icon and one with the initial; one action on the click, its slot spinning and the status bar naming it; several in a menu on the press; a popup from the rail and from a tab's menu, toasted when its program ended and silent after its `✕` or `plugin popup-close`; turning a plugin off and on in the sheet moving the rail at once; a plugin turned on from a shell showing once the sheet opened, and another after `kill-server` and the reconnect; a press from before a change refused, with the slot gone after it; with no plugin the rail, the menus and the sheet as before; a window on `--remote` through the bench's fake ssh showing the other server's plugin, its run in that server's plugin log. Not tried: a real ssh, a popup on another machine, and an icon from a private use area (only its test).

Not tried: the relaunch after an update, a real ssh, and the command failing at start.
