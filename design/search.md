# Search

Code: `src/panels/search.rs`, `src/panels/search/` (`candidates.rs` what Names lists, `names.rs` ranking it, `found.rs` the In sessions answer, `settings.rs` the settings Names lists after them)

- **Two modes, as the TUI's search**: "Names" finds anything open by name as you type, from the session already in memory; "In sessions" finds where some text was said (`cornercase search --json`): agents' transcripts and every pane's history, grouped by pane. `Tab` switches, the arrows move, `Enter` or a click goes there.
- **Names covers everything the sidebar lists** (asked for on 2026-10-31: "⌘F should search among projects, agents, workspaces, tabs, etc."): groups, projects, workspaces (worktrees included), tabs and agents. "Etc." was read as what the sidebar shows of them, so each is also found by those details: a project by its folder's name, a workspace by its branch and by its pull request's number and title, a shell tab by the programs it runs, an agent by its kind, flow role and model. Tabs and agents are also found by their workspace's name and branch, as the TUI finds tabs. Rejected: panels and commands, which the rail, the ⌘ shortcuts and ⌘/ already reach (a command palette would be a feature of its own); files, which the Files panel searches; and the lists of other sheets (TODO, queue, issues, flows), which have their own filters. The TUI's search finds groups, projects, workspaces and tabs (cornercase's `design/search.md`); agents are new here.
- **An agent is named as the sidebar names it**: by its conversation's title without the mark its program puts in front (`PaneInfo::agent_title`, shared with the sidebar), else by its tab's name. Its kind, role and model follow the name.
- **A tab that holds agents is listed as its agents**, one row per agent pane, and gets no row of its own, so a shell split beside an agent is reached through the agent's row. The tab's sidebar row already reads as its agent, under both `tabs` settings, and a tab row and an agent row would go to the same place. Choosing an agent focuses its pane (`focus --pane`), which also shows its tab. An agent's place names its tab only when the tab's name adds something to the agent's name and kind (a renamed tab), so a match on the tab's name still shows where it is. Shell tabs keep their own row.
- **Each row says what it is, which one, and where**: a chip with the kind's icon and name (group, project, workspace, agent, tab); then the name; then a detail (an agent's kind, role and model, a workspace's branch and pull request, a project's folder shortened with `~` against the session's `home`, a tab's other programs and its pane count, a group's project count); the place at the right (`project › workspace`, a project's group); and the status badge. Agents' chips take the terminal palette's magenta, a colour no status uses. Statuses are the sidebar rows': a project shows a status only when it needs you, and a group shows its loudest project's.
- **An empty query lists the whole session in the sidebar's order**, with what the window shows already selected, and the list scrolled so that its project heads it (at most five rows above it, `context_top`). The order is `Session::sections` (projects without a group first, then each group followed by its projects), and under each project its workspaces, each followed by its tabs and agents. The shown row is the shown pane's agent, else the shown tab (or its first agent), else the workspace, else the project. So ↑ ↓ ↩ walk the session at once, and ⌘F also works as a switcher. Until 2026-10-31 an empty query listed nothing, as in the TUI: the sheet then looked empty and gave no hint that agents could be found, which is how the request read. Rejected: putting what needs you first, since the notices and toasts already do that and the list would reorder itself as statuses change; and following the sidebar's folds, since in the stacked arrangements a project row has no fold, so collapse flags left over from the tree would hide workspaces for no reason anyone could see. Clearing the query selects the shown row again.
- **The first scroll waits for the list's first layout**: gpui 0.2.2 applies a `ScrollHandle` request in prepaint before it records whether the element scrolls, so a request made before the list was ever drawn is dropped. `reveal` keeps asking, one frame at a time, until the handle has bounds.
- **The query is not kept once the sheet closes**: each opening starts afresh in Names, as the TUI does.
- **Ranking**: exact, prefix, a word's prefix, anywhere, then the query's letters in order (fuzzy, each as early as it comes); ties by kind, then the sidebar's order. The kind order is group, project, workspace, agent, tab: agents come before shell tabs because they are what one usually goes to. At most 200 rows are listed, and the status says when more were left out.
- **Letters in order count only in the name**: a branch, folder, model or workspace name matches only as a piece of text. Fuzzy matching on those let every agent match short queries through its model or kind, for reasons its row did not show.
- **A match outside the name is highlighted where it shows**: on the name when the name matched; otherwise on the query's first occurrence in the detail, else in the place. A worktree's `⎇ ` prefix shifts the name's highlight.
- **Case folding keeps byte ranges**: each character is lower-cased one for one (a character whose lower case is longer keeps its first), so matches map back onto the original text for highlighting.
- **Names also lists settings, after every name** (cornercase 0.12.280, #561 step 2 upstream): typing lists what `config search --json` finds, each as a `setting` chip, where it lives (`UI › sound`), its value as cornercase words it (`[x] on`) and its note, which is often why it matched. They are never ranked among the names, so groups, projects, workspaces, agents and tabs keep the places people's fingers know, and since names draw at once and settings join below them when they come, nothing above moves when they do. An empty query lists none, and In sessions lists none, as in the TUI. The highlight is the literal query's on the title, so a match on a value or on two words in another order highlights nothing, as upstream. There is no cap: they are a hundred or so at most, and they come after the names.
- **`config search`, not `search TEXT --settings`**: both answer from upstream's `Settings::found`, and gave the same rows on 74 hand-picked queries over labels, values and pages (2026-11-06). `search` also reads every pane's history without its cache, on the server's main thread for the text, and each agent's transcript: about four times as long with two panes of scrollback, growing with each pane, for `matches` that Names would throw away. Names had never cost the server anything, so this would make each pause while typing a tab's name read everything every pane ever printed. `--settings` suits a program that wants what was said too; In sessions, which does, lists no settings.
- **Asking**: debounced like In sessions, and an older answer is dropped by its generation. Until the answer comes the rows of the previous query stay, dimmed, rather than the list jumping at each key. The status says `3 results · 4 settings`; with no name matching it says `Looking in the settings…`, and `Nothing matches` only once the settings answered too. A spinner turns while the command runs; a failure shows in red in the status line, as In sessions' does, and names keep working. `Enter` on a settings row before the answer, or with nothing listed yet, goes when the answer comes.
- **Choosing changes nothing**: a row of a page Settings has opens Settings on it (`Store::land_on`, `design/settings.md`). A tab or row of what is a sheet of its own here (Accounts, Machines, Flows, Plugins) opens that sheet, found by `PanelKind::title`, not on the row, since those rows are not settings the sheet could mark. `Worktrees` and `Issues` are pages of Settings first, although sheets have those names too.
- **Machines' entries do come up** (checked on 0.13.1): the tab, `▭ this computer`, each machine by its name, destination or state (`Machines › ☁ vps`, value `vps.example.com`, note `linked · 0.13.1`) and `+ add machine`, all without a `key`. They open the Machines sheet, not on the row, since its rows are entries of a list that it draws by itself. A tab this window has no place for, such as a later cornercase's, says in Settings that it is in cornercase's own window.
- **What Names does not list**: the window's own Links settings and Settings' Projects and Share pages, which `config search` cannot know of. Settings' own search finds them.
- **Sessions searches are debounced** (220 ms) because each one reads every pane; a generation counter makes an older answer moot once the query or mode changes. `Enter` before the answer arrives goes to the first match when it does.
- **Matches are grouped by pane**, panes in the order their first match comes (the sidebar's), matches in the server's order (newest first). The output caps matches (20 a pane, 300 in all); `capped` says some were left out.
- **Opening a match scrolls to it**: `focus --pane P --reveal=QUERY` in our view (`Store::act`), with `--line=L` when the match has a line (a screen match); without one cornercase takes the newest place the pane shows the text (an agent's prompt or reply). The text is the query the search ran, and is joined to its flag with `=` so a query starting with `-` is not read as an option. The scroll and selection are the pane's, so every view shows them. A pane header still opens the pane only. (#467 upstream, checked with cornercase 0.12.225.)
- **Times are RFC 3339** (`2026-10-23T17:48:54.840Z` or with an offset), parsed by hand with the queue's days-from-civil, so no date crate is needed; fractions of a second are dropped.
- **Checked live** on 2026-10-31 with cornercase 0.12.230, on a throwaway project with three workspaces (one a worktree) and three tabs. Two of its panes were given an agent's fields (kind, conversation, model, role, status) by a `CORNERCASE_BIN` wrapper that edited only the `view` stream, so no agent ran and nothing in cornercase changed. Checked: ⌘F lists everything with the shown tab selected under its project; `login`, `opus` and `codex` find agents by their conversation, model and kind, with the highlight on what matched; ↩ on an agent focuses its pane, and reopening starts on it; In sessions still finds a marker and reveals it. The user's own agent was seen in the list and never chosen.
- **Settings checked live** on 2026-11-06 with cornercase 0.13.1, on Linux x86_64 under Xvfb with lavapipe, against a private server with a fake `ssh` to a second one on the same box; no real sshd, no macOS, no Windows. Checked: `sound` (four rows with their values and notes, ↩ lands on `UI › sound`, nothing changed); `shop` (the project first, then `Issues › Jira filter`, reached with ↓ and a click); `copilot` (an agent low in the table); `forum` (two muted rows saying what they need, ↩ lands on Discord's bot with the notice); `machines` and `vps` (the tab, this computer, each machine with its destination and link, `+ add machine`; ↩ opens the Machines sheet, where typing reaches nothing and Escape closes it); `accounts` with ↩ before the answer (its sheet opens, and Escape closes it); `config search` made to fail by a wrapper (the reason in red, the names still listed). `config search` through the fake `ssh` answered the same shape; the window itself was not run with `--remote` for this. The comparison with `search --settings` and its timing were on the same server, with two panes of 400,000 lines each.
