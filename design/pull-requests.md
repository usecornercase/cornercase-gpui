# Pull requests

Code: `src/model/pull_request.rs`, `src/dialogs/pull_request.rs`, `src/dialogs/pull_request/` (`read.rs` asking for every check, which answer counts and when to ask again, `signs.rs` the row's tags and the signs, colours and lines of checks, `stack.rs` the stack section), the row's tags in `src/sidebar/workspace.rs`, `Store::ask_agent`

- **The TUI's pull request dialog, as a dialog** (cornercase's `design/pull-requests.md`; asked for on 2026-11-01, when the window only had the row's tag): a click on a workspace row's `#485✗` (or its stack mark), **Pull request #485…** in the row's menu, or ⌘P for the workspace on screen opens it, and ⌘P closes it again. It shows the title; the state, a conflict with the base and the checks (their counts once every check is known, the rollup until then) as chips; the branch and its base; the stack; and every check. Its buttons: **Ask agent** (only while it conflicts or a check failed), **Copy link**, **Done** and **Open on GitHub**, the default (Enter). Until then the tag opened the pull request in the browser, and the menu had a submenu with the title, Open in browser and Copy link.
  - **Opening it here**, where the TUI's default is to copy the link: the TUI's server may be on another machine and cannot open a browser on yours, while this window always runs on the Mac you look at, so the address opens here even with `--remote`, and so does a check's.
  - **Ask agent is not offered once merged or closed**, unlike the TUI, which offers it for a merged pull request whose checks had failed: there is nothing left for the agent to fix.
- **Where it comes from**: the row, its tooltip and the dialog's first look come from the session (`view`): each workspace's `pull_request` carries `number`, `title`, `url`, `state`, `checks` (the rollup: `failing`, `pending`, `passing`, or none), `failed` (the failed checks' names), `conflicts`, `base`, `provider` and `stack`. Every check comes from `cornercase pull-request --workspace ID --json` (#567 upstream, cornercase 0.12.237), which the dialog runs as it opens: it asks gh or glab at once, lifting the project's wait as the TUI's dialog does, and answers `status`'s object plus `all_checks` (`name`, `workflow`, `outcome`, `url`, in the dialog's order), or `pull_request: null` with a `reason`. `view` leaves the list out (each line would grow by every check of every workspace), so the window asks for it only while the dialog is open. The dialog follows the session while it is open (a `Store` observer), so a check that finishes shows at once, and it closes itself when the pull request goes away (the branch changed, the setting was turned off), as the TUI's does. It closes only when the store still shows it, so a dialog still animating out cannot close the one opened after it. Running `gh pr view` from the window was rejected (`design/upstream-gaps.md`): it would redo the server's rules (which run of a check counts, GitLab's pipeline, which tool a host needs) and poll GitHub a second time.
- **How soon a merge shows** (asked about on 2026-11-02: from a merge until the row shows it "takes quite a while"): when the server next reads gh, and nothing the window sends or leaves out changes that. The server reads a pull request whose last answer was open a minute after that answer (20 s while its checks run), so the read that finds the merge comes at that pace; only after an answer that says merged or closed does it slow to 5 minutes, and a project whose read failed waits 5 minutes. It does so on its 1 s step, whether a window is attached, shown or focused or not (`OPEN_EVERY`, `RUNNING_EVERY`, `SETTLED_EVERY`, `FAILED_EVERY` in its `src/app/pull_requests.rs`; neither a TUI's focus nor `view-set --visible` touches the poll), and the TUI asks no sooner: only its dialog and `pull-request` ask at once. So a merge shows about half a minute later on average, about 61 s at worst (5 minutes after a failed read), and `view` brings it within its 500 ms. The user's `server.log` on 2026-11-02 agreed: reads of an open pull request a minute apart, and merges often within two minutes of the checks turning green, once the server is back at its minute pace. #584 upstream asked for the 20 s pace for a few minutes after the checks finish, and a read when a window comes back, which this window's `view-set --visible` on activation (`design/window.md`) would trigger with no change here. It was closed on 2026-11-04 with no linked change, and neither is in upstream's code at 0.13.19 (`design/upstream-gaps.md`), so all of this still holds. A click on the row's tag opens the dialog, which asks at once, and the row turns within a second or two; an agent that merges with `gh pr merge` can run `cornercase pull-request --worktree BRANCH` after it.
  - Rejected: the window running `pull-request --workspace ID` for every open pull request on activation, or after Open on GitHub, since it would put the server's pacing in one client (the TUI would still wait, two windows would read twice, and each read costs a GraphQL point and re-reads the stack); and a "needs #584" note, since nothing is missing from the row or the dialog, it is only late. Not checked live: merging a real pull request is an outward action, so the delay was read in cornercase's sources (origin/main 6d55dcd9) and the user's log.
- **Asking for every check** (`read.rs`): a job beside the queue (`store::run_busy`, key `pull-request:<workspace>`, `Asking GitHub about #482…` in the status bar), since it waits on gh, a second or so and up to gh's minute; in the queue it would hold every key and focus behind it. While it runs, a spinner under the checks says `Asking GitHub…` (`GitLab` for a merge request) and the section shows what `view` gave: the failed checks by name, or one line for the rollup (`Checks are running`, `Every check passed`, `No checks`).
  - **It asks again when `view`'s pull request for that workspace changes** while the dialog stays open (any field: a check finishing, a conflict, a layer of the stack), compared whole with the one it last asked about, so other changes to the store never ask. That costs gh one more read per change while a dialog is open, as upstream accepted when it left a cached read out; the read the dialog itself caused usually brings one such change, so opening it on a pull request whose checks moved reads twice.
  - **And a minute after an answer that lists a pending check** (`Reads::refresh_due`, found in review of PR #12): with one check failed and two running, either running one can finish without changing `checks`, `failed` or any other field of `view`'s object, so the dialog kept the old pending row, counts and links until it was reopened. While the dialog is open, the answer shown lists a pending check and no read runs, it asks again 60 s (`REFRESH_AFTER`) after that answer came. A minute is the server's own pace for an open pull request whose rollup is not pending (`OPEN_EVERY` upstream; 20 s while it is), and asking restarts that workspace's minute there, so the dialog's read mostly takes the place of the server's poll; when the poll lands just before it, gh is read twice that minute. It stops once nothing is pending, after a failed read (its reason is shown, and a logged-out gh would only fail again; a change in `view` still asks) and on a server too old for the command. The timer is a task the dialog holds, replaced at each answer, so closing the dialog drops it, and when it fires it checks again that the dialog is still shown, has a pull request, and that no read runs. Rejected: a signal from the server, since `view`'s object would have to carry every check's state, which #567 left out to keep `view` small.
  - **Which answer counts**: each request takes the next number, and an answer is kept only when its number is above the one shown, so an older answer that comes late never replaces a newer one, while one that comes first shows until the newest arrives (the spinner stays until then). A dialog that closed drops its answers with its entity; a reopened dialog is a new one and asks again. An answer about another workspace (never expected, since it names one) only ends the wait. The list is used only while the answer's pull request is the one `view` shows (same number and address), so a branch that moved to another pull request never shows the old one's checks. Rejected: dropping every answer but the newest's, which made the dialog wait a second more for a list it already had.
- **The checks section**: every check in the order given (failed, pending, passed, skipped), one line each as in the TUI: its sign in its colour (a skipped check a faint ring, the TUI's `-`), its name, and its workflow (a GitLab job's stage) muted after it, cut with "…" to the dialog's width (`signs::CheckLine`). A check with a web address (`link::is_web`, `design/terminal.md`; review of PR #12: a check's link comes from any app or commit status, and a `file:` or custom-scheme one would open in its macOS handler, so such a row stays plain text) shows the external-link icon, takes the pointer and the hover, and a click opens its job in the browser and leaves the dialog open, so several failed jobs can be opened one after the other (Open on GitHub closes it, being the dialog's answer). The TUI left clickable lines out, since its server cannot open a browser here. The checks chip counts them as the TUI's summary does (`1 failed, 1 pending, 2 passed`, `no checks`), and its colour follows them; the row's tooltip keeps `view`'s rollup (`open · conflicts with main · checks failing · layer 2 of 3 of stack #480`), since the row has no list.
  - **A read that fails** shows its reason as cornercase words it (`gh is not logged in: run gh auth login`, `install gh, GitHub's CLI, to see them`, gh's own line), in red under the checks, on one line, and the section goes back to what `view` gives. No toast: the dialog says it where you are looking, and a toast would say it twice.
  - **An older server** has no `pull-request` command and no feature string to look for, so its refusal is told by its text (``has no `pull-request` command``, or `unrecognized subcommand` from an older command line): the dialog says `Every check with its link needs cornercase 0.12.237 or newer`, muted, keeps `view`'s checks and does not ask again while it stays open.
  - **No pull request** in the answer (the branch moved, pull requests turned off) shows its `reason`, muted; `view` follows within the second, and the dialog closes itself as before.
- **The row** (`dialogs::pull_tag`, `dialogs::stack_tag`): `#485` and the rollup's glyph in its colour (`✗` red, `•` yellow, `✓` green; muted without checks). An open or draft pull request that conflicts shows `#486!` in the waiting orange whatever its checks, as the TUI's (#359 upstream: GitHub runs no `pull_request` workflows while it conflicts, so the checks would read green). Merged takes GitHub's merged purple (`colours::merged`, xterm 99, the TUI's `MERGED_COLOR`) without a glyph; closed is faint and crossed out. In a stack, `2/3` follows (GitHub's position and size), muted, red when what blocks below is a failed check, orange when it is a conflict. Both open the dialog, and their tooltip gives the title, the summary (`open · conflicts with main · checks failing · layer 2 of 3 of stack #480`) and the failed checks. They stay in place and readable while the row is hovered: its buttons sit before them (`design/sidebar.md`).
- **The stack** (#448 upstream): `#480 on main · layer 2 of 3`, then the layers top first, each with its position, number, sign, title and the workspace of this project that holds it (the one whose pull request has the layer's address, this workspace first); merged ones purple, closed ones crossed out, this one tinted. A click on another layer that a workspace holds goes there and closes the dialog. This layer's sign comes from its own checks, so it never contradicts its row (a layer's `checks` is GitHub's own rollup state). Layers come bottom first without their positions, so they count from this one's (`Stack::rungs`), and the list agrees with the row even if a layer were missing. A line says what blocks the merge (`Stack::blocker`, the TUI's rule: the lowest open or draft layer below that conflicts or failed its checks, else the lowest with changes requested; merged and closed layers never block), in red, orange or grey; a merged layer below while the branch is behind its remote asks to pull before pushing again. Working these out from the layers is drawing what the session gives, not redoing the server: `status` lists the layers for clients to draw.
- **GitLab** (#402 upstream): `provider` `gitlab` gives the dialog GitLab's words (`Merge request !486`, `pipeline`, `Asking GitLab…`, `Open on GitLab`), while the row keeps `#486`, as the TUI's. An older server sends no provider, read as GitHub.
- **No pull request**: ⌘P toasts `No pull request for <branch>`, or that the workspace is not on a branch. Why gh found none (not installed, logged out) shows where the TUI shows it: in the note of Settings › Worktrees › pull requests, which `config --json` carries.
- **Ask agent** is `Store::ask_agent`, shared with the Changes panel's hunks (`design/changes-panel.md`) and the merge check (`design/shared-files.md`): it pastes into the workspace's agent (the shown tab's first) with `send` and no Enter, so a note can follow, focuses it and toasts; without an agent it copies the text. With every check known it pastes the TUI's text, each failed job with its link and one without a link by its name: `pull request #482 failed its checks: tests (ubuntu-24.04) https://github.com/…/job/2001, bot `, `merge request !486 has merge conflicts with main and failed its pipeline: rspec https://gitlab.com/…/jobs/81001 `, and a conflict alone as `pull request #486 has merge conflicts with main `. Before the answer (or when the read failed) it names the failed checks and adds the pull request's address, from which the agent finds them: `pull request #485 has merge conflicts with main and failed its checks: test, clippy (https://github.com/…/pull/485) `.
- Checked live on 2026-11-01 with cornercase 0.12.234, on a throwaway project of three plain workspaces with fake pull requests injected into `view` by a `CORNERCASE_BIN` wrapper (a stack of three: a merged one, one conflicting with failed checks and behind its remote, one pending): ⌘P opening and closing it, the tags and their colours, a click on another layer (it went to that workspace), a click on a row's tag, Escape. Not pressed: Copy link and Ask agent (no agent there, so it copies), which would replace the clipboard, and Open on GitHub (fake addresses). GitLab's words are covered by tests only.
- Every check was checked live on 2026-11-02 (debug build, gpui 0.2.2, cornercase 0.12.238) on an isolated server (`CORNERCASE_SOCKET`) with a throwaway repository, through a `CORNERCASE_BIN` wrapper that injected a pull request into `view` and answered `pull-request --json` itself after 3 s (the repository has no remote, so the real command answers none, with that reason): ⌘P opening the dialog on `view`'s failed names with `Asking GitHub…` under them and the job in the status bar, then six checks of every outcome with their workflows and link icons, the counts chip, and a long name cut with "…"; the hover and pointer on a check with a link; a change of the injected pull request asking again with the list kept under the spinner, answered by a failed read (its reason in red, `view`'s checks back) and by an older server's refusal (the 0.12.237 line, and no request on the next change); a merge request (`Asking GitLab…`, its jobs' stages, `Open on GitLab`) after ⌘P closed and reopened the dialog, which asked again. Not pressed: a check's link and Open on GitHub (fake addresses would open in the browser), Copy link and Ask agent (no agent there, so it copies), which would replace the clipboard. Not tried: a real pull request, a real older server (its refusal was read in cornercase's sources), and a remote server, where the command goes through `cli` like every other.
