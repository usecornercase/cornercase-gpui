# Worktrees

Code: `src/panels/worktrees.rs`, `src/panels/worktrees/`

- **The TUI's Worktrees dialog as a sheet** (⇧⌘T, the rail's drive icon, or **Worktrees…** in a project's menu): every worktree on disk, from `worktrees list --json`, in the order cornercase gives (leftovers, merged, then the rest, oldest first), with its marks (`●n` changed, `↑n` not pushed, merged or no commits, upstream gone, locked, what runs in it, processes outside cornercase, open), its age, its size and the part in build folders, and the risks of removing it.
- **One project's worktrees** (`worktrees list --project ID`, 0.12.163): a project's menu opens the sheet on that project (`Store::open_on_project`), with a line that names it and **Show every worktree**; the rail and ⇧⌘T always open every worktree, whatever the last opening showed. Changing project drops the rows and the ticks of the other list at once. The filter stays beside it: it narrows what the command answered.
- **Two answers**: `--no-sizes` answers at once and fills the list; the measured list replaces it when it comes. A newer reload drops older answers. A worktree that could not be checked or measured makes the command exit 3 after the whole answer; that answer is used (`store::run_partial`) and the row shows its own error or `?`. A measure that fails outright keeps the list and says why in a toast.
- **Unknown counts are not errors**: `changed` is null for every kind but `linked`, and `unpushed` too when cornercase could not scan the worktree (a `repository-gone` one). They read as unknown and show no mark; read as numbers, one such leftover failed the whole list. Found on 2026-10-31 on a Linux server whose list held `prunable` and `repository-gone` leftovers (cornercase 0.12.234); this Mac had none, so the sheet only failed over ssh.
- **Safe first or largest first**: the second sorts by size, unmeasured ones last. A filter matches the project or the branch. The footer adds up what every listed worktree takes and the builds of those idle for 7 days, with `+` while some size is unknown, as the TUI does.
- **Every row can be removed** (`worktrees remove`, #671 upstream, 0.13.18): an open workspace, a closed project's worktree with its teardown, a prunable entry, a folder whose repository is gone or that git no longer knows. Only a role of a running flow (it goes with the run's workspace, and its row says so) and a row already being removed cannot be ticked, as in the TUI. The sidebar's Remove worktree… and a machine's worktree's `✕` ask this same question about their one folder (below).
- **The question is a second look** (`removal.rs`), as the TUI's confirmation is: Remove runs `worktrees remove --check --json` on the row or the ticked ones, the row or the footer's button says `Checking…` meanwhile, and only then `dialogs::confirm` asks, with the words the check answered per folder, so a list minutes old cannot hide what was written since. A title in yellow marks a folder at stake, red lines what cannot go (`cannot be removed: why`) and what the box would lose. The check exits 3 when some folder cannot go or be checked, which is an answer (`store::run_partial_busy`). When nothing can go there is no question: a toast says why, by name.
- **Also delete the branch** is a tick in the question (`dialogs::Tick`, with `Question::body` for the lines), named with the branch where the TUI's says only `also delete the branch`: the name says which branch goes, where that is chosen (#141), off by default, offered only when a folder that goes has a branch, so not for a leftover or a detached `HEAD`. One check serves both states: upstream answers `lost` whatever the flag says, so a client drawing its own box needs no second check, and the only line that follows the flag, `no branch is checked out, so none is deleted`, is written here in upstream's words. The default branch and the main checkout's cannot be told from the row, so the box shows for them and the toast says it was kept, as in the TUI.
- **`--force` and `--unlock` only after the person saw why**: the flags come from the check's `needs`, and from `lost` when the box is ticked, since a branch losing commits refuses without `--force`. The button says what it will do: `Remove`, `Remove anyway`, `Unlock and remove`, `Unlock and remove anyway`, and changes with the box. Rejected: a tick per risk, as the sidebar's dialog had until #74, since the TUI's one button after one list reads better for several rows.
- **One command per folder, not one for all**: the flags apply to a whole command, so a shared `--force` would also go to a folder that was clean when asked and got files since. Alone, that folder is refused and left as it is. Several run at once, each its own job and each row leaving as it answers. A folder that changed after the question comes back with a toast that says so in words and that removing it again asks again, built from `lines`, since `why` says `add --force`, which means nothing in a window.
- **Exit 3 is read, not failed on**: one toast when the last answer of a batch is in, as in the TUI: what went, with the branches deleted, then each problem by name (`Could not remove`, `Did not remove`, a branch kept, a teardown that failed). A failed teardown has no field of its own: upstream writes it as `<branch or path>: <why>` in `warnings`, so a warning of that shape on a folder with a teardown reads `its teardown failed: why`, and any other reads as it came.
- **A removal shows while it runs**: its row says `Removing…` with a spinner, dims and cannot be ticked, and the status bar names it. An open workspace uses `Busy::remove_worktree`, shared with the sidebar, whose row dims with `removing…` (`design/sidebar.md`); a folder with no workspace has a key of its own (`removing`). A removal that succeeds drops the row at once instead of waiting for the list read again, so it does not come back for a moment, and the list is read again when the batch ends. Measuring builds before Free builds asks, and freeing them, show the same way (`Measuring builds…`, `Freeing builds…`); the footer says `measuring` with a spinner while sizes are read. Other rows' Remove rests while a check runs, since a second check would replace the first's question.
- **A row with no branch goes by its folder** (`shop › gone-repo`), as in the TUI: `(no branch)` could not say which of two leftovers a toast means.
- **The sidebar asks this question too** (#74, `row_removal.rs`). Its Remove worktree… opens at once a dialog that says it checks, while `worktrees remove --check --json --path FOLDER` runs as a job; FOLDER is the workspace's `path`, the same text as the row of `worktrees list` (checked on 2026-11-09 with 0.13.21). A dialog closed before the answer drops it, so nothing is asked after Cancel. A check that fails, or finds nothing that can go, is `cannot_go`'s toast and the dialog closes. Otherwise this sheet's question replaces it (`removal_question`), and its yes runs `Folder::remove_command` from the Store (`Store::run_then`), since the question is gone by then; the toast is `summary` of one folder. Rejected: checking first with no dialog, as the row's button here does: from a menu nothing shows for 300 ms and then only the status bar, and over ssh a check takes seconds. Rejected: keeping `close --remove-worktree`: it keeps the branch, sees no risk in a running agent, and asks with a tick per risk, so the two places asked differently. The TUI's row `✕` still keeps the branch; here both places ask the same, as #74 asked. The old dialog's folder line went with it, as this question has none.
- **Free builds** runs `worktrees free-builds --path P --check` first and asks with what goes and its sizes; when a program runs in the worktree the button says "Free anyway" and passes `--force`, since without it cornercase refuses. The question opens in the window even if it went behind while the check ran, as Remove's does, and with no window to ask in a toast says nothing was freed, where it used to stop silently. Checked live on 2026-11-07 (debug build, cornercase 0.13.19, Linux x86_64 under Xvfb with lavapipe; no macOS, no Windows), with the check slowed by a wrapper and the display's focus taken off the window while it ran: the question opened. The toast was not seen, since it needs no window at all.
- **Changes** focuses the workspace and opens its Changes panel.
- **The confirmation runs a closure** (`dialogs::Question::on_yes`) so the sheet runs the command itself and reloads on its answer.
- Checked live on 2026-10-29 with cornercase 0.12.225, on a throwaway repository with two worktrees, one with a changed file, a commit, `node_modules` and a running server.
- Checked live on 2026-10-30 with cornercase 0.12.230, on a throwaway repository, with the commands slowed by a `CORNERCASE_BIN` wrapper so the busy state could be seen. The sheet's Remove, the sidebar's Remove worktree and a removal of the worktree the window shows were tried.
- Checked live on 2026-11-06 with cornercase 0.13.1, on Linux x86_64 under Xvfb with lavapipe, on a server of its own with its own worktrees folder: a closed project's worktree with its tick dim and no Remove, the note under the list, and both Remove questions, left unanswered.
- One project's checked live on 2026-11-06 (debug build, cornercase 0.13.1, Linux x86_64 under Xvfb with lavapipe, a private server; no macOS, no Windows), with a worktree in each of two throwaway projects: from each project's menu, Show every worktree, and the rail opening every worktree after it.
- Removing checked live on 2026-11-07 (debug build, cornercase 0.13.19, Linux x86_64 under Xvfb with lavapipe, a fake ssh between two servers on one box; no real sshd, no macOS, no Windows), on throwaway worktrees of a throwaway repository, with the check and some teardowns slowed so the busy states could be seen: one of each kind (open, a closed project's with its teardown, prunable with its branch, repository gone, unknown to git) in a batch of eight with the box ticked, whose toast named a branch kept (a worktree on the default branch) and a teardown that failed; a lock (`Unlock and remove`), a running program and uncommitted files (`Remove anyway`), an unpushed commit whose red line and `Remove anyway` came with the box; a file written while the question was open (refused, the folder stayed, the row came back marked); and a teardown writing a file in a clean folder beside two forced ones, which git refused because the `--force` was not shared. Not tried: a flow run's workspace and its roles (their count and lines are tested from the answer's shape), a removal of the workspace the window shows, and the sidebar's row dimming during one, whose key is the one it had.
