# Worktrees

Code: `src/panels/worktrees.rs`, `src/panels/worktrees/`

- **The TUI's Worktrees dialog as a sheet** (⇧⌘T, the gear's menu, or **Worktrees…** in a project's menu): every worktree on disk, from `worktrees list --json`, in the order cornercase gives (leftovers, merged, then the rest, oldest first), with its marks (`●n` changed, `↑n` not pushed, merged or no commits, upstream gone, locked, what runs in it, processes outside cornercase, open), its age, its size and the part in build folders, and the risks of removing it.
- **One project's worktrees** (`worktrees list --project ID`, 0.12.163): a project's menu opens the sheet on that project (`Store::open_on_project`), with a line that names it and **Show every worktree** (the line wraps a long name, in a `min_w_0` box that keeps its natural width otherwise, so the button stays beside it; found in #144's sweep); the rail and ⇧⌘T always open every worktree, whatever the last opening showed. Changing project drops the rows and the ticks of the other list at once. The filter stays beside it: it narrows what the command answered.
- **Two answers**: `--no-sizes` answers at once and fills the list; the measured list replaces it when it comes. A newer reload drops older answers. A worktree that could not be checked or measured makes the command exit 3 after the whole answer; that answer is used (`store::run_partial`) and the row shows its own error or `?`. A measure that fails outright keeps the list and says why in a toast. The panel keeps the whole answer (`List`), because the merged figure (below) belongs to the measured answer: the `--no-sizes` one has no `merged_builds` and drops it with the sizes.
- **Unknown counts are not errors**: `changed` is null for every kind but `linked`, and `unpushed` too when cornercase could not scan the worktree (a `repository-gone` one). They read as unknown and show no mark; read as numbers, one such leftover failed the whole list. Found on 2026-10-31 on a Linux server whose list held `prunable` and `repository-gone` leftovers (cornercase 0.12.234); this Mac had none, so the sheet only failed over ssh.
- **Safe first or largest first**: the second sorts by size, unmeasured ones last. A filter matches the project or the branch. The footer adds up what every listed worktree takes, the builds of those idle for 7 days and the builds of merged worktrees (below), with `+` after the first figure only while some size is unknown, as the TUI does. Its figures are parts of `ui::separated`, each one line with a dot drawn only between two parts on one line: at a narrow width a part moves whole to the next line and no line starts or ends with a dot (at 640 px with both buttons: three short lines). There are no shorter forms, as the TUI has: a terminal row is one line and chooses by its width, while the window has room to wrap, and dropping the idle figure would hide a fact. Rejected: one text that wraps anywhere (it splits `4` from `merged worktrees`), and a row of its own for the clause and its button (two places for one summary).
- **Every row can be removed** (`worktrees remove`, #671 upstream, 0.13.18): an open workspace, a closed project's worktree with its teardown, a prunable entry, a folder whose repository is gone or that git no longer knows. Only a role of a running flow (it goes with the run's workspace, and its row says so) and a row already being removed cannot be ticked, as in the TUI. The sidebar's Remove worktree… and a machine's worktree's `✕` ask this same question about their one folder (below).
- **The question is a second look** (`removal.rs`), as the TUI's confirmation is: Remove runs `worktrees remove --check --json` on the row or the ticked ones, the row or the footer's button says `Checking…` meanwhile, and only then `dialogs::confirm` asks, with the words the check answered per folder, so a list minutes old cannot hide what was written since. A title in yellow marks a folder at stake, red lines what cannot go (`cannot be removed: why`) and what the box would lose. The check exits 3 when some folder cannot go or be checked, which is an answer (`store::run_partial_busy`). When nothing can go there is no question: a toast says why, by name.
- **Also delete the branch** is a tick in the question (`dialogs::Tick`, with `Question::body` for the lines), named with the branch where the TUI's says only `also delete the branch`: the name says which branch goes, where that is chosen (#141), off by default, offered only when a folder that goes has a branch, so not for a leftover or a detached `HEAD`. One check serves both states: upstream answers `lost` whatever the flag says, so a client drawing its own box needs no second check, and the only line that follows the flag, `no branch is checked out, so none is deleted`, is written here in upstream's words. The default branch and the main checkout's cannot be told from the row, so the box shows for them and the toast says it was kept, as in the TUI.
- **`--force` and `--unlock` only after the person saw why**: the flags come from the check's `needs`, and from `lost` when the box is ticked, since a branch losing commits refuses without `--force`. The button says what it will do: `Remove`, `Remove anyway`, `Unlock and remove`, `Unlock and remove anyway`, and changes with the box. Rejected: a tick per risk, as the sidebar's dialog had until #74, since the TUI's one button after one list reads better for several rows.
- **One command per folder, not one for all**: the flags apply to a whole command, so a shared `--force` would also go to a folder that was clean when asked and got files since. Alone, that folder is refused and left as it is. Several run at once, each its own job and each row leaving as it answers. A folder that changed after the question comes back with a toast that says so in words and that removing it again asks again, built from `lines`, since `why` says `add --force`, which means nothing in a window.
- **Exit 3 is read, not failed on**: one toast when the last answer of a batch is in, as in the TUI: what went, with the branches deleted, then each problem by name (`Could not remove`, `Did not remove`, a branch kept, a teardown that failed). A failed teardown has no field of its own: upstream writes it as `<branch or path>: <why>` in `warnings`, so a warning of that shape on a folder with a teardown reads `its teardown failed: why`, and any other reads as it came.
- **A removal shows while it runs**: its row says `Removing…` with a spinner, dims and cannot be ticked, and the status bar names it. An open workspace uses `Busy::remove_worktree`, shared with the sidebar, whose row dims with `removing…` (`design/sidebar.md`); a folder with no workspace has a key of its own (`removing`). A removal that succeeds drops the row at once instead of waiting for the list read again, so it does not come back for a moment, and the list is read again when the batch ends. Measuring builds before Free builds asks, and freeing them, show the same way (`Measuring builds…`, `Freeing builds…`); the footer says `measuring` with a spinner while sizes are read. Other rows' Remove rests while a check runs, since a second check would replace the first's question. Free merged's own jobs show as `Measuring…` and `Freeing…` on its button, and the status bar names them.
- **A row with no branch goes by its folder** (`shop › gone-repo`), as in the TUI: `(no branch)` could not say which of two leftovers a toast means.
- **A long name is cut in its row, whole in its tooltip** (#144, 2026-11-12). The heading's `project › branch` is a `ui::one_line` in a box sized by its text (`rows::name`, `min_w_0().flex()`), so it ends in "…" where the marks begin, and the marks, the age and the size keep their places at any width; as a bare text it could not shrink (`design/widgets.md`), and a 115-character branch pushed them out of the row. Cut rather than wrapped, since the sheet is a list: one line per heading keeps the marks and figures where the eye finds them, as the TUI's rows cut the project and the branch (its `ui/dialog/worktrees.rs`). The name stays reachable: the tooltip holds it whole, the folder line under it, which ends in the branch's folder, wraps whole, and the question before removing names it whole (#141). The tooltip is on every row's name, since the sheet's width follows the window's and no count of characters says whether it was cut. A long project name can leave no room for the branch; the tooltip and the folder line say it then. Rejected: wrapping (a heading of two or three lines among one-line ones, and a name box taking the row's room pushes every row's marks to its end); cutting the project before the branch, as the TUI does (more code for a rare name). Many marks at a narrow width can still pass the row's end with the name at nothing: they are fixed texts, left for their own decision.
- **The sidebar asks this question too** (#74, `row_removal.rs`). Its Remove worktree… opens at once a dialog that says it checks, while `worktrees remove --check --json --path FOLDER` runs as a job; FOLDER is the workspace's `path`, the same text as the row of `worktrees list` (checked on 2026-11-09 with 0.13.21). A dialog closed before the answer drops it, so nothing is asked after Cancel. A check that fails, or finds nothing that can go, is `cannot_go`'s toast and the dialog closes. Otherwise this sheet's question replaces it (`removal_question`), and its yes runs `Folder::remove_command` from the Store (`Store::run_then`), since the question is gone by then; the toast is `summary` of one folder. Rejected: checking first with no dialog, as the row's button here does: from a menu nothing shows for 300 ms and then only the status bar, and over ssh a check takes seconds. Rejected: keeping `close --remove-worktree`: it keeps the branch, sees no risk in a running agent, and asks with a tick per risk, so the two places asked differently. The TUI's row `✕` still keeps the branch; here both places ask the same, as #74 asked. The old dialog's folder line went with it, as this question has none.
- **Free builds** runs `worktrees free-builds --path P --check` first and asks with what goes and its sizes; when a program runs in the worktree the button says "Free anyway" and passes `--force`, since without it cornercase refuses. The question opens in the window even if it went behind while the check ran, as Remove's does, and with no window to ask in a toast says nothing was freed, where it used to stop silently. Checked live on 2026-11-07 (debug build, cornercase 0.13.19, Linux x86_64 under Xvfb with lavapipe; no macOS, no Windows), with the check slowed by a wrapper and the display's focus taken off the window while it ran: the question opened. The toast was not seen, since it needs no window at all.
- **A row's free reads exit 3** (`store::run_partial_busy`, `frees::row_toast`): a free that kept or could not delete a folder exits 3 and, with `--json`, prints nothing on stderr, so through `run_busy` its toast read `cornercase worktrees: failed`. Now it says `Freed 296.0 KB` and then each `Could not free X in NAME: error` or `Kept X in NAME: …`, as an error. Its check keeps `run_busy`: a single `--check` deletes nothing and exits 0. The row's and Free merged's reading share `frees.rs` (`Freed`, the folder lines, the question's words).
- **The merged worktrees' figure** is `merged_builds` (`bytes`, `count`) of a measured `worktrees list --json` (cornercase 0.13.70, upstream #811, PR #828, feature `merged-builds`), shown after the idle figure as `6.2 GB of builds in 4 merged worktrees` (`1 merged worktree` for one), in the TUI's words and the window's own size format (`human_size`, as the other figures; the TUI's `text::size` would put two formats in one line). It is **never computed here** from the rows' `merged`: the rule (linked, tickable, not a live run's role, `no commits` is not merged, builds above zero) is the server's, and a client adding up rows would drift from it. A `count` of 0 shows nothing, no clause and no button; `+` stays on the first figure only, since a second `+` would say again what the first says, and the CLI's own `+` for the merged figure is a line of its own there.
- **Between the two lists the figure is not kept**: nothing shows while `measuring` (a reload clears the kept figure at once, so a measured list that fails brings no stale one back), and a removal drops the figure with the row (`List::drop_row`) until the list is read again. A kept figure would name builds just freed and offer to free them again, or count a worktree that went, while the rows' own sizes already show `…`. Rejected: keeping the last figure while it is measured again.
- **Free merged…** runs `worktrees free-builds --merged --check --json` (with `--project ID` on one project's sheet) as a job, then asks once through `dialogs::confirm`, then runs the same command without `--check` as a job and says in one toast what went and what stayed. Exit 3 is an answer. Entries are read by `outcome`, a contract key: `freeable` and `freed` go, `refused` is kept, `failed` and anything else is failed and never counted as freed; a missing `why` reads `cornercase did not say why`. The question names only what goes: one worktree asks as the row does (`Free the build folders of NAME?`), several `Free 5.0 MB of builds in 2 merged worktrees?` (the sum over the worktrees that go), the body lists each one that goes with its folders and sizes, then each one that keeps its builds with why (yellow name, red line), then what stays and the hints; the button is `Free`, never `Free anyway`. With nothing to confirm (every entry kept or failed) there is no question: an error toast names each with why; with no entry at all, an info toast and the list is read again. A body longer than the dialog scrolls (`dialogs::body_height`).
- **What is kept, and why.** The command never forces and the window has only the command, so a worktree where a program runs or whose build folder holds a git checkout stays and is named with the server's `why`. A row's Free builds… (`Free anyway`, `--force`) is still the way to free a running one, and the hint says so only for a kept entry that names a program. A row cannot force a nested git checkout (its check does not say so): today's behaviour, not changed here. The command frees the whole list as the figure counts it, whatever the filter shows, so the question says so when the filter has text. Rejected: one `free-builds --path` per confirmed worktree, the loop upstream rejected (the rule repeated by every client, an ssh per worktree through `--remote`, and a running program refused with exit 1 instead of named); narrowing the free to the shown rows.
- **The free decides again**: the list may change between the question and the yes. A worktree merged or built meanwhile is freed too, one where a program started keeps its builds, one freed elsewhere is left out. The question remembers the paths it offered to free, and the toast names each worktree freed that it did not (`Also freed X, which the question did not offer to free`, an error toast; true also for one the question named as keeping its builds), so a free never takes more than was confirmed without saying so, and its size and count come from the same entries as the question's. The toast reads the free's own answer: `Freed 5.0 MB in 2 merged worktrees` (or `Nothing was freed`), then each problem by name, `Did not free X: why`, `Could not free X: why` and the folder lines; `Info` only when no problem line was written, `Error` otherwise, even for what the question already named, since a program may have started since.
- **The jobs and what rests.** `check-merged-builds` and `free-merged-builds` are two fixed keys, global and not per project (a sweep on one project's sheet may hold worktrees the every-worktree sheet shows). While either runs every row's Free builds… rests; while any listed row has an activity (a removal, a check, a measure or a free) the button rests. So the window never frees one worktree twice at once, and the server also leaves out of the sweep a folder a single free is freeing. A merged job shows its busy button even while the list is read again. Not covered: Remove… does not rest during Free merged's check (a question that answers later replaces the other with nothing done, as a row's check does). Rejected: one key for all frees (`Store::busy` matches exact keys; a prefix test would touch the job store).
- **After the free** the toast comes first, then the list is read again: rows show `…` and the footer the head with `measuring`, no clause and no button, until the measured answer brings the smaller figure or none. The sheet does not follow a free made elsewhere (nothing streams sizes upstream): it reads when it opens, on ↻ and after its own frees and removals, so a figure can be as old as the last read, and Free merged's own check sees the disk as it is.
- **The gate has two halves.** (a) The figure and the button's presence need no release check: an older server leaves the key out and the sheet shows nothing, exactly as before; whether the key is absent because the server is older or because nothing is merged, nothing shows, so `Store::server_has` (for what is said or done according to the server's release) is not used and `design/connection.md` does not change. (b) The command line that sends `--merged` is this computer's, clap parsing the flag locally, also with `--remote` (the request is built here and sent through the proxy), so the button needs `Store::cli_release()` of 0.13.70 or newer (`FREE_MERGED_SINCE`), per the bullet in `design/connection.md` on flags parsed here. Below it, or unreadable, the figure still shows (an older command line prints the server's raw JSON, seen) and a muted line takes the button's place: `Freeing the merged worktrees' builds in one go needs cornercase 0.13.70 or newer on this Mac (it has 0.13.69).` An old command line answers clap's usage error, exit 2, before sending anything; the window never sends it and never reads those words. Rejected: no button and no word, and telling an old command line by its error.
- **Another machine.** With the window on another machine's server (`--remote`, ⇧⌘K) the sheet's commands run there through this computer's command line: the list, its figure and the free are that server's, and the gate's second half is this computer's release. The sheet never lists a linked machine's worktrees (a machine's workspace is removed from its sidebar row, `row_removal.rs`, which only removes), so Free merged never reaches one.
- **Changes** focuses the workspace and opens its Changes panel.
- **The confirmation runs a closure** (`dialogs::Question::on_yes`) so the sheet runs the command itself and reloads on its answer.
