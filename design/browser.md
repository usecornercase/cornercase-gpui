# Browser panel

Code: `panels/browser.rs`, `panels/browser/`, `assets/browser/page.js`

## Why and what

- **A real Chrome inside the window**, docked right of the terminal like Changes and Files (⇧⌘B, the rail's globe): the page of the workspace's dev server next to the agent changing it, and what the agent needs from it (an element, a screenshot, the console's errors) one click away.
- **The second exception to "only a UI over the command line"**, after the Files panel: cornercase has no browser, and a browser is not server logic to reimplement, so the panel runs Chrome itself and talks to it over the DevTools protocol (CDP). What it hands an agent still goes through cornercase (`paste-file`, `input`).

## Engine (decided 2026-10-31)

- **Headless Chrome, its frames drawn by gpui.** `Page.startScreencast` sends JPEG frames that `frame.rs` decodes off the main thread to BGRA and `viewport.rs` paints with `paint_image`; the pointer and keys go back as `Input.dispatch*`. Rejected: a native web view (WKWebView, WebView2, WebKitGTK through wry) sits above gpui's drawing, so dialogs, menus and toasts over the dock would hide under it; it is three engines with three behaviours; it cannot be embedded on Wayland, where gpui uses no GTK; and an agent cannot drive it. A Chrome window beside the app was rejected because the point is to see the page here. The screencast costs some smoothness against a native view (a frame is encoded, sent and decoded), which was judged worth it.
- **Any Chromium the machine has**: `CORNERCASE_GPUI_CHROME`, else Chrome, Chromium, Edge, Brave or Canary in their usual places on macOS and Windows (Windows' folders and order are under Windows), else those names and `chrome-headless-shell` on the `PATH` (an executable file, the first name in that order wherever it is on the `PATH`, as `desktop::on_path` finds tools). The engine is plain Rust over a socket, so nothing in it is macOS-only. **The browser and its profile are chosen once per process** (`chrome::chosen_in`), the first time one is found, so the launch, the downloads' folder and the cleanup on quit agree even if the `PATH` changes, and the downloads and the quit read no binary on the main thread; until one is found, Try again looks again, so a browser installed meanwhile is picked up.
- **Its own profile**, `~/Library/Application Support/cornercase-gpui/browser` (`$XDG_DATA_HOME` on Linux, `%LOCALAPPDATA%` on Windows; `CORNERCASE_GPUI_BROWSER_PROFILE` moves it): since Chrome 136 the DevTools switches are ignored on the everyday profile, and the `chrome://inspect` toggle that allows it asks the user on every connection and hands over every tab and cookie. Logins to dev apps are kept in this profile. `--use-mock-keychain` on macOS keeps Chrome from asking for the keychain. The profile's path reaches `--user-data-dir=` as it is on disk, not as text, so with a home whose name is not UTF-8 Chrome writes its `SingletonLock` in the folder the window reads it from (until 2026-11-04 it was made text, with such bytes replaced: Chrome then used another folder and the window waited 20 s for a port it never found; CodeRabbit's review). Checked live on 2026-11-04 (Debian's Chromium 156 through a `--no-sandbox` wrapper, `CORNERCASE_GPUI_BROWSER_PROFILE` set to `/tmp/caf\xe9/profile`): the previous build's Chrome made `/tmp/caf\357\277\275/profile` and the panel said "the browser did not open its DevTools port within 20 s"; this one's wrote its `SingletonLock` in `/tmp/caf\xe9/profile` and the panel attached.
- **On Linux** (decided 2026-11-04): Chrome is found by its names on the `PATH` (`google-chrome-stable`, `google-chrome`, `chromium`, `chromium-browser`, `microsoft-edge-stable`, `microsoft-edge`, `brave-browser`, Arch's `brave`, `chrome-headless-shell`), since every Linux package puts one there; Flatpak browsers are not looked for, since their sandbox keeps them from a profile outside it. `--password-store=basic` keeps Chrome from asking GNOME Keyring or KWallet to unlock, as the mock keychain does on macOS; the dev logins of this profile are kept unencrypted on disk, as a profile only for dev apps can afford. Nothing else differs headless: no display is needed, and the GPU flags stay Chrome's own.
  - **Ubuntu's Chromium is a snap**, and a snap's confinement lets it write only non-hidden folders of the home folder, so the profile under `~/.local/share` would fail as Chrome starts. A snap is told by its command in `/snap/bin` (a link to `/usr/bin/snap`) or by the script that runs it (Ubuntu's `/usr/bin/chromium-browser` ends in `exec /snap/bin/chromium`): only a line that runs `/snap/bin/…` counts, so a script that merely tests for a snap and then runs a native browser keeps the native profile. The snap is the one the command belongs to, found as `snap` itself finds it: a command in `/snap/bin` that links to a bare name is an alias (`snap alias chromium google-chrome`), and the name it points to is the snap's (`chromium`), not the alias's. Its profile is then `~/snap/<name>/common/cornercase-gpui-browser`, the folder the snap may write (`$SNAP_USER_COMMON`), which this app can also read; downloads land there first, as in any profile. `CORNERCASE_GPUI_BROWSER_PROFILE` still wins. Not checked live: Docker runs no snapd.
  - **A Chrome that stops as it starts says why**: its standard error is a pipe that a thread reads for the browser's lifetime, keeping only the last `ERROR` or `FATAL` line (up to 500 characters; a line is read 4 KB at a time), which the failure gives. Found live: Debian's Chromium where unprivileged user namespaces are off (a container, Ubuntu 23.10+ without its AppArmor profile) exits with "No usable sandbox!", which names the fix (Debian's `chromium-sandbox`); the panel said only "exit status: 1". Until 2026-11-04 it went to `cornercase-chrome.log` in the profile, which nothing bounded while the browser ran (CodeRabbit's review); rejected: capping the file (Chrome writes it, so only a size limit on the process could, and that kills it) and rotating it (a thread watching the file for what a pipe gives). The pipe is safe when the window crashes and the next one adopts its Chrome: Chrome ignores `SIGPIPE`, so its writes to the pipe nobody reads fail and it runs on (checked on 2026-11-04 with Debian's Chromium 156 logging verbosely: it kept answering `/json/version` after the reader closed; and in the window, under Xvfb: the panel gave "No usable sandbox!" read through the pipe, no log file was left in the profile, and with `--no-sandbox` a window killed with `SIGKILL` left its Chrome running, which the next window attached to and drew). `--no-sandbox` is never passed: the profile holds logins, and the pages are dev servers that could run anything.
  - **Checked live on 2026-11-04** (Debian 13 arm64 in a container, Xvfb and openbox, Debian's Chromium 156.0.8078.79): `chromium` was found on the `PATH` and launched with `--password-store=basic`; it stopped at once on the container's missing sandbox, which the panel then showed in Chrome's words; through a wrapper adding `--no-sandbox` (`CORNERCASE_GPUI_CHROME`, for the container only), typing `8765` in the address loaded a `busybox httpd` page, drawn in the dock, and "Open in the system browser" reached `xdg-open` through gpui. Not checked: Google Chrome, Edge or Brave on Linux, a snap, and GNOME Keyring or KWallet prompting without the flag.
- **Port 9222 when free**, else one Chrome picks: 9222 is what `chrome-devtools-mcp --browser-url` and Playwright examples use, so an agent's MCP setup works unchanged. With a fixed port Chrome writes no `DevToolsActivePort`, so the port is kept in `cornercase-port` in the profile and the socket's path read from `/json/version`, which answers only HTTP/1.1 and keeps the connection open (read up to `Content-Length`).
- **One Chrome per profile, shared**: a second window attaches to the Chrome its profile already runs (found by the `SingletonLock`'s live pid, then the port; on Windows by Chrome's singleton window, under Windows). The window that launched it owns it (`cornercase-owner` holds its pid) and ends it on quit (SIGTERM, then a kill after 1.5 s so cookies reach the disk; on Windows `Browser.close`, under Windows); a Chrome left by a window that crashed is adopted by the next one. When the connection drops (the owner quit), the panel starts again with a back-off and reopens the tabs it had.
- **A WebSocket client of ~150 lines** (`socket.rs`) instead of a dependency: Chrome on localhost needs text frames, fragments, ping and close, nothing more.
- **The page sees a plain Chrome**: the user agent's `HeadlessChrome/` becomes `Chrome/`, focus is emulated so carets blink and `:focus` applies, and the page script (`assets/browser/page.js`, injected before the page's own scripts) talks back through the `cornercaseBridge` binding (the cursor under the pointer, and what the features below add).

## Tabs

- A tab belongs to the workspace on screen when it opened; each workspace remembers its active tab, and switching workspaces switches what the panel shows. Tabs opened from a page (`window.open`, `target=_blank`) follow their opener; tabs nobody here opened (an agent driving the browser) belong to no workspace and show in all.
- Only the active tab of the workspace on screen is screencast, and only while the dock shows the panel; the last frame of each tab is kept for an instant switch.
- The page is sized to the panel in CSS pixels at the display's scale (`Emulation.setDeviceMetricsOverride`), so it is sharp on Retina; a resize settles for 150 ms before the page is resized and the screencast restarted.

## Input

Code: `browser/pointer.rs`, `keyboard.rs`, `typing.rs`, `select.rs`, `input.rs`, `viewport.rs` (the canvas that listens), the second block of `assets/browser/page.js`, `terminal/browser.rs`

- **The pointer goes to Chrome as `Input.dispatchMouseEvent`** in the page's CSS pixels, through the frame's fit (`viewport::page_point`), so a phone-sized or shrunk frame maps right: presses and releases with their button (left, middle, right, back, forward), the held `buttons`, gpui's click count (macOS's, so a double click selects a word and a triple click a line, as in Chrome), the modifiers, moves and the wheel. The canvas listens on the window for its frame (`window.on_mouse_event`): presses and the wheel only over its hit box, so a dialog, a toast or the select menu over it keeps them; moves and releases anywhere while a button is held, so a text selection or a slider drag goes on outside the panel and ends where the button is let go. A move that comes with no button held ends a drag whose release was lost. Leaving the page sends a move to (-1, -1), so the page's hover styles and `mouseleave` end.
- **One move and one wheel in flight**: each waits for Chrome's answer, which comes once the renderer took the event; what arrives meanwhile is kept, a newer move replacing the kept one and wheels adding up, and a press or a release sends what is kept first, so the order holds. Chrome coalesces moves itself, but a trackpad sends 120 a second and a busy page would trail the pointer behind a queue in the socket. Rejected: a fixed rate (late on a fast page, still too much for a slow one).
- **The wheel**: gpui's pixel deltas as they are, the sign turned (gpui gives the content's motion, Chrome the scroll's), a line as 40 px.
- **A drag keeps the page's cursor**: while a button is held, the page's last cursor is the whole window's (`set_window_cursor_style`), so it stays an I-beam or a grabbing hand outside the panel.
- **Keys reach the page only while the viewport has the focus** (a click on it gives it), as the terminal takes them only with its own: `Browser::page_key_down` on the viewport sees them before `Root`. The ⌘ keys of `keymap.rs`'s table are left to `Root`; every other ⌘ key goes to the page (⌘A, ⌘Z, a web app's ⌘K). Other keys stop at the viewport, so none reach a pane.
- **On macOS, keys go as a Mac sends them, with its editing commands**: a key is a `rawKeyDown` with its `key`, `code`, `windowsVirtualKeyCode` and modifiers, and the Cocoa command macOS would run for it (`selectAll`, `undo`, `redo`, `moveWordLeft`, `moveToEndOfDocument`, `deleteToBeginningOfLine`, the Ctrl-letter moves…, after Playwright's `macEditingCommands`). On macOS Blink leaves these to the browser's `NSResponder`, so without them ⌘A, ⌥← or ⌘⌫ do nothing in a headless Chrome. Enter goes as `keyDown` with `\r` and no command, so its `keypress` reaches the form: with `insertNewline` the command took the key at keydown, and no keypress followed (seen live).
- **On Linux, keys go as Chrome on Linux gets them, without commands**: Blink edits from the key itself there (Ctrl+A selects all, Ctrl+Z undoes, Ctrl+Shift+Z and Ctrl+Y redo, Ctrl+←, Ctrl+⌫, Home and End), as Playwright relies on, so the Cocoa commands are left out (`keyboard::key_down`), and an Alt key goes as a key, since Alt types nothing on Linux (AltGr does, through the input method). The panel answers to the keys a Linux user presses in Chrome (`design/terminal.md`, Keys on Linux): Ctrl+C, Ctrl+X and Ctrl+V are its Copy, Cut and Paste with the window's clipboard, for the reason below, Ctrl+L the address, Ctrl+R and F5 reload, Alt+← and Alt+→ go back and forward; their Ctrl+Shift forms work too. Rejected: leaving Ctrl+C, Ctrl+X and Ctrl+V to the page, which would copy into headless Chrome's own clipboard, out of reach of every other app. Limit: a page that wants those keys itself, such as a web terminal's Ctrl+C, does not get them, as a page on macOS does not get ⌘C. Checked live on 2026-11-04 (Chromium 156.0.8078.79 headless on Debian trixie under Xvfb, xdotool): in a textarea, typed text arrived once, Ctrl+A selected all, Ctrl+⌫ deleted a word and Ctrl+Z put it back with no command sent, Ctrl+C then Ctrl+V pasted the selection through the window's clipboard once, and Ctrl+L selected the address. Not checked: Ctrl+X, Ctrl+R, F5, Alt+← and Alt+→ (unit-tested).
- **Text comes from macOS's input method**, as in the terminal (`EntityInputHandler for Browser`), so dead keys, ⌥ characters (`@` is ⌥2 on a Spanish keyboard) and compositions work. A printable key is held back when pressed; when the input method answers with its text, the two go as one `keyDown` carrying that `text`, so the page sees keydown, keypress, beforeinput and input as when typing, and a page that cancels the keydown cancels the character, as in Chrome (a site's `/` shortcut does not type a slash into the field it focuses). Text that comes without its key (a composed `é`, the emoji picker, dictation) goes as `Input.insertText`, marked text as `Input.imeSetComposition`, committed by `insertText`. Never both: the key carries no text of its own, and text carries the key it came from. A held key repeats as `keyDown`s with its text and `autoRepeat`, past the input method, so macOS's press-and-hold accent menu does not open (on Windows it repeats through it, under Windows): its choice replaces the character before the caret, which the window cannot read from the page.
- **The input method's window opens at the page's caret**: the page script reports the caret's rectangle (`caret`) when the selection, the focus, the text or the scroll changes, once per animation frame: in a field, the text before the caret measured with a canvas in the field's font (by lines in a textarea; soft wraps are not counted), in a contenteditable its range's rectangle; offset by same-origin frames. Rejected: a hidden copy of the field to measure the caret exactly (it adds a node to the page, which the page's MutationObservers would see).
- **Escape goes to the page while the viewport has the focus**, still handled once, in `Root`, which passes it on (`Browser::escape`) once no dialog or sheet is open, as it passes it to vim in a pane. Pages close their own dialogs, menus, lightboxes and full-screen video with it; a dock that closed on Escape would take that from every page. ⌘W still closes the dock, and a click on the terminal leaves it.
- **⌘L, ⌘R, ⌘[ and ⌘] belong to the browser while it has the focus** (the viewport or the address): they are rows of `keymap.rs`'s table in a Browser group, which `keymap::find` prefers when the browser has the focus and skips otherwise, so ⌘[ stays the previous pane elsewhere, ⇧⌘[ still switches tabs, and the ⌘/ dialog lists them. **A key's release goes where its press went** (`Typing::claim_down`, `claimed_up`): the window remembers the keys whose press it kept and drops only their release, rather than asking again with the modifiers held at release. Asked again, Ctrl+T pressed for the page and released after Shift read as the window's Ctrl+Shift+T, so Chrome kept a key down that never came up, and a Ctrl+Shift+T released after Shift sent the page a release with no press (found in review, 2026-11-04).
- **The clipboard is the window's, not Chrome's**: headless Chrome keeps a clipboard of its own in memory. ⌘C and ⌘X (Copy, and Cut in the Browser group) read the selection through the page script (`selected`: a field's selected text, else the document's selection, through same-origin frames, never a password field's) and write it with gpui; ⌘X then deletes it with `execCommand('delete')`, so the page sees its `input` and undo works. ⌘V types the clipboard's text with `Input.insertText`. The page sees no `copy`, `cut` or `paste` event. Rejected: ⌘C with Chrome's `copy` command (it fills the headless clipboard, which the window cannot read).
- **`<select>` menus are drawn by the window**: Chrome draws a select's popup in a widget of its own, which the screencast does not show. The page script cancels the press on a single-choice select (and Space, ↑ and ↓ on a focused one, which open it on a Mac), focuses it and sends its options, their groups, the chosen one and its rectangle (`select`). The window draws the context menu's card under it: groups as headers, disabled options faint, the chosen one ticked, the highlight starting on it. A click or ↩ chooses: `choose(i)` runs in the frame that asked (the binding call's execution context), sets the index and fires `input` and `change`. ↑ ↓ move (skipping disabled options), a letter jumps to the next option starting with it, and Escape, Tab or a click elsewhere closes it; that click does not reach the page, as on a Mac. A multiple select, or one with a `size`, is drawn in the page and needs none.
- **Limits**: gpui 0.2.2's `Keystroke` has no physical key code, so `code` and `windowsVirtualKeyCode` come from the character as on a US keyboard (a key the US layout lacks, such as `ñ`, has none), and a key the input method composes sends no keydown (Chrome sends `Process`, 229). gpui's macOS view hears no drag with the right or the middle button (`design/terminal.md`), so those reach the page as a press and a release only. Cross-origin frames run in processes the panel does not attach, so their caret and selection are not known. Files dropped on the viewport are not handed to the page (`Input.dispatchDragEvent`): not done yet.
- **Checked live** on 2026-10-31 (Chrome 156.0.8078.79 headless, cornercase 0.12.234, a Spanish ISO keyboard), events posted to the window and read back from a test page: typing into a field and a textarea (keydown, keypress, beforeinput, keyup for each key, nothing typed twice), ⇧A, ⌥2 typing `@`, the dead key ´ then e composing `é` (compositionupdate, compositionend), ←, ⌥←, ⌫, Enter submitting a form and breaking a line in a textarea, ⌘A, a click, a double click (dblclick) and a triple click selecting the line, a drag selecting text, a right click (contextmenu), the wheel both ways, Escape reaching the page with the dock left open, ⌘L focusing the address, ⌘R reloading, and the select menu (drawn under the select with its groups, disabled option and tick; ↓ skipping the disabled option, ↩ choosing and firing `change`; Escape and a click beside it closing it with nothing reaching the page). macOS dropped the first synthetic wheel event of each burst before gpui saw it (the test tool's events, not the panel's). Not checked live: ⌘C, ⌘X and ⌘V (they would touch the user's clipboard; the page side was read in unit tests), ⌘[ and ⌘] (a Spanish keyboard has no [ key without ⌥, so gpui never sees ⌘[; the window's ⌘[ for panes has the same limit), the input method window's place at the caret (no Japanese or Chinese input source here), and a select in a frame.

## Toolbar, tabs and devices

Code: `toolbar.rs`, `tab_bar.rs`, `devices.rs`, `device_menu.rs`, `states.rs`; the dock's width in `app.rs`

- **The tab bar sits above the toolbar, as in Chrome**, since the address belongs to the tab shown, and **only with two tabs or more**: with one, a strip under the dock's own header would spend 40 px of height on nothing to choose. The new-tab button is in the toolbar for that reason, always in one place. Tabs share the strip, up to 220 px each, and shrink to their globe (44 px) before the strip scrolls; the shown tab keeps 120 px so its title stays readable, and the strip scrolls to it when it changes (`Strip`, once per change, so a scroll by hand is not undone by the next frame). A tab reads its title, else its address without `http(s)://` and the last `/`; a blank one is "New tab". Its close button shows on hover, always on the shown tab; a middle click closes it, as in every browser. The shown tab is the lighter rounded fill of the window's own tabs; a loading tab turns its globe into a spinner.
- **Titles are asked for when a page has loaded** (`Target.getTargetInfo` on `Page.loadEventFired`, and once after attaching to a page already loaded): Chrome 156 sends `Target.targetInfoChanged` for a title only sometimes. A probe on the same browser saw the change while the panel's connection did not, for the same target, so tabs kept their address as title.
- **A page already loaded when the panel attaches is not left loading** (`check_loading`, `document.readyState` after attaching): its load events came before `Page.enable`, so `loading` stayed true, with the stop button and the loading bar for good, after every restart or `/json/new`.
- **The toolbar**: back, forward, reload (stop while the shown tab loads, `Page.stopLoading`), the address, then a group of tools and the new-tab button. A button with nothing to do is drawn faint and takes no clicks, rather than hovering like a live one. The address shows the full URL; a click into it (or ⌘L, through its focus) selects it all, as browsers do, escape puts back the page's address, and leaving the field drops the selection (`TextField` draws one even unfocused, so the whole address stayed highlighted). The press that focuses the field is noted in the capture phase and the selection made on release, since the field places its caret on press and any jitter while held would otherwise shrink the selection. "Open in the system browser" (`cx.open_url`, for `http`, `https` and `file` pages) sits inside the address's box: it concerns that address, and a dock 420 px wide has no room for one more button.
- **The tools group** (`Browser::tools`) holds the device button; the console, picker, screenshot and agent buttons join it there, between the address and the new-tab button.
- **A thin loading bar** sweeps along the toolbar's bottom edge while the shown tab loads: CDP gives no progress, so it does not pretend to fill; it moves only while loading.
- **Devices** (`devices.rs`): Responsive, the default, fills the panel at the display's scale; the presets are iPhone 15 (393×852 at 3×), Pixel 8 (412×915 at 2.625×), iPad Air (820×1180 at 2×), Laptop (1280×800 at 2×) and Desktop (1440×900 at 2×). A preset sets `Emulation.setDeviceMetricsOverride` with its size, density, `mobile` (phones and tablets), a screen of its size and an orientation (portrait or landscape by its shape, 90° when rotated); phones and tablets also get `setTouchEmulationEnabled` (5 points) and `setEmitTouchEventsForMouse`, and their own user agent built from the browser's version: `CriOS/<version>` on an iPhone or iPad (what Chrome on iOS sends), `Chrome/<version> Mobile` on Android. A Safari agent was rejected: the page is drawn by Blink, and CriOS keeps the real version. Laptop and Desktop keep the desktop agent.
- **The device lives in `View`**, so `metrics()`, `device_pixels()`, `size_page`, `start_cast`, `apply_size` and every new tab follow it; `size_page` also sends the touch and agent emulation, which `set_up` sent before. A measure of the panel replaces only the panel's size, never the device.
- **A screencast is never bigger than what the panel shows**: frames are the device's CSS size times the smaller of its density and the display's scale times the share it is shrunk to (`frame_pixels`). An iPhone at 3× in a 600 px tall panel is sent at about 554×1200, not 1179×2556; sending more would only be thrown away when `fit` draws it.
- **Picking a device whose agent differs reloads the page**, since servers and scripts read the agent and touch support when the page loads; switching between two iPhones or rotating does not. Other tabs take the device when they are shown, and its agent on their next load.
- **The device menu is a popover under the device button** (the presets with their icon and size, Responsive with the panel's size, the current one checked); a device bar under the toolbar, only while a preset is on, gives its name, size, density, rotate and the way back to Responsive. While the menu is open, a transparent layer over the panel takes the presses that close it: the menu's own "press outside" runs before the button's press, so without it a press on the button closed the menu and opened it again. Presses outside the panel close it too.
- **Starting and failed**: the start says what it waits for; a failure shows its reason and "Try again". When no browser is found (`chrome::NO_CHROME`) it says how to fix it: install Chrome, Chromium, Edge or Brave, or set `CORNERCASE_GPUI_CHROME` (before starting, since a running app cannot read a new variable); installing one and pressing "Try again" is enough.
- **The Browser dock has its own width** (`DockWidths::browser`): it opens on half the window, between the other panels' 428 px and 720 px, and can be dragged to anything that leaves the terminal `TERMINAL_KEEP` (no 1,208 px cap). A fixed 720 px was rejected because it would squeeze the terminal in a small window. The other three panels keep sharing one width, and both are kept across a switch of server.
- **Rejected for now**: page zoom (`Emulation.setPageScaleFactor` is a pinch zoom, which changes what a pointer position means for the input code); a frame drawn around the device (the page's own edge shows it on most pages, and `viewport.rs` paints the frame); `userAgentMetadata` with the agent (without it, `navigator.userAgentData` and client hints keep the desktop's, as with the core's own override).
- **Limits**: touch emulation turns the mouse events Chrome receives into touches; with the input from `Input.dispatchMouseEvent` that was not checked on this branch, which has no input yet. A page loaded before a device was picked keeps `ontouchstart` absent until it reloads.
- **Checked live on 2026-10-31** (debug build, Chrome 156.0.8078.79 headless, cornercase 0.12.234, macOS 26.6, a 1280×800 window on a Retina display, a test page printing its viewport, density, screen, orientation, touch and agent): the dock opened at 640 px; the tab bar with 2, 4 and 18 tabs (titles, the shown tab kept in view, globes only when narrow); a click on a tab, a middle click closing one, the new-tab button (a "New tab", the address focused and empty); the address selected whole on click and cleared on leaving; stop and the loading bar on a page that answers after 6 s; the device menu opened by a click and iPhone 15 picked (393×852 at 3×, portrait, 5 touch points, `pointer: coarse`, `ontouchstart` after the reload, the CriOS agent), rotated (852×393, landscape 90°, shrunk to the panel's width) and back to Responsive; the failed state with `CORNERCASE_GPUI_CHROME` pointing nowhere. The starting state passed too quickly to see.

## Console, network and page dialogs

Code: `console.rs` (the log and how CDP events read), `console/objects.rs` (a console call's arguments), `console_view.rs` (the drawer), `prompts.rs` (JavaScript dialogs), `chooser.rs`, `downloads.rs`, `notices.rs` (routing, crashes, popups' openers).

- **One log per tab, its latest 500 entries**, from what DevTools' console shows: console calls (`Runtime.consoleAPICalled`, their arguments read from the previews Chrome sends, with `%s %d %i %f %o %O %c` filled in), uncaught exceptions and rejections (`Runtime.exceptionThrown`, with `url:line:col` and the stack, lines counted from 1), the browser's own messages (`Log.entryAdded`: CSP, mixed content, interventions; verbose ones dropped), responses of 400 and more (with the method seen in `Network.requestWillBeSent`) and loads that failed (`Network.loadingFailed`, not the cancelled ones, naming a CORS error). The same message twice in a row is counted (×3), as DevTools does. The toolbar's count is the errors kept.
- **A request is reported once**: Chrome also logs "Failed to load resource" through `Log` for every failed request, so a `Log` entry whose `networkRequestId` was already reported is dropped. One that was not is kept: `Log.enable` replays what came before the panel attached and `Network.enable` does not, so a page loaded before attaching still shows its 404s (without the method). A missing `favicon.ico` is left out: headless Chrome asks for it on every page, and it says nothing about the app. `data:` URLs are cut to their type.
- **A new document in the main frame clears the log** (DevTools without "Preserve log"): a `Document` request whose request id is its loader id in the main frame (whose id is the target's, checked), or a main-frame `frameNavigated` with a loader id not seen yet (a page restored from the back-forward cache, `about:blank`). Chrome's error page commits with the failed navigation's loader id, so "connection refused" stays (checked). What the old page logs between the request and the new commit lands in the new log; it was judged too rare to track.

## Agents

Code: `agent.rs` (which agent, handing over), `picker.rs`, `element.rs` and `card.rs` (picking an element), `shots.rs`, `watch.rs` (reloading), `follow.rs` (an agent's tabs), `agent_tools.rs` (the toolbar's buttons and menus), the picker's part of `page.js`.

- **Which agent**: the agents of the workspace on screen (`Workspace::agent_rows`, named by program and conversation title, else the tab's name). The one chosen in the picked card's chooser or the agents menu is remembered per workspace for the session; without a choice, the shown tab's agent, else the workspace's first (`agent_pane`). `Browser::target_agent` is what the console's "send errors" uses too. A workspace with no agent says so where the hand-off would be, with "Start an agent" (`dialogs::start_agent`).
- **Nothing is pasted into an agent that would take it as an answer**: before any hand-off the session is read, and an agent `waiting` (a question or a permission prompt), showing a `dialog` or `resuming` gets a toast instead, since `paste-file` and an `input` paste go in whatever the program shows (as `send` refuses for the same reasons).
- **Picking an element** is Chrome's own inspect mode (`Overlay.setInspectMode searchForNode`, cobalt boxes, `showInfo` and `showStyles` for DevTools' tooltip), so the highlight follows the pointer inside the page at the page's speed and is drawn into the screencast; drawing our own box from `DOM.getNodeForLocation` on every move was rejected (a round trip per move, and frames lag the pointer). `DOM.enable` and `Overlay.enable` are sent when a pick starts, not for every tab. One click picks (`Overlay.inspectNodeRequested`), then inspect mode ends; the button again, the banner's Cancel, `Overlay.inspectModeCanceled`, switching tabs, or `cancel_pick` (the window's Escape) cancel. `DOM.resolveNode` and `Runtime.callFunctionOn` run `page.js`'s `describe` on the element, in its own frame.
- **What `describe` reads**: a selector that is unique in the element's document or shadow root (a test id or a stable id first, then tag, up to two plain classes and `nth-of-type`, from the element up until it matches one element; generated class names such as `css-1x2y3` and Tailwind variants are skipped), text and outerHTML trimmed (200 and 1,500 characters), key attributes, a few computed styles, the rectangle in the top page's coordinates (through same-origin frames) with the page's scroll, and the component that rendered it when a dev build exposes it: React's fiber (`__reactFiber$…`: component names up the tree, `_debugSource` file:line of the JSX, or for React 19, which dropped it, the first frame of `_debugStack` outside React, marked "near" since bundlers move lines), Vue 3's `__vueParentComponent` (`type.__file`, names) or Vue 2's `__vue__`, Svelte's `__svelte_meta.loc` (0-based, so one is added, as Svelte's inspector does). Up to 12 ancestors are tried. Production builds expose none of it, and say nothing.
- **The crop** is `Page.captureScreenshot` of the element's box padded by 8 px and kept within 2,000 CSS px a side, at the page's device scale, written as a PNG under `std::env::temp_dir()/cornercase-gpui/` (files over a day old are swept on each new one; `paste-file` copies it to the server, so it is not needed long). `captureBeyondViewport` is asked only when the box leaves the viewport: Chrome then lays the page out at its full height for the capture, which a responsive page can notice. A hidden or empty element has no crop and is handed over without one.
- **The picked card** sits over the bottom of the viewport: the tag and selector, the component and its file:line (else the text), "What should change?" (a `wraps()` field, focused after a pick; Escape there closes the card, as dialog fields do) and **Send to agent**. The description is a few labelled lines (page, element, component, text, attributes, styles and size, HTML), at most 4,000 characters, so it reads in a prompt and in a review. With no instruction, the crop and the description are pasted and nothing is submitted: the user finishes in the agent. With one, it goes after the description and is submitted with `send --pane P --enter -- TEXT` rather than an `{"key":{"code":"enter"}}` input: `send --enter` presses Enter once the agent's screen settles and confirms the prompt reached its history, where an Enter right after a paste can be taken into the paste. `send` waits, so it runs beside the queue as a job ("Sending to the agent…"); the crop's `paste-file` goes through the queue first and `send` starts when it answers, so the image always comes before the text.
- **Screenshots** (the camera): the visible area, or the full page (`Page.getLayoutMetrics`' CSS content size, at most 20,000 px tall, scaled so no side passes 16,000 device pixels, which is about what Chrome can draw), with a one-line caption (URL, which, size in pixels from the PNG's header). The button turns while it runs and the status bar names the job. Checked live that a clip's `scale` multiplies the device scale, and that a capture beyond the viewport leaves the page's size as it was; but the screencast's last frame is then the page at its full height, drawn squeezed into the viewport until something repaints (seen live), so the screencast is restarted after such a capture, which sends a fresh frame.
- **Reload when an agent finishes** (on by default, in the agents menu): from every Store change, the agents `working` before and not now (`waiting`, `done`, `idle`, `failed`: the turn is over) are found by comparing two snapshots, and their workspace's `http(s)` tabs reload 1.5 s later, unless that agent went back to work meanwhile (a blip between tool calls) or a pick is under way. Finishes in one workspace within that time reload once. A closed agent is no finish. "Reloaded: claude finished" (the agent's program) shows for 2.5 s in a small card at the top right of the viewport (beside the agents button it covered the address in a 420 px panel, seen live). Agents' own tabs (below) are not reloaded: the agent drives them.
- **Agents drive this browser**: the agents menu shows the DevTools address (`agent_endpoint`, the remote side's when the window shows another machine) and **Tell <agent> about it**, which pastes one line into its prompt, without Enter, naming `chrome-devtools-mcp --browser-url=…` and Playwright's `connectOverCDP`, and that the user sees its tabs here. A tab nobody here opened (not claimed by the panel, not opened by a workspace's page) is an agent's: it is marked with the agent icon in the tab strip and, when it opens or moves to another address (not a reload or an anchor), the panel switches to it unless the user is at the panel (the viewport, the address or the card's field focused, a menu open, a pick under way), or "Show the tabs agents open" is off. Tabs found in the first 2 s after connecting are not followed: they were there before. A tab stays an agent's only while it has no workspace: Chrome announces a tab the panel opened (`Target.targetCreated`) before it answers `Target.createTarget`, so the panel's claim can come after the tab was taken for an agent's (seen live: the workspace's own tab was marked).
- **Checked live on 2026-10-31** (Chrome 156.0.8078.79 headless, cornercase 0.12.234, gpui 0.2.2), on a throwaway project whose "agent" was a pane running `cat > /dev/null`, marked as `claude` by a `CORNERCASE_BIN` wrapper that rewrites `view`'s lines (its status read from a file, to fake a turn), and a test page with a hand-made React fiber: an agent's tab opened with `/json/new` was followed and marked, the workspace's own tab not (after the fix above); a pick showed Chrome's highlight and tooltip, the banner, then the card (`[data-testid="sign-in"]`, `LoginButton`, its file:line); Send pasted the crop (the button, padded) and the description; both screenshots arrived with their captions (836×1200 and 836×5360 px at 2×); Tell pasted its note; a faked working → idle reloaded the workspace's tab only, with the note. The pointer during the pick was played over CDP (`Input.dispatchMouseEvent`), as this branch does not forward the pointer; inspect mode takes those events like real ones. `send -- TEXT` was checked from the command line without `--enter`. Not checked live: submitting with an instruction (Enter is never pressed in checks), Escape (wired by the window), the chooser with two agents, Vue and Svelte pages, a production build.
- **Limits**: a second window sharing the profile's Chrome sees the first one's tabs as an agent's (nothing in a target tells who created it). Picking inside a cross-origin iframe picks the iframe, since only the top page's session runs inspect mode. Selectors do not cross shadow roots. "At the panel" is read from focus, not from recent input, so a viewport left focused keeps the panel from following until the focus moves.

## Ports and remote servers

Code: `ports.rs`, `start_page.rs`, `held.rs`, `tunnels.rs`, `tunnels/ssh.rs`, `agent.rs` (`agent_endpoint`); outside the panel, `model/tunnels.rs`, `store/tunnels.rs`, `cli/holds.rs`, `cli/kept.rs`

- **The workspace's dev servers come from `ports --json`**, the only source: while the panel is shown, `ports --json --workspace W` for the workspace on screen every 2 s, beside the queue (`poll::Watch`, which follows a docked panel as it follows a sheet; the serde types are the Ports sheet's, `panels/ports/data.rs`). Only ports with a `url` count (cornercase gives one when the program listens on every address or on 127.0.0.1), once per number, lowest first. A change of the workspace on screen drops the list at once and samples again. Nothing guesses from a pane's output or runs `lsof` here.
- **The start page** takes the place of "nothing open" while the workspace has no tab: the address hint, then its dev servers as cards (the URL, the command line, the pane or agent that started it, and "via HOST" for a tunnelled one), a click opening one. A spinner while the first sample comes; with nothing listening it says so, and that the dev server shows there and opens once started.
- **A port opens on its own, once**: when one appears in the workspace on screen while it has no tab and no open on its way, the lowest new one opens. Every port listed is remembered for its workspace whether it opened or not, so a tab the user closed never comes back, a server restarted on the same port does not open again, and a frontend and its API appearing together open one tab. The memory lasts as long as the panel. Rejected: opening every new port (the API's JSON would land in front of the app), and opening even when the workspace already has a tab (it would take the panel from what the user is looking at).
- **The Ports sheet's Open shows the port here** (`Store::open_in_browser` sets `Store::browse`, which the panel takes and clears in `store_changed`; `design/ports.md`), and so does a click on a web address in the terminal when Settings › Links says so (`design/terminal.md`): the sheet closes, the dock shows the panel, and the URL opens in the workspace on screen, or that workspace's tab already on that page comes forward (`ports::same_page`). An address without a path, what a port gives, counts as shown by any page of its origin, so the app comes back wherever it was; an address with one only by a tab at that exact address, so a link to a pull request opens it rather than bringing back another page of GitHub. A URL asked for before Chrome is ready waits with the tabs to restore.
- **The terminal's card previews pages with this Chrome** (`preview.rs`, `design/terminal.md`): in a browser context of its own, cookieless and with downloads denied, whose pages the panel never adopts as tabs. Chrome restarting drops that context, and the next preview makes another.
- **Another machine's ports open through a tunnel, by one of two ways** (`model::tunnels::Way`, #106): when the window shows another machine (`cli::host()`), a port's `localhost` is that machine's. From cornercase 0.13.50 on **both** this computer and the server there (`TUNNEL_HOLD_SINCE`), the tunnel is cornercase's own (`Way::Cornercase`, below); below that on either side, it is the panel's own ssh (`Way::Own`, the bullets after it); until this computer's release is read and the first view line is in, `Waiting`: nothing starts and an open waits. Both sides, because `tunnel hold` is parsed and run by this computer's command line, and registers with a `tunnel-hold` request the server there refuses by name when it is older (a server left running across an update can be older than the binary beside it, which `--remote` checks). The local server plays no part. One way at a time: when the way turns to cornercase's, the panel's own forwards stop before the first hold starts (`keep_tunnels` wants nothing outside `Own`), so no port is forwarded twice, and what the window shows (the status bar's count, the machine's menu, a row's mark) is what `cornercase tunnels` lists.
  - **cornercase's way is one `cornercase --remote D tunnel hold PORT` child per tunnel** (`cli/holds.rs`, kept by `cli/kept.rs`), made with `Target::command` so the remote flags and `platform::command` come as for every command. It prints one line once ssh is up and the hold is registered, `{"port":5173,"local":5174,"url":"http://localhost:5174"}`; the local port is the same number when it is free here, else another one, and the window says which. The hold's lifetime is the tunnel's: exit 0 when it is closed or forgotten (by a script, by another window, by this one) or the server stops; exit 1 with ssh's line on stderr when ssh fails before or after it was up, and nothing retries it (the program that holds decides). So a failure before it was up is a toast with that line (`Could not tunnel port 5173: ssh: …`), one after it was up shows `down` in the row and the menu and is tried again with `cli::backoff`, silently, while the window is linked, and an exit 0 nobody here asked for is told by a view line's `boot` (a hold also exits 0 when its server stops or restarts): the same boot is a close or forget there (the port leaves the window's memory), a new one the server's restart (hold it again). A view line can arrive before the hold's exit is read, so a 3 s timer decides too, but only while the window is linked: after a lost connection the old view line says nothing about the server, so the decision waits for the next one.
  - **A hold ends with SIGTERM on Unix, never `Child::kill`** (seen on 0.13.50 on 2026-11-12): a hold killed with SIGKILL leaves its ssh running and listening, an orphan, while the server forgets the hold. On Windows there is no SIGTERM, so `Child::kill` ends the hold, and the Job object it was put in (`KILL_ON_JOB_CLOSE`, dropped without `let_go`: `End::TakeAlong` in `cli/kept.rs`) ends the `ssh.exe` it started, which sits in that job since a child starts in its parent's jobs (`design/plugins.md`); `plugin windows` lets go of its job instead (`End::LetGo`). A hold whose job could not be made is ended at once and reported (the toast says why), since ending it later would leave its ssh listening. A Try again on a down tunnel starts a new hold as a click does: its job shows in the status bar when it lasts, and a failure is the usual error toast with cornercase's line (which may name the connection rather than the port, as `Could not reach cornercase on …`); a quiet retry is only the automatic one. A failed `tunnel close` puts the tunnel back and keeps it remembered: the port leaves the window's list only once `close` or `forget` answered. Holds are not in `cli`'s list of children, so `kill_all` and a `Stream`'s drop never reach them; `main.rs`'s `leave` (quit and relaunch) and `Root::switch` end them. A window killed with SIGKILL ends them through their stdout reader (a hold exits when it cannot write its line), which the manual check shows.
  - **Tunnels are explicit**: from 0.13.50 the window tunnels the ports a person opens or asks for (Tunnel on a Ports row, Open there or in the Browser, a card, a typed workspace port, one remembered), not every web port of the workspace as the older way does. Rejected: tunnelling every port as before. Upstream refuses it too (#735's alternatives), and with remembering every port of every dev server would come back at each connection. A page that calls its API on another port needs that port tunnelled too, from its row. An open waits for its hold (`held.rs`: `HeldOpen`, asked once per open, dropped when the hold fails or is closed, handed to the older way if the way turns `Own`); a typed address goes through a hold only when the workspace lists its port or the window holds it (any other stays on this Mac, which was true below 0.13.50 too, since only listed ports had a tunnel); **a preview never starts a tunnel**, since hovering would start one for every address it passed: it loads through a tunnel that is up, waits for one that is opening, and otherwise says `Port 5173 on devbox is not tunnelled to this Mac: open it to tunnel it.`.
  - **Remembered by the window, not by cornercase**: `remembered-tunnels.json` beside `settings.json` (`store/tunnels/memory.rs`), the ports last held per destination, at most 64, brought back at each link to it (the first view line of a connection or a new `boot`), silently, also after the window is restarted; a port the person closed or forgot leaves it. cornercase's `tunnels.json` is a TUI window's own: a hold is told to remember nothing (`tunnel --help`), so a program decides, and this window never reads or writes cornercase's file. Rejected: sharing it (it would need an upstream change #766 declined on purpose). It keeps ports only: `tunnel hold` takes no local port to prefer (filed as part of the follow-up below), so a remembered tunnel may land on another local port after a reconnect and a tab on the old one shows connection refused until reopened.
  - **Limits**: two windows of this app on one destination each hold their own tunnels; a TUI window and this one on one computer forward a port twice; a program on that machine cannot ask this window for a tunnel (`tunnel open` is refused: "no window holds tunnels for this server"), which waits on usecornercase/cornercase-terminal#776 and is named in the machine's menu; a machine linked by the server (the Machines sheet) has no tunnels here (`design/machines.md`).
  - **Leaving**: `Root::switch` also calls `browser::left_server`, which ends the panel's own forwards and reverse tunnel and drops what waits on a tunnel, so nothing to the server left behind lives on under the next one's port numbers (the old ssh forwards used to live until a sample). The Browser panel is a global and observed the `Store` of its time, so after ⇧⌘K it never heard the new one (ports, Open from the sheet and held opens all stopped): `Store::publish` now tells it (`browser::follow_store`), which observes the new `Store` and forgets the old server's workspace, ports and what it had opened (`left_server` forgets the same on the way out, and closes the tabs of the left server's workspaces: a tab is keyed by a workspace id, which means nothing on the next server and would show under whichever workspace there has the same number; found on the bench 2026-11-12, where the tunnelled page of a left machine showed on this Mac's workspace). Leaving this Mac for a server closes none: those tabs are this Mac's own.
  - **The panel's own ssh (`Way::Own`)**: each of the workspace's web ports gets `ssh -N -L 127.0.0.1:LOCAL:localhost:PORT DESTINATION`, all of them and not only the one opened, so a page on 3000 calling its API on `localhost:8000` keeps working. LOCAL is the same number when it is free here (nothing answers on 127.0.0.1 or ::1 and it can be bound), else one the system picks; the URL is rewritten to `localhost:LOCAL`, keeping `localhost` so the origin, its cookies and the dev server's host check stay as they are there when the number is kept. An address typed while remote whose port has a tunnel goes through it; any other stays on this Mac. Ports and the start page say what 0.13.50 adds (`older_note`). Kept only for older cornercase, and removed with the window's minimum (`design/upstream-gaps.md`, "To remove once these land").
    - **A tunnel is a process, so it shows that it runs**: it is ready when its local port takes a connection; until then a URL waits for it, its card says "Tunnelling…" and the status bar names the job (`Opening a tunnel to port 3000 on devbox…`, the same words cornercase's way uses).
    - **A tunnel that dies** (the link dropped, the Mac slept) starts again after 1, 2, 4, 8, then every 15 s (`cli::backoff`), on the same local port when it can, so open tabs work again after a reload. The first failure in a row is a toast with ssh's last line, as is any failure that drops an open waiting on it.
    - **A tunnel lives** while its port is listed, an open waits on it, or a tab (or a tab to restore) uses its local port; the others stop at the next sample. All stop when the panel goes, on quit (`browser::quit`, which `main.rs` calls) and when the window connects elsewhere (`left_server`).
    - **Its ssh**: the user's config applies (keys, agent, jump hosts); `BatchMode=yes`, since there is no terminal to ask; `ExitOnForwardFailure=yes`, so a port that cannot be bound ends ssh instead of leaving a tunnel that forwards nothing; `ServerAliveInterval=5` with `ServerAliveCountMax=3`, so a dead link ends it and it restarts; `ConnectTimeout=10`, `-N -T`, `RemoteCommand=none`; `LogLevel=ERROR`, so its last line is the error; and `ControlMaster=no` with `ControlPath=none`: through a user's master a forward lives in the master, so stopping our ssh would not release it, and a tunnel that became the master would cut the user's other sessions when stopped. Each tunnel is one connection of its own. Windows' OpenSSH gets the same options (under Windows).
    - Rejected: one ssh for every forward (adding a port would restart it and break the tabs on the others), `ssh -O forward` (needs the user's master), and asking for the tunnel to be set up by hand (the sheet's old note).
    - Limits: a host whose config sets `LocalForward` tries it on every tunnel, and with `ExitOnForwardFailure` one already bound here fails them all (`ClearAllForwardings` would clear ours too). A port that listens there only on another address is tunnelled to `localhost` and fails.
- **Agents on the other machine reach this browser through a reverse tunnel, which stays the window's own** (cornercase has no command for a reverse tunnel, so no hold can carry it, and it is the exception the README names): Chrome always runs on this Mac, so `127.0.0.1:9222` there is not it. The first time `agent_endpoint` is asked while remote, `ssh -N -R 127.0.0.1:PORT:127.0.0.1:CHROME DESTINATION` starts (same options), trying 9222 (what `chrome-devtools-mcp --browser-url` and Playwright examples use) then 9223, 9224, 9225 and 9229, and the endpoint is `http://127.0.0.1:PORT` as seen there; it answers `None` while it starts. It counts as ready when Chrome's `/json/version` answers through a `-L` the same ssh opens to that port there: the check goes through the forward itself, and since sshd answers the `-R` request before it opens the check's channel, a port already taken there ends ssh (`ExitOnForwardFailure`) before the check could reach whatever holds it. Chrome builds its WebSocket URL from the `Host` header, so agents there get `ws://127.0.0.1:PORT/…`. It stays until quit, a switch to another server, or a new Chrome port; a failure is a toast, and it is tried again on the next ask 30 s later.
  - **Security**: while it is open, anyone who can connect to that machine's loopback (every user and process there) can drive this browser: read its pages, run scripts in them, use the logins it holds. That is why it uses the panel's own profile, which holds only dev logins and never the everyday one, opens only once an agent's endpoint is asked for, and closes with the window.

The Ports sheet's Open closed the sheet and opened the port in a new tab. Through `--remote` to an sshd run as the user on 127.0.0.1 with throwaway keys, and an isolated server (`env HOME=<short folder> cornercase`), so every port there was already taken here: both of the workspace's ports were tunnelled to other local ports and the lower opened through its tunnel; the start page said "via testbox, port 8790 there"; killing a tunnel's ssh gave the toast and it came back a second later on the same local port; a stopped server's tunnel stopped while the one a tab used stayed; `8791` typed in the address went through its tunnel; the sheet's Open on a new port opened it through a new tunnel. The reverse tunnel, asked through a debug build that logged `agent_endpoint`: 9222 was taken there (ssh: "remote port forwarding failed for listen port 9222"), 9223 answered, and `/json/version` through it named `ws://127.0.0.1:9223/…`. Not checked: quitting (the checks stop the app with `kill`, which skips the quit hook, so its ssh were stopped by hand), another machine or a Linux host, a host whose config sets `ControlMaster` or `LocalForward`, a dev server's WebSocket (hot reload) through a tunnel.

## Windows

Code: `chrome.rs` (`candidates`, `path_names`, `own_flags`, `browser_pid`, `ask_to_stop`), `win32.rs` (the Win32 calls, Windows only), `keyboard.rs` (`alt_gr`, `route`), `typing.rs` (`window_claims`), `downloads.rs`, `states.rs`, `tunnels/ssh.rs`

Decided 2026-11-04. Checked by cross-compiling (`cargo xwin clippy` and `cargo xwin test --no-run` for `x86_64-pc-windows-msvc`), by unit tests on macOS, which run each decision for `Os::Windows`, and by CI's Windows job, which runs `win32/tests.rs` too. **On the Windows runner** (2026-11-04, Windows Server 2025, Google Chrome installed there, `design/windows.md`): Ctrl+Alt+Shift+B opened the panel, which found Chrome, started it headless (ten `chrome.exe` processes) and drew the start page with its dev-servers note; Alt+F4 quit the window and no `chrome.exe` was left a few seconds later.

- **Where the browser is**: each of Google Chrome, Chromium, Brave, Chrome Beta, Dev and Canary (`Google\Chrome SxS`), then Microsoft Edge, under `%ProgramFiles%`, `%ProgramFiles(x86)%` and `%LOCALAPPDATA%` (the folders Playwright and Puppeteer look in, read from the environment), then the `.exe` names on the `PATH` (`desktop::on_path` joins the name as given). A browser is looked for in its three folders before the next one, so a Chrome installed for the user alone beats an Edge installed for the machine. **Edge comes last** because Windows 10 and 11 install it everywhere: it makes the panel work out of the box, but a Chromium the user installed is the one they chose; on macOS and Linux Edge is such a choice and keeps its place before Brave. Rejected: the registry's App Paths, which would find a browser installed elsewhere but needs a registry reader for what `CORNERCASE_GPUI_CHROME` already covers. The snap check reads the browser's first bytes only on Linux.
- **None found** (Edge can be removed in the EEA since 2024): the help names Chrome, Edge and Brave and shows `setx CORNERCASE_GPUI_CHROME "…\chrome.exe"`, since `setx` keeps the variable for the next start, the only moment the app reads it.
- **The profile** is `%LOCALAPPDATA%\cornercase-gpui\browser`, the app's data folder (`prefs::app_dir`). **Who runs it**: there is no `SingletonLock` on Windows. Chrome's process singleton there holds `lockfile` in the profile and creates a message-only window of class `Chrome_MessageWindow` named after the user data folder (Chromium's `process_singleton_win.cc`, `base/win/message_window.cc`), by which a second Chrome finds the first (`chrome_process_finder.cc`). The panel asks the same way, `FindWindowExW(HWND_MESSAGE, …)` with the profile made whole and without a trailing separator, as Chrome makes it, and the window's process is the browser's pid. Edge and Brave keep Chromium's `base`, so their window should have the same class (not checked). `lockfile` holds no pid, and `DevToolsActivePort` is written only with port 0, as elsewhere. Rejected: opening `lockfile` for writing to see whether it is held (it tells that a Chrome holds it, not which, and such an open could make a Chrome starting at that moment fail to take it).
- **A launch waits for the port, not for the pid**: the window that started Chrome attaches as soon as the port answers while its child runs (`answering`); the pid check is for a Chrome another window started or left (`running`). On macOS and Linux this changes nothing (the lock is made before the port opens); on Windows a singleton window not found would cost a second window its attach, not the first its browser.
- **Alive** (`win32::alive`): `OpenProcess` with limited query rights and `GetExitCodeProcess` against `STILL_ACTIVE`; a process it may not open (another user's, or perhaps an elevated one) counts as alive, as cornercase's `os::process::alive` does (its `design/windows/processes.md`), so a window attaches to such a browser through its port rather than start a second one on its profile, and does not adopt one whose owner it cannot open.
- **Ending it** (`ask_to_stop`): Windows has no `SIGTERM`, and the graceful end of a headless Chrome there is DevTools' `Browser.close`, which saves cookies and logins as `SIGTERM` does and ends the renderer, GPU and utility processes it started. The owner (or the window that adopted it) reads the profile's port, checks that the browser's own pid listens on it (`win32::listening_pid`, Windows' TCP table, the loopback socket first as a connection to `127.0.0.1` reaches it), sends `Browser.close` and waits up to 0.5 s for the answer, which Chrome gives before it closes; for the Chrome it launched it then waits up to 1.5 s for the exit and ends it with `TerminateProcess` (`Child::kill`), at once if it could not be asked. An adopted Chrome is only asked, as elsewhere it is only sent `SIGTERM`. Rejected: `TerminateProcess` alone (cookies Chrome had not committed, up to its 30 s interval, and logins with them, would be lost), `WM_CLOSE` (a headless Chrome has no window to close), and a Job object (Chrome's children end when its pipes close, and a job that kills on close would end the Chrome a crashed window leaves for the next one to adopt). **The port must be the browser's** (2026-11-04): with 9222 Chrome writes no `DevToolsActivePort`, so the port in `cornercase-port` is only the one asked for; if another program (a Chrome or Edge of the user's, started with `--remote-debugging-port=9222`) took it between the check that it was free and the launch, or listens on it in a way that check does not see, the panel would drive that program and quitting would close it. So on Windows a launch whose port answers for another pid fails with a toast saying so, and quitting asks only a port the browser's pid listens on. Checked with unit tests on Windows (a socket of the test's own process, and a port the pid asked for does not own); macOS and Linux end the browser by its pid and keep attaching to the port as before.
- **Launch flags**: no keychain or keyring flag (Chrome encrypts with DPAPI and asks nothing). `--enable-logging=stderr --log-level=2`: Chrome on Windows writes nothing to standard error unless asked, so the pipe stayed silent and a browser that stopped as it started gave no reason; level 2 keeps `ERROR` and `FATAL`, what `keep_errors` keeps. With a valid standard error Chrome writes there and opens no console (`RouteStdioToConsole`). No sandbox or GPU flag: both work for a normal user. The profile reaches `--user-data-dir=` as one argument with spaces and accents (std quotes it by the C runtime's rules, which Chrome's `CommandLineToArgvW` reads back); a test with a lone surrogate runs on Windows. The DevTools port and the tunnels bind 127.0.0.1 only, which Windows' firewall does not ask about.
- **Keys in the page** go as on Linux (Blink on Windows edits from the keys too), with three Windows answers:
  - **Alt+F4 closes the window**: `window_claims` counts `keymap::left_to_system`, so the key and its release skip the page and reach Windows.
  - **AltGr reported as Ctrl+Alt** (gpui's `current_modifiers` takes AltGr off only on the layouts it lists, so US-International and others give Ctrl+Alt) goes as text when its `key_char` is a printable character other than its key: AltGr+e types `é` through `WM_CHAR` instead of sending Ctrl+Alt+E. Its Ctrl and Alt stay on the event, as Chrome on Windows reports AltGr, and Blink on Windows inserts such text. On the listed layouts AltGr comes as plain text already.
  - **A held key repeats through `WM_CHAR`** rather than with its `key_char`: gpui builds `key_char` with `ToUnicode` without Caps Lock and, on the listed layouts, without AltGr, so a held key with Caps Lock would repeat in lower case and a held AltGr+2 would repeat `2`. The held key waits for its text like a first press, and the text carries `autoRepeat`. For the same reason a typed character's `key` is the character itself (`keyboard::typed`, on every platform, as Chrome names it), not gpui's `key_char`.
  - An AltGr character reported as Ctrl+Alt, Shift or not, is text and never one of the window's Ctrl+Alt+Shift shortcuts (`keymap::typed_with_alt_gr`, shared with the terminal, `design/terminal.md`, Keys on Windows). Alt+Space goes to the page, as it does to a pane: gpui 0.2.2 never turns it into the window menu.
- **Downloads** go to the Downloads known folder (`SHGetKnownFolderPath`, without checking that it exists, since the move makes it), where Chrome saves its own, so a folder the user moved (its Location tab, folder redirection) is honoured; `%USERPROFILE%\Downloads` only when that fails. A suggested name loses what Windows refuses: `<>:"/\|?*` and control characters become `_` (so `a.txt:x` cannot name a stream), trailing dots and spaces go, and a device name (`CON`, `PRN`, `AUX`, `NUL`, `COM` and `LPT` with a digit or a superscript, `CONIN$`, `CONOUT$`, in any case and with any extension) gets a leading `_`, as Chrome's `GenerateSafeFileName` does. The toast names the whole folder, since `~` means nothing there. Not handled: names over 255 characters, and an antivirus holding the finished file, which makes the move copy it and then fail to delete the staged copy (an error toast with the file already in Downloads). The file input's picker is gpui's `IFileOpenDialog`, which gives file-system paths.
- **ssh tunnels** use Windows' OpenSSH client, `ssh.exe` on the `PATH` (`%SystemRoot%\System32\OpenSSH\` since Windows 10 1809, as cornercase's `design/windows/beyond-this-machine.md` finds it), with the same argv: Win32-OpenSSH is OpenSSH's own code for `-N`, `-T`, `-L`, `-R`, `ExitOnForwardFailure`, `BatchMode`, `ServerAlive*`, `ConnectTimeout` and `LogLevel`, and `RemoteCommand` needs 7.6 where 1809 ships 7.7. `ControlMaster=no` with `ControlPath=none` matter more there: Win32-OpenSSH has no multiplexing, so a `ControlMaster auto` from a config shared with macOS or WSL would fail every tunnel, and the command line's options win over the config. A tunnel stops with `Child::kill`, `TerminateProcess`, as it is `SIGKILL` on Unix: no signal is needed, the connection drops and sshd frees the forwards; a `ProxyJump`'s child `ssh` ends when its pipes close. When ssh cannot start, the toast says Windows has it as the OpenSSH Client among Settings' Optional features.
- **Not checked**: that Chrome, Edge and Brave make the `Chrome_MessageWindow` in headless mode and a second window attaches; a page loaded and drawn, and Edge on a machine without Chrome; Chrome's errors through the pipe; AltGr on US-International, Alt+F4 with the page focused, a held key with Caps Lock; a download into a moved Downloads folder; tunnels through Windows' `ssh.exe`.
