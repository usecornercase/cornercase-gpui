# Files panel

Code: `panels/files.rs`, `panels/files/` (`source.rs` picks the disk or the command line, `served.rs` reads `cornercase files`, `there.rs` a machine's workspace, `lines.rs` what the viewer's selection does, `find.rs` the find in the open file, `gutter.rs` the git marks of the viewer's margin and `gutter_view.rs` reading and drawing them, `finder.rs` the ⇧⌘P finder, `peek.rs` and `peek/` the card of a path under the pointer)

The workspace's files: a tree, a viewer and a search. It follows the TUI's panel (cornercase's `design/files-panel.md`).

## Reading the disk

- **The panel reads the disk itself**, the one exception to going through the command line (#345 upstream, `design/upstream-gaps.md`): a file viewer through `cornercase` would copy every file through a process.
- **On another machine** (`design/remote.md`) the panel asks cornercase there, through `cornercase files` (#477 upstream): this Mac's disk at the same path would show other files, or none. See "Through the command line" below.
- **Nothing blocks the window**: listings, reads, highlighting and searches run off the main thread, and each answer is dropped when what it answers is no longer shown (another workspace, another file, a newer query).
- **Polling, not watching**: while the panel shows, the open file's size and modification time are checked every second (`CHECK_EVERY`) and the open folders are listed again every second check (`LIST_EVERY`), so what an agent writes appears. A closed panel polls nothing.
- **Git marks always come through the command line**, also on this Mac: what git says of a file is the server's to know (`design/upstream-gaps.md`), so running `git status` here would reimplement it. See "Git marks" below.

## Per workspace

- The panel follows the shown workspace and keeps, per workspace and in memory, the open folders, the open file (marked in the tree once closed) and the query. Coming back to a workspace brings its query back; a workspace whose folder changed starts afresh.
- A folder that went away closes; a root that cannot be listed shows why.
- Closing the viewer scrolls the tree to the file's row.

## The tree (`tree.rs`)

- **Each open folder is listed on its own, one level deep**, then flattened into rows. A huge folder (a home folder opened as a project) costs nothing until it is opened. At most `MAX_ENTRIES` per folder; the panel says when some were left out.
- The `ignore` rules apply (`.gitignore`, `.ignore`, the global and `.git/info/exclude` ones, also from parent folders, without needing a git repository). `.git` is never listed; hidden files are, and the eye in the tree's header hides them.
- **A row is clickable across the panel's whole width**, as in Finder and editors (asked for on 2026-10-30): gpui 0.2.2 lays a `uniform_list` item out at its content's width unless it is `w_full`, so the hover and the click stopped at the name. Search results take the whole width too.
- **The look** (asked for on 2026-10-30, the old `▸ ▪ •` glyphs read as noise): Lucide chevrons, then the icon of the file's type (`ui::file_icons`, `design/widgets.md`), the same as the TUI's; a level indents 18 px, which puts a folder's children's icons under its name. The search results and the viewer's title show the same icons. The selected row (the open file, or the menu's) is lit as rows are elsewhere (`design/widgets.md`) and does not hover.
- **The header names the root folder**, its full path in a tooltip: a long path cut off at the panel's edge said less than the name. It holds the tree's own controls as icon buttons with tooltips: hidden files (an eye, crossed out while they are hidden; a tint would have lit it all the time, since they show by default) and collapse all. They left the search bar, whose results they do not touch.
- A link to a folder opens like a folder. A folder that is gone fails as `read_dir` would rather than listing nothing.
- Opening a file from a search opens every folder above it (`reveal`), so it shows in the tree.

## Git marks (`tree.rs`, `gutter.rs`, `gutter_view.rs`)

The TUI's 0.11.5.

- **The tree's rows end in a letter**: `files list --json`'s `status` for a changed file and for a folder holding one, drawn by the Changes panel's `status_letter`, so a letter and its colour mean the same in both panels. `files list` makes a folder `A` when everything under it is new and `M` otherwise; the TUI draws a dot there, a letter says the same and lines up with the files'. A deleted file is not on disk, so only Changes lists it; the folder that held it still says `M`.
- **One read per set of open folders**: through the command line the listing itself holds the marks, so nothing more is asked. On this Mac the tree comes from the disk (a process per listing was rejected, above), so a second, separate `files list` of the same folders runs off the main thread at the listing's pace, and never more than one at a time: a server that hangs cannot pile them up or hold the tree back. Each is one `git status` for cornercase. Rejected: `changes list --follow`, whose model reads every hunk with its colours to give the same letters (cornercase's `design/commands-for-scripts-and-agents/files.md` weighed the same).
- **The margin reads `changes file --json`**, only for a file the tree marks. A file git has nothing to say about asks nothing, and cornercase answers `there is no change` to those anyway. It reads again when the file's mark changes, when the file itself was read again, and every 10 s (`CHANGES_EVERY`) while it stays marked, since a commit of only part of a file changes its hunks and neither its mark nor its bytes. Off the main thread, the older answer dropped by a generation. These are polled reads: as with the file's stamp a failure toasts nothing, it leaves no marks (a toast every two seconds would say less than the lost connection's page does).
- **What a line says** (`gutter.rs`, plain functions tested without a window, the TUI's rule): green for added lines, blue for changed ones (removed lines right before added ones), and a short red bar on the bottom edge of the line above where lines went, or on the top edge of the first line when they went above it. Blocks are kept as ranges of lines rather than a mark per line, so an untracked or added file, which is green whole, costs one block and does not need its hunks; a file of 60,000 lines has no per-line table. A file cornercase folds as too large has no hunks, so its letter shows and its margin stays blank.
- **A click on a mark with old lines shows them** above its block, tinted as Changes tints removed lines, and another click hides them. A changed line's old text is as useful as a removed one's, so a blue mark does it too, as in the TUI. They come with no number (a `−`), as they are no line of the file, and in the text colour with no syntax colours. **They belong to the line's item in the list**, whose height changes (`ListState::splice`), so a line's index stays a list's index and selection, find and scrolling need no second numbering; the TUI, which draws rows, keeps a table from rows to lines. Lines removed past the end sit under the last line. At most 200 show (`OLD_LINES_SHOWN`), with a note that Changes shows the rest: a list lays a whole item out, so a file rewritten from scratch would make one row cost as much as thousands.
- **The mark takes the press** (`selection::keep_selection`), since it lies on the numbers, where a press selects the line. An added line's mark takes nothing and selects as the number does. Old lines cannot be selected, and a press on them is a press on nothing; they are not part of the file, so find does not search them either.
- **Uncommitted only**: `files list`'s marks are, whatever mode Changes shows. Rejected: following Changes' mode and base, as the TUI does, which would give the tree a process per mode and make a closed panel's choice change what this one shows.
- **Behind `Source`** (`Source::marks`, `Source::gutter`), so a future way to read a workspace needs only those two.
- **Checked live** on 2026-11-06 (cornercase 0.13.1, Linux x86_64 under Xvfb with lavapipe, a fake ssh between two servers on one box; no real sshd, no macOS, no Windows): `M`, `A` and `U` on files and folders, from the disk and through `--remote`; a file with changed, added and removed lines, with lines removed above the first and past the last; a click on a mark showing the old lines, in both settings of Long lines and through `--remote`, and another hiding them; an edit marked within seconds, and a commit clearing the marks and the letter. Not checked: a commit of part of a file (its 10 s are a timer), a rename, a Windows server.

## The viewer (`disk.rs`, `highlight.rs`)

- **Only regular files are read**: a link to `/dev/zero` or a FIFO would never end.
- The first 16 bytes say whether a file is an image (PNG, JPEG, GIF, WebP, BMP, TIFF; SVG by extension), which may be up to 32 MB; text stops at 8 MB. The read stops one byte past the cap, so a file that grew since the size check cannot get past it.
- A NUL in the first 8,000 bytes makes a file binary. Invalid UTF-8 is replaced, not refused. Tabs are drawn as four spaces, `\r` is dropped and a final newline ends the last line rather than starting an empty one.
- **Colours never flash**: the first read shows plain text at once and the colours after; a re-read after a change answers only once coloured.
- Each line spans the panel, so the selected line's tint does too. The title gives the file's name at most 60 % of its row and the folder the rest, both cut as long names are, as Changes shows its open file. Checked live on 2026-10-31. Their boxes, the tree header's and `ellipsis` are flex containers, or the names were left 0 px wide and the title showed only the icon (`design/widgets.md`, fixed the same day).
- **Highlighting uses syntect's default grammars**, with scopes mapped to a few kinds drawn in the palette's colours as the TUI does: keyword magenta, function blue, type cyan, string green, number and constant yellow, property and tag red, comment grey in italics. The grammar is found by file name (`Makefile`), then extension, then first line (a shebang); extensions the default set lacks borrow a close relative (TypeScript as JavaScript, TOML as INI, Swift and Kotlin as Java, Vue and Svelte as HTML). Lines are parsed in order so the state carries across them (block comments, strings); a grammar that fails leaves the rest plain.
- Sources over 1 MB stay plain: syntect's pure-Rust regexes are slow on big files.
- **One list per open file** (`Viewer::list`), so each workspace's file comes back where it was, as its query does.

## Long lines (`ui/selection/code.rs`)

The TUI's 0.12.224 (its #532). Until 2026-11-06 the viewer always cut a line in "…" at the panel's edge, as long names are, and the diff, whose rows `list` measures, always wrapped.

- **Long lines wrap by default, in the viewer and the diff, and a button in each cuts them instead** (the wrap icon, in the viewer's title row and on the diff's open file). Why wrap: this panel is a narrow column, where a cut line says little, and a find could land on a match nobody could see; in a diff a change past the edge made the removed and the added line look the same. Why a button, which the TUI rejected: here a cut line reads as one row of a table, a good way to scan a log or a data file, and the choice costs one enum.
- **One setting for both** (`Prefs::long_lines`, in the window's `settings.json`, `prefs.rs`), the same button seen twice: someone who wants cut lines wants them everywhere. No row in Settings: the button is where it is used and says what it does. A failed save is a toast and changes nothing.
- **The numbers stay on the first row**, as the row's flex cells start at its top; the tint, the marks and the selected line's ground cover every row of the line. Word breaks are gpui's, so a space or `;` ends a row; a character is never lost and a line stays one line for numbers, selection and copying.
- **gpui's `list` in place of `uniform_list`**, for both settings: rows of different heights are what it is for, and it measures only what it draws, so 60,000 lines cost nothing more (checked live, below). One list keeps one way to scroll, jump and select. Rejected: a list for each setting (every scroll and jump written twice), and counting rows ourselves to keep `uniform_list` (the TUI can, its cells are known; here it means shaping the whole file for a font's real widths). What it costs: `list` knows only the heights it measured, so a jump cannot reckon where a far line sits in pixels. So a line's position is an item and an offset, and turning wrapping on or off, or a re-read, keeps the top line (`refit`).
- **A line takes at most about 100 rows** (`Fit::Wrap`, 100 rows of the columns that fit, in bytes), then ends in "…", as the TUI's: gpui shapes a text whole, and a minified line of 8 MB would stop the window for seconds on every first draw and fill a list with thousands of rows of nothing. Copy and Open give the rest. It is our own cut (`capped`), before the text reaches gpui. Rejected: `line_clamp` with `text_ellipsis`, which cuts a text's runs in place and crashed the window (`design/widgets.md`), and which loses the "…" whenever word breaks take more rows than the width says. The "…" stands for what it hides, as it does on a cut line: a drag onto its right half selects the rest of the line (`past_the_cut`), and it takes the tint of what is lit behind it, a selection, a find's match or a diff's changed words.
- **Where a jump lands** (`top_for`): the rows a line takes are reckoned from its bytes and the columns that fit, to put the top where the spot shows three rows down (opening at a line) or in the middle (a find's match). That is a guess where a character is not one cell, such as Chinese text or a minified line with few places to break, so a frame later, when the line is drawn and its layout knows, a spot that did not land in view is scrolled there exactly (`Viewer::reveal`, once; and if its line is not drawn at all, the line goes to the top and it is tried again). A spot whose line is already drawn needs no guess. Rejected: always going to the line's top and correcting a frame later, which makes every jump flash.
- **The diff** keeps its own `ListState`, reset when the setting changes. Peek's card stays cut: it is a glimpse, and a list of `uniform_list`'s rows.
- **Checked live** on 2026-11-06 with cornercase 0.13.1, Linux x86_64 under Xvfb with lavapipe, a fake ssh between two servers on one box; no real sshd, no macOS, no Windows. A file of long lines in both settings, in the dock and full screen, the numbers on the first row; a drag across wrapped rows and its copy (`xclip`); find to a match at the end of a wrapped line; a 312 KB minified line ending in "…", lit by a match past it; a 60,000-line file: a jump to line 50,000, and the wheel back up; Chinese text with no font for it, drawn as boxes, each first draw slow there (fallback looking through every font), a jump far inside it landing in view. The diff in both settings, and its "…" lit by a change past the edge; the setting surviving a restart, in `settings.json`. Not checked: a font with real CJK glyphs.

## Full screen (`app/dock.rs`, `Store::file_full_screen`)

The TUI's 0.12.117 (its #278).

- **A button in the viewer's title row gives the file the terminal's area and the dock's**, on any file: text, picture or a note. The rail, the sidebar, the tab row and the status bar stay, so the way to anything else is still on screen. The same button (with the arrows turned in) or Escape go back.
- **The terminal keeps its size**: `Root` lays the terminal out as before, with a blank of the dock's width beside it (`render_body`), makes it `invisible` and puts the dock over both. So no `view-set --cols`, no program redrawn, and going back is instant at the width you dragged. The terminal's `prepaint` still runs, so a resize of the window reaches the programs. `invisible` stops its painting and its listeners, so a pane that prints costs no drawing meanwhile. Rejected: a dialog or sheet holding the file (a second viewer, or moving the panel's entity between hosts), and not drawing the terminal at all (its element is what asks for the size).
- **The covered tab counts as not seen** (`view-set --hidden`, as for a window in the background, `design/window.md`), so an agent finishing there still notifies.
- **The flag is `Store`'s**, since `Root` lays out and the panel draws the button. It goes with the file (`close_file`) or the panel, and when the pane must show: **Ask agent and every way that gives the keys to the terminal** (`give_keys_back`, `ask_agent`), and any change of the shown tab, pane or workspace, a machine's included (a click in the sidebar or the tab row, a new tab, Open running the editor there). It is never saved. Copy, and Ask agent with no agent to ask, stay.
- **Keys**: the panel has the focus, as the click on the button gave it. A key that still finds the terminal focused (a click in the sidebar that moved nothing) reaches no program, since nobody could see what it did: `on_key` drops it, and text has no input handler while it is not painted. The focus comes back to the panel when a dialog or sheet closes. ⌘W closes the panel, not the hidden pane.
- **Escape takes it after the panel's own steps**: the menu, the find field, the selection, full screen, then the panel (`dock_escape`), whichever part of the window has the focus.
- **Checked live** on 2026-11-06 with the same bench: in and out with the button and with Escape, a selection and then full screen going one press each; the status bar's `78×46` the same before, during and after; turning wrapping off and on in it; an edit arriving under it; Ask agent into a fake agent leaving it, with typing going on in the agent; a click on another tab, and on a machine's tab, leaving it. The covered tab's `view-set` was read in the server's log (`visible=false`, then `true`). Not checked: macOS's and Windows' input while covered.

## Selecting in the viewer (`lines.rs`, `ui/selection.rs`)

The TUI's lines (0.11.5) and characters (0.12.185, its #440); the rules live in `ui/selection.rs`, shared with the Changes diff (`design/changes-panel.md`), the pure logic apart from the pointer (`ui/selection/pointer.rs`).

- **Two zones, as the TUI's**: a press on the numbers selects its line at once and a drag there a range of whole lines; on the code, a click selects its line and a drag selects characters. A shift-click makes a range of lines from where the selection started, whichever the zone, a character selection included. A click on the only selected line clears it, and so does a press under the last line.
- **A drag on the code stays characters when it leaves its line**, from the press to the pointer across lines, as the TUI's and any editor's, covering those lines for Ask agent. Rejected: turning it into whole lines once it leaves the line that it started on, since nothing could then copy from the middle of one line to the middle of another; the numbers are the way to whole lines. A drag back to where it started falls back to the line.
- **A double click selects a word and a triple click the line** (the TUI left them for later): a double click would otherwise select the line and clear it again.
- **Carets between characters, not cells**: the closest boundary on the line as drawn (gpui's `closest_index_for_x`), as text fields do. The TUI counts cells because a terminal has them. A press counts as a drag from 3 px, so a shaky click is still a click.
- **Kept by what it selected**: a line and a byte offset in the shown line, never a row, so scrolling cannot move it. A re-read keeps it: an offset is cut to the line's length and to a whole character whenever it is read, a selection that reaches past the end stops at the last line, and one wholly past it (the file shrank) is dropped.
- **Copy takes the file's own text**, a tab as a tab (`Text::own`): the shown lines have tabs as four spaces, so a Makefile copied from them would break. Each of a tab's four spaces stands for the tab, and lines join with `\n`, as a `\r` was dropped on reading. Only the lines holding a tab keep a second copy (`Text::tabbed`). Rejected: the TUI's whole copy of the file beside its lines, up to 8 MB per viewer, whatever it holds.
- **A line cut at the panel's edge gives its hidden end**: the "…" stands for what it hides (`ui::one_line`'s `LaidOut`, or `past_the_cut` on a line past the 100 rows), so a drag onto it selects, and copies, the rest of the line. The "…" takes the tint of what is lit behind it, a selection or a find's match.
- **Wrapped rows are one line**: a line and an offset name a caret whatever the row, a caret on a later row comes from gpui's `TextLayout` (`selection::row_probe`, as the diff's), and a click anywhere on the line selects it.
- **The actions float by the selection**, the diff's own widgets (`selection::action`, `action_bar`): Open, Ask agent and Copy, with the lines they cover. Under the line the pointer ended on, or above it where there is no room, at the panel's right edge; on the nearest line still drawn when that one is scrolled away; gone with the whole selection scrolled away and during a drag. It is placed while the frame is laid out, from the rows just laid out (`selection::layer`), so a scroll never leaves it a frame behind, and `bar_origin` and `host` are plain functions. Rejected: placing it when rendering, from the last frame's rows, and making it a child of its row, which a list measures and only `uniform_list` tells which rows show.
- **Ask agent** quotes `path:a-b ` (`Store::ask_about`), the lines with something selected: a character drag that ends at a line's start leaves that line out. The keys then go to the pane (`Store::keys_to_terminal`), so the question can be typed at once; until 2026-11-06 a hunk's Ask agent left them on the panel.
- **Open** shows the menu's apps at the first of those lines, with the `Target` that "Open in…" takes. On another machine those apps cannot reach the file, so it runs the editor in a new tab there, as the diff's Open.
- **⌘C copies the selection while the focus is in the panel** (`Root::dock_copy`), and on Linux a drag also fills the primary selection, as a text field's does; a click does not, so selecting a line does not take what a middle click pastes.
- **The pointer is followed from the window's listeners, not the rows'** (`selection::layer`), since a drag goes on outside the panel and past the window. They are there on every frame: a press and a release within one frame would otherwise lose the release and leave the press waiting (found live under Xvfb, where a frame is slow). A move with no button down also ends it, since a release outside the window may never be reported.
- **Scrolling while selecting**: once it is a drag, a pointer above or below the code scrolls a row every 50 ms and takes the selection along; the wheel works too, as each turn reads the row under the pointer again. A turn with nothing to do costs no frame. The TUI also scrolls on the first and last row, since a terminal reports no row past its window; a window's pointer goes on past the panel, and there selecting in the last row would run away from under the pointer.
- **The menu takes the press** (`occlude`): it floats over the code, and a press on an entry also pressed the line under it.
- **The panel has its own focus handle, at its root**: gpui gives keys to nothing when the focused element is no longer drawn, not even `Root`'s shortcuts. So a click in the viewer focuses the panel rather than something that goes with the file, and a search or find field hidden while it had the keys hands them on as the panel draws (`settle_focus`).
- **Escape takes one step per press**, in `Root` (`dock_escape`, `design/terminal.md`): the menu, the find field, the selection, then the panel.
- **Left out**: selecting with the keyboard, which needs a caret the viewer has not got; the terminal's rule stays that only ⌘ shortcuts are read.

## Find in the open file (`find.rs`)

- **⌘F while the viewer has the focus, Ctrl+Shift+F on Linux and Windows** (the TUI's 0.12.168, which has a button and no key), and the header's Find button. "Has the focus" is the focus in the panel with a text file shown; anywhere else ⌘F stays Search, so a click in the terminal takes it back (`design/terminal.md`).
- **A field floating over the code's top right**, with the count (`3 of 12`, or `No matches`), ↑ ↓ and ✕. Rows that would lie under it are not hidden: the first line's item gets the field's room above it while it shows, so it scrolls away with the text, and scrolled down, opening and closing move nothing. A jump treats that room as out of view, so it never lands under the field. A top padding of `list`'s own was rejected: `list` keeps it for good, a blank band over every scrolled line.
- **Matching is the text search's own** (`search::matcher`: a literal, smart case, trimmed), so a query behaves the same in both, over the shown lines, so the lights land on what is drawn.
- **It runs off the draw path**: a background task per edit of the query and per re-read, the older one cancelled and its answer dropped by a generation. A drawn row finds its hits with two binary searches, and only those up to 4 KB past where it stops being drawn (`Fit::lit_bytes`), since a minified line can hold hundreds of thousands, plus the current one wherever it is, so the "…" lights for it. Until now a search's query was matched again for each row at each frame. A hit is 12 bytes and there is no cap, so the count and the steps are exact. A hit left from before a re-read that no longer falls on whole characters is not drawn. The older answer stays shown until the new one comes, and past 150 ms a spinner takes the count's place. Live on 2026-11-06, in a debug build under lavapipe: one letter in 7.5 MB and 160,000 lines gave 640,000 matches within a second.
- **Moving**: Enter or ↓ the next, Shift+Enter or ↑ the previous, wrapping. Typing goes to the first match at or after the top line shown. A jump scrolls only when the match is out of view, and then centres it, on the row of a wrapped line it falls on (see Long lines). The current match is cobalt with `on_brand` text ("cobalt marks what is chosen", `design/widgets.md`), the others the yellow tint they had.
- **Live files**: a re-read counts again, the current match stays on its line or the next match after it, and the view does not move.
- **A selection and a find leave each other alone**: finding never touches what is selected, whose tint goes over the lights, and ⌘F with characters selected inside one line fills the field with them.
- **A text search's result opens with the field holding its query**, at that match, so Enter goes on through the file; this took the place of the query that stayed lit with nothing to move on. It takes the keys only if the search field had them.
- **Escape** clears the text (`clears_on_escape`), then `Root` closes the field, then goes on as under Selecting. Per viewer and in memory: another file drops it, another workspace keeps its own.
- **Limit**: a match past a "…" counts and cannot be seen: on a cut line, wrapping shows it; past the 100 rows of a wrapped line, Copy and Open do. The "…" lights up to say so. Rejected: scrolling sideways, which moves the numbers or the other lines out of view.
- **Checked live** on 2026-11-06 with cornercase 0.13.1, Linux x86_64 under Xvfb with lavapipe, a fake ssh between two servers on one box; no real sshd, no macOS, no Windows. A click, a shift-click, a drag on the numbers, characters inside a line and across lines, a double and a triple click, a press under the last line; holding below the code (lines 7 to 93); Copy and Ctrl+Shift+C with tabs kept (read back with `xclip`) and the primary selection after a drag; the hidden end of a long line; Ask agent into a fake agent and typing on after it; Open's menu, and "Open in VS Code" through a logging `code` (`-g …/main.go:11`). Ctrl+Shift+F in the viewer, and Search from the terminal; Enter, Shift+Enter, ↑ and ↓; Escape step by step; a result of a text search; an edit under an open find; another workspace shown under a focused field (`focus --view`), the keys still answering; a 160,000-line file. Through `--remote` and the fake ssh: selecting, copying a tab through `files read`, finding, and Open running the editor in a tab there. Not checked: macOS's and Windows' input, a real sshd, dragging out of the window.

## The search (`search.rs`)

- **One index of paths, reused**: a single `ignore` walk (hidden files included, ignored ones and `.git` not), at most 200,000 paths, reused by new queries for 10 seconds (`INDEX_FRESH`). A walk cut short, by a newer query or by the finder closing, gives no index: until 2026-10-31 its partial list was kept and reused, so for 10 s a fast typist's later queries missed files.
- **File names**: nucleo's matcher with fzf's scoring and smart case; on a tie a file whose own name matches the whole query, then the shorter file name, then the shorter path, so the file a query names comes first. At most 200 results. The first tie-break came with the finder (2026-10-31), as fzf's `pathname` tiebreak: nucleo scores a match in a folder's name as one in the file's, so “finder” listed `finder/view.rs` and `finder/tests.rs` before `finder.rs`, the shorter names winning the tie. cornercase's own ranking (the TUI, and `files search --names` on another machine) has only the other two, so there such ties still go to the shorter name until it adopts this.
- **Text**: ripgrep's searcher, the query a literal with smart case, binary files skipped, on up to 8 threads. At most 1,000 matches: each match takes a slot before it is kept, so the threads together never keep more than the cap. A long line is cut to 400 characters, starting 40 before its first match.
- Enter opens the first result; pressed before the answer came, it opens it when it does.

## Going to a file (`finder.rs`, ⇧⌘P)

- **A quick open over the window, as VS Code's Go to File** (asked for on 2026-10-31): a field, and the files ranked as you type by the panel's own name search (above: nucleo, fzf's scoring, at most 200), each with its type's icon, the matched letters lit and its folder dimmed beside the name, drawn by the panel's own result row. ↑ ↓ (and Page Up, Page Down) choose; ↩ or a click opens the file in the panel's viewer, revealed in its tree (`reveal`: the folders above it open), and docks the panel. A sheet over the window closes too, or it would hide the file. The keys go back to the terminal as the dialog closes, since the viewer only reads.
- **"The selected project" is the shown workspace's folder**: the project's checkout, or the worktree when a worktree's workspace is shown. It is the folder the panel shows and opens the file in. Rejected: every workspace of the project (each file once per worktree, and the panel shows one at a time) and the project's main folder while a worktree is shown (another branch's files, opened in a panel that shows this one). The footer names the place (`project › workspace`), and the finder follows the shown workspace while it is open.
- **The panel's index, not a second one**: opening starts the walk (`search::index`) unless the panel walked that folder less than 10 s ago, so it is often done by the second letter; letters typed meanwhile wait for it rather than each starting a walk, and the walk is handed to the panel (`keep_index`), whose next search reuses it. The opening keeps its index until it closes: a file written while it is open shows on the next opening. On another machine there is no index here: each query is `files search --names` through the panel's `Source`, as its own search. A newer query drops the older answer, and ↩ before the answer opens the first file when it comes, as the panel's Enter.
- **A dialog** (`Store::show_dialog`), not a sheet or a panel of its own: the host already gives it the veil, the rise, a click outside that closes it and the rule of one dialog at a time. It is centred like every dialog, at a height fixed by the window's (`frame_for`), so the field never moves as results come and go; a list that grew and shrank in a centred card would. `Root` builds the Files panel to hand it over (`Root::panel`), so the panel and its index exist even if it was never opened. ⇧⌘P closes it again, as a sheet's key closes the sheet; the other ⌘ shortcuts are ignored under it, as under any dialog.
- **Escape clears the query, then closes**, as the Search sheet and every search field here (`clears_on_escape`, `design/terminal.md`). Rejected: closing at once with a query typed, as VS Code does, which would make this the one search field that behaves otherwise.
- **Each opening starts empty**, as the Search sheet; an empty query shows a hint, not recently opened files, since the panel keeps only the last file of each workspace.
- **The panel's own query is kept**: the viewer's back button then says "‹ Results", since closing it shows them, "‹ Flow" for a run's file opened from the Flow panel (`design/flows.md`), and "‹ Files" otherwise.
- **Checked live** on 2026-10-31 with cornercase 0.12.230, in a throwaway project holding a copy of `src` and `design`: ⇧⌘P over the terminal and over a sheet (which closed), the ranking as you type and its tie-break, ↑ ↓, ↩, ↩ typed right after the query, a click, no match, Escape clearing then closing, ⇧⌘P closing it, the file opened in the viewer and revealed in the tree, long names cut. Through `--remote` (a local sshd and an isolated server): the server's `files search --names` answers, and a file opened through `files read`.

## Peeking at a path (`peek.rs`, `peek/`)

- **Resting the pointer on a path a pane printed shows the file in a card** (asked for on 2026-10-31: the TUI opens a path in this panel on a click, and a window can show far more kinds of file than a terminal). How the path is found, underlined and clicked is in `design/terminal.md`; the card belongs here because it reads the disk as this panel does, and on another machine through the same `Source`.
- **It waits 350 ms** (`PEEK_AFTER`), so moving across text does not flash cards, **and closes 280 ms after the pointer has left both the path and the card** (`GRACE`), so the pointer can cross into it to scroll, pause a video or press its buttons. Typing, the wheel and a click close it at once. Another path of the same file and lines moves the card without reading it again.
- **Beside the path when 420 px fit on its right, else below, or above when there is more room there** (`place.rs`). Found live: a card below the first of a column of paths (`ls`, `git status`) covered the next ones, and the pointer moving down onto it kept it open; beside, the column stays free. At most 660 px wide, as tall as the room allows.
- **Opaque** (`raised` behind the header, `pane` behind the body): the glass of floating cards let the terminal's text show through and the code was hard to read (found live).
- **What it shows**, by kind:
  - **Text**: read as the viewer reads it (8 MB at most), coloured by the same highlighter in the background, scrolled to three lines above the path's first line, with its lines lit. The header gives the lines, the count and the language. A click on a line opens the panel at that line.
  - **Pictures**: the viewer's formats, the card sized from the picture's header (the `image` crate reads only the header), so it fits without bands. A GIF moves: gpui animates an `img` only when it has an id, which the viewer's picture lacked too and now has.
  - **Videos** (`mp4`, `m4v`, `mov`, `3gp`): AVFoundation's `AVPlayer` with an `AVPlayerItemVideoOutput` asked for `420f` (full-range bi-planar YUV) and Metal-compatible buffers, drawn by gpui's `surface` element. gpui's Metal renderer asserts that exact format, so a frame in any other is dropped rather than drawn. It plays without sound and loops; a click pauses it, the speaker turns the sound on. While it plays the card asks for every display frame and copies a new buffer when there is one; only the card redraws, not the terminal. A file AVFoundation cannot open (WebM, MKV) falls back to Quick Look's thumbnail.
  - **Sounds**: the same player without the video output, which never starts on its own (a card that appears under a resting pointer must not make noise): a play button, the progress and the time.
  - **Anything else** (PDF, Office and iWork documents, fonts, 3D models, a binary or a file over 8 MB): `qlmanage -t -s 900` into a temporary folder, its PNG read and the folder removed, killed after 8 s. Without a thumbnail the card says there is no preview.
- **On Linux** (decided 2026-11-04): there is no Quick Look and no AVFoundation, so `peek/player.rs` is replaced by `peek/no_player.rs` (it opens nothing) and anything else goes to the freedesktop thumbnailers (`peek/thumbnailers.rs`), which file managers already use: the file's type from shared-mime-info's `mime/globs2` of every XDG data folder, ranked together as GLib's xdgmime merges them, a tie going to the folder that comes first (`$XDG_DATA_HOME`); until 2026-11-04 the first folder with any match decided, so a user's `*.gz` hid the system's `*.tar.gz` (by name, the longest glob of the highest weight, case-insensitive unless marked `cs`, each matched as `fnmatch` does, with `*`, `?` and bracket expressions such as `*.anim[1-9j]` and `*.so.[0-9]*`, as the spec asks; until 2026-11-04 only literal names and `*` before a suffix matched), then the first `thumbnailers/*.thumbnailer` entry, in those folders and in name order, that lists the type and whose `TryExec` (else its command) runs, its `Exec` split into words as the desktop entry spec quotes them (double quotes with `\` before `"`, `` ` ``, `$` and `\`; single quotes and a `\` outside quotes as GLib's `g_shell_parse_argv`, which GNOME's thumbnailer code uses, so `--size="%s"` is one word) and filled in word by word (`%i` the path, `%u` its URI, `%o` the PNG, `%s` 900), the paths as they are on disk, so a path with spaces or bytes that are not UTF-8 stays one argument and no shell reads it. It runs under the same 8 s limit as `qlmanage`. **Its temporary folder is private** (`desktop::Scratch`, shared with Quick Look): Linux's `/tmp` is shared by every user, unlike macOS's per-user temporary folder, so the folder is made with mode 0700 and must not exist yet (a name someone else took is skipped for the next), and it is removed when the thumbnail is read or anything fails. Before 2026-11-04 it was `create_dir_all` on a predictable name, which accepted a folder another user had made (with a link inside, the thumbnailer wrote through it), and an `Exec` the app could not fill left it behind. So a PDF shows with Evince's or Papers' thumbnailer, a video with `ffmpegthumbnailer`'s, a font with GNOME's, a document with LibreOffice's, when installed. A video or a sound says plainly that it plays only on macOS, in the header (beside its thumbnail when there is one) or as the card's note, which points at the header's default-app button. Without a thumbnailer the note says that none on this computer reads the type; one that ran and failed is named with how (its exit status, the 8 s limit, no picture written), since "none reads it" would be false and give no reason (before 2026-11-04 both said the same). A video or a sound keeps its own note either way: there the thumbnail is only extra. The picture is read up to 32 MB, the viewer's limit for an image, and refused past it, so a thumbnailer that writes a huge file cannot fill the memory; `qlmanage`'s picture is read the same way.
  - Checked live on 2026-11-04 (the same container, two thumbnailers written for the check in `~/.local/share/thumbnailers`): `clip.anim5` took `video/x-anim` from `*.anim[1-9j]` and showed the picture its thumbnailer drew; a PDF whose thumbnailer exits with 3 said "sh ended with exit status: 3." (its `TryExec` names it); a binary file with no type still said that none reads it.
  - Checked live on 2026-11-04 in the same container, with `ffmpegthumbnailer` 2.2.3 installed: resting on `clip.mp4` showed its thumbnail (with the film strip `-f` asks for) and "Plays only on macOS" in the header, whose default-app button ran `xdg-open /tmp/demo/clip.mp4`; `tone.wav` showed the note "Plays only on macOS"; a binary file "No thumbnailer on this computer reads this kind of file". Not checked: a PDF, a font or a document (no such thumbnailer installed), and a thumbnailer that hangs.
  - Rejected: sniffing the type with `file --mime-type` or `xdg-mime` (a process per peek, and libmagic's names differ from the ones thumbnailers list, such as `font/sfnt` for `font/ttf`); a video player of our own (GStreamer or ffmpeg bindings, a large dependency for a hover card); running thumbnailers in `bwrap` as GNOME does (not on every machine; the user installed them to make pictures of their own files).
- **On Windows** (decided 2026-11-04): no Quick Look, no AVFoundation and no freedesktop thumbnailers, so `peek/no_player.rs` stands in for the player, as on Linux, and anything else asks the shell for the picture File Explorer shows (`peek/shell.rs`): `SHCreateItemFromParsingName` then `IShellItemImageFactory::GetImage` at 900 px with `SIIGBF_RESIZETOFIT | SIIGBF_THUMBNAILONLY`, so the thumbnail handlers Windows and the user's apps installed answer (PDFs, videos through Media Foundation, Office files, fonts) and a type without one gives no picture rather than its icon, which says nothing about the file. Each peek runs it on a thread of its own, which sets up COM apartment-threaded and takes it down when the shell answers, under the 8 s limit of the other helpers: a handler that hangs leaves the card saying Windows made no thumbnail within 8 s, its thread finishing on its own (a thread cannot be killed; the handlers run in a surrogate process when Windows isolates them). The `HBITMAP` is read with `GetDIBits` as 32-bit top-down BGRA and turned into a PNG for gpui: an alpha that is zero everywhere is a thumbnail without one (opaque), any other is premultiplied, as GDI's are, and is taken out. A video or a sound keeps "Plays only on macOS", in the header beside its thumbnail or as the note; any other type without a thumbnail says "Windows has no preview for this kind of file", and one the shell could not find or read says why. Rejected: `IThumbnailCache` (more calls for the same picture), `SIIGBF_ICONONLY` as a fallback (an icon is not a preview), WIC to encode the PNG (the `image` crate already does it here). The paths reach it as Windows writes them: a link's `path` is the canonical one cornercase gives, and one that reaches the network is no link there (its `design/windows/network-paths.md`), so a peek never opens a share. Checked only by cross-compiling and unit tests on macOS (the pixel conversion, the PNG, the deadline); no thumbnail has been asked of a real Windows yet.
- **The header** opens the file in this panel (at its lines) and, on this machine, in its default app (`desktop::open`, a job that toasts its failure).
- **The same card shows a web page** under the pointer (`peek/web.rs`), with the Browser panel's picture of it; why and how are in `design/terminal.md`. One card for both keeps one look, one delay and one way to close.
- **Rejected**: a native `AVPlayerLayer` view over the window (gpui draws into one Metal layer; a native view sits above every gpui overlay, toast and menu included, and has to be moved by hand); decoding with `ffmpeg` (not on every Mac); `qlmanage -p` (its own window, outside this one); `QLThumbnailGenerator` through its block API (more unsafe code for the same picture); the `objc` crate, whose macros trip `unexpected_cfgs` in this crate, for `objc2`, which also checks every message's argument and return types in debug builds.
- **Pitfall**: `core-video`'s `CVPixelBuffer::get_io_surface` takes ownership of a reference it does not own and over-releases it; a prototype crashed on it, so it is not used.
- **On another machine** the card reads text and pictures through `files read` (an absolute path is passed as it is, see below); videos, sounds and documents say that only text and pictures are shown from there, since the player and Quick Look need the file on this Mac. Not checked live through `--remote`.
- **A path outside the workspace** opens in this panel by its absolute path, without opening folders in the tree.
- Checked live on 2026-10-31 with cornercase 0.12.234: code, Markdown, a PNG, a GIF (moving), an MP4 (playing), an MP3 and a PDF; a click on a path opening it here at its line.

## Paths on Windows and across machines

- **The panel follows its root's rules** (`Place::style`, from the form of the workspace's folder, `design/remote.md`): the disk's on this machine, the server's through `cornercase files`, so a Windows window on a Linux server shows and sends `/` and a Mac on a Windows server shows `\`.
- **Inside, a relative path is this machine's `PathBuf`**: the tree joins its folders with `Path::join` (so its rows hold `src\lib` on Windows; the tree draws names, never that text), and a Windows server's relative paths (its search results, a link's `relative`) have their `\` made `/` as they come in (`Style::relative`), so on a Mac their parts are still parts and opening one opens its folders in the tree. The disk's own index keeps `/`, as before.
- **What the panel shows uses the root's separator**: the viewer's title (`Style::shown`, by parts), the folders of search results and of the finder's rows (`Style::in_form`, which keeps the lit ranges, since `/` and `\` are one byte each), the card's folder and the tree header's name. A file's full path is the root and its parts joined with the root's separator (`Style::join`), so on Windows it reads `C:\proj\src\x.rs` rather than `C:\proj\src/x.rs`.
- Checked only by unit tests on macOS (and the tree's test by the Windows runner); the panel itself was not driven on Windows or through a Windows server.

## Opening elsewhere (`open.rs`)

- **cornercase leaves opening in other apps to each window on purpose** (its `design/opening-in-other-apps.md`: "No request"): only the window knows the apps of the machine it runs on. Detection and command lines follow that design.
- Openers, in a fixed order: the file manager (Finder on macOS), then VS Code, Cursor, Zed and Sublime Text (their command on the `PATH`, which takes `FILE:LINE`, else on macOS their bundle in an Applications folder through `open -a`, which takes no line), then the default app. VS Code and Cursor need `-g` for the line.
- Finder reveals a file and opens a folder, but reveals bundle-like folders (`.app`, `.xcodeproj`…), which `open` would launch.
- The default app takes plain files only, never folders or programs; the menu checks this with one `stat` per entry.
- **The apps are found once per `Store`, off the main thread** (`Store::openers`), as nothing is found on another machine and a new connection makes a new `Store`; the panel and the menus of a project, a workspace and a pane read that list (`design/sidebar.md`).
- **How a path reaches the desktop is one shared helper** (`desktop.rs`), also used by the sidebar's **Open in…**, the peek card's default app, the Flows sheet's buttons that open a flow's file or a run's folder (gpui's `open_with_system` until 2026-11-04, which on Linux logs a failure and says nothing) and ⌘-click on a path (`design/terminal.md`): `open` and `open -R` on macOS; on Linux `xdg-open` (else `gio open`) for the default app, and for the file manager the freedesktop `org.freedesktop.FileManager1` D-Bus call (`ShowItems` selects a file in its folder, `ShowFolders` opens a folder; through `gdbus`, else `dbus-send`), which GNOME Files, Dolphin, Nemo, Thunar and Caja answer; when no tool or no file manager answers, `xdg-open` opens the folder. The URI is percent-encoded, with `'`, `,` and `\` escaped too, so a name can neither close `gdbus`'s quotes nor split `dbus-send`'s array. Every tool is found on the `PATH`, and a missing one is an error toast that says what to install (xdg-utils).
- **A launch waits at most 8 s** (`desktop::run`): a tool that answers within that time gives its success, or its failure with its last line on standard error (kept in an unlinked temporary file, not a pipe, so an app the tool leaves running can never block on it or die of a closed pipe; the file is made new with mode 0600, never opened over one already there, since `/tmp` is shared on Linux); one still running after that counts as launched and is reaped on a thread of its own, blocked in `wait` (a single reaper polling every such child was rejected: it trades idle threads for a wake-up that lasts as long as any app opened from here stays open, and only `xdg-open` outside a desktop leaves one). **The file manager's D-Bus call is a call, not a launch**: on Linux it waits for its answer, which `gdbus` and `dbus-send` give within the bus's 25 s reply timeout, and one still unanswered after 30 s is ended and counts as failed, so the folder fallback runs either way. Until 2026-11-04 a call past 8 s counted as launched and its later failure was lost, skipping the fallback (CodeRabbit's review). Rejected: a limit under the bus's, which would also open the folder when a file manager that starts slowly then shows the item, two windows for one click. `xdg-open` outside a known desktop (a bare window manager) runs the app in the foreground, so waiting for its exit would keep the job in the status bar until the app closes. Before 2026-11-04 the menu waited for the exit with no limit and said only the exit status.
- **Linux labels**: "Show in file manager" for a file and "Open in file manager" for a folder (the macOS menu keeps "Reveal in Finder" and "Open in Finder"). "Open in Files" was rejected: GNOME's file manager is called Files, but so is this panel, and KDE's is Dolphin.
- **Editors on Linux** are also found under their other names (Arch's `zeditor` for Zed) and as Flatpak exports (`com.visualstudio.code`, `dev.zed.Zed`, `com.sublimetext.three`, in `~/.local/share/flatpak/exports/bin` and `/var/lib/flatpak/exports/bin`) and snaps (`/snap/bin`, which a desktop session started without a login shell may leave off the `PATH`); all take `FILE:LINE` as their command does. Only editors are looked for there: the desktop's own tools (`xdg-open`, `gio`, `gdbus`, `dbus-send`) count only on the `PATH`, where `desktop.rs` runs them from, so the menu never offers a file manager or a default app that would then fail as missing (until 2026-11-04 they were detected in those folders too).
- **On Windows** (decided 2026-11-04, following cornercase's `design/opening-in-other-apps.md`, "On Windows", #600 upstream, which was checked on Windows 11): the same openers and the same `desktop.rs`, with `Os::Windows` answers that are plain functions tested on every host (`Lookup`, `explorer_steps`, `runs_when_opened`, `extra_dirs`); only the Win32 calls are `#[cfg(windows)]`, in `desktop/win32.rs`, with stubs in `desktop/no_win32.rs`.
  - **The shell, not `cmd /C start`**: the default app and File Explorer go through `ShellExecuteExW`, never through a command line, since `start` is `cmd`'s built-in and `&`, `^` and `%VAR%` in a file name would act there. It runs on a thread made for the call, with COM initialised apartment-threaded on it as the shell's documentation asks (not on gpui's pool threads, where `run_local` jobs run), `SEE_MASK_NOASYNC` since that thread ends right after, and `SEE_MASK_FLAG_NO_UI`, so a failure comes back as the OS's own message ("No application is associated with the specified file for this operation.") in the usual error toast rather than as a dialog. The default app is the file's default verb; a folder is opened with the `explore` verb (a drive's root included); a file is shown with `explorer.exe /select,"<path>"`, the path in quotes since Explorer splits its arguments on commas, and `explorer.exe` taken from `GetSystemWindowsDirectoryW` (`desktop::windows_folder`), never from the `PATH`, where an earlier folder could hold another (`GetWindowsDirectoryW` can answer a per-user folder under Terminal Services). Explorer is started by the shell too, so its exit status, always 1, is never read. When it cannot be started (or there is no Windows folder), its folder opens with `explore`, as Linux falls back to `xdg-open` on the folder. A verbatim path (`\\?\C:\…`, `\\?\UNC\…`) loses its prefix first (`desktop::plain`), which neither Explorer nor editors take. File Explorer and the default app are always offered: the shell is always there.
  - **What counts as a program is its extension**, since there is no execute bit: the types Windows runs, or hands to an interpreter or an installer, when opened (upstream's `RUN_WHEN_OPENED` list: `exe`, `cmd`, `bat`, `msi`, `lnk`, `url`, `ps1`, `py`, `js`, `reg`, `scf`…), and any the shell calls dangerous (`AssocIsDangerous`). The extension is read from the real name (`canonicalize`, then the verbatim prefix dropped), which is what is handed to the shell: Windows trims a trailing dot or space, so `run.bat.` would have no extension yet run `run.bat`. A path that cannot be resolved counts as a program. Unlike macOS and Linux, `desktop::open` itself refuses a program on Windows ("it is a program, which Windows would run rather than open"), not only the menu: Ctrl+click on a path in a terminal, the peek card and the Flows sheet open through it, and Windows runs far more types on open than an execute bit marks, so a `.bat`, `.lnk` or `.url` an agent printed would run at a click. A folder is never refused.
  - **Programs are found through `PATHEXT`** (`desktop::Lookup`, which takes the `Os` and the extension list, so tests run anywhere): only `.com`, `.exe`, `.bat` and `.cmd`, in `PATHEXT`'s order, all four when it is unset or names none of them, so a `code.vbs` that `PATHEXT` lists is never run; never the bare name, since VS Code's `bin` holds both `code.cmd` and `code`, a shell script for WSL and Git Bash that Windows cannot run. A file counts when it exists with one of those extensions. A name that already has one is looked for as it is. Every lookup goes through it (`desktop::on_path`, the Browser panel's Chrome included). A relative `PATH` entry, an empty one included, is skipped, so the current folder is never searched.
  - **Editors** are `code.cmd`, `cursor.cmd`, `zed.exe` and `subl.exe`. VS Code's, Cursor's and Zed's installers put their command's folder on the user's `PATH`, which a window started from the Start menu inherits; Sublime Text's only offers to. So the panel also looks where they install themselves: `%LOCALAPPDATA%\Programs\Microsoft VS Code\bin` and `%ProgramFiles%\Microsoft VS Code\bin` (the user and the system installer), `%LOCALAPPDATA%\Programs\Zed\bin`, and `%ProgramFiles%\Sublime Text` (and `Sublime Text 3`). Not Cursor's `resources\app\bin`: it also holds a `code.cmd` that opens Cursor, so on a machine without VS Code "Open in VS Code" would open Cursor. No bundles, no Flatpak or snap. They take `FILE:LINE` (VS Code and Cursor with `-g`) and run through `desktop::run` as on Unix: std runs a `.cmd` through `cmd.exe /c` with its arguments escaped for `cmd` (Rust's fix for CVE-2024-24576), so a path with spaces, `&` or `%` reaches it whole, and `platform::command` starts it without a console window.
  - **Temporary files are private by their folder**: `Scratch` and the launcher's error log get no mode on Windows, since `%TEMP%` is the user's own (`AppData\Local\Temp`, which only the user, SYSTEM and Administrators may open) and what is made there inherits that, as private as macOS's per-user folder. The log is unlinked while open, as on Unix (std opens files with `FILE_SHARE_DELETE`); the file goes when its last handle closes. There are no XDG data folders (`desktop::data_dirs` gives none), so no freedesktop thumbnailer is looked for.
  - **Checked on the Windows runner** (2026-11-04, `design/windows.md`): Ctrl+click on `C:\demo\notes.txt`, printed by `echo` in a PowerShell pane, opened it in Notepad through the shell, and resting the pointer on it first underlined it and drew its card with the file's line. The tests that need Windows itself (`cmd` and `ping` standing for a tool that fails or does not answer, `AssocIsDangerous`) pass in CI's Windows job. Not checked: File Explorer showing a file, an editor, the refusal of a program, a path with spaces or `&`, and the shell's thumbnails (no PDF, video or document on the runner).
- Rejected: gpui's `reveal_path` and `open_with_system`. On Linux they ask the desktop portal, then fall back to `xdg-open` on the folder, and only log a failure, so a machine without them would open nothing and say nothing; ours selects the file through `FileManager1` and toasts. The portal's activation token, which helps a browser come forward on Wayland, matters less for a file manager; web addresses still go through gpui (`design/terminal.md`).
- **Checked live on Linux** on 2026-11-04 (Debian 13 arm64 in a container, Xvfb and openbox, gpui 0.2.2, cornercase 0.12.280, the debug build of this branch), with logging stubs of `xdg-open`, `notify-send` and `paplay` first on the `PATH` and a logging wrapper around the real `gdbus` (GLib 2.84): the sidebar's "Open in file manager" on a project ran `gdbus call … FileManager1.ShowFolders ['file:///tmp/demo'] ''`, which failed (no file manager on that bus), then `xdg-open /tmp/demo`; the Files menu showed "Show in file manager" and "Open with default app" (no editor installed), the first ran `ShowItems ['file:///tmp/demo/main.rs']` then `xdg-open /tmp/demo`, the second `xdg-open /tmp/demo/paths.txt`; with a `PATH` holding only `cornercase`, the sidebar entry gave the error toast naming xdg-utils. Not checked live: a real file manager answering `FileManager1` (GNOME, KDE), `dbus-send` (only `gdbus` was there), Flatpak and snap editors, a Wayland session, and macOS after the move to `desktop.rs` (unit tests only; its command lines are unchanged). Again on 2026-11-04, with a `gdbus` stub that fails after 10 s: "Open in file manager" showed its job in the status bar, then ran `xdg-open /tmp/demo` when the call failed; with one that never answers, the call was ended at 30 s and `xdg-open` ran then.

## Through the command line (`source.rs`, `served.rs`)

- **One `Source` per workspace, picked once**: `Disk(root)` on this Mac, `Server(workspace)` when the window drives another machine's server (`cli::host()` when the panel is built; switching servers builds a new panel). The tree, the viewer and the search ask the source and do not know which it is; their state, polling and dropping of stale answers stay the same.
  - Rejected: `cornercase files` on this Mac too. The disk is the documented exception (#345 upstream), and a process per read and per check costs more than a `stat`.
- **The tree**: one `files list ./A ./B … --workspace W --json` for all the open folders, whose `status` are its git marks, answered in the order asked (the answer echoes each argument, so it is zipped with the request rather than matched by path). Entries are sorted here as on disk; `kind` `folder` is a folder (a link to one too), `more` is "some were left out". A folder's `error` fails that folder alone; a command that fails (ssh down) fails every folder with its reason, so the root shows why. `list` exits 3 when a folder fails and `read` 1 for a folder or a missing file, both with the JSON on standard output, which the CLI documents, so the answer is read whenever standard output holds an object.
- **Paths go after `--` and start with `./`**: a name starting with `-` would read as an option and one starting with `~/` as the server's home folder. The root is `.`. The parts are joined with `/` whatever this machine's separator, which a Windows server reads too, and an absolute path (a file outside the workspace) goes as its server wrote it, judged by its form (`paths::rooted`, `design/remote.md`): until 2026-11-04 a Windows window sent `/home/me/x` as `.//home/me/x` and a Mac sent `C:\x` as `./C:\x`, both relative to the workspace. A file's stamp asks its folder by the same rules (`served::folder_and_name`), so `C:\x\y.rs` is listed in `C:\x`.
- **The viewer**: `files read ./P --json`, or the absolute path as it is for a file outside the workspace (the CLI takes either). Text and images go through the same `classify` as the disk (an image's bytes are `image.data` in base64), so an SVG, which the CLI answers as text, still shows as an image. `binary`, `too-large`, `folder` and `missing` map to the viewer's notes; the limits (8 MB of text, 32 MB of an image) are the server's and the same as here. The grammar is still picked here from the name and first line, not from the answer's `language`, so a file colours alike on both sides.
- **The margin**: `changes file --workspace W --json -- PATH`, the path as `changes` lists it (`/` between parts, no `./`, or it finds no change; after `--`, for a name starting with `-`). Only for a file the tree marks, so never for a path outside the workspace.
- **Checking the open file**: every second `files list` of its folder gives its `bytes` and `modified` (UTC, to the millisecond, parsed into a `SystemTime` so the disk's `Stamp` serves both); only a change reads the file again. The open folders are listed every second check, as on disk.
  - Rejected for now: `files list --follow` and `files read --follow`, which push changes from the server. A connection follows one thing at a time, so the tree needs a stream per set of open folders, restarted on every expand, plus one for the file; polling keeps one code path for both sources and a closed panel still costs nothing. Worth revisiting if the round trips show on a slow link.
- **The search**: `files search -- Q --names|--text --json`, ranked and capped by the server as the disk search is here (200 names, 1,000 matches). Its `indices` and `ranges` count characters, so they become byte ranges here; a tab becomes one space, which keeps them in place. A search over ssh cannot be cancelled: a newer query only drops the older answer. So a query that takes a process waits 200 ms of quiet first (`querying::QUIET`), and one typed over it is never asked: a word typed at any speed was a command per letter, each its own ssh session on a link where one takes a second or more. The panel and the finder share it (`Job::spawn`). A failed search says so in the summary line (`Results::Failed`).
- **The menu**: the openers launch apps of this Mac, so on another machine they are gone (and not even detected); "Copy path" (the path there) and "Copy relative path" stay. The selection's Open runs the editor in a tab there instead (see Selecting in the viewer).
- **Checked live** on 2026-10-29 with cornercase 0.12.225: the JSON of `list`, `read` (text, image, binary, too large, folder, missing) and `search` (names, text, non-ASCII lines), the exit codes, `--` and `./` paths, against a throwaway project on this Mac; the answers are the fixtures in `tests/fixtures/files/`. Through ssh (the local sshd and isolated server of `design/remote.md`) the panel listed the shown workspace's tree; the viewer, the search and the menu were not driven there.
- **Open with is a job** until the app it opens answers, so the status bar says so if it takes a moment.

## A machine's workspace (`there.rs`)

Upstream's `design/files-panel.md`, "A machine's workspace", and its `design/remote-windows/machine-panels.md`. How the choice is made and what the panels share is in `design/remote.md`.

- **With a machine's workspace picked in the sidebar the tree, the viewer and the search read that machine** (`Source::There`): `cornercase --remote DESTINATION files list`, `read` and `search`, parsed by the same functions as "Through the command line" above, with the `Target` of the machine rather than the window's. Browsing, searching by name and text, the viewer, find, selecting and copying, and the ⇧⌘P finder work as for a window on another server, and the tree's folder names its path with the machine's home as `~`.
- **This computer's disk is never asked about a machine's path, though the same path can exist here** (it does on the bench, where the machine is this box): only `Source::Disk` reads the disk, a machine's place cannot have one (`there::source_of`), a search asks the source first so nothing falls through to the walk (`Source::search`), the finder warms an index only for `Disk`, and the menu's `stat` for the default app is skipped unless the place is on this disk. The tests hold the same path here with other text. Live, a trace of the window's own threads (`strace -f`) over the tree, folders, search, viewer and finder found no file call under the machine's folder, and what it ran there was `cornercase --remote`.
- **Only reading**: `Open in…` and the selection's Open and Ask agent are not offered and the strip says `read only`; a row's right-click offers **Copy path** and **Copy relative path**, the machine's paths, to this computer's clipboard. A viewer's `Open` runs an editor in a tab there when the whole window is on another server, but a machine's tab is not this panel's to start.
- **A place of its own, gone when left**: it lives in `places` with the others, under a key made from the `Aim` and the destination with the top bit set (`there::place_key`), so it can name no workspace here even if a guard were missed, and a late answer for another machine, another `boot` or another destination finds no place; the destination stays known while the link is down, so a machine going down keeps its place. The local places stay as they were. Rejected: a key enum, which would take every `id` of the panel and of `find.rs` for a case that lasts while one workspace is picked, and a second `FilesPanel`, since the tree, viewer and search take their source already. Leaving also drops any search still running (`Search::forget`): its answer, opened with Enter, would have asked this disk for a machine's path.
- **Git marks, as on another server**: the tree's come in each `files list`'s `status`, and the viewer's margin from `changes file` there, only for a file the tree marks; a margin the machine does not answer keeps the marks it had. Upstream's panel leaves the margin out, since its marks come from the local Changes model; here it takes nothing but the request the margin already makes.
- **Polling, as a window on another server does**: one `files list` of the open folders every 2 s and one of the open file's folder every second, each a one-shot command, an ssh session each without the user's `ControlMaster`. The panel never asks while closed. `files list --follow` and `files read --follow` would be cheaper on a slow link; see "Rejected for now" above, which still holds.
- **A machine down keeps what is on screen**: the tree and the open file stay under `vps unreachable · reconnecting…`, and nothing is asked until the link is back. Opening a folder or a file, or searching, sends nothing and says so in a toast; closing a folder, going back to the tree, finding in the open file and copying still work. A search refused so runs by itself once the machine answers, rather than staying `Cannot search` under a live panel. A workspace picked while its machine is down shows `Nothing read from vps` until it is back.
- **A command that fails while the link says linked is not news about the files**: `There` answers `Content::Lost` and an error of kind `NotConnected` for each folder, which leave the file and the open folders as they are, where the same failure through `--remote` shows why in their place. The listing is not asked again until `cli::backoff`'s wait is over (`on_machine::Retry`, where the failures of one wait count once), with `vps did not answer · reconnecting…`, and until one is heard nothing new is asked: a folder, a file or a search sends nothing and says `vps did not answer: nothing was sent` (`on_machine::may_ask`). Only an answer about what shows counts, so a late one from a machine left cannot start or end this wait for the next. A file that really is gone or a folder's own `error` still reads as here. A stamp and a margin say nothing of their own: a stamp that fails reads the file, whose failure is what shows, and a margin that fails keeps its marks, while the listing every 2 s says when the machine stops answering. Rejected: a toast each 10 s over a decoration, and a `reconnecting…` for a `changes file` that fails while the machine answers everything else.
- **A server there that restarted drops what was shown**, since another `boot` is another `Aim` and so another place; the workspace is found again by path and name (`MachinePlace::followed`), its tree starts afresh and the viewer closes. `files list` and `files read` answer with `boot`, so an answer from a server that restarted before the view's line says so is not believed and counts as a failure. `files search` has none (#677 upstream); a result opened then asks by path, and only reads.
- **A file of a Flow run goes back here first** (`Store::read_run_file` leaves the picked place): the Flow panel stays on what is here (`design/machines.md`), and its path would otherwise be asked of the machine.
- **Left out**: a path printed in a machine's tab opens nothing, here or in the card, which reads `Disk` or the window's server (`spot_under`, `design/machines.md`). The search here has none of the ranking tie-break, as on another server (above).
- **Checked live** on 2026-11-06 with cornercase 0.13.1, Linux x86_64 under Xvfb with lavapipe, a fake `ssh` between two servers on one box; no real sshd, no macOS, no Windows: `only-there.txt` listed and opened though this computer's clone has none, a folder opened, a right-click with only the two copies, a search by name and by text with a result opened at its match, ⇧⌘P (`1 file in shop on vps`), a selection with only Copy, the tree's letters and the margin's bar for a file changed there, full screen, kept with the marks while the machine was down; `machines retry` with `ssh` held, keeping the viewer and the tree, the toast for another file, back to the tree and on again; `ssh` held with the link still up, `vps did not answer · reconnecting…` and folders still open, then back by itself; a search typed while the machine was down, its toast counting up and `Cannot search`, and its results by themselves once the link was back. Not checked: a real sshd and network, a big image over a slow link, a machine on another system.
