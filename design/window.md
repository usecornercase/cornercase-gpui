# Window

Code: `app.rs`

- **A connection is one struct** (`app/connection.rs`, `Connection`: a queue, a view and its surface, the grid, the size): `Root::own` is the window's, and while a machine's tab shows `MachineTab::conn` is beside it (`app/machine.rs`, `design/machines.md`). `Root::shown` is what the terminal area reads. Each stream's lines carry a serial, unique for the app's life, and a connection owns the serials of its live streams (`Connection::owns`), so a line of a stream that was dropped goes nowhere, and one code path handles both connections' lines. It replaced `generation`, which fenced a whole view and could not stop a surface alone.
- **While a machine's tab shows, the view stays and the surface stops** (`Connection::pause_surface`, `resume_surface`): the sidebar and every panel stay live on `view` and the feeds, the view is told `--hidden` and keeps its size and its claim on the tab, and nothing draws its frames, so nothing streams them. Why not `view-set --inactive` is in `design/machines.md`.
- **One connection, two streams**: the window first finds and checks the `cornercase` binary (`design/connection.md`; when it cannot use one it shows the missing page of `design/terminal.md` and does not retry by itself, unlike a lost connection); then `cornercase start-server --theme -` finds the running server or starts one and gives the terminals the theme in use's colours (a change gives `theme -` again once it settles, `design/theme.md`) (so programs pick a look that matches what we draw); only then does `view` open, and `surface --view` follows the view's id. A lost connection retries every 1.5 s (another machine backs off, `design/remote.md`); each new `view` bumps `generation`, so lines from an old stream are dropped.
- **Where the first view starts**: `--tab`, `--workspace` or `--project` on our own command line, else on what cornercase's window shows. Later views (after a reconnect) start on what the server's view settles on.
- **Another server replaces `Root`** (`Root::switch`, `design/remote.md`): the dialog asks through `Store::connect`, and the window builds a new `Root` with `replace_root` rather than resetting every field, keeping only the sidebar's and dock's widths and the zoom. The status bar (`app/status.rs`) names the server and opens that dialog.
- **A surface that ends is opened again** after 400 ms: the view lives on (it settles on a neighbour when its tab closes), so the stream is reopened for the same view instead of opening a new view. When it ends with the same error as last time (a server too old for `surface`, say), it waits 5 s instead, so a lasting failure does not run `cornercase` twice a second. The error stays in the terminal's place, in full, until a frame arrives: a toast alone left "Waiting for the terminal…" there with no reason given. It is toasted once, when it changes.
- **A view that shows no tab streams nothing** (`app/surface.rs`): cornercase pauses the surface while the view shows a project or workspace with nothing open, and refuses to open one then. So the surface opens only once the session shows a tab, and one that ends while the view shows none waits for a tab without a toast or a retry (`Feed::Waiting`); the terminal's place says no tab is open (`design/terminal.md`).
- **A window in the background does not count as seeing its tab**: `view-set --view ID --hidden` on deactivation and `--visible` on activation, so agents in the shown tab notify while the window is behind others. Since #461 upstream this works with `--view`, so it is always sent, with no fallback for a server that refuses it.
- **Keys go back to the terminal** when a dialog or sheet closes: `Root` watches `Store` and refocuses its own handle on that transition, since gpui would otherwise leave the focus on the closed view. It does the same when one sheet gives way to another, such as Search's row opening Accounts: the focused field left the tree while its panel, kept alive, keeps the handle, and gpui then sends keys to the root of its dispatch tree, where nothing listens, so Escape and every shortcut went dead until a click (found on 2026-11-06). `Root`'s observer runs before the panels', so a sheet that takes the focus when it opens still gets it. **While a sheet or dialog stays open and nothing holds the focus** (a question over a sheet was answered, a sheet's form closed and its fields went with it), `Root` takes it back as it draws (`keep_the_keys`): gpui clears the focus once the focused handle's last frame is gone, and a key with no focus reaches no listener of `Root`'s, whose `on_key` hangs on a child of the tree's root, so Escape stopped closing the sheet and every shortcut stopped working until a click (seen live on 2026-11-06 on the Machines sheet). A field a sheet keeps alive after hiding it is not caught, so a sheet drops its forms' fields with them (Machines', Accounts' since 2026-11-06), and a widget that stays keeps its handle in the tree (`design/accounts.md`, the picker).
- **Panels are built once** and kept in `Root::panels`, so a closed panel keeps its scroll, filters and fields when it opens again.
- **Floating surfaces on one ground** (`design/widgets.md`): `Root` paints the ground, and the rail's and the sidebar's cards, the panes, the dock and the tab pills float on it, 8 px (`GAP`) apart and in from the window's edges. The title row is 44 px (`TITLEBAR_HEIGHT`) of ground, the traffic lights moved to 16, 16 so they sit centred in it on a Mac (on Linux the mark takes their corner, below), and every card starts below it (`design/sidebar.md`). The status bar is quiet text on the ground under the panes, without a band or a line.
- **The sidebar and the dock take the width they are dragged to** (`design/widgets.md`), and a drag always leaves the terminal room for a few dozen columns. Changes, Files and TODO share one width, so switching between them does not resize the terminal and the programs in it; the Browser and the Flow panel each keep a width of their own, half the window up to 720 px until dragged, since a page and a flow's diagram need the room (`design/browser.md`, `design/flows.md`). The dock's width includes its right margin, so its handle sits on its card's left edge and a drag still measures from the window's edge (428 px, a 420 px card, until dragged). The sidebar no longer shrinks with the window, so its handle stays on its border; the row holding it and the workspace area is `min_w_0`, or its content's width (a long path in the status bar) would push the dock out of the window.
- **A file can take the terminal's area and the dock's** (`design/files-panel.md`, Full screen): the dock is laid over a terminal that keeps its size and is not painted, so its programs never notice.
- **The first window fits the screen** (`frame::opening_size`, every OS, 2026-11-04): it opens at 1280 × 800 where that fits in the primary display less 48 px on each side, else at what fits, and never below the minimum of 640 × 360; Linux's frame margin comes on top (`frame::outer`). The first run on Windows, on CI's 1024 × 768 screen, opened 1280 × 800 centred and lost the sidebar's left part and the title row past the screen's edges; a Mac or Linux laptop at a small resolution had the same problem. gpui 0.2.2 knows only a display's whole bounds, not the part the taskbar, the menu bar or a panel leave free, so the 48 px stand for them: Windows' taskbar is at most 48 px tall, and a window centred with 48 px above and below clears it (at 1024 × 768, 1366 × 768, and 1920 × 1080 at 125 % and 150 %). A 1440 × 900 Mac still opens at 1280 × 800, as before; a Mac's Dock can still cover the bottom of a window on a small screen. Rejected: asking each system for its work area (code per platform for one number at start).
- **The bell** in the shown tab is a short flash of the terminal's edge, not a sound: the sound is for agents' notices (`design/notifications.md`).
- **Drags**: `Drag::Program` sends presses, motion and releases to a program that reads the mouse; `Drag::Select` is cornercase's own selection, in cells of the pane; `Drag::Divider` moves a divider of the tab's split.
- **`CORNERCASE_GPUI_OPEN=<panel>`** opens a panel at start, to check it by eye; `CORNERCASE_GPUI_FONT_SIZE` sets the terminal's font size (13 by default); `CORNERCASE_GPUI_OPACITY` the opacity of the terminal's background over the theme's own (0.65 in cornercase dark, kept between 0.3 and 1; 1 makes it opaque, and below the ground's 0.55 it shows the ground alone, `design/widgets.md`), read once at start, as Ghostty's `background-opacity` is. Translucency depends on what is behind the window, so it is a setting rather than one value for everyone. On Linux, where the ground is opaque, it is how strongly Tokyo Night covers the ground, with no floor (`design/widgets.md`).

## Linux

- **The window draws its own frame** (`app/frame.rs`, 2026-11-04). It asks for client-side decorations (`WindowDecorations::Client`), as Zed does, and draws a title bar's work whenever gpui says the frame is the app's (`Decorations::Client`). GNOME on Wayland, the most common desktop, has no server-side decorations at all, and gpui 0.2.2 cannot tell a window that asked for them whether the compositor will draw them: without `xdg-decoration`, `request_decorations(Server)` still reports `Decorations::Server`, so a window that asked for server-side ones opens on GNOME with nothing to move, resize or close it by. Asking for client-side ones is safe everywhere because gpui falls back by itself where they cannot work: on X11 without a compositor, or under a window manager that does not support `_GTK_FRAME_EXTENTS` (openbox), it keeps the window manager's frame and reports `Decorations::Server`, and a Wayland compositor with `xdg-decoration` (KDE, sway) may answer server-side; the app then draws none of its own. Rejected: server-side with a client-side fallback (gpui does not say when the fallback is needed) and a setting to choose (Zed has one; nothing asks for it yet). The frame is read once per render (`Frame::read` in `Root::render`, passed down to the title rows, the sheet and the dialogs), and on macOS it is the system's title bar without asking the window, since nothing of it is used there: it was read three to five times a frame, each asking whether the window is maximised (a window lock and an `NSScreen` query on macOS).
- **The frame** is a 12 px margin around the window (`set_client_inset`) that holds a soft shadow and the resize grips, outside what shows as the window, as GNOME's own windows have; 20 px corners, the cards' 12 plus the 8 px between them, so the curves stay parallel; and a 1 px `border` line. A side that is tiled loses its margin, the corners beside it their curve, and a tiled or maximised window its shadow (`Tiling`). The grips are eight invisible strips with the resize cursors, each edge reaching 4 px into the window and each corner 16 px further, that start `start_window_resize`. A sheet's or dialog's veil takes the window's corners, or it would darken the margin's corners into squares, and the window clips what it holds, so the rail of a window too short for it ends at the window's edge rather than in the margin. The window opens larger by its margins (`frame::outer`), so it shows 1280 × 800 as on a Mac: at 776 px the rail did not fit. **The inset stays set while the compositor draws the frame** (sway answers server-side for a tiled window): gpui 0.2.2 reads it on Wayland in the configure that hands the frame back to the app, before the app renders again, so clearing it then would size that configure, and the window's geometry, without the margin until the next one. Meanwhile it only widens the margin a menu keeps from the window's edge when gpui snaps it (`snap_to_window_with_margin` adds the inset), from 8 to 20 px (rejected in review, 2026-11-04).
- **Under a window manager's frame the window gives the margin back** (`frame::fit_to_frame`, found 2026-11-04). Where the frame turns out to be the window manager's (X11 without a compositor or without `_GTK_FRAME_EXTENTS`: openbox, and most window managers without a compositor) no margin is drawn, so the window showed 1304 × 824. On X11 gpui settles the frame while it creates the window, so the window shrinks by its margins as soon as it is open, before its first frame, unless it opened maximised, tiled or full screen. **On Wayland it is not fitted** (`fitted` takes whether the window is on Wayland; gpui 0.2.2 reports the decorations the window asked for until the compositor first answers, after the window is built, so the fit already did nothing there, but the check says so rather than lean on it): the frame there comes in the compositor's answers, which can change, and sway answers server-side before it maps the window and client-side once the window floats. Fitting on that first answer, inline or on the next frame, fought sway's next configure (gpui's `resize` updates the size asynchronously, after sway had taken the smaller buffer) and left a floating window 12 px short with its bottom edge cut off. A Wayland compositor that keeps a frame of its own mostly tiles the window and sizes it itself. Limit: under sway a floating window still opens 1304 × 824, as it did before, since sway takes the size gpui gave while sway still answered server-side.
- **The minimum size counts what the window manager measures** (`frame::min_size`, 640 × 360 shown): on Wayland the window's geometry, which leaves the margin out whoever draws the frame, so 640 × 360 (it was 664 × 384, 24 px more than meant); on X11 the X window, margin included under our frame (`_GTK_FRAME_EXTENTS`), so 664 × 384. gpui 0.2.2 sets `WM_NORMAL_HINTS` once, as the window opens, and has no call to change them, so under a window manager's own frame (openbox) the minimum stays 664 × 384 of content; most X11 desktops have a compositor and draw our frame (GNOME on Xorg, KDE, Xfce, Cinnamon), where the margin belongs in it.
- **Checked live on 2026-11-04** (the same container, cornercase 0.12.280): openbox, `xwininfo` 1280 × 800 of content (1304 × 824 before), `WM_NORMAL_HINTS` minimum 664 × 384; xfwm4 with its compositor, unchanged: the X window 1304 × 824 with `_GTK_FRAME_EXTENTS` of 12 on each side, 1280 × 800 shown, and asked for 100 × 100 it stopped at 664 × 384, 640 × 360 shown; weston 14, unchanged: geometry 1280 × 800, and weston does not hold a window to its minimum size (it let one shrink to 127 × 72), so the minimum was not seen there; sway 1.10 nested in the X screen with a floating rule: 1304 × 824 as before, and shrunk by its corner it stopped at a geometry of 640 × 360.
- **The title row is the title bar** under a frame of the app's own: its empty ground (the sidebar's title strip, which reaches over the rail there, and the tab row between its tabs and its buttons) moves the window when dragged, zooms it on a double press, and opens the compositor's window menu on a right press where there is one (`window_controls().window_menu`). The move starts on the first motion after the press, as Zed's does, since a move started on the press takes the pointer, so the release that ends a click, and the second press of a double press, could be lost. A press that a tab, a button or the window's buttons took first claims the row (`Grip`, a gpui global) rather than stopping the event, so a tab can still be dragged and every press still gives the keys back to the terminal, as on a Mac. **A release or a press anywhere lets go of the row** (`on_mouse_up_out` and `on_mouse_down_out` besides its own release, as Zed's title bar does): gpui gives a row its own release and motion only over it, so a press on the row that left it before the first motion and was released over a pane stayed held, and a later drag from a pane that crossed the row moved the window (found in review and reproduced on 2026-11-04 under weston: the window moved; with the fix the drag stayed a selection).
- **The window's buttons** (minimise, maximise or restore, close) sit at the right end of the tab row, after the split buttons: 24 px circles with a faint fill, lighter on hover, and icons of the app's own (`assets/icons/window-*.svg`) drawn to the size of Lucide's ×. Only what the compositor allows shows (`window_controls()`, from Wayland's `wm_capabilities`); close always shows. The set and its order are fixed: GNOME's `button-layout` (close alone by default) is not read, as it is one desktop's setting and a window that only closes surprised more than three buttons did.
- **The window's background** is `Transparent` on Linux, for the frame's margin and corners (Wayland makes a window with client-side decorations transparent anyway; X11 under a compositor needs it), with the ground painted opaque inside them (`design/widgets.md`).
- **`app_id` is `cornercase-gpui`** (Wayland's `app_id`, X11's `WM_CLASS`), the name a `.desktop` file matches the window with.
- **Leaving full screen gives the window its size back on Wayland** (`frame::toggle_full_screen`, found 2026-11-04). A compositor may answer `unset_fullscreen` with a configure of 0 × 0, the client's choice (weston does), and gpui 0.2.2 then keeps the full-screen size: it restores the windowed size only when a window leaves maximised. The window came back as large as the screen, its buttons and its bottom past the edge. So F11, when it leaves full screen on Linux, keeps the size gpui last had windowed (`window_bounds()` is `Fullscreen` with it, on Wayland only) and, once gpui reports the window out of full screen, resizes it to that size unless the compositor already did, or left it maximised or tiled. A configure of 0 × 0 calls nothing in the app, so the window is asked every 20 ms for two seconds, then every 250 ms for as long as it stays full screen or open (`frame::restore_poll`): it used to give up after two seconds, which left a compositor slower than that with the screen's size (found in review, 2026-11-04). On X11 the window manager restores the size itself and gpui never reports `Fullscreen` bounds, so nothing runs there, nor on macOS. Limit: gpui's `resize` sets the surface's geometry without the frame's margin until the next configure, so the first resize by an edge after leaving full screen starts 24 px larger. Rejected: maximising and restoring to reach gpui's own restore (the window flashes maximised).
- **Checked live** on 2026-11-04 in Debian trixie (Docker, Xvfb, lavapipe), gpui 0.2.2. X11 under openbox (no compositor, no `_GTK_FRAME_EXTENTS`): openbox's frame and none of ours, `WM_CLASS` `cornercase-gpui`. X11 with no window manager: no frame at all, since nothing can draw one. X11 under xfwm4 with its compositor (as GNOME on Xorg): our frame, its margin and corners see-through over another window, a drag on the title row moves the window, a double press maximises and restores it, the restore button, resizing from the right edge and the bottom-right corner, minimise, close, xfwm4's window menu on a right press, and a press dragged off a split button leaves the window where it was. Wayland under weston (no `xdg-decoration`, as GNOME): the frame, the resize cursors on the edges and corners, moving, maximising, restoring, resizing, minimising, closing, and a sheet's veil keeping the corners. X11 at 2× (`Xft.dpi: 192`): the frame and the layout scale with it. After the review's changes (the same day): openbox still 1280 × 800 of content; weston still opens unfitted with 1280 × 800 shown, F11 in and out comes back to the windowed grid (146 × 50 full screen, 117 × 41 after), and a drag on the title row moves the window.
- **Not checked**: GNOME, KDE and sway themselves (Mutter's and KWin's frames, KDE answering server-side, sway's tiling), fractional scales on Wayland, a real GPU. Known limits: a menu snapped to the window's edge can reach 4 px into the margin, since gpui snaps it 8 px from the surface's edge; a window shorter than the rail shows a few pixels of it past the bottom-left curve, as the window clips to a rectangle.

## Windows

- **Windows draws the frame, the app draws the title bar** (`app/frame.rs`, 2026-11-04). With `appears_transparent`, gpui 0.2.2 hides Windows' title bar and keeps the rest of the frame: DWM draws the border, the shadow and Windows 11's rounded corners, and the left, right and bottom edges resize through the frame's invisible borders. So the window draws no margin, grip, shadow or corner of its own (`Frame::captioned` leaves `drawn` false). The title bar's work goes through Windows' hit test: gpui answers `WM_NCHITTEST` from the elements marked with `window_control_area`. The title row's ground (`title_row`: the sidebar's title strip, which reaches over the rail, and the tab row) is `Drag`, so Windows itself moves the window, snaps it to the screen's edges and maximises it on a double press (a right press was meant to open the system menu, and on the runner did not: below). The three buttons are `Min`, `Max` and `Close`, so Windows 11 shows Snap Layouts over maximise, and gpui minimises, maximises or restores, and closes the window when the button is released; they have no click handler of their own. Rejected: Linux's frame (`start_window_move`, `start_window_resize` and `show_window_menu` do nothing on Windows), and moving the window from the app's own handlers (no snapping, no Snap Layouts, no system menu).
- **Everything in the title row occludes** (from reading gpui 0.2.2's `on_hit_test_window_control` and `handle_nc_mouse_down_msg`). The hit test takes the first marked element under the pointer, up to the first one that blocks the mouse, so a tab or a button over the row's `Drag` would count as the title bar: what claims the row (`claimed`: the tab group and the split buttons) and the window's buttons `occlude`. gpui also hands a press on the title bar to the app's elements first, and leaves it to Windows only if none prevented the default. `Root`'s `track_focus` prevents it on every press that reaches it, so the row's ground occludes too, or no press on it would move the window. A press on a tab or a split button no longer reaches `Root` either, so `claimed` gives the keys back to the terminal itself, as `Root` does on a Mac and on Linux, unless an element in front took the focus first (the tab's rename field, whose `track_focus` prevents the default, and a context menu, which prevents it when it opens, so a right press on a tab leaves the keys to the menu on every platform).
- **A 4 px band along the top edge resizes the window** (`frame::resize_band`, while it is not maximised). gpui asks the marked elements before it reports the top edge (the top `SM_CYFRAME` pixels of the content), so a title row marked up to the top would leave nothing to resize by, and a press there would reach `Root` first, as above. An unmarked strip that occludes, in front of everything (dialogs included), lets gpui fall through to the edge, as the left, right and bottom edges always do. A maximised window has no band, and the close button reaches the screen's corner.
- **The window's buttons look like Windows'**: 46 px wide, the title row's full 44 px tall (Windows' 32 px would put their glyphs 6 px above the tabs' centre), flush with the window's top and right edges (the tab row drops its right margin, `Frame::title_end`) and with no gap between them; a faint fill on hover (`colours::hover`), and close turns `#C42B1C`, Windows 11's red, with a white glyph. The glyphs are the Linux buttons' (`assets/icons/window-*.svg` and Lucide's ×) at 18 px, about the 10 px box Windows draws its own in. Rejected: Segoe Fluent Icons (missing on Windows 10, and gpui falls back silently to a font without those glyphs) and Segoe MDL2 Assets; a font's glyph is text, which gpui 0.2.2 cannot recolour on hover (`design/widgets.md`), and close's glyph has to turn white. No pressed look: Windows does not capture the mouse for a press on these buttons, so a release outside the window would leave one looking pressed. In full screen (F11) gpui stops answering the hit test, so the buttons, the `Drag` and the band go, as the traffic lights do on a Mac; F11 leaves it.
- **The window's background is `Opaque` to gpui, and acrylic to Windows** (`frame::show_backdrop`, `app/frame/win32.rs`, 2026-11-04): gpui 0.2.2 leaves its own accent off, and the window asks DWM for Windows 11's acrylic backdrop (`DWMWA_SYSTEMBACKDROP_TYPE`, `DWMSBT_TRANSIENTWINDOW`) in dark mode, with the frame extended over the whole client area. gpui draws into a DirectComposition swap chain with premultiplied alpha, so where the ground is translucent the backdrop shows through. When DWM refuses (Windows 10, or 11 before 22H2) the ground stays opaque, as on Linux (`design/widgets.md`).
- **Sizes**: gpui sizes the content on Windows and adds the frame's borders itself (`calculate_window_rect`, and `WM_GETMINMAXINFO` for the minimum), so the window opens at the size it shows (`frame::outer` adds nothing), its minimum is 640 × 360 of content, `fit_to_frame` has nothing to give back, and F11 is gpui's own, which keeps and restores the windowed rectangle, so `windowed_size` stays Linux's. The first size fits the screen (above).
- **The exe's icon, manifest and version** (`build.rs`, `assets/windows/`, 2026-11-04) are resources that `embed-resource` compiles from `assets/windows/cornercase-gpui.rc`: rc.exe on a Windows host, `llvm-rc` (on the `PATH`) after the target's C preprocessor when cross-compiling (`cargo xwin`). The build script returns at once for any other target. The cost on macOS and Linux is compiling `embed-resource` and the `toml` crates it reads `Cargo.toml` with, once.
  - **The icon** is resource 1, which gpui 0.2.2 loads for the window and the taskbar (`load_icon`). `assets/windows/cornercase-gpui.ico` holds the mark on the ground, as `assets/linux/cornercase-gpui.svg` draws it (`ui/brand.rs`'s 12-unit grid on a tile with 28/128 corners), at 16, 20, 24, 32, 40, 48, 64 and 256 px; each size snaps the grid's unit to whole pixels, so the bars stay sharp (the mark is 75 % of the tile at 16 and 32 px, 50 % at 24 and 48, 56 % from 64, as on Linux). Sizes up to 64 px are bitmaps with an alpha channel and a mask, 256 px a PNG, as Windows' own tools write them. `tools/icon.py` draws it with Python's standard library alone: `python3 tools/icon.py assets/windows/cornercase-gpui.ico` after a change to the mark or the Linux icon. The same tool writes the macOS bundle's `.icns` from the extension of its output file, on Apple's grid (`design/releases.md`).
  - **The manifest** (`cornercase-gpui.manifest`) is required: gpui 0.2.2 imports `TaskDialogIndirect` from `comctl32.dll`, which only common controls 6 export, so without the manifest the exe does not start, and gpui relies on it for DPI awareness (it never calls `SetProcessDpiAwarenessContext`; unaware, Windows would stretch a blurry window on a scaled screen). It declares Per-Monitor V2 DPI awareness (with `dpiAware` for older systems, as gpui's own), common controls 6, Windows 10 and 11 (`supportedOS`), and UTF-8 as the process's code page (Windows 10 1903 and later), so any `A` API a dependency calls reads Rust's UTF-8 strings; Rust's standard library and gpui use the `W` ones. Rejected: `longPathAware` (Rust's `std::fs` already turns long paths into `\\?\` ones), a `trustInfo` (a 64-bit process is never virtualised).
  - **gpui's own manifest is turned off** (`default-features = false` without `windows-manifest`): gpui's build script embeds it only on a Windows host, and links it through a library, so it reached the exe built on Windows but not one cross-compiled from a Mac, which had no resources at all and could not start. Two manifests are a duplicate resource the linker refuses, so one place, ours, now gives every build the same one.
  - **The version** (`VERSIONINFO`, from `Cargo.toml`'s version through the build script's macros) names the program "cornercase" (`FileDescription`, `ProductName`) where Windows shows a program's name rather than its window's title: Task Manager, the volume mixer, the taskbar's menu and Open with.
  - **Release builds on a Windows host need `fxc.exe`** from the Windows SDK (gpui compiles its HLSL shaders then; `GPUI_FXC_PATH` points at it), and a release build cannot be cross-compiled from a Mac (gpui's build script compiles the shaders only on a Windows host, and the release crate includes them; read in gpui's `build.rs`, not tried). Debug builds compile the shaders at run time.
- **Errors before the window opens show in a message box** (`main.rs`, `fail`): a program built for the GUI subsystem started from Explorer has no console, so a bad argument, no font to draw with, or a window gpui cannot open would end it silently. They still go to standard error, which a console or a redirect gets.
