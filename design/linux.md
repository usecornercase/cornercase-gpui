# Linux

Code: `Cargo.toml` (the macOS-only crates, the `libc` cap), `platform.rs`, `panels/files/peek/no_player.rs`, `.github/workflows/ci.yml` (the Linux job), `assets/linux/`, `tools/linux/Dockerfile`; each area's Linux behaviour is in its own file

- **Linux is a second platform of the same app, not a port**: one code base, the same commands and the same look, with the platform's conventions where a Mac's would be wrong there (asked for on 2026-11-04). gpui 0.2.2 draws on both through its default `wayland` and `x11` features (Vulkan through blade on Linux, Metal on macOS); macOS's behaviour did not change.
- **Platform code is plain logic that takes the platform**: what differs (a label, a key, a command, a path) is a function of `platform::Os`, tested for both values on any host, and the call site passes `Os::CURRENT`. `#[cfg(target_os = "macos")]` is kept for code that cannot compile elsewhere: the AVFoundation player (`peek/player.rs`), whose Linux twin `no_player.rs` is an uninhabited `Player` with the same methods, so the preview card compiles unchanged and media fall back to a preview; and the three crates it needs (`core-foundation`, `core-video`, `objc2`), which are macOS-only dependencies. Rejected: a trait per platform service (a second implementation of every method for one difference each) and `cfg` blocks spread through the panels (code that only one platform's clippy sees rots on the other).
- **clippy and the tests run on both** (CI's Linux job on ubuntu-24.04, x86_64): code for one platform must leave no dead code, unused import or unused variable on the other, so a test that only one platform runs keeps its imports inside it.
- **Building needs a C compiler, `pkg-config` and four libraries' headers** (xkbcommon with its X11 part, FreeType, Fontconfig, Wayland's client library), the README's `apt` line. The binary links only `freetype`, `xcb`, `xkbcommon` and `xkbcommon-x11`; gpui opens Wayland's client library, Fontconfig and the Vulkan loader at run time, so running needs a Vulkan driver (Mesa's on most machines). Checked on 2026-11-04 with a clean build in a bare Debian trixie with only those packages.
- **`libc` stays below 0.2.190** (`Cargo.toml`): 0.2.191 dropped `ENOATTR` on Linux, and `xattr` 0.2.3, which gpui 0.2.2 pulls in through `gpui_http_client` and `zed-async-tar`, does not build without it. The cap goes once gpui no longer depends on `xattr` 0.2; a newer gpui is a manual bump anyway (`AGENTS.md`).
- **Starting it from the desktop**: `assets/linux/cornercase-gpui.desktop` and its icon (the mark on the ground, drawn as `ui/brand.rs` draws it), installed by hand as the README says, since there is no package yet. The window's app id is `cornercase-gpui`, the desktop file's name and `StartupWMClass`, so docks group the window with its launcher. A launcher sees the session's `PATH`, not the shell's, so the README shows `CORNERCASE_BIN` on its `Exec` line for a `cornercase` that only the shell finds.
- **Checking it from a Mac** (`tools/linux/Dockerfile`): a Debian trixie image with the build libraries, Rust (the pinned version, installed on first use), `cornercase` for Linux, Xvfb, openbox (an X11 window manager with server-side decorations), weston (Wayland without server-side decorations, as GNOME), Mesa's software Vulkan (lavapipe), xdotool, ImageMagick, Chromium, libnotify and the freedesktop sound theme. Build it once, keep a container with the checkout mounted and the target directory in a volume, and run the checks or the window in it:

  ```sh
  docker build -t cornercase-gpui-linux tools/linux
  docker run -d --name cornercase-gpui-linux -v "$PWD":/work -v cornercase-gpui-linux-target:/target cornercase-gpui-linux sleep infinity
  docker exec cornercase-gpui-linux bash -lc 'cargo clippy --all-targets --all-features --locked -- -D warnings && cargo test --locked'
  docker exec -d cornercase-gpui-linux bash -lc 'Xvfb :99 -screen 0 1600x1000x24 & openbox & cargo run'
  docker exec cornercase-gpui-linux bash -lc 'import -window root /work/target/linux.png'
  ```

  Software Vulkan is slow but draws everything; keys go in with `xdotool key ctrl+shift+t`. Everything in the container is throwaway, so a project to try things on is `cornercase open` of a `git init` in `/tmp`.
- **First run on Linux** (2026-11-04, Docker Debian trixie arm64, Xvfb and openbox, lavapipe, cornercase 0.12.280): once it built, the window opened on the server it started, drew the rail, the sidebar and a shell that answered, with nothing changed but the build. What needed Linux's own answers is in the areas' files: keys and the mouse (`design/terminal.md`), the window's decorations, ground and fonts (`design/window.md`, `design/widgets.md`), and opening files and links, openers, notifications, sounds, previews and Chrome (`design/files-panel.md`, `design/notifications.md`, `design/browser.md`).
- **Checked together** (2026-11-04, the merged keys, window and desktop work; Debian trixie arm64 in a container, lavapipe, cornercase 0.12.280, gpui 0.2.2, xdotool), in three setups: X11 under openbox (its frame), X11 under xfwm4 with its compositor (our frame, see-through corners and shadow over another window) and Wayland under weston nested in the X screen (our frame). In each: the window opened with that frame, moved, maximised and restored, minimised and quit, the grid filled its pane (`stty size` matched the status bar), bold showed; Ctrl+Shift+T, Alt+1 and Alt+2, Ctrl+Shift+D, Ctrl+Shift+[ and ], Ctrl+Shift+W, the docked panels' Ctrl+Alt+Shift keys, Ctrl+Shift+/ with every Linux label, Escape, Ctrl+Shift+=, - and 0, F11, Ctrl+Shift+M and Ctrl+Shift+Q; copying a double-clicked word and pasting it; Ctrl+click on a path and on an address reaching `xdg-open`. Typing arrived exactly at xdotool's default speed and with no delay at all (`echo "a b  c" && ls -la`, `cat paths.txt; echo one two three four five`), on X11 and on Wayland: an earlier branch's report of spaces lost ("catpaths.txt") did not happen on the merged build, and a space still goes as text through gpui's input handler (`keys::key_event` leaves it alone). On X11 also: Ctrl+C on `sleep 100`, Alt+B, Tab completion and ↑ in bash, AltGr, dead keys and ñ on a Spanish layout (`cat -v` got them once each), a drag and a double click selecting, the terminal's and the sidebar's menus (Open in file manager ran `FileManager1`, then `xdg-open`), dragging a tab, the split and the sidebar's edge, the wheel through history, Files (the tree, the viewer, the finder on Ctrl+Alt+Shift+P, the cards of a PNG, a binary file, a video and a sound), Changes and its diff, Settings' search field with Ctrl+A, Ctrl+C, Ctrl+X, Ctrl+V and Ctrl+Shift+V, Search, Processes, the Browser panel loading a local page through Chromium, a toast, and a finished fake agent's `notify-send` and `paplay` while minimised (on Wayland too). Found and fixed: leaving full screen on Wayland kept the screen's size (`design/window.md`). Bash in the container's C locale reads UTF-8 bytes as meta keys, so AltGr characters typed into it looked wrong there; `cat -v` showed they arrived intact. On macOS the same day (macOS 26, cornercase 0.12.244, a throwaway tab, keys posted to the app's pid): the window looked as before, with its traffic lights, glass and mark; typed text, ⌘T, ⌘W, the ⌘/ dialog (`design/terminal.md`), ⌘M and ⌃⌘F worked.
- **Not checked**: a real GNOME or KDE session, a hardware GPU driver, a HiDPI screen, x86_64 outside CI's build and tests.
