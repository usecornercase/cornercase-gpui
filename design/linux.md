# Linux

Code: `Cargo.toml` (the macOS-only crates, the `libc` cap), `.github/dependabot.yml` (the `libc` ignore), `platform.rs`, `desktop.rs`, `panels/files/peek/no_player.rs`, `notify/center/no_cocoa.rs`, `ui/text_field/secure/no_carbon.rs`, `.github/workflows/ci.yml` (the Linux job), `.github/workflows/release.yml` (the Linux download), `assets/linux/`, `tools/linux/Dockerfile`, `tools/linux-check.sh`, `tools/linux-check-test.sh`; each area's Linux behaviour is in its own file

- **Linux is a second platform of the same app, not a port**: one code base, the same commands and the same look, with the platform's conventions where a Mac's would be wrong there (asked for on 2026-11-04). gpui 0.2.2 draws on both through its default `wayland` and `x11` features (Vulkan through blade on Linux, Metal on macOS); macOS's behaviour did not change.
- **Platform code is plain logic that takes the platform**: what differs (a label, a key, a command, a path) is a function of `platform::Os`, tested for both values on any host, and the call site passes `Os::CURRENT`. `#[cfg(target_os = "macos")]` is kept for code that cannot compile elsewhere: the AVFoundation player (`peek/player.rs`), whose Linux twin `no_player.rs` is an uninhabited `Player` with the same methods, so the preview card compiles unchanged and media fall back to a preview; macOS's own notifications (`notify/center/cocoa.rs`, whose twin `no_cocoa.rs` has no bundle identifier, so Linux keeps `notify-send`); macOS's secure event input (`ui/text_field/secure/carbon.rs`, whose twin `no_carbon.rs` takes nothing); and the crates they need (`core-foundation`, `core-video`, `objc2`, `objc2-foundation`, `objc2-user-notifications`, `block2`), which are macOS-only dependencies. Rejected: a trait per platform service (a second implementation of every method for one difference each) and `cfg` blocks spread through the panels (code that only one platform's clippy sees rots on the other).
- **clippy and the tests run on both** (CI's Linux job on ubuntu-24.04, x86_64): code for one platform must leave no dead code, unused import or unused variable on the other, so a test that only one platform runs keeps its imports inside it.
- **The Linux job also checks the shell scripts** (#123): shellcheck on `tools/*.sh`, then every `tools/*-test.sh` (the bench's, `windows-clippy-test.sh` and `linux-check-test.sh`) under two shells (which, and why, in `design/manual-check.md`). They follow the tests and run unless the run is cancelled, shellcheck's install included, so a red clippy hides none of them and they hide nothing of it. shellcheck is 0.11.0, pinned through `taiki-e/install-action` as the guardrails pin their cargo tools, at its default severity, so an `info` note such as an unquoted variable (SC2086) fails too. Rejected: the runner's own shellcheck, Ubuntu 24.04's 0.9.0 (0.10.0 alike), which flags `A && [ … ] || C` (SC2015) on three lines of `machine-bench.sh`, a form 0.11.0 no longer flags, so what Homebrew's 0.11.0 passes on a Mac would fail in CI; and the guardrails job, also on Linux, since #123 asked for this one. Checked on 2026-11-10 in an `ubuntu:24.04` container, as a user without root and with the runner's shells (dash 0.5.12 as `sh`, bash 5.2.21, no zsh): the 44 stub tests passed under each shell; with `machine-bench.sh`'s refusals exiting 3 instead of 2, the run failed; shellcheck 0.11.0 passed `tools/*.sh`.
- **Building needs a C compiler, `pkg-config` and four libraries' headers** (xkbcommon with its X11 part, FreeType, Fontconfig, Wayland's client library), the README's `apt` line. The binary links only `freetype`, `xcb`, `xkbcommon` and `xkbcommon-x11`; gpui opens Wayland's client library, Fontconfig and the Vulkan loader at run time, so running needs a Vulkan driver (Mesa's on most machines). Checked on 2026-11-04 with a clean build in a bare Debian trixie with only those packages.
- **`libc` stays below 0.2.190** (`Cargo.toml`): 0.2.191 dropped `ENOATTR` on Linux, and `xattr` 0.2.3, which gpui 0.2.2 pulls in through `gpui_http_client` and `zed-async-tar`, does not build without it. The cap goes once gpui no longer depends on `xattr` 0.2; a newer gpui is a manual bump anyway (`AGENTS.md`). Dependabot ignores `libc` from 0.2.190 up (`.github/dependabot.yml`, #122): left alone it rewrites the cap to take the new release (`<0.2.192` in its pull request #30), and the Linux job fails on `ENOATTR`; the ignore goes with the cap.
- **Starting it from the desktop**: `assets/linux/cornercase-gpui.desktop` and its icon (the mark on the ground, drawn as `ui/brand.rs` draws it), installed by hand as the README says (they also come in the release's archive, `design/releases.md`); packages wait on #25. The window's app id is `cornercase-gpui`, the desktop file's name and `StartupWMClass`, so docks group the window with its launcher. Its category is `Development` and not `TerminalEmulator`: xdg-terminal-exec, which GLib 2.82 and later use to open `Terminal=true` apps, picks a terminal by that category and would run `cornercase-gpui -e <command>`, which this window does not take (it is cornercase's window, not a terminal that runs a command); `desktop-file-validate` 0.28 passes it. A launcher sees the session's `PATH`, not the shell's, so the window asks the login shell and looks in the installers' folders itself (`design/connection.md`); `CORNERCASE_BIN` on the `Exec` line is no longer needed for the usual installs. The README's `sed` writes the binary's full path in double quotes, as the desktop entry spec asks of an argument with a space: unquoted, a home with a space left GLib unable to launch it (`gio launch`: "Unable to load application information"), though `desktop-file-validate` passed both (checked on 2026-11-04).
- **Checking it from a Mac** (`tools/linux/Dockerfile`): a Debian trixie image with the build libraries, Rust (the pinned version, installed on first use), `cornercase` for Linux, Xvfb, openbox (an X11 window manager with server-side decorations), weston (Wayland without server-side decorations, as GNOME), Mesa's software Vulkan (lavapipe), xdotool, ImageMagick, Chromium, libnotify and the freedesktop sound theme. Its `RUN` lines run in bash with `pipefail`, so a download that fails fails the build rather than piping nothing into `sh`. Build it once, keep a container with the checkout mounted and the target directory in a volume, and run the checks or the window in it:

  ```sh
  docker build -t cornercase-gpui-linux tools/linux
  docker run -d --name cornercase-gpui-linux -v "$PWD":/work -v cornercase-gpui-linux-target:/target -e CARGO_TARGET_DIR=/target cornercase-gpui-linux sleep infinity
  docker exec -d cornercase-gpui-linux bash -lc 'Xvfb :99 -screen 0 1600x1000x24 & openbox & cargo run'
  docker exec cornercase-gpui-linux bash -lc 'import -window root /work/target/linux.png'
  ```

  Software Vulkan is slow but draws everything; keys go in with `xdotool key ctrl+shift+t`. Everything in the container is throwaway, so a project to try things on is `cornercase open` of a `git init` in `/tmp`.
- **The checks from a Mac** (`tools/linux-check.sh`, #191's "Beside it"): one team wrote "Linux Docker (no image)" while the image was there, so the script looks, in order and stopping at the first that is missing, for `docker` on the `PATH`, a daemon that answers (`docker version`) and the image, and says which and what Docker said. Statuses: 0 clean; 2 a wrong word (`-j N` is the only one); 3 something it needs is missing, nothing run (the same 3 as `design/windows.md`); anything else is the container's, cargo's 101 or docker's 125 to 127. Decisions:
  - **A container of its own for each run** (`--rm --init`, named for the script's pid), never the recipe's long-lived one: that mounts one checkout, so a container made from another worktree checks that worktree's files, and it may not exist (it does not on this Mac).
  - **This checkout mounted at its own path.** The build volume is shared and cargo's freshness check for a path package compares file times, so two checkouts both mounted at `/work` would be one package in one target, and a checkout older than another's last build would get that build's results. At its own path each checkout is a package of its own, and the dependencies are still built once. The cost is a build of the crate per checkout left in the volume (#231).
  - **The volume stays shared**, so the dependencies compile once and two runs wait on cargo's lock, which cargo prints, better than two builds at once on a Mac of 10 cores and 16 GB. A volume per checkout was rejected: each would compile every dependency and nobody would remove them.
  - **`CARGO_TARGET_DIR=/target` is set by the script**: the image on this Mac was built from a draft of the Dockerfile that lacks that `ENV`, and without it the build lands in the checkout's `target/`, over the macOS build (`target/debug/cornercase-gpui` would become a Linux binary, the path `tools/manual-check.swift` acts on). The recipe's `docker run -d` line gets the flag for the same reason.
  - **`--pull never`**, and no image is built: a missing image is the owner's to build (a long, deliberate act), and the message points here. The crates download on each run, since the registry lives in the container; kept small on purpose, the rest is #231.
  - Measured on 2026-11-13 (Docker 29.1.2, arm64, nothing else building): a first run, with the volume holding a build from 2026-11-09, took about 5 minutes (the crate and its dependencies' changes, `-j 4`); a second run 22 seconds. The container was gone after each, and `target/debug/cornercase-gpui` was still a Mach-O.
  - Tested by `tools/linux-check-test.sh` with a stub `docker` on a `PATH` of its own, in CI's Linux job, which has a real one that must never be reached.
- **Following the system and the ground**: the light and dark switch comes from the xdg-desktop-portal's `color-scheme` through gpui; the Appearance page's ground slider is replaced by a note, since the ground is opaque (`design/theme.md`).
- **First run on Linux** (2026-11-04, Docker Debian trixie arm64, Xvfb and openbox, lavapipe, cornercase 0.12.280): once it built, the window opened on the server it started, drew the rail, the sidebar and a shell that answered, with nothing changed but the build. What needed Linux's own answers is in the areas' files: the keys (⌘ as Ctrl+Shift, ⇧⌘ as Ctrl+Alt+Shift, tabs on Alt+1…9) and Ctrl+click (`design/terminal.md`, `keymap.rs`, `keys.rs`); the window's own frame where the compositor leaves it to the app (`design/window.md`, `app/frame.rs`); an opaque ground in the same colours, since Linux compositors do not blur, and fonts that are installed, which also gave the terminal its real cell width (`design/widgets.md`, `theme.rs`, `theme/fonts.rs`); and opening files and links with `xdg-open` and the file manager, editors, `notify-send`, the freedesktop sounds, the desktop's thumbnailers and Chrome's flags (`desktop.rs`, `notify/alert.rs`, `design/files-panel.md`, `design/notifications.md`, `design/browser.md`).
- **Checked together** (2026-11-04, the merged keys, window and desktop work; Debian trixie arm64 in a container, lavapipe, cornercase 0.12.280, gpui 0.2.2, xdotool), in three setups: X11 under openbox (its frame), X11 under xfwm4 with its compositor (our frame, see-through corners and shadow over another window) and Wayland under weston nested in the X screen (our frame). In each: the window opened with that frame, moved, maximised and restored, minimised and quit, the grid filled its pane (`stty size` matched the status bar), bold showed; Ctrl+Shift+T, Alt+1 and Alt+2, Ctrl+Shift+D, Ctrl+Shift+[ and ], Ctrl+Shift+W, the docked panels' Ctrl+Alt+Shift keys, Ctrl+Shift+/ with every Linux label, Escape, Ctrl+Shift+=, - and 0, F11, Ctrl+Shift+M and Ctrl+Shift+Q; copying a double-clicked word and pasting it; Ctrl+click on a path and on an address reaching `xdg-open`. Typing arrived exactly at xdotool's default speed and with no delay at all (`echo "a b  c" && ls -la`, `cat paths.txt; echo one two three four five`), on X11 and on Wayland: an earlier branch's report of spaces lost ("catpaths.txt") did not happen on the merged build, and a space still goes as text through gpui's input handler (`keys::key_event` leaves it alone). On X11 also: Ctrl+C on `sleep 100`, Alt+B, Tab completion and ↑ in bash, AltGr, dead keys and ñ on a Spanish layout (`cat -v` got them once each), a drag and a double click selecting, the terminal's and the sidebar's menus (Open in file manager ran `FileManager1`, then `xdg-open`), dragging a tab, the split and the sidebar's edge, the wheel through history, Files (the tree, the viewer, the finder on Ctrl+Alt+Shift+P, the cards of a PNG, a binary file, a video and a sound), Changes and its diff, Settings' search field with Ctrl+A, Ctrl+C, Ctrl+X, Ctrl+V and Ctrl+Shift+V, Search, Processes, the Browser panel loading a local page through Chromium, a toast, and a finished fake agent's `notify-send` and `paplay` while minimised (on Wayland too). Found and fixed: leaving full screen on Wayland kept the screen's size (`design/window.md`). Bash in the container's C locale reads UTF-8 bytes as meta keys, so AltGr characters typed into it looked wrong there; `cat -v` showed they arrived intact. On macOS the same day (macOS 26, cornercase 0.12.244, a throwaway tab, keys posted to the app's pid): the window looked as before, with its traffic lights, glass and mark; typed text, ⌘T, ⌘W, the ⌘/ dialog (`design/terminal.md`), ⌘M and ⌃⌘F worked.
- **Not checked**: a real GNOME or KDE session, a hardware GPU driver, a HiDPI screen, x86_64 outside CI's build and tests.
