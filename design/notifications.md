# Notifications

Code: `src/notify.rs`, `src/notify/`, `src/app/toasts.rs`, `src/store/toasts.rs`

- **What cornercase tells the user outside the terminal**: agent notices (a toast with a "Go" button that runs `go TOKEN`, a desktop notification while the window is in the background (on macOS a click on it does what Go does), the sound the server chose), what the server says besides (`message` events: `cornercase notify`, the queue's and its routines', a failed setup, a flow's agent waiting for your consent, a run whose agents closed after its merge; the bullet "Messages" below), what programs ask of the host terminal (clipboard writes, bells), and the app's state in the status bar (an update to install, away on chat apps, keeping the machine awake).
- **One `events --notices --host --json` stream per server run**: the notifier follows the run (`boot`) the view shows, and starts again when the boot changes. A new boot also resets what this window installed or was waiting to restart, since that is now running, or gone, and says whether the restart took (see Updates). A generation number tells the current stream from a replaced one whose end arrives late.
- **When `events` ends** (the server stopped or refused), it is followed again after 3 s while the window is connected; the first failure with a message becomes one error toast, not one per retry.
- **Events format 1** is parsed with serde (`notify/feed.rs`); events this client does not act on (status, opened, closed…) and those of a newer server read as `Other`, so a new event kind never breaks the stream. Tests use cornercase's own fixtures in `tests/fixtures/events/` and `tests/fixtures/app/`.
- **A notice of an agent on a machine** (`machine` in the line, `Notice::there`, fixture `events/notice-machine.json`, captured on the bench): cornercase tells it on `events --notices` with the machine's name, its message (`claude on vps needs you in shop › notes`), its sound, and `panes` of that machine, with no `project` or `workspace`. It goes through the same toast, desktop notification and sound as ours. **Its ` Go ` cannot be `go TOKEN`**: `go --view` refuses it, and without `--view` it would move cornercase's own window. So the toast keeps the machine, the `boot` it came under and the panes as `ThereId`s (`ToastGo::Machine`), and ` Go ` picks the tab holding the first of them that is still there (`Store::go_there`, `design/machines.md`); a pane gone, or another `boot`, says `claude in shop › notes is gone`. The token is not used, so the server's own "still needs you" toast logic is unaffected. While that workspace is the picked place and the window is active, the notice is dropped, as cornercase drops one for a tab seen in a view; with the window behind, it comes.
- **Messages** (#217, `notify/telling.rs`, `Event::Message` in `notify/feed.rs`; cornercase 0.13.39 and newer, #700 and #748 upstream; no version gate, since an older server sends none): `events --notices --host --json` also carries the sentences the server tells by itself, as `{"event":"message","kind":…,"message":…,"panes":[…],"workspace":N}`. Fixtures `events/message.json`, `message-workspace.json` and (#260) `message-failed.json` are upstream's own files, byte for byte; `message-workspace.json` stays because older servers still send its ▶ sentence. `kind` is read by `telling::Kind::of`; a kind this window does not know, a newer server's, is told like `notify`, since it is still a sentence for a person. A line with no `message` is skipped like any line serde refuses. `project` and `time` are not read (nothing would use them).
  - **What each kind becomes** (the toast's kind, the button, the desktop notification's headline while the window is behind): `notify` Done, Show, `Message`; `queue-started` Done, Show, `Queue`; `queue-failed`, `queue-missed` NeedsYou, Open Queue, `Queue`; `queue-kept` NeedsYou, Show, `Queue`; `setup-failed` NeedsYou, Show, `Setup`; `flow-consent` NeedsYou, Show, `Flow`; `flow-merged` Done, or NeedsYou when its line has `failed: true`, Reopen agents, no notification; any other kind with `failed: true` is NeedsYou too (the contract defines `failed` as the bad ending of a kind that has two, and `Message::failed` is read for every kind); an unknown kind Done, Show if it names a pane or workspace, `Message`. The notification's body is cornercase's sentence. No message plays a sound: cornercase's own window plays none for them and the event carries none.
  - **The toast's kind**: what waits for the person is NeedsYou, as an agent's `failed` notice already is (`Notice::toast_kind`); what only informs is Done, matching cornercase's own ✓. So no message lasts under 15 s. Rejected: Info for `notify` and `queue-started` (4 s is too short to read a person's sentence), Error for `queue-failed` and `setup-failed` (8 s, and red reads as "your press failed"; the Queue panel keeps its red cross in its rows), and a fifth toast kind and colour for what Done already says. **A failed ending is NeedsYou** (#260, cornercase 0.13.72's `failed`, upstream #824 and PR #837): a merged run's agents closed all the same, only the free of its build folders failed, which waits for the person (the same rule as `queue-failed` and `setup-failed`). Rejected: Error (red is for "your press failed"; nothing the person pressed failed), Done (the green toast that said a failure only in words was the bug) and a fifth kind. Reopen agents stays on it, since the agents closed, and it lasts 15 s like every NeedsYou.
  - **The headlines** name where the message comes from (`Message`, `Queue`, `Setup`, `Flow`), since cornercase's kinds name the source first. Rejected: headlines that repeat the sentence, `cornercase` (the banner already names the app), and the pane's program for `notify` (the foreground program is not reliably the one that ran it).
  - **The buttons' commands** are built from the message's own fields when it arrives, never from the session (only Reopen agents' status-bar label takes the workspace's name from the session, else `workspace W`): a `queue-started` for a new worktree can arrive before the view line that holds its pane. **Show** runs `focus --pane P` for the first pane named (every known kind names its subject alone or first), else `focus --workspace W`, through `Store::act`, which adds `--view`; a pane gone by the press gives cornercase's own error as a toast. **Open Queue** is `ToastGo::Open(PanelKind::Queue)`, for a queue message that names no pane or workspace (the entry waits in the sheet's "Did not start"). **Reopen agents** is `ToastGo::Job`, from `store::reopening` (the one place that writes `agents reopen`): `Store::go` runs it with `run_aside_once`, a job beside the queue that the status bar names, keyed `reopen:W`, the workspace's one Reopen job (`design/flows.md`, "One job per workspace"); `ToastGo::Run` would hold the ordered queue behind a command that only waits. `notify` from outside a pane, and an unknown kind that names nothing, have no button. Rejected: Go (it is `go TOKEN` for agents), resolving the place at the press against the session (a third variant and lookups for a 15 s toast), `focus` on every pane, no button for `queue-failed` and `queue-missed`, and `--boot` on the reopen (`reopening` sends none, `Posted` forgets clicks on a new boot, and the toast lives 15 s).
  - **The text is cornercase's sentence as it comes, whole**, `flow-merged` included, as agents' notices are shown: it carries what no field does (how much was freed, which worktree kept its builds and why, why a queue entry failed, the routine's label and the role). The price, on a server below 0.13.72, is `flow-merged`'s ` · ▶ on the workspace reopens them`, which names a control this window does not draw; the toast's own Reopen agents sits beside it. From 0.13.72 the sentence ends before it (upstream #824). Such a server also sends no `failed`, so there a failed free is a green toast whose words alone say it, and the window changes nothing for it: it never reads a sentence's words. Rejected: the window's own words from fields (no field says how many agents closed, or the freed amount, and the session's `closed_agents` can lag the message), cutting at ` · ` (scraping, `design/upstream-gaps.md`), a muted "needs …#N" line inside the toast (noise on every merged close), and capitalising.
  - **Which rules of an agent's notice hold**: no desktop notification while the window is active; the settings read on each message that would post one (`desktop_notifications`); a repeat of a toast still shown counted (`×2`); on macOS a click on the notification does what the button does, and with no button only brings the window forward (the notification still gets an id, `Posted::remember(None)`, so it goes through the app's own center). The machine drop (`shows_notice`) does not apply: a message carries no machine, and cornercase applies its "seen" rules to this window's view.
  - **`flow-merged` waits while the window is behind** (`Telling::waits`, `Notifier::until_seen`, told when the window next becomes active, dropped when the server's `boot` changes): cornercase's own window posts no notification for it and a click would reopen agents, and the merge happens elsewhere, so a 15 s toast in a window that is behind would tell nobody. A failed free follows it (#260): cornercase's own window posts none for either ending, a free changes nothing that cannot wait (the build folders stay as they were), and the toast is told whole when the window comes back. Rejected: a notification for it, toasting it at once (it expires unseen), and holding every message (the notification stands for the others, as for agents' notices).
  - **Dropped on top of cornercase's own rules, and nothing else**: (a) a `queue-*` message while the Queue sheet is open and the window active (its rows show the same change, and Start now answers its own press, so the press is not told twice; closing the sheet before a slow start ends tells `started …`, a second moment); (b) a `setup-failed` for workspace W while this window's own `setup:W` job runs (`store::setup_key`, shared with the sidebar's Run setup, whose job already toasts the failure). The race of (b) with `setup`'s exit is a limit: when the exit is handled first both show. `notify` is always told, `flow-consent` even when its tab is shown (the flow is parked), and `flow-merged` even while its workspace is shown (nothing else says why the agents went; `agents close` by hand sends none).
  - **A machine's messages** are left out upstream (the link reads only `watch`), so none is heard. The window could hear them while one of a machine's tabs shows, by adding `--notices` to that connection's `events`; it would then skip that stream's `notice` events (the local server relays them with `machine`), map panes as `ThereId`s through `go_there`, and run Reopen there with `--remote`. Filed as a follow-up (usecornercase/cornercase-gpui#233).
  - **Limits**: a server below 0.13.72 sends the ▶ and no `failed`, so there a failed free is a green toast whose words alone say it; a message published while the window is not following `events` (for example at the server's first refresh after a start, as `queue-missed` is) is never replayed; a pane gone by the press gives cornercase's error.

On 0.13.71 the same failure sent the ▶ and no `failed`. Not seen: the green toast of a run that freed, a failed free while the window is behind (it follows `flow-merged`'s wait by the code and its tests), and a press on the toast's button.

Not seen: a press on any button or on a banner, `queue-kept`, `flow-consent`, `queue-missed` (unit tests only), a bell and a clipboard write beside the change (the bell's frame did not show, see `design/manual-check.md`; a clipboard write would fill the user's clipboard), a real banner from the app's own center, the 0.1.88 "before", Linux and Windows. Older than the change: five long toasts run past the top of a 640×700 window (usecornercase/cornercase-gpui#235).
- **Settings are read on each notice and message** (`config --json`), so a change in Settings counts from the next notice without a watcher: `desktop_notifications` off stops the desktop notification; `sound_waiting`/`sound_done` name the user's own files.
- **Sounds**: `afplay` plays the user's file when it is a readable absolute path (or `~/`, as cornercase accepts them; a relative path is refused, as cornercase refuses it), else a macOS system sound per cue (`Ping` for needs-you, `Glass` for finished). Two sounds within 1 s would overlap; the second is dropped, as cornercase's own player does.
- **macOS notifications are the app's own** (`notify/center.rs`, decided 2026-11-10, #93): posted through `UNUserNotificationCenter` (the typed bindings of `objc2-user-notifications`; the Objective-C in `notify/center/cocoa.rs`, its stubs in `no_cocoa.rs` elsewhere, as the `win32.rs` modules) when the main bundle has an identifier (the release's `cornercase.app`, `dev.usecornercase.gpui`): the app's name and icon, and a row of its own in System Settings › Notifications. Until 0.1.48 they went through `osascript`'s `display notification`, which posts as Script Editor: its name and icon, listed under it (turning them off there turned off every AppleScript notification), and a click opened Script Editor. **Why bindings, not raw `msg_send!` as `panels/files/peek/player.rs` does**: the center needs a delegate protocol, completion blocks with typed arguments and the `UNNotificationDefaultActionIdentifier` constant, which the bindings check at compile time (and objc2's debug assertions check the delegate's method encoding). They are objc2's own family, already in `Cargo.lock` through gpui, except `objc2-user-notifications` itself (Zlib OR Apache-2.0 OR MIT); its default features are off, since they pull `objc2-core-location` and every UN class. `block2` and `objc2-foundation` are direct dependencies for the same reason, with only the features used. Rejected: raw `msg_send!` for all of it (the blocks and the protocol by hand, with nothing checking them).
  - **Without a bundle identifier `osascript` stays** (`cargo run`, `cargo install`, `target/*/cornercase-gpui`): `UNUserNotificationCenter` raises an Objective-C exception in a process with no bundle, which would end the window, so the center is never touched then, not even at launch (`center::available`, read once per run). The title and body are passed as arguments to the script (`on run argv`), never spliced into it, so no text can inject AppleScript. Rejected: catching the exception (objc2's `exception` feature, a C helper), when the identifier tells beforehand.
  - **Authorization is asked with the first notification, never at launch**: each post asks first, alerts only, which macOS answers at once after the user's first answer, so turning them on in System Settings counts from the next notice without a restart. A refusal is one `No desktop notification: macOS does not let cornercase notify you; turn on Allow notifications in System Settings › Notifications › cornercase, or set desktop notifications to off in Settings › UI` per run (macOS's reason first when it gives one, and on macOS 26 it does: `Notifications are not allowed for this application; …`, so the first text is the fallback; the pointer to Settings is for who refused on purpose, the way to stop the toast); a post that fails says macOS's message. The post is chained in the answer, so a notice that waited for the prompt is shown once the user allows it; the helper thread waits at most 30 s to report the outcome, never the main thread. **A refusal given after those 30 s is told with the next notice**, which asks again and is refused at once (the late answer goes to a receiver that is gone; reporting it as it comes would need a channel from the callback to the `Notifier`, for a case the next notice covers). Rejected: asking at launch (a prompt before anything happened), and keeping the first answer for the run (a change in System Settings would wait for a restart). A refusal is held like any helper's failure (see the helpers' bullet below).
  - **No sound in the notification**: none is set or asked for, since the cue already plays through `afplay`, as Windows' toast is silent.
  - **A click does what the toast's ` Go ` does** (`Store::go`, shared with the toast): the delegate, set at launch when there is a bundle and kept for the app's life (Apple asks for it before launching ends), hands the notification's identifier to the main thread over a channel, since macOS may call it on any thread; the window comes forward (through gpui's activation, `cx.activate` and `activate_window`, no Objective-C of our own) and the notice's action runs (`go TOKEN --view`, or a machine's panes through `go_there`). Identifiers are `<pid>-<n>`, so a new run never replaces an earlier one's notification in Notification Center. The `Store` keeps the last 64 notices it posted (`Store::posted`), as the server keeps the last 64 tokens (`go --help`; its count is over every notice it tells, so 64 here is an upper bound, and a click on a token the server already dropped still gets `go`'s own error toast), a click forgets its own, and a new `boot` of the same server forgets them all (`Notifier::store_changed`), since a restart forgets every token. Only the identifier crosses into Objective-C: a click on a notification of an earlier run, of the server before a switch (a new `Store`), before a restart (a new `boot`) or older than 64 only brings the window forward, rather than run a token that server no longer keeps. Rejected: the action in the notification's `userInfo` (an `NSDictionary` built and read in Objective-C, for tokens mostly gone by then). Only the default action counts (a click on the banner or its row); the notification has no buttons.
  - **In front, macOS does not show it**: the delegate has no `willPresent`, so one that lands once the window is in front stays in Notification Center, as none is posted then.
  - **Limits**: macOS 12 calls the place System Preferences › Notifications & Focus, and the toast says macOS 13's name; a build signed ad hoc with the release's identifier shares the release's notification settings; after a click the notice's toast stays until it expires (decided: a click does not dismiss it); a window minimised in the Dock is brought forward only as far as gpui's activation does (see Checked live).

- Helpers run on a thread of their own, with no input and their output dropped; their standard error is kept, so a helper that cannot start or ends with a failure says why. An in-process try says why with the platform's own message instead (macOS's `NSError` text, `Refusal::why`). **A helper's failure is held until the window is active** (`Notifier::tell_failure`, `held`), for sounds and notifications alike, on every platform (a sound's `afplay`, `paplay`, `PlaySound`, `notify-send`, Windows' toast, macOS's refusal or failed post): a desktop notification is only posted while the window is behind, and an error toast lasts 8 s, so it expired before the user came back and, being once per run, never came again. It is told, still once per run per kind, when the window next becomes active (seen live on macOS: held through 25 s behind, there when brought forward). Rejected: a toast that never expires (a second kind of toast and its dismissal for one message).
- **On Linux** (`notify/alert.rs`, decided 2026-11-04): the command lines are plain functions of the platform, tested for both.
  - **Notifications go through `notify-send`** (libnotify), with `--app-name=cornercase`, the freedesktop `utilities-terminal` icon (every icon theme has it; the app installs no icon of its own), then `--` so a title or body starting with `-` stays text. gpui has no notification API on Linux either; talking D-Bus ourselves (`org.freedesktop.Notifications`) would add a client for what one command does. The body is not escaped for the markup some servers read: an agent's notice rarely holds `<` or `&`.
  - **The system sounds are the freedesktop sound theme's**, found in the XDG data folders (`sounds/freedesktop/stereo/`): `complete.oga` for finished, `message-new-instant.oga` (a brighter ping) for needs-you, as `Glass` and `Ping` are on macOS. cornercase's own window makes its two notes in code because Linux machines may lack the theme (its `design/sound.md`); this window keeps the system's sounds as it does on macOS, and says what to install when they are missing.
  - **The players are tried in turn, `paplay`, then `pw-play`, then `aplay` for a `.wav`**, each one found tried when the one before fails: `paplay` plays on PulseAudio and on PipeWire's PulseAudio server alike, while `pw-play` fails where PipeWire runs without its audio session (Ubuntu 22.04 runs it for screen sharing only), so it comes second; cornercase's player tries `pw-play` first. A `paplay` with no PulseAudio server to reach (PipeWire without `pipewire-pulse`) hands the sound to `pw-play` (CodeRabbit's review, 2026-11-04; until then only the first player found was run). Both read WAV, OGG and FLAC through libsndfile; `aplay` reads WAV only, so it never gets an `.oga`. `canberra-gtk-play` was rejected: it would follow the user's chosen sound theme, but it is installed less often than either player. The player's path and the sound's reach it as they are on disk, not as text, so a `PATH` or `XDG_DATA_DIRS` folder whose name is not UTF-8 still plays (until 2026-11-04 they were made text, with such bytes replaced, and the player then failed unseen).
  - **A missing tool is one info toast per run of the window**, saying what to install (`notify-send`, a player, or the theme); then nothing more is said, so a notice never repeats it. The toast and the notice's own toast still show. Limit: an info toast lasts 4 s, so one that comes while the window is behind may pass unseen; the next run of the window says it again.
  - **A tool that runs and fails is one error toast per run of the window for each kind**, `No sound: …` or `No desktop notification: …`, with the tool's last line on standard error (or its exit status), each player's in turn when every one failed: no notification server on D-Bus, no audio server or device. Once per run, as a missing tool, so a broken audio setup does not toast on every notice; desktop notifications can be turned off in Settings. Until 2026-11-04 such a failure was not reported at all (CodeRabbit's review). This holds on macOS too, where an `afplay` given a sound file it cannot read had been silent; `osascript`'s `display notification` does not fail in practice, and macOS's own notifications report a refusal or a failed post the same way, once per run.
  - **Checked live on 2026-11-04** (Debian 13 arm64 in a container, Xvfb and openbox, cornercase 0.12.280, logging stubs of `notify-send` and `paplay` first on the `PATH`): a fake `claude` (a script cornercase recognises by its name, reporting `working` then `done` through OSC 7501) finished in a tab not shown while the window was minimised, and the window ran `paplay /usr/share/sounds/freedesktop/stereo/complete.oga` and `notify-send --app-name=cornercase --icon=utilities-terminal -- "claude finished" "claude finished in demo › master"`; with a `PATH` holding only `cornercase`, the same finish gave the notice's toast and the two install toasts. `cornercase notify` does not reach `events --notices`, so it cannot test this. - **On Windows** (`notify/alert.rs`, Win32 calls in `notify/alert/win32.rs` with stubs in `alert/no_win32.rs`, decided 2026-11-04): Windows has no helper program for either, so a try (`alert::Helper`) is a command line on Linux and on a Mac with no bundle, and an in-process call on Windows (`PlaySound`, `Toast`) and in the Mac app (`Center`, `notify/center.rs`); every try still runs on the helper thread and goes through the same first-that-works and once-per-run toast rules. What is played or shown (the file, the toast's XML, the registry key) is built by plain functions tested on every host.
  - **Notifications are toasts** through WinRT's `ToastNotificationManager::CreateToastNotifierWithId` with the app's own id, `Cornercase.Gpui` (`desktop::APP_USER_MODEL_ID`). An unpackaged program's toast shows only for an id Windows knows, so the first toast of each run names it under `HKCU\Software\Classes\AppUserModelId\Cornercase.Gpui` (`DisplayName` "cornercase"), the registration the Windows App SDK writes for unpackaged apps: no administrator, no installer, no Start menu shortcut. The process itself keeps Windows' own id, made from the exe's path (no `SetCurrentProcessExplicitAppUserModelID`): toasts do not need it, and a window with an explicit id that no shortcut carries cannot be pinned to the taskbar and relaunched without relaunch properties set on the window, while the default groups the window with any pin or Start menu shortcut of the same exe. Rejected: a Start menu shortcut carrying the id (the classic way, through `IShellLink` and a property store: a shortcut the user did not ask for, left pointing nowhere when the binary moves); borrowing PowerShell's id, as some crates do, which shows "Windows PowerShell" as the sender; a balloon from a tray icon (`Shell_NotifyIcon`), the old API, which needs a hidden window and an icon of its own. WinRT needs no setup on the helper thread: with no apartment there, windows-core joins the process's implicit multithreaded one (`CoIncrementMTAUsage`).
  - **The toast's XML** is `ToastGeneric` with two texts, the notice's headline and message, each escaped (`&`, `<`, `>`, `"`, `'`) and stripped of the control characters XML 1.0 forbids (which `LoadXml` would refuse), so a notice can neither add elements nor fail to parse; and `<audio silent="true"/>`, since the cue's own sound already plays and Windows' notification sound would play over it. Clicking a toast does nothing more than dismiss it (no activator is registered; the window's own toast has "Go"). No icon: `IconUri` needs an image file and the binary carries none yet, so Windows shows a generic one. The registry key is never removed (there is no uninstaller), and a failure to write it or to show the toast is the usual once-per-run `No desktop notification: …` toast, with Windows' message.
  - **Sounds play in the window's own process** with winmm's `PlaySoundW`, as cornercase's own window does there (its `design/sound.md`, "On Windows"): `SND_FILENAME | SND_ASYNC | SND_NODEFAULT`, so it returns once the sound starts and never plays the system's default beep for a file it cannot play (that is `No sound: PlaySound could not play …`, once per run). A process plays one sound at a time and a new one stops the last; the 1 s rule already drops a second cue. No 5 s limit, unlike cornercase's: `afplay` and `paplay` have none here either.
  - **The system sounds are Windows' own**, in `Media` under the Windows folder (`GetSystemWindowsDirectoryW`): `Windows Notify Messaging.wav` for needs-you, the chime Windows plays for a new message (as freedesktop's `message-new-instant` on Linux and `Ping` on macOS), and `tada.wav` for finished, the "done" fanfare every Windows has shipped since 3.0 (as `Glass` and `complete.oga`). Rejected: `Windows Notify System Generic.wav`, which every toast plays, so it would not tell a finish from any notification; `Windows Print complete.wav`, which reads as finished but is less certain to be there on every edition. When the file is missing (Windows Server, a stripped image), one info toast says so and points at Settings.
  - **A sound file of your own** is a path on a drive (`D:\sounds\ding.wav`) or one starting with `~/` or `~\`, resolved with `USERPROFILE` and joined with Windows' separator (`feed::sound_path`, which takes the `Os`, through `platform::paths`; until 2026-11-04 it accepted only paths starting with `/`, so no file of your own could play on Windows). A share or a device path (`\\server\share\…`) is refused before anything opens it, as cornercase refuses it (its `design/windows/network-paths.md`: opening a share hands the user's NTLM credentials to its host), and so is a Unix path; the system sound plays instead. `PlaySound` reads only WAV, so a file of another kind gives one info toast (`No sound: Windows plays only WAV files; choose a .wav file in Settings`) and stays silent, as a missing player does on Linux.
  - **Checked only by cross-compiling and unit tests on macOS**: no toast has been seen and no sound heard on Windows. That the registry key alone makes the toast appear follows Microsoft's documentation and the Windows App SDK's own registration, not a run.
- **A toast that repeats one still shown** (same kind, text and action) replaces it with a count (`×3`) and a fresh timer, instead of stacking copies: a retry loop once filled all five places with one message. Toast text wraps inside the toast's 348 px.
- **A stack of toasts stays inside the window** (#235, 2026-11-14):
  - **The room.** The newest toasts stand from 40 px above the window's bottom, 16 px from its right edge. The box ends `GAP` below the title bar (`Frame::title_bottom`: the title row, which holds the tab strip's controls, Windows' and Linux's window buttons and a Mac's traffic lights). gpui lays it out inside the window's frame, so the room follows the window's height, each platform's frame (Linux's margins and border are outside it) and a resize.
  - **Whole or not at all** (`ui::stack`, `design/widgets.md`). From the newest up, as many as fit are drawn. The next older one and all above it wait, drawn nowhere and taking no press. A `+N more` pill above the stack says how many wait. The order is kept: an older short toast never jumps over a taller newer one.
  - **Seconds count only while a toast is drawn** (`Shown`). One that waits, or was pushed out by newer ones, shows for its whole 4, 8 or 15 seconds once there is room.
  - **Past five**, the oldest toast already drawn makes way; with none drawn (the window was not drawing), the oldest info toast; else the oldest. The new one never does. The kind does not change which toasts are drawn.
  - **Taller than the room.** Its text scrolls inside its card, which is cut to the room, less the `+N more` line when others are live. Its button and ✕ stay in view. No scrollbar is drawn, as in dialogs' bodies; a fade into the card's colour over the text's bottom edge (`glass::bottom_fade`, shown only when the stack cut the card) says the text goes on (the text ends with that much room under its last line, so the end of the scroll is clear of the fade), since the cap can fall between two lines and then no line is cut (seen at 640×360, 2026-11-14).
  - **A toast leaves at its end**, with a sweep when its time runs out, so the one waiting takes its place at once. Before, one sweep ran 16 s after the toast was made.
  - **Rejected:** clipping the stack's top (half a card, half a button); dropping what does not fit (a NeedsYou or an Error lost unseen); counting seconds from when the toast was made (one that waits could run out before it was drawn) or from its first draw (at 640×700 the first two, pushed out after about 3 s on screen, would run out above the newer ones); choosing which toasts are drawn by kind (the stack would no longer read newest at the bottom, and with seconds counted while drawn, waiting loses nothing); a count of characters or lines as the height (it breaks with the font, its size and the language); measuring in `render`, outside the window's text style; the previous frame's heights (a frame past the top); a room computed by hand from the window's height (it would repeat `framed`'s margins and border and drift); `line_clamp` (it crashed the window, `design/widgets.md`) or the text's top cut for a toast taller than the room.
  - **Limits:** the seconds still run while the pointer is on a toast; while the window does not draw (minimised, hidden or occluded on macOS), a toast drawn before keeps counting; a full stack covers a docked panel's header, as before.
  - **Checked live** (2026-11-14, macOS, a debug build against cornercase 0.13.57 on a private server, `cornercase notify`, the window sized with `manual-check size`, which needs no press and worked under the screenshot window's cover): at 640×700 five toasts of seven lines drew the newest three under `+2 more`, none over the title row (0.1.92 drew the first over it); at 640×360 the newest alone under `+4 more` (0.1.92 cut the first at the window's top); five of five lines all fit with no pill; a 2,000-character toast filled the room with its ✕ in view and its text cut by the card's edge; a repeat gave `×2`; a 200-character path wrapped inside the card; a Show button drew; a sixth toast stood at the bottom; the waiting ones took the freed places after the bottom ones expired, and `+N more` counted down; resizing 700, 360 and 520 kept every drawn card whole. **Not checked**: Linux and Windows live, any press or scroll (the ✕, Show, scrolling a tall toast, a press on `+N more`) while the screenshot window covers the screen, the light theme, and an info toast leaving at its 4 s in a still window.
- **No desktop notification while the window is active**: the toast is enough.
- **Bells**: a bell in the shown tab flashes the terminal for 160 ms; one elsewhere gives a toast saying where (`project › workspace › tab`) with a "Show" button, at most once every 30 s per pane. A machine's tab hears its own bells and programs' copies on `events --host` there (`design/machines.md`), and only for the tab it shows.
- **Clipboard writes (OSC 52)** are applied and announced with the program's name, so a program cannot fill the clipboard unseen.
- **The window title** is the shown pane's own title (what its program set), else its tab's name.
- **Updates** (`notify/update.rs`): the status bar offers the release `status --app` reports; its dialog shows every changelog section after the running version, drawn as Markdown as cornercase's own window does (`design/widgets.md`), and installs with `cornercase update --json` (plain `cornercase update` below 0.13.53, see "Which command goes by which release"), or shows the command to copy when cornercase cannot replace itself (Homebrew, folders it cannot write: the line's own `command`, else `status --app`'s). Without a terminal and without `--yes`, `update` never restarts the server, so the restart is a second dialog: `restart --yes` at once, or `restart --when-idle --yes`, kept running until no agent is in the middle of a turn; dropping that stream cancels the restart. A version installed by another client also offers the restart. The window's own update is a separate chip and dialog (`design/self-update.md`).
- **Release notes are parsed only when they change** (`update::ParsedNotes`, one in each update dialog, this one and `design/self-update.md`'s): a dialog is drawn again on every frame its entrance or a spinner animates, and Install's spinner turns for the whole download, so parsing on each draw would read the whole changelog since the running version again on every frame. **Only a web address opens** (`model::link::is_web`, as a Recap's links): the notes come from a release, so a `file:` link or another app's scheme in them does nothing rather than hand it to the system.
- **Each chip names what it updates**: `↑ cornercase 0.13.19` for the server and `↑ cornercase-gpui 0.1.36` for this app, and so do the installing and restart chips (`notify::update::Chip`). A bare `↑ 0.13.19` beside `↑ window 0.1.36` left users guessing which program each one was (asked for on 2026-11-09).
- **A cornercase already on disk offers the restart, not the install** (`update::installed`): the server's `installed` is true only for an install it made itself, so after `brew upgrade cornercase` (the command the dialog offers for Homebrew) or an install by hand, the server kept its `↑` until it restarted, which read as an update that did not take (seen on 2026-11-09: Homebrew had 0.13.19, the server still ran 0.13.1). The window asks the `cornercase` it runs for its `--version` when `status --app` changes, when the window comes to the front and every 20 s while a release is offered and not installed; a version at least the release's turns the chip into the restart, named with the version on disk. While the dialog's install runs, the chip and the dialog stay on installing even if the new program shows up first, so the restart is never offered before `update` has answered. Only for a server on this machine: `--version` is answered by the local program even with `--remote`, so a server on another machine keeps its `↑` until it restarts. `update.installed` does not help there: the server sets it only for an install it made itself, never for `cornercase update`, which is what the window runs. The window's own install there is read from the line `update --json` prints ("What `update` did is read from its line"), not from `--version`.
- **What `update` did is read from its line** (`cli/update.rs`, `update_answer`, pure; usecornercase/cornercase-terminal#775 landed in 0.13.53): `update --json` prints one line, `{"outcome":"updated","from","version","path"}`, `{"outcome":"up-to-date","version"}` or `{"outcome":"manual","version","latest","command"}` (`--check` adds `available`, which the window never sends), and never asks or restarts. `version` is the binary on disk afterwards, on the machine `update` ran on. **The line is read only with status 0 or 6** (the two it comes with: `manual` exits 6, with or without `--json`; it was 1 before 0.13.53), and it is the first stdout line that parses, since a remote shell can print before it. Status 2 is `Refused` (a cornercase older than 0.13.53 refuses the flag, as does `--json` with `--yes`), in the window's own words (`cornercase refused update --json, which needs cornercase 0.13.53 or newer`): clap's text is a usage dump, and the status alone says what was refused. Anything else (an unknown outcome, a missing key, a line that is no JSON, a failure printing nothing on stdout, status 1) is read by its status as the plain command's answer, never by the words of a sentence. All three callers read it (this dialog, a machine's update, the older page).
  - **What the dialog shows**: `updated V` is installed under V, even below the release offered (it is what is on disk); `up-to-date V` is installed too when V reaches the release (the restart is offered, as for "A cornercase already on disk"), and below it a failure, `cornercase update found no release newer than V`, since the server's check and `update`'s disagree (another release source, a release taken down); `manual` is not a failure: the line's `command` is shown and **Copy command** copies it (the toast says where to run it), the chip stays on the release, and an amber toast with Details says it is the person's turn. When the person runs the command, the disk read offers the restart as for any install by hand.
  - **Another machine** (the window on a server there, or a machine's update): the line's `version` is what is on disk there, so it is said, with the true thing about its server: it keeps running the release it started with until it restarts there. "Not checked on M until its server restarts" stays only for an exit 0 with no line read.
- **Which command goes by which release** (`cli::UpdateGate`): `--json` is a flag the command line parses, and `update` runs without a server, so the gate is the release of the command line that parses it (`design/connection.md`: "A feature of the server the window reads is asked in one place"), which replaced the issue's "as `CLOSE_WHEN_MERGED_SINCE` is", the server's release. For this computer that is `Store::cli_release`. Through `--remote` this computer's command line parses `update --json`, rebuilds the words and the one there parses them again as that machine's own command (upstream's `design/commands-for-scripts-and-agents.md`), so both must have 0.13.53: the window's own `--remote` takes the running server's release for the binary there (a lower bound: a server older than the binary under it gets the plain command until it restarts, a known limit), and a machine's update or the older page takes the refusal's `there`, the banner of the very binary that runs `update`, not the machine's `server_version`, which is the server's and stays old after an update. An unknown release counts as lacking, since the plain command is safe on every release. A status 2 is never answered by sending the plain command: it does not say which side refused, and an error is never a reason to send again. Rejected: relying on the connection's older check (it holds as of the last connect), remembering a refusal to send plain next time (state for a case the gate makes near impossible), and clap's text as the refusal's reason.
- **An install is verified, never assumed** (`update/outcome.rs`, pure): above the gate the line's `version` is the check, here and on another machine (upstream runs the new binary's `--version` before renaming it over the old one). `--version` is read (`ask_update`, `checks_disk`) only for an exit 0 with no line the window reads, on this computer: below the gate, or a line it cannot read. A version below the release is then a failure naming the path and the version it still is; a newer one is installed under its own version; none is a failure too. The chip stays on installing until the answer. On another machine below the gate the exit status is all there is, so the install counts as done but *not checked*, and a muted line in the dialog says so. The restart's verdict is the check there.
- **Below 0.13.53 what `update` printed is shown as it is, never parsed** (`cli::said_of`, as the missing page's update does): the plain command's exit status, `--version` and `status --app` decide. A `Manual` answer (exit 1 before 0.13.53, 6 after it, the command on stdout) shows its command instead of `failed`, and a muted `Copy command needs cornercase 0.13.53 or newer on this Mac (it has 0.13.51)` (or `on <machine>`, or both) appears only under an answer that failed *and* printed on stdout; the lines name the release that is needed and which cornercase lacks it, as `needs_note` does for a feature (`AGENTS.md`: the UI says plainly what is missing). The missing page's Update cornercase… (`terminal/missing.rs`) updates a cornercase below the window's minimum (0.13.19), always below 0.13.53, so it stays the plain command read as before. Rejected: matching `Update it with:` (breaks with any rewording), and telling Manual by an empty stderr (`--remote` can add a stderr line).

In the window, without a press: the status bar's `↑ cornercase 0.13.74` on a server of 0.13.53 against the fake, and the older page's two releases with Update cornercase on vps.invalid… for 0.13.51 there and 0.13.53 there, this computer 0.13.53 and 0.13.74. **Not checked**: the update dialog, Install, Copy command, the older page's Update… and a machine's toast (they need a press, and a screenshot window covered the screen), a copy updated while the window ran, Linux and Windows, a real sshd, a real Homebrew; their words are in unit tests.
- **A failed install says so outside the dialog, for both programs**: an error toast `Could not install <program> <version>: <why>` with a **Details** button that opens that program's update dialog (`UpdateToast`, `ToastGo::Update`, which `Store::go` leaves in `open_update` for `Root::take_asks`, as a connect leaves `switch_to`). It is in memory, so a server switch loses it. Rejected: clearing it on cancel, and comparing on every boot.
